# 08. DSX GUI 화면설계서

문서 ID: DSX-GUI-001 · 버전: 1.2 · 기준일: 2026-09-17 · 상태: 개발 기준 / 화면 배치는 DESIGN 05 유지

이 문서는 7개 메뉴와 S01~S16/S07B의 기존 배치를 유지하면서 v1.2 입력·행동·오류·업무 완료 경로를 정한다. 상세 DTO·권한·접근성·AC/T 추적은 [07 프론트엔드 개발 명세](<07_프론트엔드_개발명세서.md>), API는 02, 판단은 04를 따른다.

기존 [화면 캡처](<../gui-design-20260916/screens/README.md>)와 [GUI PDF](<../deliverables-20260916-v1.1/sources/GUI_화면설계서_v1.0.pdf>)는 DESIGN 05의 가상 화면 참고본이다. 이 개정은 새 캡처를 생성하거나 웹을 수정·배포하지 않았다. 아래 추가 버튼·폼이 기존 이미지에 이미 구현되어 있다고 해석하지 않는다.

## 1. 정보 구조·공통 영역

| 메뉴 | 화면 |
|---|---|
| 운영 대시보드 | S01 전체 현황·선택 대상·추이 |
| 자산·관측 | S02 장비/GPU, S03 작업 연결, S04 관측 상태 |
| RCA 조사 | S05 목록, S06 요청, S07 사건 결과, S07B 직접 결과 |
| 운영 분석·보고서 | S08 분석, S09 요청·일정 목록/상세, S10 결과 |
| 작업 이력 | S11 목록·상세·시도 이력 |
| 지식·Runbook | S12 발행 지식·등록 절차·지식 관리 |
| 연결·설정 | S13 모델, S14 역할별 지정, S15 데이터 연결 |
| 전역 Assistant | S16 우측 패널·펼친 대화·모바일 drawer |

좌측 메뉴·상단 범위/Assistant·본문 중심 구조를 유지한다. 주 행동은 제목 옆, 상세 조건은 필요 시 펼친다. 범위 선택기는 CPC별 Namespace를 표시하고 “접근 가능한 전체 범위” 아래 실제 범위 칩을 둔다. 저장 결과·대화의 대상과 기간은 전역 조건 변경으로 바꾸지 않는다.

결과 상단은 **대상 / 기간 / 기준 시각 / 산출 상태**를 먼저 보여준다. 실행 상태는 별도로 표시하며 상세 품질·조회/정책/지식/모델 버전은 펼침에 둔다. ready=산출 가능, partial=부분 산출, blocked=근거 부족, not_applicable=적용 대상 아님으로 표현한다. 서버 result_status를 그대로 사용한다. 계산과 근거가 저장됐지만 설명만 실패하면 “계산·근거 저장 완료 / AI 설명 생성 실패 / 근거 보기”를 제공한다.

모든 화면은 로딩, 정상 빈 목록, 일부 실패, 근거 부족, 지연, 권한 부족 상태를 구분한다. 412는 최신본 비교, 428은 최신 버전 확보, 409는 멱등/상태 충돌 안내로 처리한다. 사용자가 바뀌거나 권한이 철회되면 이전 조회·초안·캐시를 그대로 노출하지 않는다.

## 2. S01 운영 대시보드

목적: 지금 확인할 대상을 고르고 관측·조사·보고서·질문으로 이동한다.

| 영역 | 내용·행동 |
|---|---|
| 상단 조건 | 허용 CPC/Namespace·기간·기준 시각. 변경하면 해당 범위 재조회 |
| 요약 카드 | 열린 사건→S05, 수신 지연/분석 준비→S04, GPU→S02 |
| 우선 검토 | 대상·이유·근거 품질·다음 행동. 사건과 관측 경로 문제를 구분 |
| 대상 선택 | Node 복수 선택·선택 범위 칩. 접근 권한 밖 대상 미노출 |
| 자원 추이 | VRAM/활동/전력·축·단위·누락. “이 그래프에 질문”은 대상·기간·지표를 S16으로 전달 |
| 최근 사건 | 운영 사건 상태와 최근 분석 상태를 구분, 사건 클릭→S07 |

호출: POST /dashboard/query, /observations/query. 데이터가 없으면 0으로 채우지 않고 필요한 입력·마지막 시각을 표시한다. 기준 이미지: S01, S01-detail. 확인: F01~F03, AC01~AC03, T01~T06.

## 3. S02 장비·GPU

목적: 장비 상태와 원본 수신 상태를 보며 안정 식별자로 대상을 고른다.

상단에 장비·GPU/작업 연결/관측 상태 탭을 유지한다. Node 목록에서 모델·GPU 수·마지막 수신을 확인하고 GPU 상세에서 CPC·UUID·신원 품질·원본 시각·지표를 본다. Node 변경 시 이전 GPU 선택이 새 대상에 잘못 남지 않게 한다.

“선택 GPU 질문”→S16, “조사 시작”→S06, “작업 연결”→S03, “관측 상태”→S04. VRAM과 실제 GPU 활동을 구분하고 같은 Node의 Pod를 GPU 직접 연결로 표시하지 않는다. 장비 관측 grant가 없는 Namespace 제한 사용자는 허용된 작업 관계만 본다.

호출: GET /assets, POST /observations/query, /mappings/query. 기준 이미지: S02, S02-detail. 확인: F02/F03/F05, R02/R08, AC02~AC04, T03~T06/T10/T39.

## 4. S03 작업 연결

목적: Pod 배치·GPU 관계·활동을 독립적으로 확인하고 Pod에서 조사를 시작한다.

| 영역 | 내용·행동 |
|---|---|
| 조건 | CPC별 Namespace, Pod 이름/UID 검색, 현재/사건 시각, 기준 시각 |
| 표 | CPC, Namespace, Pod 이름·UID, Kubernetes phase, 노드 배치, GPU 연결, 활동, 관계 유효 시각 |
| 표시 문구 | bound “노드 배치됨”, matched “GPU 연결 확인”, insufficient_data “활동 근거 부족” |
| Pod 행 행동 | “이 Pod 조사”→S06의 Pod 유형·CPC·Namespace·UID·기준 시각 자동 입력 |
| 관계 상세 | GPU UUID·공유/MIG 단위·근거·유효 구간, enum은 상세에 표시 |
| 후속 | 부족 근거→S04, 할당 분석→S08, 질문→S16 |

세 축은 03의 반환 DTO 필드 `placement_status`(노드 배치), `relation_status`(GPU 연결), `activity_status`(활동)에 각각 연결한다. 별도 `kubernetes_phase`로 Kubernetes phase를 표시한다. Node/GPU 미확정 Pod도 조사할 수 있다. unbound 장치 활동의 not_applicable는 “적용 대상 아님”을 유지한다. Pending을 미배치로 치환하지 않는다. 같은 이름의 다른 UID, 현재/과거 관계, 공유 GPU 활동의 귀속을 구분한다.

호출: GET /assets, POST /mappings/query. 기준 이미지: S03, S03-past. v1.1 추가 설계: 사용자 라벨·Pod 조사 버튼/전달 필드. 확인: R02/R03/O02/O07, AC04/AC05, T03/T04/T13/T18/T39.

## 5. S04 관측 상태·분석 범위

목적: 연결 여부와 선택한 분석을 계산할 수 있는지를 나누어 설명한다.

소스/Node별 수신 표와 R/O 분석 준비 표를 둔다. 연결 성공, 마지막 원본·수신 시각, 필드 유효성, 관측 기간, 매핑/활동/전력 품질, 부족 입력, 적용 가능한 분석을 표시한다. “연결 성공” 한 상태로 주간 보고서 준비 완료를 표현하지 않는다.

대상 선택→S02, 데이터 경로→S15, 조건을 보존한 보고서/조사로 이동한다. CPC-2 일부 target·현재 매핑 확인과 과거 이력·Loki 최신 수신·CPC-1 미확인을 구분한다. 실제 근거는 C04와 연결한다.

호출: GET /service-status의 허용 범위, POST /observations/query. 기준 이미지: S04. 확인: F02/F03/F13, O11, AC03/AC15, T04/T06/T21/T33.

## 6. S05 조사 목록

목적: 사건 조사와 직접 요청을 찾고 운영 상태·분석 진행을 구분한다.

사건/직접 요청 탭, 대상·기간·상태 필터, 새 조사 버튼을 둔다. 사건 목록 열은 사건 표시 번호·대상·발생 시각·**사건 상태**·**최근 분석 실행 상태**·**산출 상태**·결과다. 직접 요청은 질문 요약·대상·접수 시각·분석 상태로 표시하며 가짜 incident를 만들지 않는다.

“새 조사”→S06, “진행”→S11, 사건 결과→S07, 직접 결과→S07B. 기존 이미지의 S07 통칭 링크는 결과 종류별로 나눈다. 저장 결과 없는 진행 작업에서 고정 예시 결과를 열지 않는다.

호출: GET /incidents, /analyses. 기준 이미지: S05. v1.1 추가 설계: 사건/분석 분리 열·정확 결과 링크. 확인: F04/F05/F08, T07~T09/T23, AC07/AC14.

## 7. S06 새 조사 요청

목적: Node/GPU/Pod의 대상·시간·증상을 고정해 비동기 RCA를 접수한다.

| 입력 | 화면 규칙 |
|---|---|
| 대상 종류 | Node/GPU/Pod 선택. 종류를 바꿀 때 맞지 않는 이전 선택 제거 |
| Node | CPC·Node UID 우선, 대체 식별 품질은 서버 표시 |
| GPU | CPC·GPU UUID, Node는 식별 보조 |
| Pod | CPC·Namespace·Pod 이름·UID·기준 시각. Node/GPU 필수 아님 |
| 기간 | 시작·종료·timezone, 종료>시작, 사건 진입 시 incident/시각 표시 |
| 증상·목적 | 증상과 R01~R09 선택. 목적에 필요한 추가 맥락만 펼침 |
| 제출 | 조건 요약·조사 요청, 서버 제한과 권한 검사, 제출 중 중복 버튼 방지 |

접수는 POST /analyses + Idempotency-Key→202 job_id=analysis_id→S11이다. 응답 유실 시 같은 키로 확인한다. 입력 오류는 필드 옆과 첫 오류 포커스로 안내한다. Pod GPU 관계 미확정을 이유로 접수 자체를 막지 않는다.

기준 이미지: S06. v1.1 추가 설계: 대상 종류·Pod 선택·목적 필드·정식 DTO. 확인: F05/F08, R01~R09, T10~T14/T23/T39, AC02/AC04/AC09.

## 8. S07 사건 RCA 결과

목적: 원인 후보와 근거를 검토하고 사건의 운영 상태를 관리한다.

상단은 사건 대상·기간·기준 시각·사건 상태·분석 실행/산출 상태다. 본문은 확인 사실, 원인 후보, 지지·반박·미확인 근거, 영향, 다음 확인/Runbook이다. 우측 또는 펼침은 고정 범위·버전·근거 상세다. 관계·영향·원인을 각각 표시한다.

추가할 “사건 상태 변경” 폼에는 현재 상태/버전, 변경할 상태, 사유, 담당을 둔다. 종결 사유는 필수이며 If-Match로 저장한다. 변경 이력에는 시각·작성자·이전/새 상태·사유를 보인다. 알림 해제·분석 완료를 자동 종결로 표시하지 않는다. 같은 episode의 추가 근거와 새 episode 재발은 이력/recurrence_of 링크로 구분한다.

행동: 근거 열기, 호환 지식의 해당 revision 열기(S12), 추가 질문(S16), 실제 조치·검토 기록, 재분석. 재분석은 parent_job_id를 가진 새 작업이다. 실제 조치 기록은 수행자·대상·시각·내용·후속 관측을 받으며 저장을 복구 성공으로 표현하지 않는다. 수정 전 이력은 남긴다.

“현재 상태 재확인”은 새 알림 없이도 선택할 수 있다. 같은 incident_id의 후속 기간을 확인한 뒤 R01/R09 새 RCA를 접수하고 이전 분석을 parent_job_id로 연결한다. 결과를 확인하기 전에 사건을 자동 종결하지 않는다.

호출: GET/PATCH /incidents/{id}, GET /analyses/{id}, /evidence/{id}, GET/POST /reviews. 기준 이미지: S07. v1.1 추가 설계: 상태 폼·종결 사유·변경 이력·설명 실패. 확인: F04/F05/F11/F12, T08~T14/T30/T31/T40, AC07/AC09/AC10.

## 9. S07B 직접 요청 조사 결과

목적: 사건 없는 조사도 요청·결과·근거를 영속적으로 보존한다.

S07의 결과 구조를 재사용하되 사건 상태 폼은 두지 않는다. 질문·대상·기간·analysis_id(동일 job_id), 산출 상태, 관계·영향·원인, 미확정·근거를 표시한다. Pod 조사에서는 “Pod 배치 확인 / GPU 관계 미확인”을 독립 결과로 표현한다.

재분석→새 /analyses에 parent_job_id→S11, 작업 이력→S11, 근거·질문·검토/조치 기록은 해당 job에 연결한다. 현재 요청 결과를 기존 사건 예시로 바꾸지 않는다.

호출: GET /analyses/{id}, POST /analyses, GET/POST /reviews. 기준 이미지: S07B. 확인: F05/F08/F11/F12, T13/T23/T30/T31/T39/T40, AC07/AC09/AC10.

## 10. S08 운영 분석·보고서

목적: 네 주제 카드에서 세부 분석을 선택하고 필요한 보고서 조건으로 이어간다.

| 기존 카드 배치 | 세부 선택 |
|---|---|
| 관측·용량 | O01 장비·Node 변화, O07 배치 대기·용량, O11 관측 품질 |
| 할당·활동 | O02 할당 명세·시간, O03 저활동, O04 다중 GPU 편차, O08 Namespace·프로젝트 배분 |
| 반복 사건·조치 | O05 반복 사건, O06 당시 작업, O10 조치 전후 |
| 에너지 | O09 GPU 에너지 |

카드 상세는 사실·수치·왜 검토하는지·부족 입력·근거·다음 행동의 공통 구조다. 고른 topic_ids와 범위를 “보고서 요청”으로 S09에 전달한다. O04/O07/O08이 별도 메뉴에 없다는 이유로 구현 범위에서 제외하지 않는다.

현재 할당과 기간 GPU-hours, 공유 장치와 개별 작업, 수치 변화와 인과를 구분한다. 원문 없음·짧은 관측·한정 대상 결과를 전체 시스템으로 표현하지 않는다. 대상 관측→S02/S03, 질문→S16, 조치 검토는 해당 저장 결과의 기록으로 연결한다.

기준 이미지: S08. v1.1 추가 설계: 카드별 topic_ids·세부 선택. 확인: F06, O01~O11, T15~T21/T38/T40, AC07/AC15.

## 11. S09 보고서 요청·일정

목적: 일회 보고서와 일·주·월 정기 보고서를 같은 메뉴에서 끝까지 설정·확인한다.

| 영역 | 입력·행동 |
|---|---|
| 범위 | CPC별 Namespace, 선택 대상, group_by |
| 기간 | 날짜 또는 정확한 시각, timezone. 날짜는 종료일 다음 날 00:00 미만 |
| 주제 | 네 묶음의 O01~O11 체크, 최소 1개, 부족 예상 입력 안내 |
| 조건 펼침 | 비교 기간; O07 resource_selectors의 CPC·resource_name·unit과 미배치 기간; O10 선택 action_record_ids·조치 전 comparison_range/후 time_range |
| 실행 방식 | 일회 / 정기. 정기는 P0 |
| 일회 접수 | 조건 확인→POST /reports→S11→S10 |
| 정기 생성 | 일/주/월·실행시각·timezone·요일/일자·직전 완료 일/주/월·enabled→POST /schedules |

O07 자원 선택지는 허용 scope의 등록 관측 query_id=resource_catalog로 조회한다. 단위 미확인은 산출 보류로 표시한다. O10에 실제 조치 기록이 없으면 action_record_missing과 일반 기간 비교임을 표시한다. 조치 기록 연결만으로 인과적 효과를 확정하지 않는다.

동일 메뉴의 “일정 목록” 탭에서 주기·대상·활성 여부·다음 실행·최근 발생을 본다. 일정 상세에는 적용 revision·보고서 조건·변경 적용 시점·소유자와 일시중지/재개/수정을 둔다. 발생 이력은 scheduled_for·revision·대상/기간·pending/accepted/missed/blocked/failed·사유·dispatch/job/결과 링크를 표시한다.

GET /schedules, /schedules/{id}, /schedules/{id}/occurrences; PATCH는 If-Match를 사용한다. 일정 일시중지는 이미 실행 중인 job 취소와 별도다. 변경 시 접수된 발생분의 조건은 그대로 남는다. 월말·DST·누락 보충은 서버/C08 정책을 따르고 권한 부족은 blocked로 드러낸다.

기준 이미지: S09. v1.1 추가 설계: 전체 O 입력·일/주/월·일정 목록/상세/발생 이력. 확인: F06/F07, T15~T22/T37/T38, AC06/AC10/AC14/AC15.

## 12. S10 보고서 결과

목적: 계산된 내용과 보류된 내용을 동일 저장 버전으로 읽고 공유한다.

상단은 보고서 대상·기간·기준 시각·실행/산출 상태·설명 상태다. 본문은 주제별 상태·값/단위·근거·품질·부족 입력·다음 확인을 표시한다. 버전 펼침에서 query/policy/knowledge/model·부모 작업·실제 입력 범위를 확인한다. 화면의 기간 변경·차트 확대가 저장 수치를 바꾸지 않는다.

행동: 관련 관측, 이 보고서 질문, 검토/실제 조치 추가·수정 이력, 새 보고서 재생성, **HTML 보고서 / 집계 CSV 내려받기**. 제품 PDF 버튼은 기본 요구에서 제거한다. 출력은 저장 결과의 같은 버전이며 서버가 파일 접근 권한을 다시 검사한다. 설명 실패여도 유효 수치·근거는 열 수 있다.

호출: GET /reports/{id}, /reports/{id}/export?format=html|csv, GET/POST /reviews; 새 POST /reports에 parent_job_id. 기준 이미지: S10. v1.1 추가 설계: 상태 분리·HTML/CSV·이력 보존. 확인: F06/F11/F12, T20/T21/T30/T31/T38/T40, AC07/AC10/AC12/AC15.

## 13. S11 작업 목록·상세

목적: 접수부터 시도·취소·결과까지 서버 기록으로 복원한다.

| 영역 | 내용·행동 |
|---|---|
| 필터 | kind·실행 상태·생성 기간·허용 scope, cursor/limit |
| 목록 | 작업 ID/표시 번호, RCA/보고서, 대상·접수 시각, 실행 상태, 요약 산출 상태 |
| 상세 | 단계·attempt_no·기한·취소 요청 시각·종료 사유·권한에 따른 attempts 요약·결과 링크 |
| 취소 | can_cancel 안내, reason 입력, 고정 Idempotency-Key·If-Match로 cancel 접수 후 최종 상태 재조회 |
| 재시도 | can_retry 안내, reason 입력, 고정 Idempotency-Key·If-Match로 같은 job retry, 성공하면 같은 상세 조회 재개 |
| 재분석 | 새 analysis/report + parent_job_id, 새 S11 작업 열기 |

GET /jobs 목록과 /jobs/{id} 상세를 사용한다. 상세의 attempts는 접근 허용 소유 운영자/해당 업무 관리자에게만 attempt_no·started_at·finished_at·stage·termination_reason·error_code의 안전한 시도 요약을 보여준다. 그 외 사용자에게 반환되는 null은 시도 상세 숨김으로 처리하며 Worker 내부·민감 로그를 표시하지 않는다. 목록·상세·Assistant의 같은 작업은 조회 결과를 공유한다. 보이는 활성 작업은 설정 가능한 backoff, 비가시 탭 감속, terminal 중단이다. 근거 없는 진행률·내부 추론 시간은 만들지 않는다. 화면을 닫아도 작업은 유지한다.

취소 버튼을 누른 순간 “취소 완료”로 바꾸지 않는다. 완료와 경합하면 서버 확정 상태를 따른다. cancel/retry 모두 응답 유실 시 같은 키·같은 reason/요청을 유지하여 중복 변경·다음 시도를 만들지 않는다. 실제 UI에서 시안의 수동 “다음 단계” 버튼을 제거한다.

기준 이미지: S11-queued, S11, S11-cancel. 확인: F08, T23~T27, AC08/AC09/AC14.

## 14. S12 지식·Runbook

목적: 인용된 버전을 열고 허용된 관리자가 지식 발행 업무를 완료한다.

| 탭·영역 | 내용·행동 |
|---|---|
| 발행 지식 | 종류·코드/증상·지원 장비/버전·공개 범위 검색, 정확 revision 상세 |
| 상세 | 원문 출처·내부 권고·필수 근거·호환 조건·발행/폐기 상태, 결과 인용으로 복귀 |
| 조사 절차 | 등록 코드의 procedure ID/version·입력·조회·종료 규칙, 읽기 전용 |
| 관리 탭 | 지식 관리자만 초안 목록·편집·검토 요청/결과·발행·폐기 |
| 수정 흐름 | 검토 후 수정→재검토, 발행본은 새 revision 초안 생성 |
| 폐기 | 사유 필수, 새 분석에서 제외, 이전 결과의 인용은 유지 |

관리 폼은 제목·종류·내용·지원 조건·허용 scope·근거·개정 메모를 받는다. /review의 action=request|approve|request_changes와 comment·선택 evidence_refs를 사용해 draft→in_review→reviewed 또는 수정 요청 시 draft로 연결한다. 검토 후 편집은 draft로 돌아가고 검토된 content_hash의 내용만 발행한다. 요청·검토 결과·수정 요구·수행자를 관리 이력에서 확인한다. If-Match 충돌은 최신본 비교로 안내하며 입력을 덮어쓰지 않는다. 서비스 관리자라는 이유로 지식/관측 범위를 확장하지 않는다.

호출: /knowledge 목록·정확 revisions, /review, /publish, /retire, GET /knowledge/procedures. 기준 이미지: S12. v1.1 추가 설계: 관리 탭·전체 발행 흐름·범위 권한·절차 읽기 전용. 확인: F10, T11/T12/T29, AC10/AC12.

## 15. S13 사내 모델

목적: 사내 모델을 서버에 등록하고 연결 검사·사용 상태를 관리한다.

모델 카드에는 이름·추론용 모델명·Endpoint·활성 여부·사용 업무·revision을 표시한다. 등록/수정 폼은 name·endpoint_url·model_name·secret_ref를 받고 artifact_revision·engine_revision·precision·capabilities·limits_profile_id는 고급 설정에 둔다. 주소 분할 입력 UI를 유지하면 protocol·host·port·base path를 검증하여 endpoint_url로 조합한다. 화면의 추론용 모델명(model_name)과 API 프로필 식별자(model_id)를 구분한다. 실제 허용 주소 형식은 C06/서버 프로필과 일치시킨다. 비밀 원문은 응답·브라우저 저장에 넣지 않는다.

버튼은 등록, 수정, 서버 연결 검사, 비활성화다. 삭제 대신 enabled=false를 사용한다. 라우트에서 사용 중이면 대체 모델을 지정한 뒤 처리하거나 사용 중 안내를 한다. 진행 작업의 모델 revision과 기존 결과는 유지된다.

형식 정상 / 통신 성공 / 분석 품질 검증을 별도 표시한다. 브라우저는 모델 IP로 직접 접속하지 않는다. 연결 검사는 서버의 허용 목적지 제한 안에서 수행한다. 실패로 설정을 삭제하지 않는다.

호출: GET/POST /models, GET/PATCH /models/{id}, POST /models/{id}/test-connection. 기준 이미지: S13, S13-edit. v1.1 추가 설계: 서버 계약·비활성화·검증 상태 분리. 확인: F13, T32/T33/T40, AC11.

## 16. S14 질의·Agent별 모델 지정

목적: 공통 Assistant·RCA·운영보고서의 사내 모델을 지정한다.

공통 기본 모델 선택, RCA/보고서의 기본 상속 또는 개별 지정, 현재 revision·저장·미저장 변경 안내를 둔다. 비활성 모델은 신규 지정 후보에서 제외한다. 저장은 GET/PATCH /model-routes와 If-Match를 사용하며 기존 service_profiles를 재사용한다.

형식/연결/품질 근거는 S13으로 연결한다. 변경은 새 요청에 적용하고 진행 작업·과거 메시지의 모델 기록은 그대로 둔다. 실패 시 외부 모델로 자동 전환하지 않는다. 두 탭 412 충돌 때 입력을 유지하고 최신 설정과 비교한다.

기준 이미지: S14. 확인: F13, T32/T33/T40, AC10/AC11.

## 17. S15 데이터 연결

목적: Mimir·Loki·KSM·매핑·업무 이력의 경로와 분석 준비를 구분한다.

소스별 상태 카드에 연결·최신 원본/수신·필드·관측 기간·허용 범위·영향 R/O 주제·C04 근거를 표시한다. 연결 성공과 데이터 충분성을 나란히 둔다. 수정은 서비스 관리자에게만 제공하고 비밀값은 참조 형태로 처리한다.

CPC-2의 일부 수집·현재 매핑 확인을 CPC-1과 전체 이력의 완료로 확대하지 않는다. Loki 최신 도착 등 확인 대기는 그대로 표시한다. source 장애를 GPU 장비 장애로 표현하지 않는다. “분석 범위 보기”→S04다.

별도 manage_access 권능이 있는 담당자에게만 권한 관리 탭을 제공한다. role·CPC·단일 Namespace·asset_observation 권한 행과 변경 사유를 편집하고 If-Match로 저장한다. /me의 access_revision 변경을 확인해 관련 캐시를 비운다. 서비스 관리자라는 역할만으로 권한을 추가하지 않는다.

호출: GET /service-status, GET/PATCH /settings/{profile_id}, 권한 관리 시 GET/PATCH /settings/access-grants. 기준 이미지: S15. 확인: F01/F13, T01/T02/T32/T33, AC03/AC11/AC14.

## 18. S16 공통 Assistant·펼친 대화·모바일

목적: 같은 맥락의 질문을 이어가고 긴 조사·보고서로 연결한다.

| 영역 | 내용·행동 |
|---|---|
| 상단 | 대화 ID·범위 칩·현재 화면 범위 적용·펼치기/닫기 |
| 범위 | 일반 질문 / 현재 화면 / 접근 가능한 전체 범위와 실제 CPC/Namespace·기간 |
| 메시지 | 처리 주체·설명·저장 context·근거·모델/revision·실패 상태 |
| 작업 카드 | 전문 job 접수·진행·결과, S11 열기, 별도의 작업 취소 요청 |
| 입력 | 질문·전송·응답 기다리기 중지, 고급 직접 Agent 지정은 접힘 |
| 복구 | 응답 유실/진행 중이면 같은 message_id 재조회, 같은 키·다른 본문 409 안내 |

일반 메시지는 짧은 제한시간의 동기 처리이며 스트리밍 타이핑 상태를 실제 수신으로 표현하지 않는다. 진행 중 재전송은 같은 message_id의 202, 완료·실패는 저장 메시지 조회로 복구한다. accepted/processing/completed/failed를 구분하고 response=null은 완성 응답으로 보이지 않게 한다. Chatbot 처리 lease가 만료된 일반 메시지만 failed로 남으며 Backend 재시작으로 상태를 바꾸지 않는다. 사용자가 새 생성을 선택할 때만 새 키·이전 메시지 참조를 사용한다. 범위 적용은 이후 메시지만 바꾸고 같은 대화를 패널/펼친 화면에서 공유한다.

“응답 기다리기 중지”·닫기는 화면 동작이다. 서버 생성·전문 작업 취소로 표시하지 않는다. 이미 접수한 job은 명시적인 취소 버튼과 서버 확정 상태로 처리한다. 조회자는 이 경로에서도 전문 job을 새로 만들지 못한다. 질문·외부 문서·로그의 임의 스크립트나 명령은 실행하지 않는다.

데스크톱은 비모달 우측 패널, 모바일은 모달 drawer다. 입력창은 보이는 위치에 남고 메시지만 스크롤한다. 모바일 focus trap·Escape·원래 버튼 복귀·배경 inert·스크린리더·320px/200%/키보드 열림을 T37에서 실제 확인한다.

호출: conversations/messages 목록·제출·message_id 상세, 전문 jobs. 기준 이미지: S16, S16-desk, S16-mobile. v1.1 추가 설계: scope 문구·동기 응답/복구·로컬 대기 중지와 job 취소 분리. 확인: F01/F08/F09, T01/T02/T23/T25/T28/T37, AC01/AC02/AC08/AC12~AC14.

이번 개정의 완료는 문서 계약 반영이다. 기존 시안에 실제 API·DB·LLM·권한·정기 예약·복원이 연결되었다고 판정하지 않는다. 신규 시험 ID를 추가하지 않고 07의 F/R/O/S/API/T/AC 표와 05의 T01~T40에 실행 증거를 연결한다. 수정 화면 캡처와 접근성·실환경 시험은 실제 구현 후 해당 상태로 기록한다.

## 독립 모듈 구조 반영 (v1.2)

모든 브라우저 호출은 Backend /api/v1만 사용한다. S16의 Agent Chatbot 버튼은 기존 대화 패널을 열며 서버 실행은 Chatbot 모듈이 담당한다. RCA 요청은 RCA Agent, 보고서 생성/출력은 Report Agent, 사건은 Incident, 일정은 Scheduler가 담당하고 Backend가 각각 내부 API로 호출한다. 모델 라우팅의 assistant 키는 호환을 위해 유지한다.

S07 사건·S09 일정·S16 대화에서 전문 작업 전달은 pending/delivering/accepted/blocked/failed/cancelled를 표시한다. job_id가 null이면 ‘전달 대기/전달 중’이며 S11의 queued 작업을 가짜로 만들지 않는다. GET /dispatches/{id}로 복구하고 accepted와 job_id 확인 후 기존 S11 작업 흐름으로 연결한다. blocked/failed는 이유와 원본 참조를 표시하고 자동 새 요청을 만들지 않는다.

일정 발생은 pending/accepted/missed/blocked/failed를 표시한다. accepted는 보고서 완료가 아니라 job 접수다. 중복 기간 missed는 기존 dispatch/job으로 이동할 수 있다. 일정 비활성화와 저장된 전달/작업 취소는 별도 행동이다. 전달 전 취소는 POST /dispatches/{id}/cancel, 작업 접수 후 취소는 소유 Agent로 위임된 job 취소 결과를 표시한다. 전달 accepted 자체를 취소 성공으로 표현하지 않는다.

패널 닫기는 취소가 아니다. Backend 연결이 끊겨도 동일 conversation/message/dispatch/job ID로 재조회한다. 내부 모듈 장애는 관련 기능의 오류와 재조회 동작으로 표시하고 내부 URL·비밀은 노출하지 않는다. T41~T48과 기존 화면 검수를 함께 적용한다.
