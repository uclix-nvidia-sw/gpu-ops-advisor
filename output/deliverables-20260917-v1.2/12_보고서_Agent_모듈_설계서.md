# 12. 보고서 Agent 모듈 설계서

문서 버전: 1.2 · 모듈 ID: report · 대응: F06/F12, O01~O11 · 독립 실행·배포

## 1. 실행 경계와 책임

보고서 Agent는 자체 보고서 접수 API와 보고서 Worker, 저장 결과의 HTML·CSV 출력을 소유한다. Backend의 직접 보고서 요청, Chatbot 전문 전달, Scheduler 정기 발생을 같은 접수 계약으로 처리한다. 일정의 시간 계산은 Scheduler가 맡고 보고서 Agent는 전달된 절대 분석 기간을 검증·사용한다.

접수 API와 Worker는 동일 모듈 이미지에서 시작하며 부하에 따라 실행 모드를 분리할 수 있다. Backend는 보고서 집계·프롬프트·Worker 루프를 실행하지 않는다. 공통 계산 함수를 다른 Agent와 공유하며 각자 산식을 재작성하지 않는다.

## 2. 내부 API와 데이터

접두사는 `/internal/v1`이다.

| Method·경로 | 입력·처리 | 결과 |
|---|---|---|
| POST /reports | scope·time_range·topic_ids·group_by·비교 기간·조치 참조 | 커밋 후 202, job_id=report_id |
| GET /reports, /reports/{id} | 현재 권한·필터 | 작업·주제별 저장 결과·근거 |
| GET /reports/{id}/export?format=html\|csv | 저장된 final과 현재 접근 범위 | HTML 또는 집계 CSV, 재계산 없음 |
| GET /jobs/{id} | kind=report 확인 | 공통 job DTO |
| POST /jobs/{id}/cancel, /retry | If-Match·멱등·권한·예산 | 저장한 명령 결과 |
| GET /dispatch-receipts/{dispatch_id} | 전달 ID·현재 위임 범위 | 동일 job 참조 또는 404 |
| GET /health/live, /health/ready | 내부 상태 | 생존·접수 준비 |

소유 데이터는 kind=report jobs·job_attempts·job_results·command_receipts와 생성한 보고서 파일이다. schedules와 schedule_occurrences를 직접 변경하지 않는다. Scheduler/Chatbot의 전달 결과는 생산 모듈이 갱신한다.

생성 ID·scope·resource_selectors·action_record_ids 상세는 02 §4.1을 따른다. Scheduler 입력의 절대 기간·revision은 저장된 전달 내용과 대조한다. 소유자의 현재 권한과 날짜·주제 조건을 매 접수에 검증한다.

## 3. 보고서 업무

입력은 scope·기간·시간대·주제·그룹·선택 비교 기간이다. 요청을 접수할 때 실제 절대 기간과 적용 범위를 화면에 표시한다. 정기 보고서는 완료된 달력 기간을 사용한다.

주제별 조회 → 같은 시각의 신원 연결 → 단위·공백·중복 검증 → 결정적 계산 → 규칙 적용 → 사실·검토 대상·다음 행동을 만든다. 보고서는 RCA의 Incident·결과를 참조하며 별도 사건 원장을 만들지 않는다.

| ID | 주제·필수 데이터 | 결과·판단 | 부족 시 |
|---|---|---|---|
| O01 | 장비·Node 변화: D01/D03/D04/D06, 관련 작업은 D08 | 장치·Node 현황/변화와 연결 Pod. 장치 VRAM과 Pod 메모리 실사용 구분 | 현재 값만 있으면 추세 보류 |
| O02 | 할당 명세·시간: D08·전용/공유, 기간은 UID·이력·D10 | 현재 고유 장치·할당 단위, 관측 기반 GPU-hours/instance-hours | 현재 연결만 있으면 현재 수량만. GPU 요청 없어도 매핑 이력 기반 시간 가능 |
| O03 | 저활동: O02 + D02·품질·업무 예외 | 저활동 후보·실제 저활동 구간·확인할 작업·예외 | 활동 없으면 저활동 null. VRAM으로 대체 금지 |

| O09 | GPU 에너지: D11·D01/D10·기간 | 실제 W 적분 또는 검증된 에너지 증가량, 모델별 비교 | power limit만 있으면 kWh null |

O04는 v1에서 장치별 값·최대/최소·차이를 제공한다. 별도 ‘이상 편차’ 자동 판정 임계값은 검증된 정책이 있을 때만 사용한다. O05는 동일 정의·모델·관측 범위별 발생률과 건수로 정렬하고 미검증 가중 종합 점수를 만들지 않는다.

## 4. 실행·수치·결과

공통 조회로 신원·관계·관측 품질을 확인하고 04 §5 산식으로 결정적으로 계산한다. 각 topics[].metrics와 source/evidence를 저장한 뒤 LLM 설명을 검증한다. 일부 입력 부족은 해당 주제의 blocked/partial이며 독립 주제 결과를 소거하지 않는다.

작업 점유·retry·취소·유효 attempt·최종 저장은 15를 따른다. 모든 일·주·월 보고서는 같은 Worker 흐름을 사용한다. 설명이나 집계 때문에 Scheduler를 호출하지 않는다. 긴급 RCA가 공유 추론 한도를 사용하더라도 보고서의 최대 대기 정책·deadline을 적용한다.

HTML/CSV는 저장된 결과와 동일한 수치를 사용한다. 본문 이스케이프·허용 서식·CSV 수식 방어·서버 파일명·현재 권한 검사를 적용한다. 별도 PDF/DOCX 제품 보고서 엔진은 추가하지 않는다.

## 5. 장애와 완료 조건

Scheduler가 내려가도 사용자 직접 보고서는 가능하다. 보고서 API가 내려가면 Scheduler 발생은 pending 전달로 보존되고 중복 없이 복구한다. 모델 장애 시 수치·근거를 보존하고 narrative_status를 구분한다. 업무 DB 저장 실패 시 성공으로 응답하지 않는다.

O01~O11, T15~T21·T31·T38·T40을 검증하고 T42로 독립 접수·실행을, T45로 정기 전달의 중복·응답 유실·revision 경합을 시험한다. 실제 상태는 NOT RUN이다.
