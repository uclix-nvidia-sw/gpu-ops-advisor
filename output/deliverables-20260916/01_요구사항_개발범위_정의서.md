# 01. DSX 요구사항·개발 범위 정의서

문서 ID: DSX-REQ-001 · 버전: 1.0 · 기준일: 2026-09-16 · 상태: 개발 기준

## 1. 목적과 서비스 범위

CPC-1·CPC-2의 GPU·Node·Pod 관측을 CSC에서 연결하여 장애 조사와 운영 개선 검토를 지원한다. 사용자는 별도 Web Client의 대시보드·공통 대화에서 사건, 분석, 보고서, 근거를 확인한다.

전문 Agent는 **GPU Node RCA Agent**와 **최적화 운영보고서 Agent** 두 개다. 일반 Assistant는 공통 대화·요청 해석·결과 설명 역할이며 세 번째 전문 Agent로 분리하지 않는다.

RCA는 사건·증상별 사실, 관련 작업, 원인 후보, 다음 점검을 제공한다. 보고서는 현재 할당 명세와 기간별 할당·활동·사건을 비교해 검토 대상과 근거를 제공한다. 실제 복구·자원 회수·재배치·전력 변경은 운영자의 실행 영역이다.

## 2. 구조 기준

| 구분 | 채택할 구성 |
|---|---|
| 사용자 경로 | Web Client → 사용자 Gateway → Backend API |
| Backend 기능 | 사용자 API·대화 / Incident / 작업·스케줄 / RCA / 운영보고서 / 조회·계산 / Knowledge / LLM 호출 관리 |
| 실행 단위 | API 서버, RCA Worker, 보고서 Worker. 공통 기능은 공유 모듈 |
| 업무 저장 | PostgreSQL: 작업·관계·사건·결과·근거·대화·지식·운영 이력 |
| 관측 조회 | Mimir와 Loki. 원시 시계열·전체 로그를 업무 DB에 복제하지 않음 |
| 보관 | 관측 저장소용 Object Storage와 업무 근거 파일용 별도 권한 영역 |
| 추론 | 사내 Endpoint의 Dynamo·추론 엔진·Local LLM. 업무 영속 큐는 Backend에 둠 |
| 기존 수집 | 두 CPC의 기존 중앙 조회 활용. CPC-2 직접 수집 변경과 CPC-1 상태는 구분 |

Backend 8개 기능은 네트워크 서비스 8개를 의미하지 않는다. 사용자 Gateway와 관측 수신 Gateway의 논리 책임은 분리하고 실제 설치 공유 여부는 배포 설정으로 정한다.

## 3. 사용자와 권한

아래는 v1 권한 묶음이다. 실제 조직·계정 매핑은 운영 인계서 C01에서 지정한다. 한 사용자가 복수 역할을 가질 수 있다.

| 역할 | 허용 업무 | 제한 |
|---|---|---|
| 조회자 | 허용 범위의 대시보드·사건·결과·근거·발행 지식 조회, 결과 설명 질의 | 새 전문 분석·정기 일정·운영 기록·설정 변경 불가 |
| 운영자 | 조회자 권한 + RCA·보고서 요청, 본인 작업 취소, 일정 관리, 사건 상태·조치·검토 기록 | 부여받은 CPC/Namespace 범위 안에서 수행 |
| 지식 관리자 | 지식 초안·검토·발행·폐기 관리 | 발행본 원문 수정 불가. 새 revision으로 개정 |
| 서비스 관리자 | 연결 설정·허용 대상·역할·작업 관리, 타인 작업 취소 | 관리자 권한과 데이터 조회 범위를 별도로 부여 |
| 시스템 계정 | 정해진 CPC의 Webhook 수신 또는 정기 실행 | 사람 계정의 포괄 권한을 재사용하지 않음 |

Namespace 제한 사용자는 해당 작업의 관계·허용된 결과를 조회한다. 노드 전체 로그, 공유 장치의 타 Namespace 관계, 전체 GPU 활동은 별도 장비 관측 권한이 없으면 노출하지 않는다. 혼합 범위 보고서는 포함 범위 전체 권한이 없으면 원문 조회를 거절한다. 제한된 결과가 필요하면 허용 범위로 새 보고서를 생성한다.

## 4. 대표 사용자 흐름

1. **알림 조사:** Grafana 알림 → 사건 정규화·중복 확인 → RCA 접수 → 과거/현재 관계와 근거 조사 → 결과 저장 → 운영자가 원인 후보·점검 사항 확인.
2. **사용자 조사:** GPU 또는 Pod·시각·증상 선택 → 사건 없는 RCA 요청 → 조사·결과 조회 → 추가 근거로 새 실행 생성.
3. **보고서:** 대상·기간·주제 지정 또는 정기 일정 도래 → 접수 ID 확인 → 집계·설명 → 주제별 결과와 정보 부족 사유 조회.
4. **후속 운영:** 분석·보고서에 검토 의견 또는 실제 조치 기록 → 조치 전후 관측 요청 → 새 결과를 기존 결과와 연결.
5. **공통 대화:** 어느 화면에서든 현재 대상·기간·결과 맥락으로 질문 → 일반 설명 또는 등록 조회 → 긴 전문 조사는 작업으로 접수하고 진행 상태 안내.

## 5. 기능 요구사항

P0는 공통 연결과 기본 사용 흐름의 선행 구현, P1은 전문 분석 및 운영 완성 항목이다. 둘 다 이번 개발 범위다. 입력 미확보 기능도 계약·상태 처리·고정 시험 데이터 검증을 구현하고 실환경 활성 조건을 별도로 관리한다.

| ID | 기능·우선순위 | 구현 내용 | 완료 조건 | 시험 |
|---|---|---|---|---|
| F01 | 인증·범위 제어 / P0 | 계정·역할·CPC/Namespace 범위, 결과·근거 재조회 권한 | 허용 범위만 조회·변경하고 교차 범위 접근을 차단 | T01, T02 |
| F02 | 대시보드·대상 조회 / P0 | CPC·Node·GPU·Pod·Namespace, 현재 매핑·관측 품질·사건 요약 | 동일 이름을 CPC별로 구분하고 원본 시각·미확인 값 표시 | T03, T04 |
| F03 | 메트릭·로그·근거 조회 / P0 | 허용 query ID, 기간·대상 제한, 근거 원문·요약 | 원본 시각·단위·출처·누락 및 권한을 유지 | T05, T06 |
| F04 | Alert·Incident / P0 | 규칙 알림 수신, 원본 보존, 중복·상태·재발·입력 버전 | 동일 알림 재전송은 작업 중복을 만들지 않고 새 증거는 새 분석 가능 | T07, T08, T09 |
| F05 | RCA / P0·P1 | R01~R09, 사건·사용자·추가 증거 조사 | 사실·후보·지지/반박·관련 작업·부족 정보·권고 보존 | T10~T14, T39 |
| F06 | 운영보고서 / P0·P1 | O01~O11, 현재 명세·기간 집계·비교·개선 검토 | 수치·단위·품질·버전·근거와 주제별 산출 상태 저장 | T15~T21, T38 |
| F07 | 정기 보고서 / P0 | 일·주·월 일정, 시간대·분석 기간·활성/일시중지 | 동일 발생 시점의 중복 실행 방지, 재시작 후 누락 인지 | T22 |
| F08 | 작업 관리 / P0 | 영속 접수, 상태·단계·취소·재시도·복구·마감 | 재시작 후 작업 유지, 유효한 시도만 최종 결과 확정 | T23~T27 |
| F09 | 공통 Assistant / P0 | 일반 대화·화면 맥락·기존 결과 설명·전문 작업 연결 | 대상·기간을 명시하고 권한 없는 조회·임의 쿼리 실행 방지 | T28 |
| F10 | Knowledge / P0·P1 | Runbook·절차·정책·데이터 의미·참고 근거, 검토·발행 | 호환 범위 내 발행본 사용, 미등록 증상 조사, 불변 revision | T11, T12, T29 |
| F11 | 검토·실제 조치 기록 / P1 | 작성자·대상·시각·내용·근거·결과 연결 | 권고와 실제 수행을 구분하고 수정 전 이력 보존 | T30 |
| F12 | 결과·공유용 출력 / P1 | 결과 목록·상세·버전·재분석 연결, 보고서 HTML·집계 CSV 출력 | 저장된 결과로 출력하며 화면·파일 수치가 일치, 권한 검사 | T31 |
| F13 | 서비스 설정·상태 / P0 | 연결 프로필·사내 LLM Endpoint·최신성·Worker/큐 상태 | 비밀값을 숨기고 저장소 장애와 장비 장애를 분리 | T32, T33 |
| F14 | 배포·인계 / P1 | 설정·버전·마이그레이션·재시작·백업·복원·진단 안내 | 별도 환경 설치·복원·기본 연동 시험과 인계 증거 | T34~T37 |

출력 형식은 v1의 구현 기준으로 HTML과 CSV를 채택한다. 별도의 PDF/DOCX 보고서 편집·템플릿 엔진은 기본 요건에 추가하지 않는다.

## 6. Agent 업무 범위

| RCA | 제공 업무 |
|---|---|
| R01 / R02 / R03 | 알려진 오류 조사 / GPU→Pod / Pod→GPU 조사 |
| R04 / R05 / R06 | 작업 영향 확인 / 미등록·불명 증상 조사 / 재발 위치 비교 |
| R07 / R08 / R09 | 공통 장애 범위 / 조치 검토 대상 / 조치 후 관측 |

| 운영보고서 | 제공 업무 |
|---|---|
| O01 / O02 / O03 | 장비·노드 변화 / 할당 명세·시간 / 저활동 후보 |
| O04 / O05 / O06 | 다중 GPU 편차 / 반복 사건·정비 순서 / 사건 당시 작업 |
| O07 / O08 / O09 | 배치 대기·용량 검토 / Namespace·프로젝트 배분 / GPU 에너지 |
| O10 / O11 | 조치 전후 변화 / 관측 품질 |

세부 조건과 부족 시 출력은 [04 Agent 명세](<04_Agent_동작_판단_명세서.md>)를 따른다. 추가 카탈로그 A~F 60개 항목은 O/R을 보완하는 참고 분류이며, 외부 과금·Run:ai quota·업무 성과 연동을 일괄 신규 개발 범위로 편입하지 않는다.

## 7. 비기능 요구사항

| ID | 기준 | 완료 조건 | 시험 |
|---|---|---|---|
| N01 | 수치·근거 정확성 | 결정적 계산, 0/null 구분, 실행과 결과 품질 분리, 권고별 근거 추적 | T15~T21, T38~T40 |
| N02 | 재시작·중복·취소 안정성 | 사건·접수 원자성, 점유 만료, 시도별 결과 제한, 지연 응답 차단 | T07, T23~T27 |
| N03 | 접근 통제·감사 | 서버에서 범위 검증, 비밀값 보호, 변경·발행·조치 감사 기록 | T01, T02, T28~T30, T32 |
| N04 | 성능·자원 제한 | 큐·조회·LLM 동시성 및 토큰/시간 예산 준수, 대기·처리시간 측정 | T26, T33, T36 |
| N05 | 사용·운영 가능성 | 키보드 접근, 상태를 색 외 텍스트로 표시, 재시작·복원·인계 검증 | T34, T35, T37 |

성능 목표·최대 검증 규모·보존 기간·RPO/RTO는 06의 C05~C10에서 실제 장비 기준으로 지정한다. 임의의 처리량이나 복구시간을 계약값으로 간주하지 않는다. 값의 미지정은 해당 운영 검수의 미완료 항목이다.

## 8. 기본 범위 밖

- 자동 GPU 리셋·노드 재부팅·cordon/drain·Pod 종료·자원 재배치·전력 제어와 능동 진단 실행.
- 냉각·시설 전력·BMS/DCIM, Exchange/NATS 도입, Digital Twin 제어, Run:ai API·quota·플랫폼 대기열 신규 연동.
- 별도 그래프·벡터·시계열 DB, 범용 YAML 실행 엔진, 지식별 독립 서비스.
- 과금·청구·고객 계약, 미검증 비용 절감·증설 수량 확정, 공유 GPU의 프로세스별 실사용 추정.
- CPC→CSC 기존 구축을 처음부터 재수행하는 작업. 연동에 필요한 결함 수정·추가 필드 검증은 포함한다.

## 9. 개발 완료와 환경 활성 판정

1. 요구사항별 구현·API·화면 연결과 고정 데이터 시험을 완료한다.
2. 실제 두 CPC의 허용 범위 조회, Alert→RCA, 사용자·정기 보고서 생성·저장·조회 경로를 시험한다.
3. 각 O/R 주제에 대해 실제 활성 가능한 입력과 부족한 입력을 기록한다. 모의 데이터 PASS를 실제 수집 검증으로 바꾸지 않는다.
4. 필요한 입력을 갖춘 주제는 실환경 기대 결과를 검증하고, 부족한 주제는 이유·null·부분 산출을 검증한다. 실제 산출 자체가 인수 조건인 주제는 입력 확보 전까지 미완료로 남긴다.
5. 05의 필수 시험과 06의 배포·복원·인계 항목을 충족한다. 담당자·일정은 후속 WBS에 배정한다.
