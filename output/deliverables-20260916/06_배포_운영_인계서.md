# 06. DSX 배포·운영 인계서

문서 ID: DSX-OPS-001 · 버전: 1.0 · 기준일: 2026-09-16 · 상태: 배포·인계 기준 / 실제 인계 미실행

대응 요구사항: F07·F08·F10~F14, N02~N05. 기존 Kubernetes 기반 CPC/CSC와 합의된 Backend 구조를 기준으로 작성했다. 실제 앱 이미지·배포 manifest·DB migration이 아직 제시되지 않았으므로 실행 명령·설치 경로·비밀값을 가상으로 채우지 않는다. 구현 시 이 문서의 설정표에 실제 파일/명령과 실행 결과를 연결한다.

## 1. 운영 구성과 책임

| 구성 | 운영 책임 | 정상 확인 | 장애 시 영향 |
|---|---|---|---|
| Web Client·사용자 Gateway | 서비스 운영 | 접속·인증·API 라우팅 | 사용자 접근 불가, 기존 job은 별도 상태 확인 |
| Backend API | 서비스 운영 | ready·DB 접속·접수/조회·인증 | 새 요청·Webhook·조회 영향 |
| RCA/보고서 Worker | 서비스 운영 | heartbeat·유효 lease·완료/실패 추이 | 해당 유형 지연, 만료 점유 복구 필요 |
| PostgreSQL | DB 운영 | 연결·용량·백업·복원·migration | 접수·상태·결과 영속성 영향 |
| Mimir·Loki·관측 Gateway | 관측 운영 | 실제 대상·원본 시각·지연·조회 성공 | 일부/전체 분석 근거 부족. 장비 장애와 구분 |
| CPC Fleet·Alloy·KSM·Exporter | CPC/관측 운영 | target·원본 필드·라벨·UID 조인·최신성 | 해당 대상 관측·관계 누락 |
| Object Storage·볼륨 | 인프라/DB 운영 | 접근·용량·checksum·보존 | 근거 파일/관측 보관 또는 모델 적재 영향 |
| Dynamo·추론 엔진·Local LLM | AI 운영 | Endpoint·모델 버전·추론·슬롯·GPU 용량 | 설명/후속 조사 지연·실패, 계산 근거는 보존 |
| Knowledge | 지식 관리자 | 호환 발행본·검토·revision·근거 | 잘못된 권고/해석 또는 해당 권고 보류 |

역할은 책임 영역이며 사람 수나 전담 조직 수를 뜻하지 않는다. 실제 담당자·대체 담당·연락 경로는 C12에서 지정한다. 서비스 관리 권한만으로 모든 고객/Namespace 데이터 권한이 생기지 않는다.

## 5. 시작·종료·업데이트

### 정상 시작

DB/업무 파일 영역과 필수 연결 → 검증된 schema/코드·설정 → API → Worker → Client 연결 → 스모크 시험 → 자동 일정·Webhook 실행 순서로 확인한다. Mimir/Loki/LLM의 일부 장애는 해당 분석의 degraded 상태로 표시하고 API 생존과 구분한다.

### 정상 종료·점검

새 전문 작업/정기 발생을 점검 상태로 제한하고 수신 경로의 재전송·보존 방식을 확인한다. Worker 신규 점유를 중지한 뒤 진행 작업은 deadline 내 완료 또는 명시 취소한다. lease·원격 LLM 상태·미완료 job을 기록하고 Worker/API를 종료한다. DB 종료 전에 진행 트랜잭션·백업 상태를 확인한다. 단순 프로세스 종료를 작업 취소로 처리하지 않는다.

### 업데이트

1. 실행 이미지·schema·query·지식·모델 호환표와 변경 영향을 기록한다.
2. DB/업무 파일·현재 설정을 백업하고 복원 가능한지 확인한다.
3. 이전·새 코드가 함께 실행될 때 호환되는 migration을 먼저 적용한다. 불가능하면 명시 점검 창에서 Worker 점유·접수를 제한한다.
4. 새 API/Worker를 적용하고 이전 attempt의 늦은 결과 차단·공유 한도 유지·기존 결과 조회를 시험한다.
5. 새 입력은 새 revision을 사용하되 진행 중 job의 고정 revision은 유지한다. 사용 불가능하면 실패/새 실행으로 명시하고 몰래 교체하지 않는다.
6. 스모크·영향 시험 PASS 후 자동 실행을 재개한다.

### 롤백

앱만 되돌려도 되는 schema 호환이면 검증된 이전 이미지·설정으로 복귀한다. 비호환 migration이면 앱만 롤백하지 않는다. 접수를 제한하고 호환 전진 수정 또는 검증된 백업 복원을 선택한다. 복원 시점 이후 새로 저장한 결과의 보존/재처리 방법을 기록한다. 발행 지식은 과거 내용을 수정하는 대신 신규 선택 기준을 이전 호환 revision으로 돌리고 변경 이력을 남긴다.

## 7. 장애 대응 Runbook

### OP01. 관측 값·매핑이 사라짐

1. 대상 CPC·Node·GPU·기간·source를 고정하고 `empty/unavailable/parse_error`를 구분한다.
2. 원본 timestamp·up·허용 필드·Alloy 필터·tenant/cluster 라벨·Gateway·저장소 도착 순서로 확인한다.
3. 매핑이면 Exporter 작업 라벨과 같은 시점 KSM uid를 비교한다. util=0 관계를 필터로 제거했는지 확인한다.
4. 조회 실패·불완전성을 collection_observations에 보존하고 영향 주제만 partial/blocked로 표시한다.
5. 기존 성공 설정을 기준으로 수정 후 동일 대상·원본 시각·공백을 검증한다. 빈 매핑을 미할당·작업 종료로 기록하지 않는다.

### OP02. 작업이 계속 대기하거나 진행 중으로 남음

1. job status·stage·available_at·deadline·lease·현재 attempt·취소 요청을 확인한다.
2. Worker heartbeat와 DB 연결, 유형별 점유·공유 LLM 슬롯·unknown 호출을 확인한다.
3. 유효 lease 동안 다른 Worker로 강제 중복 실행하지 않는다. 만료 작업은 공통 회수 절차로 retry_wait/failed/expired를 판정한다.
4. 이전 Worker의 늦은 완료가 차단되는지 확인하고 원격 추론 상태 불명은 OP03으로 처리한다.
5. 회수·재시도·최종 결과를 같은 job ID로 추적한다. 새 근거 조사일 때만 새 job을 생성한다.

### OP03. LLM timeout·과부하·원격 종료 불명

1. job·attempt·stage·LLM request ID, 공유 슬롯, 제출 시각·timeout·예산을 기록한다.
2. Dynamo/엔진의 실제 상태 확인·취소 지원 범위 안에서 원격 종료를 확인한다.
3. 확인할 수 없으면 unknown 상태와 슬롯 격리를 유지하고 검증된 최대 원격 수명 또는 담당자의 조정 절차를 따른다.
4. 같은 호출을 무제한 다시 제출하지 않는다. 일반 대화·RCA·보고서 전체의 공유 한도를 확인한다.
5. 확보한 계산/근거를 보존한다. final 구조화 결과를 이미 발행했다면 새 설명 재생성은 새 연결 job으로 남긴다.

### OP04. 알림 또는 정기 보고서 중복

1. 생산자 재전송 키, source event key, Incident episode/evidence_version, 요청 멱등 키, 일정 occurrence 키를 확인한다.
2. 이미 커밋된 job·final 여부를 조회한다. 중복을 막기 위해 정상 결과를 삭제하지 않는다.
3. 규칙/권한/일정 revision 변경과 단순 재전송을 구분하고 키·원자적 저장 결함을 수정한다.
4. 영향 기간과 잘못 추가된 실행을 연결 기록한 뒤 동일 중복 시험을 재수행한다.

### OP05. PostgreSQL·업무 파일 장애

1. 접수 성공을 반환할 수 있는지 확인한다. 영속 저장 불가면 새 접수를 503으로 거절한다.
2. 진행 Worker의 결과·lease·원격 호출을 보존하고 중복 재시도를 제한한다.
3. DB 용량·연결·권한·migration·파일 접근·checksum 상태를 확인한다.
4. 복구가 필요하면 8절의 격리 복원 절차를 따른다. DB만 복원하고 참조 파일을 검증하지 않은 상태로 운영 재개하지 않는다.

### OP06. 보고 수치·RCA 판단 오류

1. 문제 결과·job·규칙/지식/모델 버전·원본 기간·입력 스냅샷을 보존한다.
2. 03의 식별/소스/단위/시간/공백과 04의 산식·근거·인과 조건을 대조한다.
3. 영향 query/지식/모델 revision의 신규 적용을 제한하고, 올바른 독립 기능은 유지한다.
4. 수정·회귀 시험 후 새 job으로 재분석하고 기존 결과와 연결한다. 잘못된 과거 결과를 조용히 덮어쓰지 않는다.
5. 영향 대상·기간·사용자 확인 필요 사항은 인계된 연락 절차로 담당자가 처리한다.

### OP07. 범위 밖 접근·지식/설정 오변경

1. 해당 계정/설정/발행 revision의 신규 사용을 제한하고 감사 기록·근거를 보존한다.
2. API 조회뿐 아니라 job 실행·결과·파일·대화·evidence 재조회까지 영향 범위를 확인한다.
3. Secret 노출이면 해당 관리 경로로 교체하고 기존 참조를 폐기한다. 비밀 원문을 진단 파일에 다시 넣지 않는다.
4. 호환 설정·권한을 복구하고 T01/T02/T29/T32를 재수행한다.

## 8. 백업·복원 절차

백업은 PostgreSQL의 업무·권한/프로필 참조·지식, 업무 Object Storage 파일, 등록 코드/설정 revision, 필요한 모델 artifact 참조를 포함한다. Secret은 별도 접근 통제된 복구 경로로 관리한다. Mimir/Loki는 자체 보관·복구 정책을 따르며 업무 DB 백업으로 원본 관측이 복구된다고 간주하지 않는다.

1. C05/C10의 보존·RPO/RTO와 백업 방법·실제 명령을 지정한다. 운영 이전에 격리 복원 시험을 수행한다.
2. 백업 시점·DB schema·앱 이미지·파일 목록/checksum·진행 job·지식 revision을 기록한다.
3. 격리 환경에 DB와 업무 파일을 복원하고 외부 Webhook·정기 실행·Worker 자동 처리는 일단 중지한다.
4. FK·결과/근거/파일 참조·checksum·발행 지식·계정 범위를 확인한다.
5. 복원된 running job의 과거 lease/Worker를 무효화한다. 복원 전 원격 추론이 남아 있는지 확인·정리하고 현재 세대에서만 점유를 재개한다.
6. 이미 외부에 결과가 반환됐지만 백업 시점 밖인 작업을 요청/감사 기록과 대조한다. 재접수/재분석 여부를 명시하며 중복 성공을 조용히 발행하지 않는다.
7. 사용자 조회·RCA/보고서 신규 실행·기존 결과 조회·범위·정기 중복 시험을 수행한다.
8. 실제 데이터 손실 구간·RPO·전체 서비스 복원시간/RTO를 기록하고 기준 충족 후 운영 재개한다.

## 9. 사용자 인계 시연

인계받는 담당자가 직접 다음을 수행하고 화면·job ID를 남긴다.

1. 허용 CPC와 대상·기간을 선택하고 원본 최신성·매핑·정보 부족을 읽는다.
2. Incident 상세에서 당시/현재 Pod, RCA 근거·원인 후보·다음 점검을 확인한다.
3. 사건 없는 Pod/GPU 조사를 요청하고 진행·실패·취소·결과 조회를 수행한다.
4. 보고서 주제·기간을 지정하고 결과·부분 산출·HTML/CSV를 확인한다.
5. 정기 일정을 만들고 다음 발생·일시중지·실행 이력을 확인한다.
6. 권고와 실제 조치 기록의 차이를 확인하고 조치 후 분석을 연결한다.
7. 지식 담당자는 초안·검토·발행·폐기와 이전 결과 인용을 확인한다.
8. 운영 담당자는 서비스 장애와 장비 장애를 구분하고 OP01~OP07의 진단 경로·연락 담당을 확인한다.
