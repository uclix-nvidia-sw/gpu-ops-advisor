# 06. 배포·운영 인계서

버전 1.3 · 목표 배포 기준. 실제 배포/성능/복원 시험은 NOT RUN.

## 실행 구성

Frontend, Backend(정기 일정 포함), Incident, Job Controller, RCA Agent, 보고서 Agent를 각각 기동한다. PostgreSQL·업무 파일 저장소·기존 Mimir/Loki·사내 추론 endpoint를 연결한다. 공통 코드는 이미지에 포함하는 라이브러리다. 별도 Scheduler/Chatbot/HPA/큐 메트릭 어댑터는 배포하지 않는다.

GUI는 Backend, Grafana Webhook은 Incident, 생산자/Agent는 JC 내부 주소를 사용한다. 제품 인증은 이번 범위 밖이며 모듈 포트를 외부 GUI 경로로 임의 노출하지 않는다. 기존 관측 저장소·모델 접속에 필요한 환경 비밀은 secret_ref로 관리한다.

## 운영 설정 원장

| ID | 확정할 값 | 확인/책임 |
|---|---|---|
| C01 | DB 주소·migration·업무 파일 경로·백업 | 운영자, 시작/쓰기/복원 |
| C02 | CPC별 Mimir/Loki 주소·tenant/라벨·시간대 | 기존 수집 환경 재확인, 사용자 tenant와 별개 |
| C03 | 원본 주기·query/parser·최대 유효시간·보존 | 표본·UID·신선도 검증 |
| C04 | CPC·D01~D14·R/O 활성 범위 | 충분/부분/미확인과 근거 시각 |
| C05 | Grafana source·Webhook·사건 중복 정책 | Incident 재전송·배열 검수 |
| C06 | 모델/엔진/정밀도·endpoint·secret_ref·토큰 상한 | 실제 서빙·스키마·응답 검증 |
| C07 | Agent 배포 수·worker_slots·kind_limit·shared_limit·lease/heartbeat·retry/deadline·조사 예산 | 양의 정수/주기 관계·부하 시험, 운영자가 수동 설정 |
| C08 | 달력 catch-up 범위/건수·사건 evidence 갱신·유효 정상 연속 관측 기준 | 일정/회복 정책, 미정 값은 해당 자동 판단 보류 |
| C09 | R/O·수치·LLM 평가 입력·기대값 | 05 제품 시험 증거 |
| C10 | 보존/정리·백업 주기·복구 목표·담당 | DB·파일 동시 복원 |

실제 값·담당·검증일·증거를 배포별 원장에 채운다. 문서의 예시는 운영 확정값이 아니다. 모듈 readiness는 DB/설정 준비와 Worker 실행 여유를 구분한다. Agent 부재 때문에 JC의 영속 접수를 불필요하게 막지 않는다.

## 수동 용량 조정

1. 큐 길이·최장 대기·실행 중 수·LLM 지연/격리 상태를 확인한다.
2. 운영자가 실제 서버/LLM 여유를 확인하고 Agent 배포 수와 C07을 결정한다.
3. 배포 도구로 RCA 또는 보고서 Agent를 수동 추가한다. 새 boot_id로 등록해 claim 가능한지 확인한다.
4. capacity 프로필 변경을 JC가 읽고 적용한 revision과 실제 점유를 확인한다. 클라이언트 요청으로 한도를 바꾸지 않는다.
5. 줄일 때 해당 Worker를 draining으로 전환해 새 인수를 멈추고 진행 잡 종료를 기다린다. 강제 종료 시 lease·원격 추론 상태를 확인한다.

한도보다 running이 많은 상태로 수동 축소하면 진행 잡을 강제 중단하지 않고 신규 claim만 제한한다. 큐 길이에 따른 자동 배포·replicas 변경은 없다. 모델 슬롯 부족을 Agent 수 증가만으로 해결된 것으로 판단하지 않는다.

## 기동·업데이트

DB/파일/관측·모델 준비 → migration/설정 검증 → JC → 두 Agent → Incident·Backend → Frontend·Grafana 연결 순으로 확인한다. 대표 사건·즉시 보고서·정기 발생을 실행하고 저장 결과를 다시 읽는다.

업데이트는 신규 claim/생산 중단 또는 drain → 작업·outbox·일정 snapshot 보존 → 호환 DB 변경 → 소비자/생산자 순 배포 → 재전송/접수 확인으로 진행한다. rollback은 읽을 수 있는 이전 계약·이미지와 복원된 DB/파일 조합을 사용한다. 파괴적 migration은 별도 계획이 필요하다.

## 장애 대응

| 증상 | 확인·대응 |
|---|---|
| queued 증가 | 종류별 Worker 존재·freshness·slots·shared_limit·격리 확인, 필요 시 운영자가 수동 조정 |
| running 고착 | heartbeat/lease/원격 호출 확인, 무조건 슬롯 초기화하지 않음 |
| LLM timeout | 종료 불명이면 quarantine, 종료 증거/검증된 수명 없이 재사용 금지 |
| JC 장애 | 신규 접수/claim 중단, 생산자 outbox 보존, 같은 키 재전송 |
| Backend 일정 지연 | next_run/catch-up/missed 확인, 저장 pending은 별도 복구 |
| DB 장애 | 성공 확정 중단, 복구 후 attempt/final/receipt 대조 |
| 결과 불일치 | job·query·산식·evidence·candidate hash 추적, final 덮어쓰기 금지 |
| 관측 부족 | 0으로 채우지 않고 데이터 품질·영향 주제·확인 시각 표시 |

## 백업·인계

DB·업무 파일·설정 revision을 함께 백업한다. 복원 후 final 파일 checksum, source_key/receipt 유일성, occurrence와 outbox 참조, 이전 Worker lease/격리 상태를 점검한다. 이전 프로세스가 살아 있는 환경에 복원 Worker를 병행 기동하지 않는다.

인계 증거: 각 이미지/공통코드 버전, migration, C01~C10, 05 실행 기록, 수동 증설/축소·DB/Worker 장애·정기 복구·백업 복원 결과, 담당자·미확인 항목. 제품 검수 완료 전 성능 수치·가용성·무손실을 보장하지 않는다.
