# DSX 현재 설계와 마이크로서비스 적용안

기준일: 2026-09-16. CPC의 데이터 수집부는 변경하지 않고 Alloy의 중앙 전송 출구만 같은 외부 입력으로 표시했다. 이번 작업은 구조도 작성이며 클러스터 접속·설정 변경·배포를 수행하지 않았다.

## 그림을 읽는 기준

첫 그림은 기존 관측 연동과 최신 분석 서비스 설계를 함께 보여준다. Agent·작업 큐·KB·Dynamo의 구현 완료나 실제 프로세스 배치를 뜻하지 않는다. 현재 백엔드가 모놀리스라는 근거가 없으므로 논리 모듈로 표현했다.

두 번째 그림은 같은 기능을 아래 5개 배포 단위로 나누는 제안이다. 기존 관측 계층, 저장소, 추론 계층의 역할은 유지한다. 개별 서비스 박스는 물리 노드가 아니다. 양방향 선은 요청/응답 또는 읽기/쓰기, 회색 점선은 조회 요청이다. Client의 결과 반환은 AI API 연결에 포함한다.

| 독립 배포 단위 | 책임과 계약 |
|---|---|
| AI API Service | 인증·대상/기간 해석·공통 Assistant·업무 접수와 상태/결과 반환. Assistant는 세 번째 전문 Agent가 아니다. |
| Incident / Job Service | Aggregator의 정규화·중복/flapping 통합, 사건·작업의 원자적 접수, 영속 큐, 스케줄 접수, Worker 점유/갱신/재시도/취소, 결과 확정. 사건·jobs·실행/결과 테이블의 쓰기를 소유한다. |
| Data / KB Service | Mimir/Loki 조회, 시간·단위·식별·품질 검증, 결정적 계산, 관계 이력과 발행 KB 조회. 관계/KB 데이터의 쓰기를 소유하고 사건/분석 결과는 Job Service API로 조회한다. |
| GPU Node RCA Worker | 커밋된 RCA 작업을 API로 점유하고 근거 조회·추론 후 조건부 결과 확정을 요청한다. 인프라에 대해서는 읽기 전용이며 원인 후보·다음 점검·관리자 권고를 제공한다. |
| 운영보고서 Worker | 정기/사용자 보고서 작업을 같은 계약으로 처리한다. 검증된 계산과 근거에 설명을 붙이며 RCA와 별도로 배포·확장한다. |

API를 받는 서비스에는 Deployment + Kubernetes Service, 작업을 가져가 실행하는 Worker에는 별도 Deployment를 제안한다. 두 Worker는 시작 시 HTTP push를 받아야 하는 구조가 아니므로 각각의 수신 Service를 필수로 추가하지 않았다. 서비스 간 인증과 업무별 허용 범위는 내부 통신에서도 검증한다. 이는 Kubernetes의 [Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)와 [Service](https://kubernetes.io/docs/concepts/services-networking/service/)를 이용한 설계 제안이다.

## 두 그림에 공통으로 남긴 계약

- Grafana 관리형 Alerting → 직접 Webhook → Aggregator. 별도 Ruler/Alertmanager 서비스는 추가하지 않는다.
- 사건·작업 저장 성공 이후에만 실행한다. 신규·재발·심각도 상승·유의미한 신규 근거를 분석하며 단순 재전송마다 RCA를 실행하지 않는다.
- 초기 영속 큐는 기존 수단이 없으면 PostgreSQL 작업 레코드를 이용한다. 사건 갱신과 작업 접수는 같은 트랜잭션으로 처리한다. Worker 점유 만료, 시도 버전, 조건부 결과 확정, 취소/마감 및 제한된 재시도 계약을 유지한다.
- 업무 큐와 Dynamo 추론 대기는 다르다. 업무 전체의 복구·우선순위는 백엔드가 책임진다. 마이크로서비스 안에서는 Job Service가 DB 기반의 공통 호출 점유/한도를 관리하고 Assistant와 두 Worker가 한도를 확보한 뒤 Dynamo를 호출하는 초기안을 제안한다. 프로세스별 한도로 전역 한도를 대신하지 않는다.
- Dynamo 설치·버전·queue 활성 설정은 미확인이다. 공식 Frontend의 대기는 활성 설정과 실제 엔진/버전 지원을 검증해야 하며, 영속 업무 큐를 대체하지 않는다. [Dynamo Frontend 설정](https://docs.nvidia.com/dynamo/reference/components/frontend-configuration)
- Local LLM 초기 후보는 Nemotron 3 Super다. 추론 GPU·서빙 엔진·가중치/PV·양자화·복제 수는 미확정이다. 같은 사례의 품질·지연·처리량·VRAM을 평가하고 품질 기준을 충족하면 소형 모델을 검토한다.
- Object Storage는 Mimir blocks와 Loki chunks/index 보관용이다. 관계형 업무 원장이나 모델 실행 메모리를 대체하지 않는다. 별도 보고서/근거 파일을 보관하면 앱 전용 영역과 DB의 참조를 사용한다. 모델 가중치/캐시는 추론 엔진에 맞춘 별도 볼륨 설계다.
- 물리 PostgreSQL은 초기 공동 사용하되 서비스별 계정과 쓰기 소유권을 구분한다. KB 박스의 발행 지식은 같은 PostgreSQL의 논리 영역이며 별도 DB 인스턴스가 아니다. 공유 DB·Job Service·추론 서비스의 장애와 용량 제한은 여전히 공통 의존성이다.
- 복구 확정에는 유효 PASS reason·최신성·관측 범위·연속 N회 성공이 필요하다. Healthy/resolved만으로 복구를 확정하지 않는다. 근거·정책·모델·시각 버전을 결과와 함께 보존한다.

## 노드 정보가 필요한 부분

2026-09-08 통합 기록에는 CSC가 **dell-l40s 단일 노드 kubeadm**으로 나타난다. 같은 호스트 안의 Kind 환경도 기록되어 있으나 별도 Kubernetes 환경으로 구분돼 있다. 이를 합쳐 다중 노드 CSC로 간주하지 않았다. 최신 노드 목록·가용 자원은 이번 자료에서 확인되지 않았다.

논리적인 서비스 분리는 지금 제안할 수 있다. 실제 배치에는 다음 CSC 정보가 필요하다.

| 정보 | 결정할 내용 |
|---|---|
| 클러스터/context, 노드 목록·역할·Kubernetes 버전 | 실제 배포 대상과 제어/작업 노드 구분 |
| 노드별 CPU·RAM allocatable, 기존 requests/limits·사용량 | API/Worker/관측·DB의 자원 여유와 배치 |
| GPU 모델·수량·장당 VRAM·현재 점유·공유/MIG 방식 | 모델 적재, 동시 추론, GPU 노드 격리 |
| labels·taints·현재 Pod 배치·노드 간 연결 | 배치 제약과 장애 도메인 분산 |
| StorageClass·PVC·스토리지 위치·용량·백업 | DB·관측·모델 볼륨과 재시작/노드 장애 복구 |

단일 노드에서도 프로세스·배포 단위를 나눌 수 있지만 노드 장애는 함께 받는다. HPA와 복제 수는 지표·용량 검증 뒤 설정하며, Worker 수 증대가 GPU 추론 처리량 증대로 직결된다고 가정하지 않는다. [Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)
