# 05. DSX 테스트·검수 기준서

문서 ID: DSX-QA-001 · 버전: 1.1 · 기준일: 2026-09-16 · 상태: 개발·검수 기준 / 실제 시험 미실행

이 문서는 구현 결과의 합격 조건과 실행 증거를 정한다. 문서 작성·예시 계산 대조는 서비스 시험 PASS가 아니다. 요구사항 원본은 01, 실행/API는 02, 데이터는 03, 판단은 04다.

## 1. 검수 구분

| 구분 | 대상 | 필요한 증거 |
|---|---|---|
| 계약·계산 시험 | 고정 데이터의 신원·기간·산식·상태·출력 | 입력 파일·계산 기대값·실제 구조화 응답·코드/규칙 revision |
| 통합 시험 | Web→API→DB→Worker→도구/LLM→저장→화면 | request/job/attempt ID, 저장 상태, 화면·서버 실행 기록 |
| 실환경 연동 | CPC-1·CPC-2의 실제 허용 대상·시각·수집 경로 | 조회 원문·원본 시각·배포 버전·수집 경로·해당 시험 결과 |
| 장애·동시성 | 중복·점유·지연·취소·과부하·복원 | 주입한 장애·시각·각 Worker 기록·최종 DB·호출 수 |
| 사용자·운영 인수 | 사용자 흐름·접근성·설치·복구·인계 | 실제 수행자, 단계별 증거, 확인한 한계·미완료 |

고정 데이터는 기능 계약을 검증한다. 실제 입력이 없는 기능의 실환경 산출은 BLOCKED로 남기며 고정 데이터 PASS로 대체하지 않는다. 정보 부족을 정상 표현하는 시험은 별도로 PASS가 될 수 있다.

## 2. 공통 시험 환경·사전 조건

- 운영 데이터를 변경하지 않는 검증 환경과 명시적으로 허용된 읽기 대상 CPC를 사용한다. 장애 주입·Worker 종료·DB 복원은 검증 환경에서 수행한다.
- 06의 C01~C12에 시험 대상 Endpoint·버전·권한·원본 주기·한도·성능·복구 목표를 채운다.
- 조회자, 운영자, Namespace 제한 사용자, 지식 관리자, 서비스 관리자, CPC별 Webhook 시스템 계정을 준비한다.
- 테스트용 두 CPC에 같은 Node/Pod 이름과 다른 UID를 준비하고 공유·전용·MIG 표본을 구분한다.
- 시간 고정 또는 기록된 원본 timestamp를 사용한다. 수집 주기·평가 주기·전송 지연을 각각 남긴다.
- 모델·프롬프트·지식·procedure·query·계산·parser revision과 실제 런타임 설정을 실행 기록에 고정한다.
- 권한은 `scope.clusters[]`의 `cluster_id`와 `namespaces`를 한 쌍으로 시험한다. 예: CPC-1의 dev와 CPC-2의 prod만 허용하며, 두 배열의 교차곱으로 확대하지 않는다. `namespaces: null`의 전체 Namespace 권한과 장비 관측 권한은 별도로 검사한다.
- GUI S01~S16/S07B와 FE AC01~AC15는 화면·기존 검수 식별자로 참조한다. 아래 개정 계약이 v1.0 화면 제안과 다르면 화면·목업도 같은 기대값으로 검수한다. 문서 대조만으로 화면 수정·실행 완료라고 표시하지 않는다.

## 3. 고정 시험 데이터

아래 수치와 자산은 가상이다. 구현 시 작은 JSON/CSV 입력으로 고정하고 실제 제품의 공통 계산 함수를 호출한다. 기대값 계산 코드를 제품 구현과 똑같이 복제해 비교하지 않는다.

| 세트 | 입력 | 기대값·핵심 조건 |
|---|---|---|
| S01 신원 | cpc-1/node-a/pod-a UID U1, cpc-2/node-a/pod-a UID U2 | 서로 다른 두 대상. cpc-1 이름 재사용 U3도 U1과 분리 |
| S02 할당·저활동 | 같은 Pod 전용 G1/G2 각 8시간, 각 5시간 저활동, 충분한 공동 품질 | 16 GPU-hours, 10 저활동 GPU-hours |
| S03 후보 경계 | 60분 중 공동 유효 58분·저활동 54분 | 58/60, 54/58, 후보 true, 저활동 54/60=0.9 GPU-hours |
| S04 공유 | G1 물리 1개에 A/B 공유 관계 2개, 장치 util 80% | 물리 1·관계 2, A/B 실사용 각각 null |
| S05 사건률 | G1 4건/100 관측 GPU-hours, G2 5건/500 | 40·10건/1,000 GPU-hours |
| S06 에너지 | 4 GPU×10시간, 전 250W/후 200W | 10·8kWh, 감소 2kWh |
| S07 배치 | Pending 6개 각 유효 요청 1, bound 4·unbound 2 | 미배치 GPU 요청 2단위, 부족량 null |
| S08 당시·현재 | 14:03 G1↔A, 14:04 A 종료, 16:00 G1↔B | 당시 A·현재 B, 중단 관측과 원인 미확정 |
| S09 공동 품질 | 기대 [0,100분), 매핑 [0,96), 활동 [4,100) | 각각 96%, 공동 92%. 전체 기간 순위 보류 |
| S10 시간 가중 | util 10%가 9분, 90%가 1분; 각 구간 유효 | 평균 18%, 시간 가중 P95 90% |
| S11 경계·공백 | 원본 T=15초, 동일 매핑 t=0·15초·90초 | [0,15초)만 이어 계산. 15→90 공백/마지막값 무기한 연장 금지 |
| S12 편차 | 같은 작업 4 GPU, 같은 30분 평균 82·79·81·9% | 최대-최소 73%p, G4 추가 점검 후보, 병목 원인 확정 없음 |

S03의 60분은 같은 `cluster_id + gpu_uuid + pod_uid + 전용 할당 episode`가 유지되는 벽시계 시간이다. v1.1 후보 창은 episode 시작에 정렬한 겹치지 않는 60분 단위이며, 공동 유효 관측 시간은 커버리지 분모 60분의 일부다. 공백 때문에 episode 길이를 줄여 커버리지를 높이지 않는다. 60분 미만 꼬리는 관측된 저활동 시간만 제공하고 장시간 후보는 `not_assessed`, 사유 `short_allocation_window`로 남긴다.

카운트·ID·상태는 정확히 일치해야 한다. 부동 소수점 계산은 저장값 기준 절대 오차 0.000001 또는 상대 오차 0.000001 중 큰 값 이내를 사용한다. 시간 계산은 입력 timestamp 정밀도 안에서 비교한다. 화면 반올림은 표시 규칙대로 별도 검사하고 반올림된 값을 재계산 입력으로 쓰지 않는다.

이 표의 숫자는 고정 시험 기대값이며 실환경 성능·수집 결과가 아니다. 실제 C04 행에는 CPC별 정상 산출/부족 처리 증거를 따로 기록한다.

## 6. LLM·Agent 품질 평가표

RCA 알려진/미등록/상충/현재·과거, 보고서 할당/저활동/공유/전력/누락의 고정 사례를 같은 입력으로 3회씩 실행한다. 문구의 완전 일치는 요구하지 않는다. 숫자·대상·인용·판단 경계는 모든 실행에서 충족해야 한다.

| 항목 | 통과 기준 |
|---|---|
| 사실 정확성 | 수치는 facts[].value_refs가 참조한 measurements 또는 topics[].metrics의 값·자료형·단위·대상·기간으로 렌더링하며 구조화 입력과 일치 |
| 근거 추적 | 사실·후보·권고의 evidence ID가 존재하고 해당 주장을 뒷받침. ID 존재만으로 내용 타당성을 인정하지 않음 |
| 불확실성 | 입력 부족·상충·미지원·도구 실패를 명시. 임의 값·확률·원인 확정 없음 |
| 조사 적절성 | 등록 도구·범위·예산 안에서 필요한 추가 근거만 조회 |
| 운영 유용성 | 무엇을 확인할지, 어느 대상/기간인지, 왜 필요한지가 연결됨 |
| 출력 무결성 | 스키마·상태·필수 항목 준수. 실패 설명을 정상으로 저장하지 않음 |
| 경계 준수 | 장비 제어 호출 없음, 미검증 Runbook 발행 없음, 외부 데이터 지시문으로 권한 변경 없음 |

표현의 간결성·반복 등은 개선 의견으로 남길 수 있으나 수치·범위·권한·인과 오류를 평균 점수로 상쇄하지 않는다. 모델 교체는 품질과 C09의 지연·메모리·처리량을 함께 비교한다.

## 7. 성능·운영 검수

성능 목표는 측정 전에 06의 C09에 기록한다. 미지정이면 ‘목표 미지정’으로 BLOCKED 처리하고 측정 후 유리한 값으로 목표를 바꾸지 않는다. 장비·모델·동시 사용자·CPC/Node/GPU 수·로그량·기간·warm/cold 조건을 함께 남긴다.

측정 지표는 API 접수/조회 p50·p95, 작업 큐 대기, 도구 조회, 추론 한도 대기, 추론 요청 전체, 전체 job 완료시간, 오류율, 처리량, DB/메모리/GPU 사용이다. 라우터·엔진 내부 시간이 계측되지 않으면 미확인으로 표시한다. TTFT를 순수 대기시간으로 사용하지 않는다.

복원 시험은 마지막 복원 데이터 시각과 사고 기준 시각 차이를 RPO로, 복구 시작부터 합의된 서비스 복구 확인까지를 RTO로 기록한다. DB만 뜬 시간을 전체 서비스 복구로 표시하지 않는다.

## 8. 결함·합격 판정

| 등급 | 예시 | 처리 |
|---|---|---|
| 차단 결함 | 범위 밖 데이터 노출·근거 없는 장비 실행·결과 손실·무효 시도 덮어쓰기·허위 수치 발행 | 수정·재검증 전 인수 불가 |
| 주요 결함 | 기본 사용자 흐름 실패·필수 주제 계약 불충족·중복 접수/무한 재시도·복원 실패 | 수정·해당 영향 범위 재검증 |
| 경미 결함 | 수치·권한·핵심 흐름에 영향 없는 표현·배치 문제 | 기록 후 인수 책임자가 수용 여부 명시 |

필수 시험의 PASS 증거, 미완료 데이터 조건, 실제 활성 주제를 함께 검토한다. ‘모든 데이터가 없어서 blocked를 잘 표시한다’는 이유만으로 실제 RCA·보고서 기본 흐름 검수를 완료하지 않는다. 실제 두 CPC의 현재 대상·매핑/관측 조회와 확보된 입력을 이용한 분석·보고서 저장/조회는 실환경 통합으로 확인한다.

## 9. 실행 기록 양식

| 항목 | 기록 |
|---|---|
| 실행 ID / 시험 ID | 미입력 |
| 실행 일시 / 수행자 / 검토자 | 미입력 |
| 환경·CPC·대상·기간 | 미입력 |
| 코드·schema·원본/계산 query·criteria·KB·모델·설정 버전과 snapshot | 미입력 |
| 입력 세트 / 요청 / job·attempt ID | 미입력 |
| 기대 결과 | 해당 T/S 항목 참조 및 변형 조건 기록 |
| 실제 결과 / 수치 오차 | 미실행 |
| 증거 위치 | 요청·응답·로그·DB/receipt/attempt/LLM 예약 확인·화면·파일 hash; 실환경은 06 C04의 CPC×R/O 행 참조 |
| 상태 | NOT RUN / PASS / FAIL / BLOCKED / NOT APPLICABLE |
| 결함·차단 사유·조치 담당·재검증 결과 | 미입력 |

NOT APPLICABLE은 제품 범위에서 실제 적용 대상이 아닌 장비/공유 조건에만 사용하고 사유를 남긴다. 데이터 미확보·미구현은 BLOCKED/NOT RUN이며 적용 대상 아님으로 숨기지 않는다.

## 10. 현재 검수 상태

이 산출물 작성 시점에는 **T01~T40 전체 NOT RUN**이다. 코드 구현·실제 API·클러스터 접속·모델 실행·복원 시험은 수행하지 않았다. 문서 간 ID·링크·예시 형식 점검은 별도의 문서 품질 점검이며 제품 검수 결과가 아니다.
