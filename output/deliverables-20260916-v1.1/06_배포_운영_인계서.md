# 06. DSX 배포·운영 인계서

문서 ID: DSX-OPS-001 · 버전: 1.1 · 기준일: 2026-09-16 · 상태: 개발·배포·인계 기준 / 실제 인계 미실행

대응 요구사항: F07·F08·F10~F14, N02~N05. 기존 Kubernetes 기반 CPC/CSC와 합의된 Backend 구조를 기준으로 작성했다. 실제 앱 이미지·배포 manifest·DB migration이 아직 제시되지 않았으므로 실행 명령·설치 경로·비밀값을 가상으로 채우지 않는다. 구현 시 이 문서의 설정표에 실제 파일/명령과 실행 결과를 연결한다.

## 1. 운영 구성과 책임

| 구성 | 운영 책임 | 정상 확인 | 장애 시 영향 |
|---|---|---|---|
| Web Client·사용자 Gateway | 서비스 운영 | 접속·인증·API 라우팅 | 사용자 접근 불가, 기존 job은 별도 상태 확인 |
| Backend API | 서비스 운영 | ready·DB 접속·접수/조회·인증 | 새 요청·Webhook·조회 영향 |

역할은 책임 영역이며 사람 수나 전담 조직 수를 뜻하지 않는다. 실제 담당자·대체 담당·연락 경로는 C12에서 지정한다. 서비스 관리 권한만으로 모든 고객/Namespace 데이터 권한이 생기지 않는다.

### C04-1. 출처와 현재 확인 범위

### C04-2. CPC별 업무 검증·활성화 원장

NR=NOT RUN, B=BLOCKED(사유 필수), P=PASS(실행 증거 필수), F=FAIL. 아래 세 결과 칸은 모두 신규 검수 상태이며 초기 NR이다. 입력 미확보가 실행 단계에서 확인되면 해당 실환경 산출을 B로 바꾸고 담당·해소 조건을 남긴다. 기존 자료의 한계만 보고 시험을 실행한 것처럼 B/P로 기록하지 않는다.

`기본 필수`는 두 CPC 각각 실제 허용 대상의 현재 관측/매핑과 해당 입력을 사용한 RCA·보고서 저장/재조회 인수 항목이다. `활성 시 필수`는 해당 수치·판단을 실제 사용 가능으로 인계하기 전에 정상 산출 증거가 필요하다는 뜻이다. 기능 구현·고정 사례·부족 처리 검수는 두 구분 모두 수행한다. 활성하지 못한 주장은 범위와 원인을 최종 인수표에 명시하며, P1 업무도 삭제하지 않는다.

## 5. 시작·종료·업데이트

### 정상 시작

DB/업무 파일 영역과 필수 연결 → 검증된 schema/코드·설정 → API → Worker → Client 연결 → 스모크 시험 → 자동 일정·Webhook 실행 순서로 확인한다. Mimir/Loki/LLM의 일부 장애는 해당 분석의 degraded 상태로 표시하고 API 생존과 구분한다.

### 정상 종료·점검

새 전문 작업/정기 발생을 점검 상태로 제한하고 수신 경로의 재전송·보존 방식을 확인한다. Worker 신규 점유를 중지한 뒤 진행 작업은 deadline 내 완료 또는 명시 취소한다. lease·원격 LLM 상태·미완료 job을 기록하고 Worker/API를 종료한다. DB 종료 전에 진행 트랜잭션·백업 상태를 확인한다. 단순 프로세스 종료를 작업 취소로 처리하지 않는다.

### 업데이트

1. 실행 이미지·schema·query·지식·모델 호환표와 변경 영향을 기록한다.
2. DB/업무 파일·현재 설정을 백업하고 복원 가능한지 확인한다.
3. 이전·새 코드가 함께 실행될 때 호환되는 migration을 먼저 적용한다. 불가능하면 명시 점검 창에서 Worker 점유·접수를 제한한다.
4. 새 API/Worker를 적용하고 이전 attempt의 늦은 결과 차단·공유 한도 유지·기존 결과 조회를 시험한다.
5. 새 입력은 새 revision을 사용하되 진행 중 job·대화 응답의 모델/설정/계산 snapshot은 유지한다. 기본·Agent 지정 모델을 비활성화할 때 참조를 검사하고 대체 지정 또는 사용 중 거절을 적용한다. 사용 불가능한 고정 revision은 실패/새 실행으로 명시하고 몰래 교체하지 않는다.
6. 스모크·영향 시험 PASS 후 자동 실행을 재개한다.

### 롤백

앱만 되돌려도 되는 schema 호환이면 검증된 이전 이미지·설정으로 복귀한다. 비호환 migration이면 앱만 롤백하지 않는다. 접수를 제한하고 호환 전진 수정 또는 검증된 백업 복원을 선택한다. 복원 시점 이후 새로 저장한 결과의 보존/재처리 방법을 기록한다. 발행 지식은 과거 내용을 수정하는 대신 신규 선택 기준을 이전 호환 revision으로 돌리고 변경 이력을 남긴다.

로그에 request_id/job_id/attempt_no/stage/cluster_id/profile revision을 연결한다. 일반 사용자에게 내부 스택·Secret·타 Namespace 원문을 노출하지 않는다. 정상 상세 로그를 줄여도 경로별 신선도·작은 상태 신호·오류 원문 근거는 유지한다.

기간 할당 이력은 조회·계산 모듈이 요청 시 보존된 Mimir의 실제 원본 timestamp와 관계/활동·성공/완전성 증거에서 재구성하고 기존 관측/할당 테이블에 실행 snapshot을 저장한다. UI 접속 여부에 의존하지 않으며 별도 주기 수집 서비스를 추가하지 않는다. C03/C05의 원본 보존·성공/완전성·계산 해상도 조건이 부족하면 영향받는 기간 수치만 보류한다. 차트 표시 step 변경은 저장된 계산 query/criteria revision·값을 바꾸지 않는다.

진행 사건의 추가 알림 없는 상태 확인은 운영자가 S07에서 R09 또는 R01 재확인을 명시 요청하여 원래 incident_id를 참조하는 새 job으로 수행한다. 원본 조회 성공·최신성·검사 유효성 결과를 남기며, 별도 자동 모니터를 운영 전제로 추가하지 않는다.

## 7. 장애 대응 Runbook

### OP01. 관측 값·매핑이 사라짐

1. 대상 CPC·Node·GPU·기간·source를 고정하고 `empty/unavailable/parse_error`를 구분한다.
2. 원본 timestamp·up·허용 필드·Alloy 필터·tenant/cluster 라벨·Gateway·저장소 도착 순서로 확인한다.
3. 매핑이면 Exporter 작업 라벨과 같은 시점 KSM uid를 비교한다. util=0 관계를 필터로 제거했는지 확인한다.
4. 현재 조회와 기간 재구성을 구분한다. 원본 timestamp·query revision·원본 보존 만료·lookback/다운샘플 영향, collection_observations의 성공/완전성을 확인하고 영향 주제만 partial/blocked로 표시한다.
5. 기존 성공 설정을 기준으로 수정 후 동일 대상·원본 시각·공백을 검증한다. 빈 매핑을 미할당·작업 종료로 기록하지 않는다.

### OP02. 작업이 계속 대기하거나 진행 중으로 남음

1. job status·stage·available_at·deadline·lease·현재 attempt·취소 요청을 확인한다.
2. Worker heartbeat와 DB 연결, 유형별 점유·공유 LLM 슬롯·unknown 호출을 확인한다.
3. 유효 lease 동안 다른 Worker로 강제 중복 실행하지 않는다. 만료 작업은 공통 회수 절차로 retry_wait/failed/expired를 판정한다.
4. 이전 Worker의 늦은 완료가 차단되는지 확인하고 원격 추론 상태 불명은 OP03으로 처리한다.
5. GET /jobs와 상세에서 회수·재시도·최종 결과를 같은 job ID로 추적하고 각 attempt의 시작/회수/종료 감사 기록을 확인한다. 재분석은 parent를 가진 새 job으로 구분한다.
6. 수동 retry 응답 유실이면 같은 키·정규화 payload로 재조회한다. 서버는 현재 권한 확인 후 저장 receipt를 ETag보다 먼저 확인하여 이전 응답을 재현한다. job이 다시 failed여도 같은 의도를 두 번 적용하지 않는다. 다른 payload는409, 새 키의 변경은 현재 ETag·마감·누적 예산을 검사한다.

### OP03. LLM timeout·과부하·원격 종료 불명

1. job 또는 message·attempt·stage·LLM request ID, 공유 슬롯, 제출 전 예약 토큰·실제 사용량·누적 예산·시각을 기록한다.
2. Dynamo/엔진의 실제 상태 확인·취소 지원 범위 안에서 원격 종료를 확인한다.
3. 확인할 수 없으면 unknown 상태·슬롯 격리·보수적인 토큰 예약을 유지한다. 원격 종료로 슬롯을 해제할 수 있어도 사용량 미확정 예약을0으로 되돌리지 않는다. C07의 검증된 원격 수명·사용량 대조/예약 정산 절차를 따르고 조정 근거를 감사 기록에 남긴다.
4. 같은 호출을 무제한 다시 제출하지 않는다. 일반 대화·RCA·보고서 전체의 공유 한도를 확인한다.
5. 확보한 계산/근거를 보존하고 narrative_status=failed/omitted와 서버 산출 요약을 표시한다. final 구조화 결과를 이미 발행했다면 새 설명 재생성은 새 연결 job으로 남긴다. 일반 대화 패널의 기다림 중단은 이미 접수한 전문 job 취소가 아니다.

### OP04. 알림 또는 정기 보고서 중복

1. 생산자 재전송 키, source event key, Incident episode/evidence_version, 요청/수동 retry receipt, 일정 occurrence 키·revision 효력시각을 확인한다.
2. 이미 커밋된 job·final 여부를 조회한다. 중복을 막기 위해 정상 결과를 삭제하지 않는다.
3. 동일 episode의 정정·추가 근거는 같은 사건 재개와 새 분석으로, 새 episode 재발은 새 사건·recurrence_of로 구분한다. 경계 불명은 unknown과 원문으로 남기고 오류별 C08 정책을 확인한다.
4. 일정은 예정 시각에 유효한 revision으로 처리하고 accepted 발생의 조건을 유지한다. 이전 누락은 당시 revision·catch-up 한도로 처리하며, 동일 schedule·정확한 UTC 보고기간의 이미 accepted된 발생은 새 revision에서도 중복 생성하지 않고 missed/already_accepted_period로 남긴다. 의도적 재생성은 parent를 가진 새 job이다.
5. 영향 기간과 잘못 추가된 실행을 연결 기록한 뒤 동일 중복 시험을 재수행한다.

### OP05. PostgreSQL·업무 파일 장애

1. 접수 성공을 반환할 수 있는지 확인한다. 영속 저장 불가면 새 접수를 503으로 거절한다.
2. 진행 Worker의 결과·lease·원격 호출을 보존하고 중복 재시도를 제한한다.
3. DB 용량·연결·권한·migration·파일 접근·checksum 상태를 확인한다.
4. 복구가 필요하면 8절의 격리 복원 절차를 따른다. DB만 복원하고 참조 파일을 검증하지 않은 상태로 운영 재개하지 않는다.

### OP06. 보고 수치·RCA 판단 오류

1. 문제 결과·job·규칙/지식/모델 버전·원본 기간·입력 스냅샷을 보존한다.
2. 03의 식별/소스/단위/시간/공백과 04의 typed metric 참조·산식·근거 의미·인과 조건을 대조한다. 저활동 후보는 criteria v1.1의 같은 전용 episode에 정렬된 온전한60분 창이며, 서로 다른 Pod나 짧은 꼬리를 합치지 않는다. 원본 급증을 잃는 차트용 downsample을 계산에 사용했는지 확인한다.
3. 영향 query/지식/모델 revision의 신규 적용을 제한하고, 올바른 독립 기능은 유지한다.
4. 수정·회귀 시험 후 새 job으로 재분석하고 기존 결과와 연결한다. 잘못된 과거 결과를 조용히 덮어쓰지 않는다.
5. 영향 대상·기간·사용자 확인 필요 사항은 인계된 연락 절차로 담당자가 처리한다.

### OP07. 범위 밖 접근·지식/설정 오변경

1. 해당 계정/설정/발행 revision의 신규 사용을 제한하고 감사 기록·근거를 보존한다.
2. API 조회뿐 아니라 job 실행·결과·파일·대화·evidence 재조회까지 영향 범위를 확인한다.
3. Secret 노출이면 해당 관리 경로로 교체하고 기존 참조를 폐기한다. 비밀 원문을 진단 파일에 다시 넣지 않는다.
4. 호환 설정·권한을 복구하고 T01/T02/T29/T32를 재수행한다.

## 8. 백업·복원 절차

백업은 PostgreSQL의 업무·권한/프로필 참조·지식, 업무 Object Storage 파일, 등록 코드/설정 revision, 필요한 모델 artifact 참조를 포함한다. Secret은 별도 접근 통제된 복구 경로로 관리한다. Mimir/Loki는 자체 보관·복구 정책을 따르며 업무 DB 백업으로 원본 관측이 복구된다고 간주하지 않는다.

1. C05/C10의 보존·RPO/RTO와 백업 방법·실제 명령을 지정한다. 운영 이전에 격리 복원 시험을 수행한다.
2. 백업 시점·DB schema·앱 이미지·파일 목록/checksum·진행 job·지식 revision을 기록한다.
3. 격리 환경에 DB와 업무 파일을 복원하고 외부 Webhook·정기 실행·Worker 자동 처리는 일단 중지한다.
4. FK·결과/근거/파일 참조·checksum·발행 지식·계정 범위와 CPC/Namespace 쌍, 요청/retry receipt·attempt 이력·LLM 예약/정산, 일정 revision/occurrence·모델/설정/계산 snapshot을 확인한다.
5. 복원된 running job의 과거 lease/Worker를 무효화한다. 복원 전 원격 추론이 남아 있는지 확인·정리하고 현재 세대에서만 점유를 재개한다.
6. 이미 외부에 결과가 반환됐지만 백업 시점 밖인 작업을 요청/감사 기록과 대조한다. 재접수/재분석 여부를 명시하며 중복 성공을 조용히 발행하지 않는다.
7. 사용자 조회·RCA/보고서 신규 실행·기존 결과 조회·범위·정기 중복 시험을 수행한다.
8. 실제 데이터 손실 구간·RPO·전체 서비스 복원시간/RTO를 기록하고 기준 충족 후 운영 재개한다.

## 9. 사용자 인계 시연

인계받는 담당자가 직접 다음을 수행하고 화면·job ID를 남긴다.

1. 허용 CPC와 대상·기간을 선택하고 원본 최신성·매핑·정보 부족을 읽는다.
2. Incident 상세에서 당시/현재 Pod, RCA 근거·원인 후보·다음 점검을 확인하고 상태 변경·종결 사유·변경 이력을 남긴다. 분석 완료를 사건 종결과 구분한다.
3. S03 Pod 행에서 S06으로 이동해 GPU UUID·Node 미확정 Pod도 CPC·Namespace·UID·시각으로 조사 접수한다. 브라우저를 닫은 후 서버 작업 목록에서 진행·실패·취소 요청·retry·결과를 복원한다.
4. 보고서 카드의 세부 O01~O11 주제·허용 범위·group_by·비교 기간을 선택한다. O07 자원/미배치 기간, O10 실제 조치 연결을 입력하고 부분 산출·AI 설명 실패·근거·HTML/CSV를 확인한다.
5. 일·주·월 일정을 만들고 시간대·다음 발생·일시중지·발생별 보고서·missed/blocked 사유를 확인한다. 일정 변경 전후 및 중단 복구 이력을 대조한다.
6. 권고와 실제 조치 기록의 차이를 확인하고 조치 후 분석을 연결한다.
7. 지식 담당자는 S12에서 초안 작성→검토 요청→승인/수정 요청→발행→폐기를 수행한다. 수정 후 draft·재검토, 폐기본 신규 선택 제외와 이전 결과 인용을 확인한다. 조사 procedure는 등록 코드 revision의 읽기 항목으로 확인한다.
8. 운영 담당자는 서비스 장애와 장비 장애를 구분하고 OP01~OP07의 진단 경로·연락 담당을 확인한다.
9. 서비스 관리자는 모델/라우팅을 저장·조회하고 서버 허용 목적지 연결 검사와 스키마·분석 품질 평가 결과를 구분한다. 진행/과거 실행의 모델·설정 snapshot이 유지되는지 확인한다.
10. Assistant의 같은 메시지 재전송으로 전문 job이 하나만 생기는지, 패널/전체 화면의 대화가 같은지 확인한다. 재로그인·권한 변경 시 캐시가 삭제되고 새 질문에만 새 맥락이 적용되는지 시험한다.
