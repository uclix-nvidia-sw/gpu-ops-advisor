## 1. 전체 의견

v2.0은 이전 버전보다 명확하다. 장비 이력, 불변 발행본, 이벤트 계약, 미등록 값 처리, 공급자 권고와 내부 권고 분리, 분석 근거 보존은 채택할 만하다. 현재는 이 방향을 유지하면서 **전체 요청이 어디서 들어오고, 어떤 증거로 판단하고, 어떤 결과로 끝나는지**를 완성해야 한다.

구현을 작게 시작하는 것과 설계 범위를 나중으로 미루는 것은 다르다. 개발 전 설계를 확정하려는 단계이므로, 운영 최적화와 원인 불명 조사를 후속 수요로 남기면 안 된다. 두 기능은 이미 DSX의 요구사항이다.

설계 완료의 의미도 구분한다. 실환경 검증까지 문서로 대신할 수는 없다. 지금 확정할 것은 기능 책임, 데이터 계약, 실패·부분 성공 처리, 지식 변경의 영향과 합격 시나리오다. 실환경에서 확인할 메트릭명·배포 버전 등은 값을 추측하지 않고 확인 항목과 미확인 시 동작을 정한다.

## 2. 채택할 내용과 이전 제안의 조정

| v2.0 내용 | 의견 |
|---|---|
| 원본 이벤트의 component·event_name·배포 출처 보존 | 채택. 원본 계약을 추측으로 대체하지 않는다. |
| 배포 소스와 이벤트 매핑 검증 | 채택. 알려진 값의 정확한 해석에 필요하다. |
| 관측 snapshot과 수집 완전성 | 채택. 관측 사이의 실제 장비 존재 기간을 과도하게 확정하지 않는다. |
| 발행 revision 수정·삭제 제한 | 채택. 과거 판단의 근거를 유지한다. |
| 공급자 원본과 DSX 권고 분리 | 채택. 원문·출처·불일치를 보존한다. |
| 후보 조회와 최종 권고 가능 여부 분리 | 채택. 최종 검사 입력·판정 책임까지 구체화한다. |
| SDK와 모델 독립적인 도구 계약 | 채택. 공통 Local LLM 구조와 맞는다. |
| 별도 벡터 DB·범용 온톨로지 미도입 | 채택. 현재 구조를 설명하는 데 필요하지 않다. |
| YAML DSL 대신 등록 함수와 procedure_id 사용 | 동의. 이전 제안의 YAML은 필수 조건이 아니었다. |
| 구조화 지식의 기준 원본을 PostgreSQL로 통일 | 가능. 정책·절차·참고 자료의 의미와 변경 계약까지 정의하면 된다. |

이전 제안에서 말한 다섯 가지 지식은 **다섯 서비스나 Git·DB 양쪽의 중복 원본을 요구하는 것이 아니다.** Runbook, 조사 절차, 운영 정책, 데이터 의미, 참고 근거의 역할을 구분하자는 뜻이다. 동일 DB나 기존 함수에 통합해도 이 역할과 책임은 필요하다.

따라서 v2.0 §3.5의 “지식 5종·Git 이중 원본 보류”는 다음처럼 수정하는 것이 정확하다.

> 지식의 역할 구분은 설계에 포함한다. 물리적 저장과 관리 방식은 단순하게 구성한다. 동일 지식의 기준 원본은 하나로 정한다. 별도 YAML 실행 엔진과 지식별 서비스는 만들지 않는다.

## 3. 쟁점 A — 전체 요청과 분석 결과 모델

### 현재 문서

§4.6의 `analysis_run`은 `event_id NOT NULL`이고, Agent 계약도 원본 사건을 중심으로 구성되어 있다. §9.3에서는 정책·문서·사례를 후속 수요로 둔다.

### 실제 필요한 요청

1. Grafana 알림 또는 Incident에 대한 RCA.
2. 운영자의 특정 노드·시점·증상 조사 요청.
3. 매주 Namespace·Workload의 운영 패턴 분석.
4. 기존 분석에 대한 추가 조사 또는 다른 버전으로 재분석.

정기 보고서에는 단일 Fleet 이벤트가 없을 수 있다. 사용자 조사도 기존 이벤트 ID를 모르는 상태에서 시작할 수 있다. 현재 RCA 테이블을 유지할 수는 있지만, 그 경우 운영 분석과 사용자 조사 결과를 어디에 저장하고 어떻게 연결할지 별도 계약이 필요하다.

### 권고하는 계약

```text
AnalysisRequest
  purpose: rca / optimization
  trigger: incident / user / schedule
  target: cluster, node, device, namespace, workload 등의 명시적 범위
  time_range: 조사 또는 집계 기간
  incident_refs: 선택
  event_refs: 선택, 여러 개 가능
  parent_analysis_ref: 선택

AnalysisRun
  request_ref
  실행 상태와 종료 이유
  입력·사용 지식 버전·증거
  확인된 사실·원인 후보 또는 운영 발견 사항
  권고·부족한 정보
```

물리 테이블을 하나로 통합할지는 별도 선택이다. 중요한 점은 **이벤트 없는 분석을 가짜 사건으로 만들어 저장하지 않는 것**이다.

설계 검토 사례: “지난 7일간 특정 Namespace의 GPU 할당과 저활동을 분석한다.” 이 요청의 생성부터 저장·조회까지 모든 담당과 필드가 설명돼야 한다.

## 4. 쟁점 B — 배포 계약과 Runbook의 결합

### 현재 문서

Runbook 한 revision에 `agent_contract_id` 하나를 연결한다. `current_runbook`은 runbook_id별 최신 발행 이력을 먼저 선택하고, 후보 조회에서 contract_id를 필터링한다.

### 구조상 발생하는 사례

```text
CPC-1: Fleet 계약 A 사용
CPC-2: Fleet 계약 B 사용

RB-XID-79 revision 1 → 계약 A
RB-XID-79 revision 2 → 계약 B

current_runbook → revision 2만 선택
계약 A로 조회 → revision 1은 이미 후보에서 빠져 있음
```

오류 의미가 같아도 새 배포 대응 Runbook을 발행한 뒤 이전 CPC의 조회가 끊길 수 있다. 계약별로 다른 runbook_id를 만드는 우회는 가능하지만, 그 경우 동일 내용의 중복 발행과 변경 동기화를 설계해야 한다.

### 권고하는 계약

배포 증거와 의미 계약을 구분한다.

```text
배포 image digest·소스·파서 정보
  → 검증된 생산자 계약
  → 원본 component·event_name·하위 코드 해석
  → DSX 내부 증상 유형
  → 지원 범위에 맞는 Runbook revision
```

- 같은 의미를 유지하는 여러 배포본이 동일한 해석 계약을 사용할 수 있다.
- 내부 증상 유형을 둔다면 검증된 매핑을 거친다. 원본을 덮어쓰지 않는다.
- 내부의 `gpu.xid` 같은 이름 자체는 오류가 아니다. 공급자가 보낸 원본 component라고 가장하는 것이 문제다.
- 정규화 유형을 두지 않더라도 Runbook과 지원 계약의 연결을 다대다로 표현할 수 있다.
- 어떤 방식을 택하든 최신본 선택은 **지원 계약·적용 범위·폐기 정책을 포함한 범위**에서 정의해야 한다.
- 호환성 미확인 배포는 임의로 기존 계약과 같다고 간주하지 않는다. 원본 보존과 제한된 조사는 계속 가능해야 한다.

일반적인 오류 의미에 대한 문서 검토와 특정 배포본 매핑의 검증도 구분할 필요가 있다. 배포본 검증이 미완료라는 이유로 모든 일반 지식까지 작성·검토하지 못하게 할 필요는 없다. 실제 권고 적용 시 두 조건을 확인하면 된다.

## 5. 쟁점 C — 원본 이벤트, 알림, Incident의 관계

### 현재 문서

§3.2는 원본 저장부터 시작하고, §4.6은 event_snapshot과 analysis_run을 연결한다. 기존 DSX 아키텍처의 Grafana Webhook·Incident Aggregator와 이 경로의 관계는 충분히 정의되어 있지 않다.

### 구분할 대상

| 대상 | 의미 | 예시 |
|---|---|---|
| 원본 이벤트 | 수집기에서 발생한 관측 사건 | 특정 시각 Xid 로그 |
| 알림 | 규칙이 생성한 통지와 상태 전이 | Grafana firing/resolved |
| Incident | 관련 관측·알림을 묶어 관리하는 운영 사건 | 같은 GPU의 반복 접근 불가 |
| 분석 실행 | 특정 입력·기간·지식 버전으로 수행한 조사 | 최초 RCA, 추가 증거에 의한 재분석 |

하나의 알림이 여러 이벤트를 포함하거나, 같은 원본이 재전송되거나, 상태·메트릭 규칙이 로그 이벤트 없이 발화할 수 있다. 이 관계를 한 event_id로 대신하면 dedup·재발·추가 조사 의미가 섞인다.

### 권고하는 흐름

```text
기존 수집 경로 → Mimir/Loki
Grafana Webhook → Incident Aggregator → Incident 저장
                                      → 실행 조건 판정
                                      → AnalysisRequest
공통 조회 도구 → 필요한 원본·증거 확보 → 해당 분석·Incident에 연결
```

원본을 Incident DB에도 별도로 수집해야 한다면, 그 경로의 담당·범위·원본 키를 명시한다. Grafana 알림에 Fleet 원문 전체가 항상 들어 있다고 가정하지 않는다. 필요한 증거 보존 목적의 복사와 전체 로그 이중 수집은 구분한다.

설계에서 정할 것은 원본 중복 제거 키, 알림 재전송 키, Incident 상관 규칙, 분석 재실행 조건이다. 미등록 node_id가 들어와도 raw payload는 보존하고, 해결되지 않은 식별자는 정규 자산 FK와 별도로 보유해야 한다.

## 6. 쟁점 D — Runbook 미해결 이후의 실행 경로

### 현재 문서

§7.5의 도구는 노드 조회, 장비 식별, Runbook 조회, Runbook 검색 네 가지다. §7.6은 Q와 required_evidence를 대조하도록 지시하지만 Q 조회 도구·절차 호출·종료 계약은 완성되지 않았다. §9.3에서는 절차 확장을 뒤 단계에 둔다.

검색은 현행 Runbook 제목·ID를 반환하고, 권고는 다시 정확 키와 적용 검사를 요구한다. 미등록 이벤트라면 정확 키를 통과하지 못할 수 있으므로, 검색 결과를 얻어도 조사로 나아가지 못하는 경로가 생긴다.

### 필요한 두 경로

```text
알려진 사건
  → 검증된 의미 매핑
  → Runbook 후보
  → 필수 증거 수집
  → 조건 판정
  → 권고

미등록·불충분·상충 사건
  → 원본과 부족한 정보 보존
  → 증상 기반 조사 절차 선택
  → 제한된 Mimir/Loki/이력 조회
  → 후보별 지지·반박 증거 정리
  → 필요하면 추가 조회
  → 설명 가능한 결론 또는 조사 한계와 다음 확인 사항
```

정확 매핑을 우회해 알려진 오류의 조치를 적용하자는 뜻이 아니다. **배포 계약을 확정하지 못해도 일반적인 읽기 조사 절차를 실행할 수 있는 경로**를 별도로 정의하자는 것이다.

### 구현 전 정의할 사항

- 증상에서 procedure_id를 선택하는 주체와 규칙.
- procedure_id의 입력·출력·버전·등록 여부.
- 각 required_evidence의 의미와 이를 생산하는 query_id 또는 함수.
- 수집 안 되는 증거, 빈 결과, 파싱 실패, 부분 결과의 표현.
- 추가 조회를 결정하는 조건, 대상·시간 확대 한도와 종료 이유.
- 운영자에게 넘기는 경우의 증거 묶음과 재개 방식.

등록 함수로 구현해도 충분하다. 함수 몸체를 나중에 작성하더라도 위 계약은 지금 정해야 한다.

## 7. 쟁점 E — 운영 정책과 Grafana 규칙의 책임

### 현재 문서

`event / observation / threshold`를 분리한 것은 유용하다. 다만 이는 입력·발견 방식의 분류다. 정책·조사 절차·참고 근거의 구분을 대체하지 않는다. threshold의 condition과 query revision만으로 운영 최적화 전체를 설명하기는 어렵다.

### 설계에서 필요한 역할

| 역할 | 책임 |
|---|---|
| Grafana 규칙 | 지정된 신호를 감시하고 firing/resolved를 알림 |
| Incident Aggregator | 알림 중복·상태·재발을 관리하고 분석 실행 조건을 판정 |
| 조사·분석 절차 | 추가로 어떤 증거를 수집할지 결정 |
| 운영 정책 | 기간, 임계값, 예외, 범위, 권고 전 조건을 제공 |
| 계산·판정 코드 | 단위·기간·결측을 처리하고 명시적인 조건을 계산 |
| LLM | 확인된 사실과 근거를 설명하고 제한된 조사·권고 선택을 보조 |

실시간 경보와 보고서의 검토 대상 선정은 목적이 달라 기준도 다를 수 있다. 같아야 하는 규칙은 공통 정책 버전을 참조하고, 다른 규칙은 목적과 차이를 명시한다. Agent가 별도 알림 엔진처럼 동일 Incident를 반복 생성하지 않도록 한다.

### 최소 정책 계약

정책을 별도 테이블로 만들지 않더라도 ID·revision, 적용 범위·기간, 값·단위, 예외, 우선순위와 충돌 처리, 개정 이유를 표현해야 한다.

예: 동일한 저활동 관측이라도 예약형 추론 서비스와 배치 학습 작업은 권고가 다르다. 요청량·대기 목적이 없으면 자원 회수를 확정하지 않는다. Namespace·Workload 분석에 필요한 당시 Pod UID·소유 관계·GPU 연결·공유 방식도 정의한다. 수집되지 않은 연결은 임의로 채우지 않는다.

## 8. 쟁점 F — 장비 상태와 데이터 신뢰 수준의 분리

### 현재 문서

6개 장비 상태는 이전의 matched/false보다 의미가 풍부하다. 다만 `matched / absent_now / mismatch / never_seen`은 관측 내용이고, `unknown / stale`은 정보 품질·판정 가능성에 가깝다.

§7.3 함수는 사건 시점과 현재 snapshot 중 하나라도 문제가 있으면 장비 대조 전에 반환한다. 이 때문에 사건 당시 식별은 충분하지만 현재 수집만 실패한 경우에도 과거 판단까지 가려진다. §7.2도 snapshot 전체가 partial이면 profile을 비우고 모든 후보를 unknown으로 바꾼다. GPU 정보가 불완전하다는 이유로 GPU 정보를 요구하지 않는 호스트 조사까지 막힐 수 있다.

### 권고하는 표현

```text
사건 시점 식별
  결과: matched / mismatch / not_observed / undetermined
  근거: 사용한 snapshot·원본 식별 정보
  품질: 필요한 정보의 완전성·시각 적합성

현재 관측
  결과: present / not_observed / undetermined
  근거: 현재 snapshot
  품질: 수집 완전성·최신성

비교 해석
  확인 가능한 변화·아직 확인할 수 없는 변화
```

UI에서 6개 상태로 요약하는 것은 가능하다. 내부 계약에서는 서로 다른 축을 잃지 않는 것이 좋다.

예: “사건 당시 GPU A의 식별은 확인됨. 현재 수집 실패로 현존 여부는 미확인. 과거 사건 분석은 진행하고 현재 조치 가능 여부는 추가 확인.”

정보 부족은 **그 정보가 필요한 판단만** 제한해야 한다. 필드별 신뢰 정보를 처음부터 복잡하게 구현할 필요는 없지만, 어떤 증거가 어떤 판단을 제한하는지는 계약에 있어야 한다.

## 9. 쟁점 G — 실행 중 버전 고정과 재분석

### 현재 문서

Runbook revision을 결과에 저장하는 것은 좋다. 하지만 서로 다른 도구 호출 사이에 current_runbook이나 현재 snapshot이 바뀔 수 있다. procedure_id에는 버전이 없고 정책 버전도 아직 계약이 없다.

### 권고하는 계약

분석 시작 시 다음을 고정하거나, 실행에서 처음 선택한 값을 명시적으로 기록하고 이후 재사용한다.

| 범주 | 고정·보존할 항목 |
|---|---|
| 시간 | 사건 시각, 분석 기준 시각, 조회 대상 기간, 지연 도착 자료 처리 기준 |
| 환경 | 사건·현재 snapshot 참조, 필요한 연결 이력 |
| 지식 | Runbook revision, 정책 revision, 문서 버전 |
| 실행 정의 | procedure 버전 또는 service build, query revision, 파서 버전 |
| 모델 | 모델·프롬프트 버전과 실제 출력 |

별도 지식 번들 서비스를 만들 필요는 없다. analysis_run에 선택한 참조 집합을 보존하는 것으로 시작할 수 있다.

과거 결과 열람과 재분석도 구분한다.

- **기존 결과 열람:** 당시 출력·증거·버전을 그대로 제시한다.
- **현재 지식으로 재분석:** 새 실행을 만들고 이전 결과와 변경 이유를 연결한다.

사건 당시 하드웨어를 사용하는 것과 사건 당시 KB만 사용해야 한다는 것은 다른 문제다. 새 조사에 현재 지식을 적용할 수 있지만 그 선택이 기록돼야 한다. 같은 모델 버전으로 다시 호출해도 출력이 완전히 같다고 보장할 수 없으므로 실제 결과를 보존한다.

## 10. 쟁점 H — 최종 권고 판정과 상충 처리

### 현재 문서

`recommendationReady=false`를 서버에서 통제하는 방향은 적절하다. 그러나 최종 판정이 무엇을 입력받아 어떤 권고를 통과시키는지, 여러 후보가 충돌할 때 어떻게 하는지까지 확정되지 않았다.

### 권고하는 계약

권고 각각에 다음을 연결한다.

```text
권고 내용과 종류: 추가 조회 / 운영자 점검 / 변경 검토
대상·범위
적용한 Runbook·절차·정책 버전
필수 조건별 결과: true / false / unknown
지지 증거·상충 증거
판정: 제시 가능 / 조건부 / 보류 / 적용 불가
판정 이유·부족한 증거
```

추가 증거 조회와 재부팅·교체 검토가 동일한 증거 수준을 요구할 필요는 없다. 분석 전체의 boolean 하나로 모든 권고를 막거나 허용하지 않는다.

일반 Runbook과 코드 전용 Runbook을 함께 반환한다면 둘의 관계도 정한다. 구체 Runbook의 어떤 조항이 우선하고 어떤 일반 점검은 병행 가능한지 명시한다. 단순 정렬 순서를 LLM이 최종 우선순위로 추측하게 두지 않는다. 해소되지 않은 공급자·문서·운영 정책 충돌은 충돌 상태와 추가 검토 대상으로 남긴다.

## 11. 설계 확정 전에 사용할 시나리오

아래는 지금 코드를 실행하라는 요구가 아니다. 설계도를 따라 입력, 선택, 증거, 판정, 결과 저장이 모순 없이 설명되는지 확인할 사례다.

| 사례 | 설명돼야 할 결과 |
|---|---|
| 두 CPC가 Fleet 계약 A/B를 동시에 사용 | 새 지식 발행 후에도 각 계약에 맞는 Runbook을 조회 |
| 알려진 이벤트와 충분한 증거 | 출처·조건을 확인한 권고와 결과 보존 |
| 등록되지 않은 이벤트 | 원본 보존, 허용된 증상 조사, 지식 매핑 미확인 표시 |
| 이벤트 없는 사용자 조사 | 대상·기간 기반 분석 생성·저장 |
| 정기 Namespace 보고서 | event_id 없이 실행하고 집계 근거·정책·결과를 저장 |
| Grafana 동일 알림 재전송 | 원본 보존 정책을 지키면서 중복 Incident·불필요한 재분석 방지 |
| 하나의 Incident에 여러 이벤트 | 인과관계를 단정하지 않고 관련 증거와 각 출처 연결 |
| 사건 당시 장비 확인, 현재 수집 실패 | 과거 분석 진행과 현재 조치 보류를 구분 |
| GPU 관측 partial, 호스트 증거 충분 | 관련 없는 GPU 누락으로 호스트 조사 전체를 막지 않음 |
| 분석 도중 Runbook 개정 | 해당 실행에서 참조한 버전의 일관성 유지 |
| 최신 Runbook 폐기 | 적용 범위별 폐기 의미대로 동작하고 우연한 구버전 부활 방지 |
| 임계값 일치, 예약 예외 존재 | 해당 정책에 맞는 운영 권고 |
| 서로 다른 Runbook의 조치 충돌 | 해결 규칙 또는 보류·추가 확인을 명시 |
| 원천 보존 기간 경과 | 보존한 핵심 증거와 당시 출력으로 판단 설명 |
| 결과 저장 실패·실행 중단 | 완료로 표시하지 않고 재시도·중복 저장 방지 계약 적용 |

## 12. 다음 문서의 권장 구성

v2.0의 SQL·TypeScript를 더 늘리기 전에 다음 본문을 확정하는 것이 좋다. 구현 예제는 참고 부록으로 유지한다.

1. 두 Agent의 입력·출력·범위.
2. Client/CPC/CSC의 호출·저장 책임과 데이터 흐름.
3. 원본 이벤트·알림·Incident·AnalysisRequest·AnalysisRun의 관계.
4. 생산자 계약과 내부 의미 매핑, Runbook의 지원 범위.
5. Runbook·절차·정책·데이터 의미·참고 근거의 기준 원본과 변경 방식.
6. 알려진 오류·미해결 조사·운영 분석의 정상·부분 성공·실패 흐름.
7. 장비 식별·증거 품질·시간·버전·상충 처리 규칙.
8. 권고 단위의 최종 판정과 결과·검증 사례 보존.
9. 설계 합격 시나리오와 실환경에서 확인할 항목.
10. 위 계약을 반영한 스키마·API·도구 예시.

문서의 “이 문서만 사용한다”는 문장은 합의된 범위에 한해 적용한다. 현재 v2.0을 RCA 조회 상세안으로 사용할 수는 있지만, 운영 최적화와 미해결 조사 계약까지 대체하는 전체 확정본으로 선언하는 것은 보완 후 결정하는 편이 맞다.

## 13. 전달 의견

v2.0의 수정 방향에는 대부분 동의한다. 이전 제안의 YAML이나 저장 위치를 고집할 이유는 없으며 등록 함수와 PostgreSQL 중심 설계로 단순화할 수 있다. 다만 생략할 수 없는 것은 기능의 계약이다.

현재 목표는 개발을 서두르는 것이 아니라, 두 Agent가 알려진 오류·미해결 조사·운영 분석을 어떻게 완결하는지 먼저 확정하는 것이다. 다음 개정에서는 구현 파일과 시드의 양보다 요청 모델, 배포 호환성, 조사 실행 흐름, 정책·버전·권고 판정에 집중하는 것을 제안한다.

본 검토는 v2.0의 첨부 인벤토리·소스 기능·배포 상태를 새로 검증한 결과가 아니다. 운영 수치의 진위는 별도로 확인하며, 여기서는 문서에 기재된 구조의 관계와 동작을 검토했다.
