## 3. 라벨·시간 조인에서 채택할 내용

- GPU 연결 키: `cluster_id + node + uuid`. 이는 동시점 소스 연결 키이며 공통 자산 키 `cluster_id + gpu_uuid` 및 시간별 Node 관계와 충돌하지 않는다.
- Exporter 작업 라벨: `namespace`, `pod`, `container`. Exporter 자신의 정보는 `exporter_*`. 기존 문서의 `exported_*`를 무조건 사용하는 쿼리는 적용하지 않는다.
- UID 조인: 같은 시점 `cluster_id + namespace + pod + node`로 KSM과 연결해 `uid`를 얻는다. 분석 계약에서는 이를 `pod_uid`로 정규화하고 원본 출처를 남긴다.
- KSM 실행 노드를 모든 Pod의 `node`로 덮어쓰지 않았다는 점은 중요한 검증 근거다.
- `collection_path=alloy-direct`와 전환 시각을 사용해 과거·현재 경로의 중복을 구분한다. 과거 기간 전체에 새 경로 필터를 적용해 이전 데이터를 버리지 않는다.
- `node_group=prod-b`, `compute_zone=us-east-1c`는 현재 테스트 분류값이다. 동적인 풀·조직 소유권 원장을 검증한 것으로 확대하지 않는다.
- B의 `cpc-2` 라벨과 dgx01/A100 표본 불일치는 A의 worker/V100 검증과 별도로 원본 시각·환경을 추적한다. 최신 A가 그 과거 오라벨을 자동 복구했다는 근거는 없다.

A의 PromQL은 KSM 정보값 1을 GPU 활용률에 곱해 UID 라벨을 붙이는 현재 조회다. GPU_UTIL=0이어도 관계는 남는다. 매핑 생성 전에 활용률 > 0 필터를 넣지 않는다.

`max by (..., uid)`는 동일 UID의 중복을 묶지만 서로 다른 UID를 하나로 해결하지 않는다. 이름 재사용 시 여러 UID가 같은 평가 시점에 유효하면 조인 실패·모호성이 발생할 수 있다. UID를 제거하거나 임의의 하나를 선택하지 않고 신선도·시점·객체 이력으로 해결한다.

현재 조인 성공은 과거 전체 기간의 신원·할당 경계를 증명하지 않는다. Prometheus lookback으로 서로 다른 원본 시각의 값이 결합될 수 있으므로 evaluation 시각만 아니라 원본 샘플 시각과 공백도 확인해야 한다. 15초 scrape는 Exporter/DCGM의 원본 값 갱신 주기를 자동으로 의미하지 않는다.

## 6. 산식·정의에서 수정할 부분

1. `count(DCGM_FI_DEV_GPU_UTIL)`은 시계열 수다. 여러 Pod/컨테이너/경로의 라벨 조합으로 GPU 수보다 클 수 있으며 사라진 장치는 누락된다. “관측된 고유 물리 GPU”와 “인벤토리 총 GPU”를 분리한다.
2. `FB_USED / FB_FREE`는 사용 대 여유 비율이며 점유율이 아니다. 장비가 정의한 유효 total/reserved를 고려한 분모와 단위를 고정한다.
3. `TOTAL_ENERGY_CONSUMPTION`은 누적 에너지다. 리셋·결측을 처리한 구간 증가량을 사용한다. mJ 단위라면 kWh = 구간 증가 mJ / 3,600,000,000. W 전력은 시간 적분한다. 누적 에너지를 다시 시간 적분하지 않는다.
4. GPU 에너지 × 단가 × PUE는 시설 실측 비용이 아니라 가정 기반 배부 추정치다. GPU 외 CPU·메모리 등 전체 IT 전력을 대변하지 않는다. 단가·PUE 출처와 범위를 기록한다.
5. ENFORCED_POWER_LIMIT는 적용 전력 제한이며 장비 정격 TDP와 동일하지 않을 수 있다. 제한값 근접을 실제 power throttling 발생 시간으로 바로 바꾸지 않는다.
6. Tensor/SM 활동의 비율은 정의·분모 유효성·같은 시점·하드웨어를 검증해야 한다. 모델/정밀도 요구 없이 AMP·batch/MIG 변경을 확정 권고하지 않는다.
7. Active·Effective는 제품에서 채택한 활동 정의이며 업무 성과 지표가 아니다. 필요하면 기존 공통 저활동 규칙과 다른 이름·정의·버전으로 제안한다.
8. Source별 보존 정책은 현재 Mimir의 tenant·저장 구조에 맞춰 재설계해야 한다. recording rule을 만들었다고 원본/집계의 보존 기간이 자동으로 분리되지 않는다.

에너지 단위 근거: [해당 Exporter 버전 dcp CSV](https://raw.githubusercontent.com/NVIDIA/dcgm-exporter/4.4.2-4.7.0/etc/dcp-metrics-included.csv), [DCGM 에너지 field 정의](https://docs.nvidia.com/datacenter/dcgm/3.0/dcgm-api/dcgm-api-field-ids.html). 제품별 지표명은 일반 정의 참고이며 현재 실환경 중앙 수집 근거가 아니다.

## 7. RCA·알림·벤더 제출 패키지

NVIDIA Node Triage의 증거 수집 항목은 RCA 산출물 구조에 참고할 가치가 있다. 다만 모든 항목이 자동 수집됐다고 표시하지 않는다. Fleet의 파싱된 events가 원본 로그 전체 파일을 보존한다는 보장은 없고, Pod 이미지·owner가 실제 프레임워크 버전·실행 인수·재현 조건을 모두 설명하지 않는다.

“자동 수집 가능한 근거 초안 / 운영자 첨부 필요 / 해당 없음 / 미확인”을 구분하는 제출 준비도가 적절하다. Agent의 읽기 조회 이력과 운영자가 실행한 진단·조치도 따로 기록한다. 실제 티켓 전송·능동 진단·리셋은 이번 분석 범위가 아니다.

Xid31을 무조건 하드웨어 문제로 고정하지 않는다. 일부 Node Triage 표에는 하드웨어 벤더 문의 안내가 있지만 현재 Xid Catalog는 같은 GPU/여러 GPU에서의 반복 패턴과 앱 검증 등으로 조사 경로를 나눈다. Xid45도 Node Triage의 정보성 안내와 최신 Catalog의 조건부 workflow가 다르다. 문서 버전·장비·드라이버·동반 오류·작업 상태에 맞는 Runbook 발행 기준이 필요하다.

따라서 B의 Xid45 무조건 알림 제외, 모든 위험군 동일 심각도, Xid48 일률적인 재부팅·drain 권고를 그대로 적용하지 않는다. 원문은 보존하고 검증된 조건으로 사건 묶음·알림 강도를 정한다. 이는 자동 조치를 요구하는 판단이 아니다.

근거: [NVIDIA GPU Node Triage](https://docs.nvidia.com/deploy/gpu-debug-guidelines/gpu-node-triage.html), [NVIDIA Xid Catalog·workflow](https://docs.nvidia.com/deploy/xid-errors/analyzing-xid-catalog.html).

## 8. 다음 문서 개정에 반영할 차이 — 이번에는 적용 보류

- 구조도: CPC-2 KSM/Exporter → Alloy 직접 scrape로 변경. 기존 Prometheus는 별도 소비자 경로. CPC-1 신규 경로 적용은 독립 검증.

- UID: Exporter 직접 옵션 활성화를 선행 조건으로 두지 않고 KSM 동시점 조인을 기준으로 활용. 시간 이력·재생성·누락은 별도 조건.
- 수집 주기: A의 KSM/Exporter scrape 15초를 채택. 원본 갱신 주기와 Fleet 실제 값 갱신/전송 주기는 별도 계약.
- 현재 가능 결과: 테스트된 시점/구간의 GPU↔Pod↔UID와 장치 활용률·VRAM 연결. 장기 저활동·쇼백·부서 귀속·정밀 피해·MTTR은 조건부.
- 최신 미완료: 최종 Alloy 배포 후 Loki 도착, 부하 반응, 이력·짧은 작업·재생성 경계, failover/내구성, CPC-1 신규 경로.
- 범위: Run:ai quota 연동·CSC L40S 자체 분석을 자동 추가하지 않음. 카탈로그 후보로만 유지.
- 상태표: “지금 가능/설정만/이력만” 대신 기능별 필요한 데이터·중앙 확인·기간 품질·원인/귀속 한계를 표시.
- 기존 공통 기준은 여전히 유효. 새로운 사실은 데이터 가용성 표를 갱신하고, 다른 임계값·퍼널·보존안은 별도 설계 변경 후보로 관리.

자료의 명령·배포·알림·주기 제안은 실행 지시로 처리하지 않았다. 이 메모만 저장했고 보고서 작성은 사용자 요청에 따라 나중으로 남겼다.

### 9.2 채택할 개선점

- 증거를 설정 확인 / 기능 근거 / 이력 참고 / 미확인으로 구분하고, 기능 조건을 기본 검증 후 / 필드 확장 / 이력 구현 / 추가 소스로 나눴다. 기존의 “이미 가능”과 “기능 지원” 혼동을 크게 줄였다.
- Fleet·Exporter는 일부 원천만 겹치며 정의·엔티티·시각·단위·전송·누락이 다를 수 있음을 인정한다. API 접근과 hostPID·마운트를 수집 완료로 보지 않는다.
- 15초 scrape와 실제 DCGM 갱신 주기, Fleet export/check 주기를 분리한다. 대표 소스는 검증된 필드 단위로 지정한다.
- GPU 할당시간과 정책 배분시간, 에너지 증가량과 전력 적분, 추정 비용과 실제 비용, 저활동과 낭비를 구분한다.
- Pending과 미배치, allocatable과 잔여 용량, 실제 업무 로그와 KSM 종료 상태를 구분한다.
- Xid45 조건 분기, Xid31 원인 미확정, remap pending/failure 구분, 검사 timeout과 장비 고장 구분을 명시했다.
- 벤더 산출물을 “인시던트 초안 + 증거 완결성 목록”으로 표현한다. 모든 첨부가 자동 확보된 완성 보고서라는 기존 표현을 교정했다.

| collectors 경로 확인, 내용 미제공 | `/etc/dcgm-exporter/dcp-metrics-included.csv`가 제공 설정의 경로라는 새 근거. 이전 default CSV 107개 참고 대조 목록을 실제 collectors 목록으로 적용하지 않음 |
| internalTrafficPolicy Local 미확정 | V에 제공된 grep은 해당 필드를 포함하지 않음. 이전 B의 “확인” 주장에 원본 근거가 없으므로 종결하지 않고 원본 정책/EndpointSlice/노드·UUID 대조 과제로 유지. Cluster로 바뀌었다고 단정하지 않음 |
| UID·owner를 함께 기본 품질 게이트로 요구 | 현재 UID 조인은 확인, owner는 별도. owner 부재로 Pod·Namespace 수준 현재 명세까지 차단하지 않음 |
| Exporter 정규화는 Prometheus 저장 결과에서 확인 | CPC-2 신규 경로의 실제 정규화·저장 검증 위치는 Alloy 처리 후 CSC Mimir. 기존 Prometheus 확인은 독립 모니터링/전환 전 경로에 해당 |

CPC-1·CPC-2 중앙 조회라는 전체 전제와 CPC-2 신규 경로 적용 검증이라는 범위를 계속 분리한다. V에 언급된 Run:ai·CSC 자체 GPU·외부 소스는 추가 기능 후보이지 이번 요청의 자동 범위 확장이 아니다.

### 9.4 60개 카탈로그와 기존 Agent 역할의 대응

새 카탈로그는 A~F 각각 10개다. 이전 P1~P5 64개를 재구성한 별도 ID 체계이며, 개수가 4개 줄었다고 기능 네 개를 제거한 것으로 해석하지 않는다. 기존 DSX O01~O11·R01~R09 ID를 교체하지 않고 기능 주제별로 대응한다.

| V의 ID 범위 | 역할 | 기존 설계와의 연결·추가 조건 |
|---|---|---|
| A01–A10 인벤토리·활용 | 주로 운영보고서, RCA 대상 식별 공통 | O01/O02/O08/O11. 기대 인벤토리·노드 용량·실제 활동·시간 품질을 항목별 확인 |
| B01–B10 작업 성능 | 주로 운영보고서, RCA 증상 조사 근거 | O03/O04/O10, R03/R05. 현재 VRAM/활동과 작업 성과·rank·dtype·컨테이너 CPU·통신/스토리지는 별개 |
| C01–C10 비용·유휴 | 운영보고서 | O02/O03/O08/O09/O10. 정책 배분·단가·조직·quota는 실제 할당/활동과 별도 데이터 |
| D01–D10 스케줄링 | 운영보고서 중심, 장애 신고 시 RCA 참고 | O07/O08. KSM 세 종류만으로 phase/queue/gang/preemption/실패 사유가 모두 확보되지 않음 |
| E01–E10 신뢰성·RCA | RCA 조사, 운영보고서의 사건 추세 참조 | R01~R09, O05/O06. 원문·당시 매핑·업무 영향·인과·조치/복구 시각 분리 |
| F01–F10 보고·운영 품질 | 양 Agent 결과와 공통 도구 | F01/02/04/09/10은 운영보고서, F03/08은 RCA 중심. F05/06/07은 공통 품질·관계·변경 근거를 재사용 |

새로운 채택 가치가 있는 주제는 F06 생산자 간 불일치, F07 버전/구성 변경과 사건의 상관관계, F03 증거 완결성 목록이다. 독립적인 새 Agent가 아니라 기존 공통 조회·RCA·보고서 기능으로 연결한다.

### 9.5 아직 보완할 계산·조건

1. **A08 = A04 − A05 주의:** 할당은 확인됐지만 활동 수집이 누락된 GPU도 차집합에 들어갈 수 있다. 동일 대상·시간·유효 활동이 있는 할당 장치에서만 저활동을 계산하고 활동 미확인은 별도 집합으로 남긴다.
2. **활동 시간창 충돌:** V의 5분 활성·50% 지속 활성 지표는 참고 후보다. 기존 DSX의 60분 저활동 후보 규칙을 자동 대체하지 않는다. 다른 질문에 답하는 지표라면 의미 ID·시간창·품질·버전을 각각 정의한다.
3. **D02 대기 시작:** Pod 생성 시각은 실제 스케줄링 준비 시각이나 Run:ai 큐 진입과 같지 않을 수 있다. 정확한 시작을 모르면 “생성 후 미배치 경과” 또는 “최초 관측 후 대기”로 표시한다. gate·중간 보류·취소를 구분한다.
4. **D03 완료 대기 분위수:** 완료된 대기만의 P50/P95라는 범위를 명시하고, 아직 대기 중인 작업 수·경과시간을 함께 제공한다. 성공적으로 배치된 작업만으로 전체 사용자 대기 경험을 대표하지 않는다.
5. **D05 잔여 요청량:** “활성 배치 요청”을 GPU 활동 중인 Pod나 Running phase로만 제한하지 않는다. 바인딩 완료·준비 중인 Pod도 스케줄러 자원을 점유할 수 있다. 실제 유효 요청과 resource 단위를 적용한다.
6. **PromQL의 0 보충:** `count(...{exported_pod!=""}) or vector(0)`은 해당 쿼리에서 일치하는 시계열이 없다는 뜻만 준다. 전체 수집이 중단돼도 0이 될 수 있으므로 수집 정상·라벨 충돌 해소 증거로 단독 사용하지 않는다. 실제 대상/기간/대표 경로 필터도 필요하다.
7. **B03 FB_TOTAL:** GPU 메모리 점유 공식과 실제 direct 전송 field 목록은 별개다. 현재 direct 경로에서 FB_TOTAL까지 수신한다고 가정하지 않는다. Fleet total과 결합하면 의미·장치·시각·reserved 분모를 검증한다.
8. **공유 배분:** share/MIG 가중치는 정책 배부 근거일 수 있지만 실측 사용 비율·성능 등가를 뜻하지 않는다. 장치 합계와 작업별 배부 단위·범위를 따로 표시한다.
9. **폴링 오차 상한:** 할당 경계 오차를 “최대 관측 간격 정도”라고 할 수 있는 것은 일정한 성공 관측·시간 정합성 조건 아래다. 전송 지연·수집 실패·재시작 구간에서는 더 커질 수 있으므로 불확실 구간을 보존한다.
10. **전체 품질 게이트의 적용:** 삭제 Pod 복원·owner·공유 검증이 모든 기본 현재 조회의 일괄 선행 조건은 아니다. 공통 기준처럼 기능/주장별로 ready/partial/blocked/not_applicable을 반환한다.
11. **초기 제공 범위:** V의 단계 1에는 A03 용량·D01/D02 대기·E01 사건이 포함된다. 현재 A의 direct KSM 3종·GPU 3종 및 제한된 사건 근거만으로 모두 활성화됐다고 표시하지 않는다.
12. **Fleet health/repair 의미:** Fleet 판정은 입력 근거가 아니라 생산자 해석으로 구분한다. Agent가 이 해석을 재사용하더라도 적용 버전·검사 실패·정책 조건을 검사한다. 같은 추정이 두 번 등장했다고 독립 증거 두 건으로 세지 않는다.

### 9.6 다음 작업 시작 시 유지할 요약

> V는 기존 기능 카탈로그의 기술적 과장을 대부분 교정한 60개 설계 후보 자료다. 실제 환경의 최신 변경·수신은 A를 기준으로 한다. CPC-2 Alloy 직접 scrape, GPU_UTIL/FB_USED/FB_FREE 수신, Exporter+KSM UID 조인은 확인된 기록으로 유지한다. 직접 UID 옵션은 off이고 재활성화가 선행 조건은 아니다. 과거 전체 이력·owner·스케줄 실패 사유·업무 성과·단가/조직·최신 Loki·CPC-1 신규 경로·DCGM Local 정책은 항목별 근거를 구분한다. 60개 후보를 구현 완료로 세지 않으며, 공통 기준의 상태·시간·품질·귀속 정의를 바꾸지 않는다. 지금은 보고서를 작성하거나 설정을 실행하지 않는다.

## 10. 2026-09-16 작업 실행과 Dynamo 검토 기록

- 사용자 제안 채택: 업무 한 건을 영속 보존하는 백엔드 큐와 개별 추론 요청의 Dynamo 대기·라우팅을 분리한다. 기존 서비스 DB/작업 처리 수단을 우선 재사용하고 별도 추론 메시지 브로커는 기본으로 추가하지 않는다.
- 공식 Frontend 참조에서 queue threshold 기본 null, 0 이상 설정 시 활성, prefill 용량 비율, 대기 요청에 priority hint 적용을 확인했다. 설치 버전/모드에서의 지원·활성은 미확인이다. [공식 설정](https://docs.nvidia.com/dynamo/reference/components/frontend-configuration)
- 보완: 다중 Worker의 전체 호출·토큰 한도, 사건/작업 접수 누락 방지, Worker 점유·늦은 복귀, 기술 재시도와 새 분석 구분, 업무 전체 deadline, 취소와 실제 GPU 중단의 차이, 최종 결과 멱등 확정.
- 계측: 백엔드 큐, 공유 한도 대기, Dynamo/엔진 대기, 실제 실행을 가능한 범위에서 분리한다. TTFT나 전체 HTTP 시간을 순수 큐 대기로 사용하지 않는다.
- 반영 파일: 공통 판단 기준 8.3절, 운영보고서 8.4절, RCA 6.2~6.3절. 실제 수집 환경 전환 내용을 이번 범위에서 전면 개정하지 않았고 관련 분석 메모로 연결했다.
- 다음 작업 기준: 큐는 새로운 GPU 운영 인사이트를 만드는 기능이 아니라 두 Agent의 접수·복구·과부하 제어를 책임지는 실행 기반이다. 모델 용량/구성 시험 없이 concurrency·timeout·retry 숫자를 운영값으로 확정하지 않는다.
