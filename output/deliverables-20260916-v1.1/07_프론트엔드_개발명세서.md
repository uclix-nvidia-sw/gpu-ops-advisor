# 07. DSX 프론트엔드 개발 명세서

문서 ID: DSX-FE-001 · 버전: 1.1 · 기준일: 2026-09-16 · 상태: 개발 기준

화면 기준: DESIGN 05의 7개 메뉴, S01~S16/S07B. 본 개정은 화면·서버 연결 계약과 누락된 업무 흐름을 보완한다. 기존 정적 웹·캡처가 아래 기능을 구현했다는 의미는 아니다. API는 [02](<02_백엔드_API_작업명세서.md>), 데이터는 [03](<03_데이터_설계서.md>), 판단은 [04](<04_Agent_동작_판단_명세서.md>)를 원본으로 삼는다. 충돌 시 해당 원본과 함께 수정한다.

## 1. 목적·범위·개정 사항

대시보드에서 대상을 선택하고 관측·조사·보고서·근거 확인으로 이어지는 프론트엔드를 개발한다. 공통 Assistant는 일반 설명과 가벼운 조회를 처리하고, 긴 조사는 RCA 또는 보고서 작업으로 접수한다. 전문 Agent는 두 개를 유지한다.

| 항목 | v1.1 개발 기준 |
|---|---|
| 서버 계약 | `/api/v1`의 analyses·reports·jobs 계약 사용. analysis_id/report_id는 해당 job_id와 동일 |
| 산출 상태 | 실행 `job.status`, 요약 `result_status`, 주제 `topics[].status`, 상세 `quality`, 설명 `narrative_status` 분리 |
| 일정·출력 | 일·주·월 정기 보고서는 F07/P0. HTML 보고서·집계 CSV는 F12/P1. 제품 PDF 생성은 범위에 추가하지 않음 |
| 권한 | CPC별 Namespace와 역할·장비 관측 권한의 조합을 보존. 지식 관리자·서비스 관리자 구분 |
| RCA | Pod에서 GPU 미확정 상태로 접수, 사건 운영 상태 변경·종결 사유·이력 제공 |
| 지식·모델 | 지식 초안→검토→발행→폐기, 모델 서버 저장·연결 검사·비활성화·라우팅 제공 |
| Assistant | 짧은 제한시간의 동기 처리로 시작. 메시지 ID 재조회로 복구하며 스트리밍은 이번 계약에서 제외 |
| 범위 유지 | R01~R09/O01~O11 전체 연결. P1은 구현 순서이며 이번 범위에서 삭제한다는 뜻이 아님 |

자동 GPU reset/drain/reboot/자원 회수, 외부 상용 모델 연결, 전체 관측망 재구성은 제외한다. 실제 장비 조치는 운영자가 수행하며 화면은 권고와 수행 기록을 구분한다.

좌측 7개 메뉴, 상단 범위·기간·Assistant 버튼, 본문, 필요 시 우측 Assistant/근거 패널의 배치를 유지한다. 전역 범위는 새 조회에 적용한다. 저장 결과·기존 메시지의 범위와 기간을 덮어쓰지 않는다. 결과 상단은 대상·기간·기준 시각·산출 상태를 먼저 보여주고 조회·정책·모델·지식 버전은 펼침 상세에 둔다.

URL에는 허용된 조회조건·리소스 ID만 저장한다. 원문 로그·비밀값·긴 질문은 넣지 않는다. 비인가 리소스는 “없거나 접근할 수 없는 항목”으로 표시한다. 일시 UI 상태는 패널·초안·펼침 정도로 유지하고 서버 작업 이력을 브라우저 메모리로 대체하지 않는다.

## 3. 인증·범위·캐시

`GET /me`는 principal, grants, capabilities, access_revision을 반환한다. grants의 각 행은 role, cluster_id, namespace, asset_observation이 묶인 권한 단위다. 행의 namespace=null은 그 CPC 전체에 대한 해당 권한이다. 역할 배열과 대상 배열을 각각 합친 뒤 교차 조합해 권한을 만들지 않는다. 요청 scope의 namespaces 배열과 권한 행의 단일 namespace 필드를 구분한다.

| 역할 | 허용 업무 | 범위 제한 |
|---|---|---|
| 조회자 | 허용 관측·발행 지식·결과·근거 열람, 일반 Assistant | Assistant에서도 새 전문 job을 생성하지 못함 |
| 운영자 | 허용 범위 RCA·보고서·일정 접수, 사건 상태·검토·실제 조치 기록 | 장비 관측 grant 없는 Namespace 제한 사용자는 Node 전체 로그·타 작업을 읽지 못함 |
| 지식 관리자 | 허용 지식 범위의 초안·검토·발행·폐기 | 발행 지식의 범위 제한·호환 조건 유지. 서비스 설정 권한은 별도 |
| 서비스 관리자 | 연결·모델·라우팅·상태 설정 | 모든 CPC/Namespace 관측 권한을 자동으로 부여하지 않음 |
| 시스템 계정 | 수신·스케줄 등 서버 처리 | 사용자 화면 로그인 역할과 구분 |

새 scope는 다음과 같다. `namespaces:null`은 해당 CPC 전체를 뜻하므로 전체 범위 grant가 필요하다. 명시한 권한 밖 범위는 403이며 서버가 조용히 줄이지 않는다. 과거의 평면 `cluster_ids`/`namespaces` 입력은 422로 거절한다.

```json
{
  "scope": {
    "clusters": [
      {"cluster_id": "cpc-1", "namespaces": ["dev"]},
      {"cluster_id": "cpc-2", "namespaces": ["prod"]}
    ]
  }
}
```

범위 선택기는 CPC별로 Namespace를 고른다. “접근 가능한 전체 범위” 선택 시 실제 CPC/Namespace 칩을 함께 표시한다. 동일 Namespace 이름을 가진 다른 CPC를 혼동하지 않는다. 목록 GET의 scope 필터도 이 객체를 JSON 직렬화·URL 인코딩하여 보내며 평면 교차 곱으로 바꾸지 않는다.

캐시 키에는 인증 principal, access_revision, 정규화 scope, 대상 ID, 기간, query/정의 버전을 포함한다. 로그아웃·사용자 교체·grant 철회/변경 시 이전 캐시와 민감한 초안을 무효화하고 화면을 비운다. 세션 재인증 뒤 같은 사용자·허용 범위일 때만 초안을 복원한다. 늦게 도착한 이전 범위 응답은 현재 화면에 쓰지 않는다. 버튼 숨김과 관계없이 서버는 조회·접수·결과·근거·내려받기 때 권한을 재검사한다.

## 4. 공통 데이터·상태 표시

| 필드 | 의미 | UI 규칙 |
|---|---|---|
| `job.status` | queued/running/retry_wait/succeeded/failed/cancelled/expired | 실행 진행 열·작업 배지 |
| `result_status` | 서버의 전체 요약 ready/partial/blocked/not_applicable 또는 null | 목록·결과 상단의 산출 상태. 결과 미확정은 null |
| `topics[].status` | 주제별 ready/partial/blocked/not_applicable | 각 주제의 산출 여부·보류 표시 |
| `quality` | 관측률·부족 입력·사유·제한을 담은 객체 | 문자열 상태로 캐스팅하지 않고 상세 설명으로 표시 |
| `narrative_status` | 설명 생성 상태 | failed/omitted면 계산·근거는 열고 “AI 설명 생성 실패/생략” 표시 |

서버 요약 규칙은 적용 가능한 항목이 모두 ready면 ready, ready/partial이 하나 이상이고 일부 부족하면 partial, 적용 가능한 항목이 모두 blocked면 blocked, 모든 항목이 not_applicable이면 not_applicable이다. 프론트에서 상태를 평균·추정하지 않는다. `succeeded+blocked`와 정상 계산·설명 실패도 유효한 표시 조합이다.

ready는 유효 범위·근거와 함께 값 표시, partial은 실제 산출 범위와 제외 범위 표시, blocked의 미산출 값은 null/“근거 부족”, not_applicable은 “적용 대상 아님”과 사유를 표시한다. blocked를 0·정상·미할당으로 바꾸지 않는다. 독립적으로 산출된 값까지 숨기지 않는다.

시간은 UTC 저장, 명시적 offset의 RFC3339 입력, `[start,end)` 계산, 기본 Asia/Seoul 표시다. 사건 시각·원본 관측 시각·수신 시각·조회 시각을 구분한다. 관계 유효 구간을 표시하고 현재 관계를 과거에 복사하지 않는다. 관측률은 필요한 입력 구간의 교집합을 서버가 계산한다.

수치의 값·단위·대상·기간·분모·계산/정책 revision·근거는 서버 결과를 따른다. 설명의 facts[].value_refs는 measurements 또는 topics[].metrics에 한 번 저장된 값의 ID를 참조한다. 프론트에서 LLM 문장의 숫자를 재해석하거나 수치·저활동 후보·인과를 계산하지 않는다. 차트 확대·축소용 표시 간격을 바꿔도 저장 보고서 수치를 재계산하지 않는다.

## 5. S01~S04 관제·관측

| 화면·영역 | 표시·입력 | 행동·연결 |
|---|---|---|
| S01 범위·기간 | 허용 CPC/Namespace, 최근 구간·사용자 기간, 기준 시각 | `POST /dashboard/query`, 선택 조건 변경 시 새 조회 |
| S01 요약·우선 검토 | 열린 사건, 수신 지연, GPU 상태, 분석 준비 | 사건 S05/S07, 관측 S04, GPU S02 |
| S01 대상·추이 | Node 복수 선택, GPU 활동·VRAM·전력, 단위·누락 | `POST /observations/query`; “이 그래프에 질문”으로 S16에 context 전달 |
| S02 자산·상세 | CPC/Node/GPU UUID, 모델, 원본 시각, 신원 품질 | `GET /assets`의 kind로 조회; GPU 선택 질문·S06 조사 |
| S03 작업 연결 | CPC/Namespace/Pod 이름·UID, 기준 시각, 세 독립 축 | `POST /mappings/query`; 현재/과거 전환, Pod 행에서 S06 |
| S04 관측 상태 | 소스·필드별 마지막 수신, 구간 품질, 분석별 필요한 입력 | `GET /service-status`의 허용 요약과 등록 관측 query, S15 연결 상세 |

S03은 다음 라벨을 사용하며 원 enum은 상세에서 확인한다.

| 03 반환 DTO 필드 | enum | 화면 라벨 |
|---|---|---|
| placement_status | unbound / bound / unknown | 노드 미배치 / 노드 배치됨 / 배치 미확인 |
| relation_status | matched / ambiguous / not_observed / unknown | GPU 연결 확인 / 연결 후보 여러 개 / 연결 미관측 / 연결 미확인 |
| activity_status | active_observed / low_activity_candidate / insufficient_data / not_applicable | 활동 관측 / 저활동 검토 후보 / 활동 근거 부족 / 적용 대상 아님 |

Kubernetes phase는 별도 `kubernetes_phase` 필드에서 표시한다. Pending은 위 placement_status와 독립이며 세 축의 응답 필드명을 placement/mapping/activity로 치환하지 않는다. unbound의 장치 활동이 not_applicable인 경우 “적용 대상 아님”을 유지한다. 공유 GPU 활동을 연결된 각 Pod의 사용량으로 복제하지 않고 물리 GPU/MIG/공유 단위를 분리한다. 활동 0이어도 관계를 제거하지 않는다. 매핑 미관측은 해제·미할당 확정이 아니다.

빈 수치·원본 갱신 지연·소스 오류는 구별한다. 연결 성공과 선택 분석 입력의 충분성을 별도 열로 표시한다. CPC-2 일부 target·동시점 GPU↔Pod UID 확인을 모든 CPC·과거 기간 완료로 확대하지 않는다. 최신 근거의 실제 확인 범위는 06의 C04를 표시 근거로 사용한다.

## 6. S05~S07B 조사·사건 운영

S05는 사건 탭과 직접 요청 탭에서 `GET /incidents`, `GET /analyses`를 사용한다. 사건 상태와 최근 분석 실행·산출 상태를 별도 열에 둔다. 진행은 S11, 사건 결과는 S07, 사건 없는 직접 결과는 S07B로 연다.

S06 입력은 대상 종류 Node/GPU/Pod, scope, 기준 시각·time_range·timezone, symptom, purpose_ids다. 사건에서 진입하면 incident_id를 연결한다. Node는 CPC·Node UID를 우선하고, GPU는 CPC·GPU UUID를 사용한다. Pod는 CPC·Namespace·Pod 이름·Pod UID·기준 시각으로 선택한다. Pod 조사에서 Node/GPU 선택을 필수로 강제하지 않는다. S03의 Pod 행에서 동일 값을 채워 S06으로 이동한다. 이름 재사용 시 UID가 다른 항목을 구분한다.

필수 대상 또는 incident, 유효 기간, 비어 있지 않은 증상, R01~R09 목적, 허용 대상 소속을 검사한다. 길이·조회 기간은 C07의 서버 제한과 맞춘다. 고정 2,000자 같은 기존 제안값을 확정 한도로 사용하지 않는다. 접수 중 중복 버튼을 막고 한 의도에 고정 Idempotency-Key를 사용한다. `POST /analyses`의 202를 받은 뒤 S11을 열고 완료 결과는 `GET /analyses/{job_id}`에서 읽는다.

S07/S07B는 사실, 원인 후보, 지지·반박·미확인 근거, 부족한 입력, 다음 확인, 호환 Runbook과 버전을 표시한다. 관계·영향·원인 판단을 독립 표시한다. `Pod 배치 확인 / GPU 관계 미확인`도 유효 결과다. 원인 미확정에 임의 신뢰도 백분율을 만들지 않는다.

S07에 사건 상태 변경 폼을 둔다. 현재 상태·버전, 변경 상태, 사유, 담당을 표시하고 `PATCH /incidents/{id}`에 If-Match를 보낸다. open→investigating→resolved→closed와 허용 재개는 서버 전이 규칙을 따른다. 종결 사유는 필수다. 알림 resolved·분석 succeeded만으로 종결하지 않는다. 수정·추가 근거로 같은 episode를 재개하는 일과 새 episode의 별도 재발 사건을 구분하여 recurrence_of와 변경 이력을 보여준다. 오래된·무효 Healthy, 조회 실패·수집 단절은 회복 확정으로 표시하지 않는다.

근거는 `GET /evidence/{id}`, 지식은 정확한 revision으로 연다. 재분석은 새 `POST /analyses`에 parent_job_id를 넣고 새로운 작업으로 이동한다. 같은 작업 재시도 버튼과 별도로 둔다.

S07의 “현재 상태 재확인”은 새 알림이 없는 사건에도 제공한다. 현재 incident_id와 후속 관측 기간을 유지·확인하고 R01/R09 목적의 새 RCA를 접수한다. 이전 분석이 있으면 parent_job_id를 연결한다. 자동 주기 실행이나 사건 자동 종결로 처리하지 않는다.

검토·실제 조치는 `GET/POST /reviews`를 사용한다. 실제 조치에는 대상·수행 시각·수행자·내용을 받고 권고와 구분한다. 수정은 supersedes_id를 가진 새 기록으로 추가하며 이전 기록은 남긴다. 보고서에서는 subject_type=job, subject_id=report_id를 사용한다. 사건·직접 조사도 해당 incident/job에 기록을 연결한다.

## 7. S08~S10 운영 분석·보고서·일정

S08의 네 카드 배치를 유지하고 각 카드 안에 세부 주제 체크 목록을 둔다. 선택된 topic_ids를 S09에서 다시 확인한다. 첫 화면에 고급 조건을 전부 펼치지 않되 모든 O 주제의 입력 경로를 제공한다.

| 카드 묶음 | 주제 선택 | 필요할 때 펼칠 입력 |
|---|---|---|
| 관측·용량 | O01 장비·Node 변화, O07 배치 대기·용량, O11 관측 품질 | 비교 기간, O07 자원 이름·단위/유형 선택과 미배치 조사 기간 |
| 할당·활동 | O02 할당 명세·시간, O03 저활동, O04 다중 GPU 편차, O08 Namespace·프로젝트 배분 | 허용 Namespace, group_by, workload/Pod 단위, 비교 기간 |
| 반복 사건·조치 | O05 반복 사건, O06 당시 작업, O10 조치 전후 | O10 조치 기록 연결 action_record_ids와 전후 comparison_range |
| 에너지 | O09 GPU 에너지 | 실제 전력/누적 에너지의 적용 범위, 필요 시 비교 기간 |

S09는 scope, 기간, timezone, topic_ids(1개 이상), group_by와 선택 comparison_range를 입력한다. group_by는 cluster/model/node/namespace/pod/workload 중 서버 허용값을 사용한다. O07은 `resource_selectors:[{cluster_id,resource_name,unit}]`를 받으며 등록 관측 `query_id=resource_catalog`의 허용 범위 내 검증된 선택지를 사용한다. 전체 조회는 선택을 생략할 수 있으나 단위 미확인은 해당 산출 blocked로 표시한다. GPU UUID가 없는 unbound Pod도 조사 대상에서 제거하지 않는다. O10은 `action_record_ids:[uuid]`를 선택할 수 있고 time_range는 조치 후, comparison_range는 조치 전 기간이다. 미연결 상태는 `action_record_missing` 사유와 함께 일반 기간 비교로 명시한다. 실제 조치의 효과를 설명하려면 조치 기록과 비교 조건이 필요하며 연결만으로 인과를 확정하지 않는다.

날짜 입력은 시작일 00:00부터 종료일 다음 날 00:00 미만까지 선택 시간대의 달력 구간으로 변환한다. 같은 날 보고서를 허용한다. 정밀 시각 입력을 선택한 경우 그 시각 구간으로 명확히 전환한다. 관측 부족한 주제도 요청할 수 있고 보류 사유를 결과로 받는다. 단위·물리/공유/MIG 구분, 현재 명세와 GPU-hours, 수치 변화와 인과를 유지한다.

일회 실행은 `POST /reports`→S11→S10이다. S10은 `GET /reports/{job_id}`로 저장 결과를 읽는다. 전역 범위를 바꾸어도 기존 결과의 대상·기간·버전을 유지한다. 재생성은 parent_job_id를 넣은 새 POST다. HTML 보고서·집계 CSV는 `GET /reports/{id}/export?format=html|csv`로 동일 저장본을 받는다. 파일 생성 여부와 별도로 출력 접근 권한을 서버가 확인한다.

S09의 실행 방식에서 일회/정기를 선택한다. 정기는 F07/P0이며 다음 전체 흐름을 제공한다.

| 단계 | 입력·표시 | API·행동 |
|---|---|---|
| 일정 생성 | daily/weekly/monthly, local_time, timezone, 주간 weekday·월간 day, 대응 previous_complete_day/week/month, scope·주제·집계 조건 | POST `/schedules`, 일정 ID·다음 실행 표시 |
| 일정 목록 | 이름/ID, 일·주·월, 대상, 활성/일시중지, 다음 실행, 최근 발생 상태 | GET `/schedules`, S09 내 목록 탭 |
| 일정 상세·수정 | 보고서 조건, 현 revision·변경 적용 시점, 소유자, 다음 실행 | GET/PATCH `/schedules/{id}`, If-Match |
| 일시중지·재개 | enabled, 변경 후 다음 실행, 사유 | 같은 PATCH. 실행 중 job 취소와 별도 동작 |
| 발생 이력 | scheduled_for, 적용 revision, 대상·기간, accepted/missed/blocked와 사유, 연결 job | GET `/schedules/{id}/occurrences`; job→S11, 결과→S10 |

월간 없는 날짜는 말일, 주간 분석 기간은 월요일~다음 월요일, DST·누락 보충·변경 적용 경계는 02 계약과 C08을 따른다. 접수된 발생분의 범위·기간은 수정하지 않는다. 일정 변경·시간대 변경 시 이미 접수한 결과와 앞으로의 발생을 구분한다. 권한 철회로 blocked인 일정을 조용히 축소 범위로 실행하지 않는다. missed/blocked 이력을 빈 목록으로 숨기지 않는다.

## 8. S11 작업 목록·수명주기

`GET /jobs`는 kind, status, from, to, scope, cursor, limit 필터를 사용한다. 시간 필터는 서버가 정의한 생성 시각 범위이며 목록 기본 정렬은 created_at DESC, id DESC다. scope는 CPC별 Namespace 조합을 보존한 직렬화 객체다. 목록 응답은 items와 next_cursor다. 브라우저에서 RCA/보고서 두 목록을 임의 병합하지 않는다.

| job.status | 화면 | 행동 |
|---|---|---|
| queued | 접수 대기·접수 시각 | 서버 can_cancel에 따른 취소 |
| running | 실행 중·조회/계산/모델 대기/추론/저장 단계 | 진행 확인·취소 요청 |
| retry_wait | 재시도 대기·다음 시도·누적 시도 | 서버 허용 취소, 기존 deadline 유지 |
| succeeded | 실행 완료·별도 산출 상태 | 결과·근거 열기, 새 분석 |
| failed | 실행 실패·사유·보존 근거 | can_retry일 때 동일 작업 재시도, 또는 새 분석 |
| cancelled | 취소 완료·보존 여부 | 필요 시 새 분석 |
| expired | 기한 만료·종료 이유 | 필요 시 새 분석 |

GET 상세의 `id,kind,status,stage,attempt_no,attempts,created_at,started_at,deadline_at,cancel_requested_at,termination_reason,result_ref,version,result_status,narrative_status,can_cancel,can_retry`를 사용한다. 결과가 없으면 result_status/narrative_status는 null이다. 작업 ID가 분석/보고서 ID다. 별도 run_id를 만들지 않는다. `attempts`는 접근이 허용된 소유 운영자/해당 업무 관리자에게만 `attempt_no,started_at,finished_at,stage,termination_reason,error_code`의 안전한 요약 배열로 제공되고 그 외 사용자는 null이다. null이면 시도 상세를 숨기며 빈 이력이나 조회 오류로 표시하지 않는다. 조회자에게는 허용 결과의 안전한 작업 상태만 보이며 Worker 내부·민감 로그는 노출하지 않는다. 확보하지 못한 TTFT·내부 큐 시간·완료율을 추정하지 않는다.

취소는 reason을 입력받아 `POST /jobs/{id}/cancel`에 고정 Idempotency-Key와 If-Match를 함께 보낸다. 응답 유실 시 같은 키·같은 reason/요청으로 확인한다. 취소 요청이 접수되어도 서버가 확정하기 전 cancelled로 바꾸지 않는다. 완료가 먼저 확정된 409는 최신 결과를 재조회한다. can_cancel/can_retry는 버튼 안내값이며 서버 권한·기한·예산·버전 검사를 대체하지 않는다.

재시도도 reason을 입력받아 `POST /jobs/{id}/retry`에 고정 Idempotency-Key와 If-Match를 함께 보낸다. 응답 유실 시 같은 키·같은 reason/요청으로 복구하고, 이미 처리된 요청의 서버 멱등 응답을 따른다. 성공 시 같은 job 상세와 폴링을 재개한다. attempt_no만 증가하고 deadline·누적 예산은 초기화하지 않는다. 재분석은 새 작업+parent_job_id다.

목록·상세·Assistant의 같은 job 조회는 하나의 캐시/조회 결과를 공유한다. 활성 작업은 설정 가능한 backoff로 조회하고 비가시 탭에서는 감속 또는 일시중지한다. Retry-After를 준수하고 terminal이면 중단한다. `poll_after_ms`는 API 필드로 가정하지 않는다. 화면 이탈·브라우저 종료·대화 닫기는 서버 job을 취소하지 않는다. 재진입 시 서버 목록부터 복원한다.

## 9. S12 지식·Runbook

열람 탭은 발행 Runbook·정책·데이터 의미·참고 근거·검증 사례와 등록 조사 절차를 제공한다. 지식 종류의 저장 enum은 03을 따른다. `GET /knowledge`는 권한 있는 발행 지식을 검색하며 상세는 `/knowledge/{id}/revisions/{rev}`다. 내용·출처·호환 모델/오류/버전·공개 범위·필수 근거·발행 revision·폐기 여부를 표시한다. 과거 결과에서 연 인용은 최신본으로 자동 교체하지 않는다.

조사 절차 탭은 `GET /knowledge/procedures`로 등록 코드의 procedure ID/version·입력·조회·종료 규칙을 읽는다. 코드가 원본이며 브라우저에서 임의 실행 절차를 편집·발행하는 기능이 아니다.

지식 관리자에게 같은 S12의 관리 탭을 제공한다.

| 단계 | 폼·행동 | 계약 |
|---|---|---|
| 초안 | 종류, 제목·내용, 근거, 지원 조건, 허용 범위, revision 메모 | POST `/knowledge` 또는 `/{id}/revisions` |
| 수정 | 초안 편집, 미저장 알림·검증 오류 | PATCH `/{id}/revisions/{rev}` + If-Match |
| 검토 | 검토 요청·담당 상태, 검토 결과·수정 요구·근거 | POST `/{id}/revisions/{rev}/review`의 action은 request/approve/request_changes, comment, evidence_refs? |
| 재검토 | 검토 후 내용 변경 시 이전 승인을 무효화하고 새 검토 | 수정 후 reviewed 상태를 그대로 유지하지 않음 |
| 발행 | 검토된 내용·scope·호환 범위 확인 | POST `/{id}/revisions/{rev}/publish` + If-Match |
| 폐기 | 사유·영향 안내 | POST `/{id}/revisions/{rev}/retire` + If-Match |
| 발행본 개정 | 이전 발행본을 읽고 새 revision 초안 생성 | 발행본 직접 수정 금지, 과거 인용 유지 |

검토 상태는 draft→in_review→reviewed 또는 수정 요청 시 draft다. 검토 뒤 편집하면 draft로 돌아가며 reviewed와 일치하는 content_hash의 내용만 발행한다. 검토 권한과 수행자를 확인·기록하고 의무적인 2인 승인 절차를 임의 추가하지 않는다. 폐기 지식은 새 분석 추천에서 제외하고 이전 결과의 인용은 열 수 있다. 초안과 범위 제한 지식은 권한 없는 목록·Assistant 검색·근거·내려받기에 노출하지 않는다. 실제 사례를 자동 승인·발행하지 않는다.

## 10. S13~S15 연결·모델 설정

S13 모델 카드에는 별칭·활성 여부·Endpoint 표시·모델 ID·지정 업무·revision을 둔다. 형식 검증, 서버 연결 검사, 분석 품질 검증 상태를 각각 표시한다. 실제 모델 artifact·엔진·정밀도·예산·성능 검증 근거는 C06/C07/C09와 T40을 연결한다.

| 업무 | API | 규칙 |
|---|---|---|
| 모델 목록·등록 | GET/POST `/models` | 기존 service_profiles의 모델 프로필을 사용 |
| 상세·수정 | GET/PATCH `/models/{id}` | If-Match, 새 revision, 비밀 원문 응답 금지 |
| 비활성화 | PATCH `/models/{id}`의 enabled=false | 삭제 버튼 대신 비활성화. 사용 중 라우트는 대체 지정 후 처리하거나 409 안내 |
| 연결 검사 | POST `/models/{id}/test-connection` | 서버가 허용 목적지에만 접속. 통신 성공을 분석 품질 PASS로 표시하지 않음 |
| 업무별 지정 | GET/PATCH `/model-routes` | 공통 기본·RCA·보고서, 기본 상속/개별 지정, If-Match |
| 데이터 상태·설정 | GET `/service-status`, GET/PATCH `/settings/{profile_id}` | 권한 있는 서비스 관리자만 변경, 비밀 참조 사용 |

모델 저장 DTO는 `name,endpoint_url,model_name,artifact_revision,engine_revision,precision,secret_ref?,enabled,capabilities,limits_profile_id`다. protocol·host·port·base path를 나누어 입력하는 UI를 유지할 경우 검증 후 하나의 endpoint_url로 조합한다. UI의 “모델 ID” 입력은 추론용 model_name이며 API 리소스 식별자 model_id(profile ID)와 구분한다. artifact/engine revision·정밀도·capabilities·예산 프로필은 고급 설정에 둔다. 기존 시안의 IPv4 전용 폼을 모든 사내 Endpoint의 영구 제한으로 확정하지 않는다. port 정수 1~65535, 지원 protocol, 허용 경로·호스트·길이 제한은 서버 프로필/C06을 따른다. 최종 허용 목적지·비밀 검증은 서버 책임이다. C06에 없는 DNS/IPv6 지원을 이번 개정으로 임의 추가 구현 요구하지 않는다.

브라우저는 Gateway/API만 호출하며 모델·Mimir·Loki·DB에 직접 접속하지 않는다. 연결 검사 실패로 설정을 삭제하지 않는다. 저장 실패·412에서는 미저장 입력을 유지하고 최신 설정과 비교한다. 모델·라우팅 변경이 진행 job과 과거 결과의 고정 revision을 바꾸지 않는다. 실패 시 외부 모델로 자동 우회하지 않는다.

S15는 경로 연결·최근 수신과 해당 R/O 주제의 데이터 충분성을 별도 표시한다. 수집 주기와 원천 갱신 주기를 구분하고, Loki 최신 도착·CPC별 확인 구간 등 C04의 미확인 사항을 드러낸다. 별도 manage_access capability가 있는 담당자에게만 같은 설정 화면의 권한 관리 탭을 제공한다. GET/PATCH `/settings/access-grants`로 역할·CPC·Namespace·장비 관측 권한의 행과 변경 사유를 읽고 저장한다. If-Match와 감사 기록을 적용하고 저장 뒤 access_revision을 재조회하여 관련 캐시를 무효화한다. 일반 서비스 관리자 역할만으로 권한 변경을 허용하지 않는다.

## 11. S16 공통 Assistant

Assistant는 전역 버튼으로 열며 기본은 닫힘이다. 데스크톱 우측 패널과 펼친 화면은 같은 conversation_id를 사용한다. 좁은 화면은 drawer다. 범위는 일반 질문(운영 데이터 참조 없음), 현재 화면, 접근 가능한 전체 범위로 구분하고 CPC/Namespace·대상·기간 칩을 표시한다. “현재 화면 범위 적용”은 이후 메시지의 context에만 반영한다.

`GET/POST /conversations`, `GET/POST /conversations/{id}/messages`를 사용한다. 일반 응답은 C07의 짧은 제한시간 안에서 동기 처리한다. 최초 제출부터 메시지 ID를 영속 저장하며 진행 중 동일 요청 재전송은 202와 같은 message_id로 응답한다. `GET /conversations/{id}/messages/{message_id}`로 accepted/processing/completed/failed 상태와 저장 답변·job 참조를 복구한다. response가 없으면 null이다. API 재시작으로 중단된 일반 메시지는 failed로 남고 같은 키로 자동 재생성하지 않는다. 사용자가 새 생성을 선택하면 새 키와 이전 메시지 참조를 사용한다. 이번 버전은 SSE·토큰 스트리밍·이벤트 순번 복구를 요구하지 않는다.

메시지 키는 사용자 의도마다 고정하고 정규화한 text+context+scope+time_range를 서버가 hash로 묶는다. 같은 키·다른 질문/범위는 409다. 네트워크 응답 유실 시 같은 키로 확인하며 메시지·전문 job을 중복 생성하지 않는다. 조회자는 일반 설명과 허용 조회만 가능하고 전문 작업 요청은 권한 부족으로 안내한다.

“응답 기다리기 중지”와 패널 닫기는 로컬 대기/화면 동작이다. 서버 생성이나 이미 만든 전문 job을 취소했다고 표시하지 않는다. 다시 열면 저장 메시지를 조회한다. 전문 job의 취소는 작업 카드/S11의 명시적인 “작업 취소 요청”으로 수행한다. 생성 진행·연결 끊김·응답 실패·접수 job을 구분하며 확인되지 않은 부분 응답을 완성 답변처럼 저장하지 않는다.

응답에는 처리 주체, 저장 context, 사용 모델·revision, 근거, 산출 한계를 표시한다. 긴 분석은 job_id 접수 카드→S11→저장 결과 링크로 연결한다. 바로가기는 허용 화면과 검증된 리소스 ID만 사용한다. Markdown의 임의 HTML·스크립트를 실행하지 않고 로그·문서·모델 출력의 지시를 실행 권한으로 취급하지 않는다.

## 12. API·DTO·오류 계약

아래 경로에는 모두 `/api/v1`을 붙인다. API 원본은 02이며 예시는 실제 접속 기록이 아닌 계약 예시다. 식별자는 클라이언트가 해석하지 않는 문자열로 다루고 내부 저장 ID 예시는 유효 UUID를 사용한다. 화면 표시 번호는 별도 라벨이다.

| 상태 | UI·복구 |
|---|---|
| 최초 로딩 | 스켈레톤·조회 중 표시, 중복 제출 방지 |
| 정상 빈 목록 | 현재 필터의 결과 없음; 조회 오류·근거 부족과 구분 |
| 일부 조회 실패 | 성공 영역 유지, 실패 영역·마지막 성공 시각 표시 |
| 400/422 | 필드 오류·첫 오류 포커스. 서버 error.details를 사용 |
| 401 | 재인증; 같은 사용자·권한 확인 후에만 초안·조회 복구 |
| 403/404 | 권한 부족/없거나 접근 불가; 민감한 상세·존재 정보 비노출 |
| 409 | 멱등 키와 본문 충돌 또는 현재 상태 불가. 최신 상태 확인 후 행동 재선택 |
| 412 | 이전 ETag의 변경 충돌. 최신본을 읽고 입력과 비교, 덮어쓰지 않음 |
| 428 | If-Match 누락. 최신 version/ETag 조회 후 조건부 변경으로 다시 제출 |
| 413 | 허용 크기 안내, 초안 보존 |
| 429 | Retry-After 준수, 대기 안내, 중복 새 접수 금지 |
| 5xx/네트워크 | 실패·request_id·마지막 성공 시각; 같은 조회/멱등 키로 복구 |

PATCH 및 02에서 지정한 상태 변경은 If-Match를 보낸다. 이전 버전 재시도와 새 사용자 변경 의도를 구분한다. 접수 응답 유실을 이유로 다른 요청 키의 새 작업을 자동 생성하지 않는다.

## 13. 구현·접근성 기준

기존 사내 프론트엔드 표준과 공통 표·폼·패널을 재사용한다. API 서버 상태, URL 조건, 일시 UI 상태를 구분하되 화면마다 새 상태 프레임워크를 추가하지 않는다. 공통 후보는 AppShell, ScopeBar, 대상 선택기, 상태 배지, 근거 패널, JobDetail, Assistant, 설정 폼이며 독립 서비스 단위로 강제하지 않는다.

DESIGN 05의 데스크톱 좌측 메뉴·본문·우측 Assistant 배치를 유지한다. 약 360px Assistant 폭·3초 폴링 같은 이전 수치는 고정 계약이 아니다. 실제 가독성·C09 부하를 기준으로 조정한다. 좁은 화면은 단일 열과 drawer, 표만 컨테이너 안에서 가로 스크롤한다. 320px 전체 페이지 넘침과 200% 확대, 모바일 키보드가 열린 입력 동작을 검수한다.

키보드로 모든 조작, focus-visible, 화면 이동 후 제목 포커스, drawer 닫기 후 원래 버튼 복귀를 지원한다. 모달 overlay에는 dialog 의미·포커스 가두기·배경 inert·Escape 닫기를 적용한다. 비모달 보조 패널은 포커스를 가두지 않는다. 채팅 입력은 보이는 위치에 유지하고 메시지만 스크롤한다. 색 이외 라벨·아이콘을 제공하며 WCAG AA 대비와 스크린리더를 확인한다. 상태는 role=status, 입력 오류는 role=alert로 과도한 반복 없이 알린다. prefers-reduced-motion을 따른다.

미저장 폼·검토·초안은 저장 실패 때 유지하되 사용자·권한 변경 시 3절의 보안 범위 안에서만 복원한다. 오류 로그에 비밀·원문 민감 데이터·내부 상세를 무분별하게 기록하지 않는다. 사용자·모델 텍스트를 안전하게 렌더링하고 CSV/HTML 출력의 방어는 서버 구현과 함께 T31에서 확인한다.
