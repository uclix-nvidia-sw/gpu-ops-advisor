# 전체 구조와 Backend 상세 구성

v2 추가: [사이트 권한·Mimir Tenant 설계](<../share/DSX_사이트권한과_Mimir_Tenant_설계_2026-09-16.md>)를 반영했다. 세 번째 그림은 수집·조회 권한 경계와 사이트별 tenant 목표 구성이다. 인증은 후속 구현이며 CPC 수집·실배포 설정은 변경하지 않았다. Backend 8개 기능은 유지하고 공통 권한 계약을 추가한다. 아래의 실행 구성에 사이트 범위를 함께 적용한다.

2026-09-16. 이번 그림은 Frontend·Gateway·Backend·PostgreSQL 구분을 기준으로 다시 구성했다. 기존 마이크로서비스 비교 그림을 확정 배포안으로 이어받지 않는다. CPC 수집 경로는 그대로 두며 클러스터 변경이나 배포를 수행하지 않았다.

## 세 그림의 차이

- **전체 구조:** 화면과 API 진입, Backend 8개 기능, 업무 PostgreSQL, 기존 관측 및 Object Storage, 별도 Dynamo·Local LLM의 관계.
- **Backend 확대:** API 서버와 두 Agent Worker를 실행 단위로 나누고, 조회·계산 / Knowledge / LLM 호출 코드를 함께 사용하는 구현 제안. 기능 8개를 8개 네트워크 서비스로 분리한다는 의미가 아니다.
- **사이트별 저장·조회:** 인증된 사이트 수집 신원으로 쓰기 tenant를 정하고, 사용자의 허용 사이트 집합으로 조회 tenant를 제한하는 목표 설계. 저장 분리와 인증·자원 격리를 구분한다.

| 구분 | 포함하는 기능 | 실행 책임 |
|---|---|---|
| Backend API 서버 | ① 사용자 API·대화, ② Incident, ③ 작업 관리·스케줄 | 사용자·Webhook·정기 요청 접수, 범위/권한 검증, 업무 저장, 작업 점유·상태·결과 API |
| RCA Worker | ④ GPU Node RCA Agent | 커밋된 RCA 작업을 점유하고 근거 조사·추론 후 결과 확정 요청 |
| 보고서 Worker | ⑤ 최적화 운영보고서 Agent | 커밋된 정기/요청 보고서 작업을 점유하고 계산·설명·근거를 작성 |
| 공통 모듈 | ⑥ 데이터 조회·계산, ⑦ Knowledge 관리·검색, ⑧ LLM 호출 관리 | API 서버와 Worker가 재사용하는 코드. 독립 서버를 기본으로 추가하지 않음 |
| 별도 추론 계층 | Dynamo, GPU 추론 엔진, Local LLM | 모델 라우팅·추론 수행. 업무 영속 큐의 책임은 Backend에 유지 |

API 서버 1종과 Worker 2종은 프로세스/배포 종류를 뜻한다. Pod 수·복제 수·물리 노드 수를 확정한 것이 아니다. 공유 모듈의 코드 버전과 데이터 계약은 함께 관리하며, 독립 배포 시 호환성을 확인한다. 이 안은 기능 경계와 실행 분리를 정하는 제안이며 모든 도메인의 완전한 마이크로서비스화를 주장하지 않는다.

## 실행과 저장

일반 대화·가벼운 조회는 사용자 API가 공통 기능으로 처리한다. 분석·보고서는 PostgreSQL의 영속 작업으로 접수한 뒤 job_id를 반환한다. API 서버는 긴 분석을 직접 붙잡고 있지 않고, 해당 Worker가 작업을 점유해 실행한다. 결과·근거가 저장되고 해당 시도의 유효성이 확인된 뒤 완료로 확정한다. 화면은 Gateway와 사용자 API를 통해 진행과 결과를 조회한다.

사건 갱신과 RCA 작업 접수는 같은 트랜잭션으로 저장한다. 중복 접수 키, Worker 점유 만료/갱신, 시도 버전, 제한된 재시도·취소·마감, 늦은 응답의 결과 덮어쓰기 방지를 유지한다. API 서버를 복제하면 스케줄 발생도 공유 잠금이나 유일한 실행 키로 중복을 막는다. 그림의 양방향 작업 연결은 점유·갱신·결과 확정 계약을 뜻하며 별도 메시지 브로커를 뜻하지 않는다.

PostgreSQL에는 대화·요청·사건·jobs·실행·분석 결과·보고서·근거 참조·시간별 관계·발행 지식·검토/조치 기록을 저장한다. 전체도의 SQL 선은 Backend 전체의 공통 저장 접근을 대표한다. 확대도의 [P]는 같은 PostgreSQL을 가리킨다. 공통 저장 계층에서 데이터별 갱신 책임을 정하고, Worker별로 작업 원장을 중복 작성하지 않는다.

공통 LLM 모듈을 각 프로세스가 불러 쓰더라도 호출 한도는 프로세스 로컬 값만으로 관리하지 않는다. PostgreSQL 등 공유 상태로 호출 점유·만료·토큰 예산을 조정하며 추론 timeout과 전체 작업 deadline을 나눈다. 공통 Assistant는 사용자 대화 역할이며 전문 Agent는 RCA와 보고서 두 개다.

Mimir/Loki [Q]는 원시 관측 조회, Object Storage는 관측 데이터 보관, Git 등의 [K]는 지식 원문과 등록 함수 관리 역할이다. 발행된 Runbook·정책은 PostgreSQL의 버전으로 조회한다. 조회·계산은 결정적으로 수행하고 LLM은 해석과 조사 단계 선택에 사용한다. Nemotron 3 Super는 초기 모델 후보이며 GPU·가중치/PV·서빙 엔진·동시 처리 용량은 실제 평가 후 확정한다.

사용자 API용 Gateway와 관측 수신 Gateway는 역할을 구분해 그렸다. 같은 Envoy 설치를 이용할 수 있는지는 실제 라우팅·보안·운영 경계를 확인한 뒤 결정한다. 그림의 두 Gateway 박스가 반드시 물리 설치 두 개를 요구하는 것은 아니다.
