# DSX 수집 데이터 — 근거 대조와 기능 매핑

작성일: 2026-09-15

> **최신 자료와 사용자 확인 반영:** 이 문서 본문은 최신 첨부를 받기 전의 근거 대조 기록이다. 현재는 CPC-1·CPC-2가 동일한 수집·연동 환경을 사용하며 CSC에서 양쪽 데이터를 조회할 환경이 구축됐다는 사용자 확인을 기준으로 한다. 최신 판정은 [CPC 공통 수집 환경과 Agent 업무](<DSX_CPC_공통수집환경과_Agent업무_2026-09-15.md>)를 우선한다. CPC-2의 개별 검증 표본은 출처를 유지하며, 과거의 라벨·전송 문제를 현재 환경의 제약으로 인용하지 않는다. 중앙 GPU↔Pod 장치 매핑·pod_uid 보완·개별 메트릭 및 기간 검증은 별도로 구분한다.

## 1. 먼저 정정할 판단

**이전 「두 Agent 지원 업무와 데이터 경계」는 필요한 데이터가 있을 때의 업무 설계안이었다. 현재 수집 데이터가 항목별로 검증된 기능 명세는 아니었다.** 구조도상 수집 대상과 실제 중앙 저장소에서 분석에 쓸 수 있는 데이터를 충분히 구분하지 못했다.

이번 검토는 프로젝트의 기술기록과 첨부 문서를 다시 대조했다. 운영 클러스터·Mimir·Loki에 새로 접속해 조회한 것은 아니다. 따라서 다음 세 가지를 구분한다.

1. 수집기·소스·구조상 지원 가능한 데이터.
2. 특정 시점·환경에서 실제로 관측됐다고 기록된 데이터.
3. 현재 대상·기간에 Agent가 조회·연결·집계할 수 있다고 검증된 데이터.

현재 확보한 자료에서는 1과 2의 일부를 확인했다. 3을 전체 항목에 대해 확인하지 못했다. **미확인은 미수집이나 수집 불가능의 확정도 아니다.**

사용자가 전달한 “CPC→CSC 전송 구성이 완료됐다”는 현재 설명은 유지한다. 9월 초의 실패·라벨 문제를 지금도 지속되는 장애로 간주하지 않는다. 다만 전송 완료와 개별 필드·식별·과거 기간의 검증은 서로 다른 확인 항목이다.

## 2. 근거 수준

| 상태 | 의미 |
|---|---|
| 현재 수신 검증 | 명시된 현재 대상·시각의 CSC 응답에서 값·라벨·품질을 확인 |
| 과거 관측 기록 | 기술기록에 특정 시점의 수집·조회 결과가 남아 있음. 지금까지 연장하지 않음 |
| 설정 확인 | 구체 수집 설정을 확인했으나 도착·조회 결과는 확인하지 못함 |
| 구조·지원 후보 | 구조도 또는 제품·소스 기능으로 경로가 가능함. 현재 활성화 증거는 아님 |
| 미확인 | 해당 판단을 뒷받침할 필드별 근거가 부족 |
| 서비스에서 생성할 데이터 | Incident·분석·검증 사례처럼 수집기 원천 데이터가 아닌 서비스 산출물 |

확인 시각이 없는 캡처나 샘플도 참고할 수 있으나 현재 수신 검증으로 승격하지 않는다. 단일 정상 샘플은 한 주간 분석 가능성이나 모든 노드의 정상 수집을 보장하지 않는다.

## 5. 가장 중요한 조인 문제

E01/E02의 과거 기록에는 다음 라벨이 남아 있다.

```text
GPU 온도:
  device, gpu, gpu_serial, job, model_name, pci_bus_id, uuid

fleetint_agent_up:
  job

target_info:
  host_name, machine_id, node_group, compute_zone, gpuInfo_gpus, job
```

이 기록만으로는 “GPU 지표와 KSM을 node로 join하면 된다”라고 할 수 없다.

1. GPU 지표에는 당시 node 라벨이 없었다.
2. target_info에는 노드 정보가 있지만 GPU와 연결되는 정보를 추출·검증해야 했다.
3. job만 같은 두 시계열은 어느 노드 것인지 구분하는 키가 아니다.
4. gpuInfo_gpus의 배열 순서 변화로 중복 시계열이 생겼다는 기록도 있다.
5. 당시 GPU 모델이 노드마다 달랐다는 사실은 영구적인 노드 식별 규칙이 될 수 없다.

최신 Alloy·수집 설정에서 이 문제가 해결됐을 수 있다. 그렇다면 **현재 GPU 시계열과 KSM 시계열의 대응 표본**으로 해결을 확인하면 된다. 과거에 소실·혼합된 식별 정보는 최신 설정만으로 과거 전체에 복원됐다고 보지 않는다.

| 항목 | 기록할 내용 |
|---|---|
| 논리 데이터 | GPU 활동, VRAM 점유, Pod GPU 요청 등 |
| 생산자 | Fleet/DCGM exporter/KSM의 실제 배포 버전·대상 |
| 활성 수집 설정 | 필드 선택, 수집 간격, 권한·노출 조건 |
| 전달 경로 | Prometheus·Alloy·Gateway의 입력·필터·변환·목적지 |
| 중앙 필드 | 실제 metric 이름 또는 로그 JSON 경로 |
| 식별자 | cluster·node·GPU UUID·Pod UID와 연결 규칙 |
| 의미 | 단위, gauge/counter, 물리 GPU/MIG/공유 범위 |
| 조회 증거 | endpoint·tenant·대상·조회 시각·실제 값·원본 샘플 시각 |
| 기간 품질 | 최초·최근·결측·유효 대상, 과거 관계 조회 여부 |
| 판정 | 현재 수신 검증 / 과거 기록 / 설정만 / 미확인 |
| 연결 업무 | R01~R07, T01~T10의 어느 입력을 충족하는지 |

인증 토큰이나 비밀번호는 표본·공유 문서에 포함하지 않는다. tenant와 대상 식별자는 팀 공유 범위에 맞춰 가명화해도 되지만 조인 관계는 유지한다.

## 8. 최신 검증에 필요한 최소 자료

전체 운영 정보를 무작정 요구하기보다 다음 자료로 시작할 수 있다.

1. **수집 설정:** 실제 Fleet/DCGM 필드 설정, KSM 활성 항목, Prometheus scrape·relabel·remote_write, Alloy filter·transform·export 관련 부분.
2. **Mimir 현재 표본:** 대상이 다른 두 노드의 GPU 활동·메모리·전력, Host 지표, 관련 KSM 지표의 라벨과 값. 날짜·원본 샘플 시각 포함.
3. **Loki 원본:** 알려진 Fleet 상태 또는 사건의 저장된 전체 필드와 원본 대비 보존 여부. 실제 오류가 없으면 상태 표본과 사건 경로의 미검증을 구분.
4. **관계 표본:** GPU UUID↔Node, Pod UID↔Node↔owner. 장치↔Pod 연결이 있다면 별도 레코드와 유효 시각.
5. **기간 표본:** 의도한 보고 기간에 대한 시계열·관계 이력의 시작·끝·결측. 현재 한 번 조회된 것을 기간 지원으로 확대하지 않음.

이 검증은 개발 구현과 다른 읽기·설계 확인 작업이다. 정상 표본이 확보돼도 필요한 기능이 비활성화돼 있거나 필드가 중간에서 제거됐다면, 그 항목은 설계 변경 대상으로 기록한다.

## 9. 이번 수정 결과

- 이전 업무 문서 상단에 ‘현재 수집 검증 완료 명세가 아님’을 명시했다.
- GPU·KSM·이벤트를 기본 보유 데이터처럼 읽을 수 있는 표현을 후보·미확인으로 수정했다.
- profiling 계열 과거 기록을 반영해 SM을 단순히 미수집·불가능으로 분류하지 않도록 했다.
- 별도 장치 연결과 과거 이력의 확보 여부는 여전히 미확인으로 남겼다.
- 최신 입력을 확보하기 전에는 확정된 현재 지원 목록을 새로 선언하지 않는다.

현재 명확히 말할 수 있는 것은 **과거 GPU 온도·일부 메트릭 계열의 수신 기록과 로컬 수집 기록이 존재한다는 점**, 그리고 **현재 기능 매핑을 확정할 최신 필드·라벨·이력 근거는 아직 부족하다는 점**이다.
