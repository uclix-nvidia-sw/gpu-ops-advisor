**DSX GPU 운영 지원 Agent — 목적과 전체 동작 흐름**

작성일: 2026-09-14  
공유 목적: 왜 이 서비스를 구축하고, 어떤 지식을 준비하며, 두 Agent가 어떻게 분석과 추천을 수행하는지 설명한다.  
상태: 논의 결과에 따른 설계 방향. 구현·배포·실환경 검증 완료를 의미하지 않는다.

**1. 무엇을 하려는가**

GPU 인프라의 지표와 로그를 활용해 운영자의 두 가지 판단을 지원한다.

- **RCA Agent:** 장애 원인과 대응 방법을 찾는다. 알려진 오류는 Runbook으로 대응하고, 명확한 원인이 없으면 특정 범위의 로그·지표를 조사해 유력한 원인과 해결 방향을 추천한다.
- **운영 관찰·추천 Agent:** 일정 기간의 운영 상태를 분석해 개선 대상과 운영 방안을 추천한다. 이용·점유·배치·전력·반복 장애를 함께 살핀다.

두 Agent는 Knowledge Base, 조회·집계 도구, Local LLM을 공유한다. 운영자는 분석 근거와 권고를 확인하고 실제 조치를 수행한다.

**2. 전체 흐름**

```text
[지식 준비]
NVIDIA 공식 문서 · GPUd/Fleet 코드 · 내부 운영 지침
                     ↓ 추출·정리·검증
Runbook / 조사·분석 절차 / 정책 / 데이터 사전 / 참고 문서
                     ↓ 버전을 지정해 사용 가능 상태로 발행
                공통 Knowledge Base
                     ↓ 두 Agent가 사용

[서비스 실행]
장애 알림·조사 요청                     정기 분석·운영 질의
        ↓                                      ↓
    RCA Agent                         운영 관찰·추천 Agent
        ↓                                      ↓
사건·장비·시간 범위 결정                  대상·기간·분석 주제 결정
        ↓                                      ↓
Runbook 또는 조사 절차 선택              분석 절차·운영 정책 선택
        └─────────────────┬────────────────────┘
                          ↓
                 공통 조회·집계 도구
         Mimir 지표 / Loki 로그 / Incident·운영 이력
                          ↓
             수치 계산·조건 판정 + Local LLM 해석
                          ↓
           RCA 결과 또는 운영 개선 추천·보고서 저장
                          ↓
                 GUI에서 근거와 권고 확인
                          ↓
                운영자 조치·실제 결과 기록
                          ↓
             검증된 결과를 사례·지식 개정에 반영
```

이 그림은 논리적인 실행 흐름이다. 한 Agent가 모든 데이터를 한 번에 읽는 방식이 아니라, 선택한 절차에 필요한 범위부터 조회하고 부족한 증거를 추가 수집한다.

**3. 먼저 지식을 어떻게 준비하는가**

| 순서 | 하는 일 | 만들어지는 결과 |
|---|---|---|
| ① 출처 확보 | NVIDIA 공식 문서, GPUd·Fleet 코드, 내부 운영 지침의 버전과 원문 위치 확보 | 추적 가능한 원천 자료 |
| ② 용도별 정리 | 오류 대응, 조사 순서, 운영 기준, 데이터 설명으로 구분 | Runbook·절차·정책·참고 문서 초안 |
| ③ 실제 데이터 연결 | 필요한 지표·로그를 실제 메트릭명·라벨·조회 함수에 연결 | 실행 가능한 조회 정의와 데이터 사전 |
| ④ 적용 조건 검증 | 장비·소프트웨어 버전, 필요한 증거, 예외, 지원 여부 확인 | 적용 가능한 지식과 미지원·미확인 항목 구분 |
| ⑤ 버전 발행 | 사용할 지식·절차·정책의 버전을 고정 | 두 Agent가 사용할 공통 KB |

GPUd·Fleet 코드는 감지·판정·권고 로직의 근거로 사용한다. 공식 문서는 오류 의미와 상세 진단 절차를 보완한다. 운영 임계값·예외·권고 조건은 내부 운영 기준으로 정리한다.

공개 소스에 기능이 존재하는 것과 현재 환경에서 관련 증거를 수집하는 것은 구분한다. Fleet와 GPUd의 동일 계열 로직은 출처 관계를 보존하고 중복된 내용을 독립적인 근거로 계산하지 않는다.

**4. 준비한 지식은 어디에 두는가**

| 구분 | 저장·구현 위치 | 실행 중 쓰이는 시점 |
|---|---|---|
| Runbook | PostgreSQL | 오류·장비·버전·상태 조건에 맞는 대응을 찾을 때 |
| 조사·분석 절차 | Git의 YAML + 실행 코드 | 무엇부터 조회하고 다음에 무엇을 확인할지 정할 때 |
| 판단 기준·운영 정책 | PostgreSQL의 버전별 설정 | 계산 결과를 임계값·예외·권고 조건과 비교할 때 |
| 데이터 사전·조회 도구 | Git의 설정 파일 + 실행 코드 | 지표·로그를 조회하고 단위·식별자·기간을 맞출 때 |
| 기술·운영 참고 문서 | Git의 Markdown + PostgreSQL 검색 인덱스 | 원인과 운영 맥락을 해석할 근거가 필요할 때 |
| 분석 결과·검증 사례 | PostgreSQL | 과거 장애·권고·처리 결과를 확인하거나 재사용할 때 |

절차 YAML은 순서·분기·종료 조건을 정의하고 서버에 등록된 함수가 실행한다. 계산 방법은 코드로, 운영자가 정하는 임계값·기간·예외는 정책 DB로 관리한다. 정책을 정한 이유와 상세 설명은 문서에 연결한다.

Runbook과 정책은 PostgreSQL의 발행 버전을 기준으로 사용한다. 절차·문서·조회 정의는 Git 버전을 기준으로 사용하며 문서 검색 인덱스는 원문에서 재생성할 수 있게 한다. 각 모듈은 논리적 구분이며 별도 서비스로 나눠 배포할 필요는 없다.

**5. RCA Agent는 어떻게 동작하는가**

```text
장애 알림 또는 사용자 조사 요청
        ↓
사건 정리: 장비·발생 시각·증상·오류 코드 식별
        ↓
Runbook 검색 + 장비·버전·상태 조건 확인
        ↓
조건에 맞는 대응이 있는가?
        ├─ 있음 → 필요한 증거 조회 → 조건 충족 확인
        │                              ↓
        │                        근거가 있는 조치 권고
        │
        └─ 없음 / 조건 미확인 / 증거 불일치
                 ↓
          증상에 맞는 조사 절차 선택
                 ↓
          특정 범위의 로그·관련 지표 조회
                 ↓
          LLM이 사건 순서와 원인 후보 분석
                 ↓
          부족한 증거를 제한된 횟수·범위에서 추가 조회
                 ↓
          유력한 원인·해결 방향·다음 확인 사항 추천
        ↓
원인 또는 후보, 근거, 권고, 한계와 사용 버전 저장
```

알림은 구조도의 Incident Aggregator에서 중복·반복 상태를 정리한 뒤 RCA 실행과 연결한다. 사용자 요청은 AI Service에서 조사 대상과 시간을 해석해 전달한다.

Xid·SXid도 일부 오류는 원인 후보가 여러 개이므로 코드 식별과 원인 확정을 구분한다. 알려진 오류 역시 필요한 지표·로그를 확인한 뒤 해당 Runbook을 적용한다.

원인 불명 조사에서는 확인된 사실, 가장 유력한 후보, 이를 지지·반박하는 증거, 부족한 정보를 함께 제시한다. 조사 한도에 도달하거나 증거를 확보할 수 없으면 그 상태와 다음 확인 절차를 남긴다.

**6. 운영 관찰·추천 Agent는 어떻게 동작하는가**

```text
정기 실행 또는 사용자 운영 질의
        ↓
대상·기간·분석 주제 결정
        ↓
분석 절차 + 적용할 정책 선택
        ↓
관측 품질과 필수 데이터 확인
        ↓
공통 도구로 기간별 조회·집계·비교
        ↓
임계값·예외·작업 조건을 적용해 검토 대상 선정
        ↓
관련 장애 이력·운영 지침·검증 사례 확인
        ↓
LLM이 사실과 운영 맥락을 해석해 개선 방안 작성
        ↓
권고 대상·우선순위·근거·적용 조건을 보고서로 저장
```

예를 들어 장시간 저활동이 관찰되면 예약·점유 상태와 작업 특성을 추가 확인한다. 필요한 정보가 부족하면 자원 회수 가능성을 확정하지 않고 점유 유지 필요성을 확인할 대상으로 제시한다.

반복 장애가 특정 GPU에 집중되면 RCA 이력을 연결해 예방 점검 우선순위를 제안한다. 기간 비교에서는 장비 종류·대상 수·관측 누락·작업량 변화 등 비교 조건을 확인한다.

수치 계산과 명시적인 정책 판정은 프로그램이 수행한다. LLM은 검증된 수치와 관련 지식을 연결해 해석·권고를 작성한다.

**7. 결과가 어떻게 다음 분석의 지식이 되는가**

```text
Agent 분석·권고 저장
        ↓
운영자가 근거 검토 후 조치
        ↓
실제 수행 내용과 이후 상태 기록
        ↓
권고의 적합성·효과 확인
        ├─ 미확인 → 분석 이력으로 유지
        └─ 검증됨 → 재사용 가능한 사례로 등록
                         ↓
                필요 시 Runbook·절차·정책 개정
```

원인 후보나 LLM의 설명을 곧바로 확정 지식으로 등록하지 않는다. 실제 결과를 통해 확인한 사례를 재사용하고, 기존 분석이 참조한 지식 버전도 보존한다.

RCA의 확정 원인과 후보 상태는 운영 Agent에 그대로 전달한다. 운영 Agent는 재발 추세와 점검 우선순위 분석에 이를 활용하고, 원인 조사가 필요한 이상은 관련 RCA 조사로 연결할 수 있다.

**8. 분석 근거를 어떻게 보존하는가**

각 실행에는 대상·기간, 실제 조회 조건, 판단에 사용한 핵심 데이터, 적용한 Runbook·절차·정책·문서 버전, 분석·권고와 제한 사항을 남긴다. 모델·실행 버전과 이후 실제 처리 결과도 연결한다.

원시 지표·로그는 기존 Mimir·Loki와 저장 기반에서 보관한다. PostgreSQL에는 사건·분석·보고서와 판단 근거를 저장한다. 원천 보존 기간 이후에도 판단을 설명할 수 있도록 핵심 결과 스냅샷을 남긴다.

두 Agent는 공통 Local LLM과 조회·집계 도구를 사용한다. 실제 운영 변경은 운영자가 수행한다.

**9. 무엇부터 구현하는가**

1. **데이터 연결 확인:** 실제 메트릭·로그·식별자·기간 조회를 확인한다.
2. **세 가지 흐름 구체화:** 알려진 오류 대응, 원인 불명 조사, 운영 개선 분석 각각에 입력·절차·증거·출력을 정의한다.
3. **최소 지식 구성:** 대표 Runbook, 조사·분석 YAML, 정책, 참고 문서를 작성하고 조회 함수와 연결한다.
4. **처음부터 끝까지 실행:** 두 Agent에서 요청 수신 → 조회 → 분석 → 추천 → 근거 저장까지 연결한다.
5. **사례 평가 후 확대:** 정답이 알려진 사례와 데이터 누락·상충 사례로 평가한 뒤 지원 항목을 늘린다.

현재 정리한 것은 두 Agent의 역할과 모듈별 구성 방향이다. 실제 메트릭명·라벨, 초기 지원 목록, 정책값·예외, 조회 한도, 모델·서빙 구성, 보존 기간은 구현 단계에서 확정한다.
