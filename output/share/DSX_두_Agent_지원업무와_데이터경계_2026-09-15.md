# DSX 두 Agent — 지원 업무와 데이터 경계

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-09-15 |
| 목적 | 현재 데이터 범위를 기준으로 두 Agent가 제공할 결과와 제공하지 않을 결과를 확정하기 위한 초안 |
| 대상 | GPU Node RCA Agent, 최적화 운영보고서 Agent |
| 현재 단계 | 구조·기능 설계. 개발·배포·클러스터 조회를 수행한 결과가 아님 |
| 주요 전제 | GPU·Node 관측과 KSM 객체 정보를 활용한다. 공유 노드의 GPU↔Pod 장치 연결은 확보된 것으로 가정하지 않는다. |

> **2026-09-15 최신 정정:** 이 문서는 업무 설계 후보 목록이며, 현재 활성화할 범위는 [CPC 공통 수집 환경과 Agent 업무](<DSX_CPC_공통수집환경과_Agent업무_2026-09-15.md>)를 우선한다. 사용자 확인에 따라 CPC-1·CPC-2는 동일한 수집·연동 환경을 사용하며 CSC에서 양쪽 데이터를 조회할 환경이 구축된 것으로 본다. CPC-2의 중앙 수신·노드 식별·KSM 세 종류·정상 로그와 테스트 GPU↔Pod 원본 매핑은 개별 검증 표본으로 보존한다. 중앙 장치 매핑·pod_uid 보완은 미완료이며, GPU 요청 시계열은 첨부 조회 시점에 0건이었다. GPU 활동률·소비전력·장기 이력은 이번 표본만으로 확정하지 않는다. 아래의 일반 기능 목록은 이 최신 판정에 따라 제한해서 읽는다.

## 1. 결정할 방향

**목표 역할은 다음과 같다. RCA Agent는 노드·장비 사건의 근거를 모아 원인 후보와 다음 점검·대응을 제안한다. 운영보고서 Agent는 기간별 자원 활동·할당·장애를 비교해 운영자가 검토할 대상과 이유를 제시한다. 실제 활성화할 업무는 데이터 근거 대조 후 확정한다.**

설계상 두 Agent의 공통 분석 중심은 **CPC·노드·식별 가능한 GPU**다. 이 수준의 집계도 실제 식별 라벨·관계와 기간 조회가 확인돼야 한다. KSM의 필요한 필드·이력이 확보되면 Namespace·Workload의 요청·배치 상태를 연결할 수 있지만, 이것을 특정 GPU의 실제 사용량으로 바꾸지는 않는다.

두 가지 축을 구분한다.

- **지원 범위:** 이 업무를 Agent가 수행하도록 설계할 것인가?
- **실행 가능 상태:** 이번 대상·기간에 필요한 데이터가 실제로 존재하는가?

아래의 기본 지원은 첫 번째 의미다. 필요한 항목이 실제 조회에서 없으면 해당 실행은 정보 부족으로 반환한다. 이 문서는 모든 메트릭·라벨의 실환경 수집을 새로 확인했다는 뜻이 아니다.

## 2. 입력 데이터의 범위

| 데이터 묶음 | 이 문서에서의 취급 | 할 수 있는 해석 | 확인할 조건 |
|---|---|---|---|
| GPU 활동·VRAM 점유 | CPC-2 VRAM 필드·식별 라벨 확인. 활동률 표본은 이번 목록에서 미확인 | GPU별·노드별 활동과 메모리 점유 추세 | 각 필드 값·단위·기간 확인. VRAM을 활동률로 대체하지 않음 |
| GPU 온도·전력·오류 상태 | 수집된 항목만 사용 | 열·전력·오류 변화의 동시 발생, GPU 에너지 패턴 | 모델별 지원과 필드, 센서 오류, 수집 기간 |
| Fleet 상태·Xid/SXid·기타 이벤트 | CPC-2 Loki 경로와 정상 상태 로그 수신 확인. 개별 오류 스키마는 별도 | 알려진 사건 분류, 시점·대상·공급자 권고 확인 | component·event_name·코드·배포 버전·오류 원문 필드 |
| CPU·메모리·디스크·네트워크 등 Host 관측 | 실제 존재하는 항목만 사용 | GPU 증상과 동반된 호스트 현상 | 노드 귀속, 시각, 필요한 세부 지표 수집 여부 |
| KSM의 Node·Pod·Namespace·owner·자원 요청 | CPC-2 node_status_condition·pod_info·container_resource_requests 세 종류 중앙 수집 확인 | 실제 필드 범위의 Node 상태·Pod 배치·resource 요청 | GPU 요청은 첨부 시점 0건. 추가 owner·재시작·과거 이력까지 확정하지 않음 |
| NodePool·프로젝트·팀 매핑 | 추가 조건 데이터 | 노드풀 또는 프로젝트 범위의 집계 | 명시적 라벨·자산 매핑과 당시 유효 범위 |
| Incident·RCA 이력 | 서비스에 축적할 파생 데이터 | 중복 제거된 사건 수, 재발·점검 이력 | 아직 이력이 없으면 로그 패턴 수준으로 제한 |
| GPU↔Pod/Container 연결 | CPC-2 테스트의 Exporter 원본·Fleet UUID 일치 확인. 중앙 활용은 미완료 | 중앙 경로 완성 후 특정 GPU를 할당받은 워크로드 연결 | Prometheus→Mimir 적재·join, 빈 pod_uid 보완, 유효 시각, MIG·공유 방식 |
| SM·Tensor·메모리 활동 세부 프로파일 | profiling 계열의 과거 수집 기록은 있음. 정확한 필드·현재 값은 미확인 | 실제 수집 시 GPU 내부 활동 세분화 | GPU 지원·필드 의미·프로파일 수집 여부 |
| 요청량·처리량·지연·학습 진행·작업 목적 | 기본 보유 데이터로 가정하지 않음 | 성능·서비스 효율·정체 원인 판단 | 애플리케이션 계측·로그·예약 정책 |

KSM 설치 자체가 표의 모든 항목 수집을 보장하지 않는다. 특히 현재 관계만 있는지, 분석 기간의 과거 관계까지 조회되는지가 중요하다. NodePool과 프로젝트는 Node 이름만으로 추정하지 않는다.

## 3. 데이터가 연결되는 범위

```text
GPU 활동·오류 ── GPU UUID / Node / 시각 ──┐
                                         ├─ 같은 노드·시간 범위의 상관관계
Pod 요청·상태 ── Pod UID / Node / 시각 ───┘
       │
       └─ Namespace → Workload → 명시적인 프로젝트·팀 매핑

추가로 필요한 연결:
특정 GPU 또는 MIG 인스턴스 ↔ Pod/Container ↔ 해당 연결의 유효 시각
```

노드 연결만 있으면 “GPU 오류 시점에 이 노드에 배치되어 있던 GPU 요청 Pod”를 찾을 수 있다. “그 GPU를 사용한 Pod”라고 확정하려면 별도 장치 연결 근거가 필요하다.

GPU↔Pod 연결이 생겨도 그것만으로 오류 유발 주체, 애플리케이션 영향, 실행 병목이 확정되는 것은 아니다. 공유 GPU에서는 장치 수준 활동을 각 프로세스에 분배할 별도 관측이 필요할 수 있다.

## 4. 첨부 표에 대한 수정 의견

| 첨부 표의 업무 | 수정한 판단 | 설명 |
|---|---|---|
| 노드 단위 이용률 추세·유휴 노드 탐지 | 활동 추세와 저활동 후보 탐지 가능 | 저활동과 미할당·회수 가능은 구분. 노드 평균뿐 아니라 GPU별 편차 확인 |
| 노드풀 rightsizing·과다/과소 공급 판정 | 자원 규모 검토 후보와 근거 제시 가능 | 적정 대수 확정은 수요·배치 제약·예비 용량·서비스 조건을 함께 확인해야 함 |
| Incident 잦은 노드와 바쁜 노드 비교 | 가능, 이력·정책 조건 필요 | 사건 중복 제거, 장비 종류·노출 기간, 점검 우선순위 정책 필요 |
| 프로젝트 전용 노드풀의 프로젝트별 효율 | 전용 귀속이 확인된 기간의 자원 활동 집계 가능 | taint/toleration만으로 프로젝트 전용을 확정하지 않음. 업무 성능 효율과 구분 |
| 공유 노드의 특정 GPU 사용 프로젝트 식별 | 현재 지원 제외 | GPU↔Pod와 프로젝트 연결의 시점별 근거가 없음 |
| 공유 노드의 프로젝트별 GPU-hour·chargeback | 측정 대상을 나눠 판단 | 요청량 기준 GPU·시간은 조건부 집계 가능. 실제 활동 귀속·정밀 청구는 추가 데이터·정책 필요 |
| 오류 GPU를 사용한 Workload 식별 | 현재 지원 제외, 노드 동시 배치 후보는 제시 가능 | 후보 명단을 실제 장치 사용자나 오류 원인으로 표시하지 않음 |

Kubernetes의 toleration은 해당 taint를 허용하는 배치 조건이다. 공식 문서도 전용 노드 사용을 위해 label·affinity 등을 함께 설명한다. 프로젝트 전용 귀속에는 운영 정책과 실제 배치 이력을 확인해야 한다. [Kubernetes Taints and Tolerations](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/)

## 5. RCA Agent의 업무

**입력:** Incident, 오류·상태 이벤트, 사용자의 대상·시점·증상 조사 요청.

**출력:** 확인된 사실, 원인 후보, 지지·반박 증거, 추가 점검, 조건부 대응 권고, 조사 한계.

| ID | 수행할 업무 | 필요한 데이터 | 제공할 결과 | 현재 경계 |
|---|---|---|---|---|
| R01 | 알려진 사건 분류와 Runbook 적용 검토 | 원본 이벤트, 코드·배포 계약, 장비 정보, KB | 오류 의미, 적용 조건, 필요한 점검·권고 | 코드 식별은 가능해도 실제 근본 원인은 자동 확정하지 않음 |
| R02 | 사건 전후 노드·GPU 증거 묶기 | 사건 시각, GPU·Host 메트릭, 수집 로그 | 시간 순서, 동반 변화, 근거 링크·발췌 | 동시 발생을 인과관계로 단정하지 않음 |
| R03 | Runbook 미해결 조사 | R02, 증상별 조사 절차, 제한된 조회 도구 | 원인 후보, 배제·미확인 항목, 다음 점검 | 수집하지 않는 앱·통신·I/O 정보는 추론으로 채우지 않음 |
| R04 | 동일 장비의 반복·재발 조사 | 자산 식별, 이벤트·Incident 이력, 수집 품질 | 최초·최근 시각, 재발 양상, 기존 권고·결과 | 로그 줄 수를 사건 수로 표시하지 않음 |
| R05 | 사건과 같은 노드의 Workload 후보 확인 | 사건 시각, 과거 Pod 배치·GPU 요청·owner | 당시 배치된 GPU 요청 Pod·Workload 목록 | 실제 오류 GPU 사용자·원인·피해자로 확정하지 않음 |
| R06 | 사건 당시·현재 장비 관측 비교 | 시점별 인벤토리와 수집 완전성 | GPU 미관측·교체·식별 충돌의 조사 단서 | 수집 실패를 장비 탈락으로 판정하지 않음. 이력 없으면 제한 |
| R07 | 조치 이후 관측 상태 평가 | 운영자 조치 시각, 해당 검사·오류·최신성·정책 | 관측된 회복 조건 충족 여부와 잔여 문제 | 조치가 기록되지 않으면 효과라고 표현하지 않음. 앱 정상까지 확대하지 않음 |

R01~R04는 핵심 지원 업무로 설계한다. R05는 과거 KSM 관계, R06은 인벤토리 이력, R07은 조치·복구 증거가 충족될 때 활성화한다. 로그 원문과 기본 메트릭이 있어도 R02/R03의 모든 세부 원인을 구분할 수 있는 것은 아니다.

### RCA에서 지원하지 않을 결론

| 지원하지 않을 것 | 추가로 필요한 것 |
|---|---|
| “Pod A가 GPU B의 Xid를 일으켰다” | 장치 연결에 더해 프로세스·앱 오류와 인과를 뒷받침할 증거 |
| “공유 노드의 GPU B는 프로젝트 A가 사용했다” | 시점별 장치 할당·사용 연결과 프로젝트 매핑 |
| “이 오류 때문에 서비스 지연이 증가했다” | 서비스 지표, 요청·오류·배치 연결과 시간 순서 |
| “낮은 활동의 원인은 NCCL·스토리지 병목이다” | 해당 통신·입출력·프로파일 증거 |
| “특정 부품이 고장났으므로 교체가 확정이다” | 해당 모델의 진단 기준과 실제 진단·벤더 확인 |

Agent는 가능성을 제시할 수 있으나, 위 문장을 확정 사실로 쓰지 않는다. 재부팅·리셋·재배치·드라이버 변경을 직접 수행하는 일은 데이터 추가 여부와 무관하게 현재 제품 범위 밖이다.

## 6. 운영보고서 Agent의 업무

**입력:** 대상 범위, 분석 기간, 비교 기간, 분석 주제·정책.

**출력:** 관측된 패턴, 검토 대상, 우선순위의 근거, 운영자가 확인할 조건, 권고와 한계.

기존 T01~T10 주제 ID를 유지하되 결과 표현의 경계를 명확하게 한다.

| ID | 수행할 업무 | 필요 데이터 | 제공할 인사이트 | 현재 경계 |
|---|---|---|---|---|
| T01 | 노드·GPU·CPC의 저활동 구간 탐지 | 활동, VRAM, 대상·시각, 관측 품질 | 반복 저활동 노드·시간대, 운영 확인 대상 | “빈 GPU”, “회수 가능”을 활동만으로 확정하지 않음 |
| T02 | 노드의 GPU 요청·할당과 활동 비교 | T01, KSM 요청·배치·생명주기 | GPU 요청이 배치돼 있으나 노드 전체가 저활동인 구간 | 특정 Pod에 노드 활동을 배분하지 않음 |
| T03 | 저활동 자원의 배치 제약 확인 | Node 상태·allocatable·taint·배치 상태 | 가용 자원으로 쓰기 어려운 노드와 확인할 조건 | 정확한 미배치 원인은 상세 조건·실패 사유가 있어야 설명 |
| T04 | 동일 집단의 기간별 변화 비교 | 비교 가능한 기간의 T01 및 관계·대상 변화 | 활동·요청·전력 변화와 동반 현상 | 작업량·SLO 없이 성능·효율 개선으로 단정하지 않음 |
| T05 | 반복 장애와 활동·점유를 함께 비교 | 정규화 사건 또는 명시된 로그 반복, 활동, 정책 | 예방 점검 우선 대상, 정비 일정 검토 근거 | 사건 수와 활동은 따로 제시. 높은 활동을 업무 중요도로 대체하지 않음 |
| T06 | Namespace·Workload별 요청·배치 패턴 | KSM 요청·Pod UID·owner·시점 이력 | 장기 요청 유지, 시간대별 요청량, 요청량 기준 GPU·시간 | 실제 GPU 활동·전력의 Workload 귀속은 지원하지 않음 |
| T07 | 노드 내부 GPU별 활동 편차 | GPU별 활동·VRAM·동일 종류·유효 시각 | 평균에 가려진 장치별 편차와 배치 점검 대상 | 같은 작업에 참여했는지 모르면 분산학습 불균형으로 확정하지 않음 |
| T08 | 높은 활동과 GPU 요청 미배치의 동시 발생 | 활동, 요청·미배치 이력, 장비 종류·배치 조건 | 수요 집중·자원 규모 검토 후보 | Pending 전체를 GPU 부족으로 보지 않음. 증설 대수 확정 제외 |
| T09 | 저활동 구간의 GPU 전력·에너지 패턴 | 전력 또는 누적 에너지, 활동·시각·단위 | 시간대별 GPU 에너지와 저활동 구간 소비 | 서버·냉각 전체 전력이나 회수 가능한 절감량으로 확대하지 않음 |
| T10 | 관측 누락·신선도·분석 범위 확인 | 기대 대상 목록, 수집 상태·샘플 시각 | 누락 대상·구간, 분석 가능 범위, 보류 이유 | 데이터 없음과 이상 없음 구분 |

T10을 모든 분석의 선행 검사로 사용한다. T01·T07은 기본 GPU 데이터로 시작할 핵심 주제다. T02·T03·T06·T08은 필요한 KSM 이력, T04는 비교 기간, T05는 사건 이력, T09는 전력 필드가 충족될 때 지원한다. 이는 구현 순서를 강제하는 것이 아니라 데이터 의존성을 정의한 것이다.

### 전용 노드풀의 프로젝트 분석

추가로 프로젝트가 전용으로 사용하는 노드풀임을 확인하면 T01·T04·T05·T09를 그 프로젝트에 연결해 집계할 수 있다. 다음 조건이 필요하다.

1. 프로젝트↔NodePool↔Node의 명시적 연결과 분석 기간의 변경 이력.
2. 해당 기간에 다른 프로젝트의 GPU 사용이 섞이지 않았다는 근거 또는 명시된 비용 귀속 정책.
3. 프로젝트의 다른 공유 노드 사용까지 포함하는지 등 집계 범위 정의.

그 결과는 “프로젝트 A 전용 자원의 활동률”이다. 처리량·지연·산출물이 없으면 “프로젝트 A의 업무 효율”이라고 부르지 않는다.

## 7. GPU·시간과 비용 집계는 네 가지로 구분

| 집계 | 의미 | GPU↔Pod 장치 연결 | 현재 지원 판단 |
|---|---|---|---|
| 요청량 기준 GPU·시간 | 선택한 Pod의 실효 GPU 요청 수 × 대상 시간 | 특정 UUID 연결은 필수 아님 | KSM 요청·생명주기·배치 이력이 있으면 관측 기반 집계 가능 |
| 할당량 기준 GPU·시간 | 실제로 배정된 GPU 자원량 × 할당 기간 | 배정 수·할당 이력이 필요. 모든 경우 UUID가 필수인 것은 아님 | 실제 할당 기록과 계량 정의가 있어야 지원 |
| GPU 활동 시간의 Workload 귀속 | 장치의 활동을 특정 사용자·작업에 연결 | 독점·공유 의미를 포함한 시점별 연결 필요 | 현재 지원 제외. 공유 방식에 따라 프로세스 계측도 필요 |
| 비용 배분·청구 | 정책에 따라 자원량·시간·가격을 비용으로 환산 | 청구 기준에 따라 달라짐 | 정밀 청구는 초기 범위 제외. 요청·예약 기반 참고 비용은 가격·정책·품질 확인 후 별도 기능 |

예: Pod가 GPU 2개를 요청하고 노드에 배치된 상태로 3시간 관측됐다면 **배치된 요청량 기준 6 GPU·시간**으로 집계할 수 있다. 이것은 6시간 동안 실제 연산했다는 뜻이 아니다.

미배치 요청 대기 시간은 별도로 집계한다. scrape 사이에 생성·종료한 Pod, 샘플 누락, init/sidecar의 실효 요청, GPU 종류·MIG·시간 공유의 resource 단위를 처리해야 한다. KSM 공식 문서는 자원 요청 메트릭을 설명하면서 더 정밀한 실효 요청에는 scheduler 메트릭을 권장한다. [KSM Pod Metrics](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/metrics/workload/pod-metrics.md)

따라서 첨부 표의 “공유 노드의 프로젝트별 GPU-hour는 불가능”은 넓은 표현이다. **어떤 GPU-hour인지 먼저 정의해야 한다.** 현재는 요청량 기반 운영 통계까지, 실제 활동 귀속과 정밀 청구는 제외하는 범위가 적절하다.

## 8. 서로 다른 네 가지 예시

아래 수치는 설명용 가상 사례이며 실환경 결과가 아니다.

### 사례 A — 공유 노드에서 GPU 하나만 바쁨

입력: 8개 GPU 중 하나가 고활동, 다른 7개는 저활동. 같은 노드에 프로젝트 A/B의 GPU 요청 Pod가 존재. 장치 연결 없음.

- 운영보고서: GPU별 편차와 요청 Pod 목록을 별도로 보여주고 배치 확인을 제안한다.
- RCA: 오류가 함께 있으면 사건 전후 해당 GPU와 노드의 증거를 조사한다.
- 제공하지 않는 결론: A가 바쁜 GPU를 쓰고 B가 나머지 GPU를 낭비한다.

### 사례 B — GPU 요청은 배치됐으나 모든 GPU가 저활동

입력: 노드의 배치된 GPU 요청량 8개, 모든 GPU가 2시간 저활동. 애플리케이션 요청량·작업 목적은 없음.

- 운영보고서: 요청 유지와 저활동이 겹친 구간을 제시하고 대기·예약·작업 진행 상태 확인을 권고한다.
- RCA: 수집된 오류·재시작·호스트 지표에서 정체를 설명할 단서를 조사한다.
- 제공하지 않는 결론: GPU 8개를 즉시 회수할 수 있다. 또는 낮은 활동의 원인이 입출력 병목이다.

### 사례 C — Xid 발생 시점에 여러 Workload가 배치됨

입력: GPU G에서 Xid 발생. 그 시점 같은 노드에 A/B/C가 배치됐다는 KSM 이력. 장치 연결 없음.

- RCA: GPU G 사건과 당시 GPU 요청 Workload 후보 A/B/C를 구분해 표시한다.
- 운영보고서: 이후 같은 GPU·노드의 사건 반복을 집계해 예방 점검 후보로 연결한다.
- 제공하지 않는 결론: B가 GPU G를 사용했고 오류를 일으켰다. A/B/C가 모두 영향을 받았다.

### 사례 D — 반복 저활동 전용 노드풀

입력: 프로젝트 A 전용임이 확인된 동일 종류 노드 4개가 한 주 동안 반복 저활동. 향후 예약·피크 수요·SLO 정보 없음.

- 운영보고서: 프로젝트 A 전용 자원의 활동 분포와 요청 패턴을 제시하고 예약·자원 규모 검토를 권고한다.
- 제공하지 않는 결론: 노드를 4개에서 2개로 줄여도 서비스가 안전하다.

## 9. 두 Agent의 역할 연결

```text
사건 또는 특정 증상                  기간별 운영 분석
         ↓                                ↓
     RCA Agent                       운영보고서 Agent
         ↓                                ↓
이 사건의 원인 후보·증거             어디를 우선 검토할지·왜 그런지
         │                                │
         └─ 사건·분석 이력 공유 ───────────┘

운영보고서가 이상 패턴을 발견하면
  → 관련 사건을 연결하거나 별도 RCA 조사 대상으로 제시
RCA 결과가 있으면
  → 운영보고서가 재발·점검 우선순위 분석에 활용
```

운영보고서가 의심 패턴을 찾았다는 이유로 확정 장애를 새로 만들어 사건 수를 늘리지 않는다. 두 Agent는 증거·지식을 공유하고 서로 다른 목적의 결과를 낸다.

단순 수치 집계는 공통 도구가 담당한다. LLM은 검증된 사실과 KB를 연결해 원인 후보·맥락·다음 확인 사항을 설명한다. 출력 목적이 수치 하나라면 LLM 추론이 필요하지 않을 수도 있다.

## 10. 기능별 데이터 계약

각 Job은 구현 전에 다음 한 장의 계약을 갖도록 한다. 별도 서비스나 범용 엔진을 요구하는 것은 아니다.

```text
job_id / 담당 Agent / 목적
허용 분석 단위: GPU, Node, CPC, Namespace, Workload, 프로젝트
입력 대상·기간
필수 데이터와 선택 데이터
필수 식별 연결·관측 품질
계산·판정 정의와 정책 버전
제공할 결과·제공하지 않을 결론
데이터 부족 시 축소할 범위 또는 종료 이유
증거·조회·KB 버전의 저장 항목
```

예를 들어 T06의 기본 지원은 Workload별 요청량 패턴이고, 실제 GPU 활동의 Workload 귀속은 별도 미지원 항목이다. 사용자가 후자를 물으면 전체 보고서를 실패시키기보다 가능한 요청량 통계를 제시하되 질문한 실제 활동은 산출하지 못한다고 명시한다.

실행 결과는 다음 상태를 구분한다.

| 상태 | 의미 |
|---|---|
| completed | 필요한 데이터를 확보하고 분석함. 발견 사항이 없을 수도 있음 |
| partial | 일부 대상·기간 또는 일부 근거가 부족한 범위에서 분석 |
| insufficient_data | 지원하는 업무지만 이번 입력의 필수 데이터가 부족 |
| unsupported | 현재 설계상 제공하지 않는 결론·분석 단위 |
| query_failed | 데이터 조회가 실패하여 판단할 수 없음 |

결과에는 대상·기간·집계 단위, 관측률, 실제 사실, 해석, 권고, 제한, 근거 ID를 포함한다. 불확실한 장치 귀속을 임의 확률이나 균등 분배로 채우지 않는다.

## 11. 추가 데이터가 들어왔을 때 열리는 기능

| 추가 데이터 | 가능해지는 일 | 여전히 별도 근거가 필요한 일 |
|---|---|---|
| GPU↔Pod/Container의 시점별 연결 | 오류 장치를 할당받은 Workload, 독점 할당 구간의 장치 활동 연결 | 오류 유발 주체·앱 피해, 공유 프로세스별 활동 분배 |
| 실제 스케줄링 실패 사유·제약 | 자원 부족·제약 충돌의 구체적 분류 | 미래 수요를 포함한 적정 대수 확정 |
| 앱 요청량·처리량·지연·작업 진행 | 대기와 정체 구별, 업무 성능과 자원 활동 비교 | 변경 후 개선 효과의 보장 |
| 세부 GPU·통신·입출력 프로파일 | 병목 후보 구분과 추가 최적화 실험 제안 | 실험 없이 최적 파라미터 확정 |
| 예약·SLO·예비 용량·수요 계획 | 자원 규모 변경의 조건·시나리오 분석 | 미래 서비스 품질의 무조건 보장 |
| 정확한 할당 계량·가격·배분 정책 | 정책 기준의 비용 집계·청구 검증 | 전력 사용량이나 GPU 활동만으로 모든 비용 귀속 |

수집 확대의 우선순위는 제공하려는 업무로 정한다. 특정 Workload의 GPU 사용을 꼭 알아야 한다면 장치 연결이 우선이고, 노드풀 규모 검토가 우선이면 수요·배치 제약·예비 용량 정보가 더 중요할 수 있다.

## 12. 이번에 합의할 범위

1. **RCA의 기본 범위:** 노드·식별 가능한 GPU의 사건 조사와 근거 있는 원인 후보·점검·대응 권고.
2. **운영보고서의 기본 범위:** 노드·GPU 활동, 기간 변화, 요청·배치, 반복 사건, 전력·관측 품질을 활용한 검토 대상 선정.
3. **Kubernetes 관계의 범위:** Node와 Pod·Workload의 동시점 관계 및 요청량을 분석한다. 장치 매핑이 없는 실제 GPU 사용량 귀속은 제외한다.
4. **프로젝트 분석:** 전용 자원 귀속이 확인되면 자원 활동 집계, 공유 자원에서는 요청량 기반 통계까지 제공한다.
5. **현재 제외:** 확정적인 노드 축소·증설 대수, 정밀 사용량 청구, 공유 GPU의 작업별 실제 활동 귀속, 근거 없는 병목·오류 원인 확정.
6. **직접 조치 제외:** 리셋·재부팅·재배치·확장·축소는 운영자가 판단·수행한다.

이 범위를 먼저 정한 뒤 각 Job에 필요한 KB·정책·조회 계약을 설계한다. KB의 크기나 LLM 모델의 성능으로 없는 관측 연결을 대체하지 않는다.

## 13. 자료와 확인 범위

- 사용자 첨부 표: Pod↔GPU 매핑 필요 여부와 노드·프로젝트 분석 가능성에 대한 비교 자료. 본 문서는 그 판단을 세분화했다.
- 내부 문서: `GPU_운영보고서_Agent_분석주제와_구현안_v0.1.md`의 T01~T10, DSX KB v2.0 및 구조 검토 의견.
- [Kubernetes Taints and Tolerations](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/): toleration과 전용 노드 배치 조건의 의미. 2026-09-15 확인.
- [KSM Pod Metrics](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/metrics/workload/pod-metrics.md): Pod UID·요청·상태 메트릭과 실효 자원 요청 관련 안내. 공개 정의이며 현재 환경의 노출 여부는 별도 확인.
- [NVML utilization 정의](https://docs.nvidia.com/deploy/nvml-api/api/structnvmlUtilization__t.html): GPU utilization은 샘플 구간에 커널이 실행된 시간 비율이며 memory utilization은 메모리 읽기·쓰기 활동 시간 비율이다. 메모리 용량 점유와 구분한다. 2026-09-15 확인.

실환경에서 사용 가능한 정확한 메트릭 목록·라벨·과거 보존 기간·관계 이력은 본 작성에서 직접 조회하지 않았다. 이를 확보하면 §2의 데이터 항목과 Job별 필수 조건을 대조해 대상·기간별 지원 상태를 확정한다.
