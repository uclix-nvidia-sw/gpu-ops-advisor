1. 사용자의 최신 명시적 결정으로 목표 구조를 정한다. 과거 생성 이미지와 assistant 제안이 이 결정을 덮어쓰지 않는다.
2. 설치·설정·수집·저장·조회·분석 완료를 각각 구분한다. 소스나 Running Pod가 있다는 것만으로 전체 연동 성공을 확정하지 않는다.
3. 9월 8일 초기 통합 문서와 9월 9~10일 대화의 상태가 다르면 대상 환경과 시점을 확인한다. 서로 다른 CPC/실험 환경을 한 클러스터의 변경 이력처럼 합치지 않는다.
4. 대화에 포함된 시험 주입 이벤트는 실제 하드웨어 장애로 기록하지 않는다. 제안한 해결 명령은 적용 완료로 승격하지 않는다.

| Aggregator | 규칙 기반 식별·중복·재전송·flap 처리. 세 번째 LLM Agent가 아님 | 두 Agent 제약과 반복 이벤트 분석 |
| Incident DB | 장애 식별·발생/최초/최근 시각·상태·근거·분석 시각/버전·권고 보존 | 사용자 DB 추적 요구, 이벤트 관련 세션 |
| Fleet 로컬 SQLite | Fleet 내부 상태 파일. 중앙 Incident DB와 구분하고 직접 AI 조회 경로로 추가하지 않음 | SQLite 상태 DB 조회 |
| RCCA 범위 | GPU/device 및 Node의 관측 근거로 원인 가설·대응 권고 작성 | 시나리오 및 구성도 제안, 수정 표 |
| 보고서 초기 범위 | GPU 이용률·메모리·전력 추세와 반복 장애/운영 이력 | 인사이트 주제 제안, DSX 에이전트 서비스 정리 |
| K8s 최적화 | 요청량·배치 수집 경로 미확정. Pod GPU 실사용은 별도 allocation 매핑 검증 후 확장 | KSM 지적과 이후 remote_write 삭제 요구의 충돌 |
| Knowledge | NVIDIA 공식 문서와 내부 Runbook 원문 + 검색 인덱스. 벡터 검색은 선택 | 수정 표, 폐쇄망·지식 활용 제안 |
| 사용자 화면 | 대상 CPC·자산·Incident·절대 시간 범위를 유지해 근거와 결과 연결 | 프론트엔드 구성 검토 |

| 내부망 | CPC↔CSC 내부 통신이 허용된 집중형 구조. 내부 LLM/KB는 목표 설계 | 초기 독립형 폐쇄망 제안과 이후 집중형 사용자 결정의 차이 |

## 데이터와 상태를 혼동하지 않기 위한 설계

- `/v1/events`에 같은 이벤트가 재노출되거나 Loki에 같은 이벤트가 반복 저장되어도 새 장애 발생으로 계속 세지 않는다. 원본 event identity, 실제 발생 시각, 대상 자산을 대조한다. fingerprint 정책은 이벤트 유형별로 정해야 한다.
- INFO 로그에도 `component_data.health=Degraded` 같은 상태가 포함될 수 있다. severity만으로 중요한 관측 데이터를 버리는 정책을 전제하지 않는다.
- 로그가 없거나 event 배열이 비어 있다는 것만으로 Healthy를 선언하지 않는다. 알림의 resolved와 Incident의 복구 확인·종료를 구분한다.
- 복구 판단에는 해당 component의 정상 상태, 관련 지표, 데이터 최신성을 함께 사용한다. 사라진 로그는 복구 증거가 아니다.
- GPU UUID가 있는 GPU 지표와 Node identity가 빠진 지표는 영향 범위가 다르다. CPC·Node·GPU 식별 속성의 보존·승격을 확인해야 한다.
- CPC 라벨은 보안 테넌트 격리 자체를 증명하지 않는다. 실제 tenant/auth 설정과 조회 권한 정책은 별도 검증 대상이다.
- Incident는 관측 사실과 분석 이력을 보존한다. 검토되지 않은 분석을 곧바로 확정된 지식으로 승격하지 않는다.
- 보고서는 상대적인 ‘최근 10분’을 계속 재평가하는 화면과 구분한다. 대상·절대 기간·집계 기준·버전을 고정해 재현할 수 있어야 한다.

## 추가 공식 문서 확인

- Mimir는 OTLP로 메트릭을 수신할 수 있다. 따라서 CPC Prometheus remote_write를 추가하지 않아도 OTLP 경로를 목표로 설계할 수 있다. [Grafana Mimir: OTel Collector 구성](https://grafana.com/docs/mimir/latest/configure/configure-otel-collector/)
- Loki Ruler의 규칙 평가와 Alertmanager 전달은 문서화된 연결이다. 이 기능의 존재와 우리 환경에서 설정·검증 완료 여부는 구분한다. [Grafana Loki: Alerting and recording rules](https://grafana.com/docs/loki/latest/alert/)
- kube-state-metrics는 Kubernetes 객체 상태에서 지표를 생성한다. 이를 GPU 장치의 Pod별 실제 사용량 측정 근거로 대체하지 않는다. [Kubernetes: Metrics for Kubernetes Object States](https://kubernetes.io/docs/concepts/cluster-administration/kube-state-metrics/)

## 아직 검증할 항목

1. 목표 Alloy Deployment의 실제 배포·확장·가용성과 각 CPC의 전송 성공. 과거 DaemonSet 설정이 있는 것과 목표 Deployment 적용은 다르다.
2. Gateway의 metric OTLP 및 Loki Push 라우트, label·tenant·인증 정책, 각 CPC 데이터 조회 범위.
3. Ruler → Alertmanager → Aggregator → Incident DB → RCCA 전 구간. Aggregator 재시작·중복 webhook·저장 실패 시 재시도 정책.
4. K8s 요청량·배치 정보의 확정된 수집 경로. Pod별 분석은 실제 GPU↔Pod allocation 매핑과 시각 정합성까지 검증.
5. 내부 LLM·Knowledge 검색·보고서 보존소의 제품 선택과 배포. 폐쇄망 Fleet 등록/provisioning 의존성은 로컬 telemetry 경로와 별도로 검토.
6. 읽지 못한 과거 접힌 메시지·소스 원문에 현재 설계를 바꾸는 결정이 있는지. 그 전까지 이 산출물은 전체 기록의 완전한 전수 검증본으로 부르지 않는다.
