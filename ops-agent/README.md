# Ops Report Agent

Job Controller(JC)에서 보고서 작업을 인수해 관측·사건을 집계하고 결과와 HTML/CSV를 저장합니다. 자동·수동 신규 보고서는 같은 분석 경로를 사용하며, 기존 O계열 요청은 [workflow.py](src/ops_agent/workflow.py)에서 별도로 처리합니다. 기존 보고서·일정을 자동 변환하거나 재작성하지 않습니다.

## 신규 기본 보고서

`report-aggregate-v1`은 일일·주간 `namespace_usage`와 `incident_summary`, 직전 동일 기간 비교를 제공합니다. 쿼리·산식·표본/신원 조건·한도는 [Ops 상세 명세](../docs/specs/ops-agent/aggregate-report-v1.md)가 관리합니다.

| 단계 | 구현과 역할 |
|---|---|
| 수집 | [report_queries.py](src/ops_agent/report_queries.py): 공통 D registry와 별개인 Ops PromQL로 활동·Pod/GPU 신원을 조회합니다. [identity_transitions.py](src/ops_agent/identity_transitions.py)는 모호한 연결 변경 시간대만 추가 검증합니다. [collector_identity.py](src/ops_agent/collector_identity.py)는 동일 Pod·Job의 수집기 교체를 구분하며, 같은 시간에 나뉜 자료는 원본 시각의 비중복을 확인한 경우에만 연결합니다. |
| 계산·근거 | [namespace_usage.py](src/ops_agent/namespace_usage.py)의 유효 표본 합계/개수로 평균을 계산합니다. [report_store.py](src/ops_agent/report_store.py)는 같은 읽기 전용 DB snapshot에서 사건과 공개 RCA ID/hash를 읽으며 새 RCA를 실행하지 않습니다. |
| 보조 관측 | 기본 활동/신원 검증 후 [gpu_memory.py](src/ops_agent/gpu_memory.py)의 GPU당 메모리와 [workload_summary.py](src/ops_agent/workload_summary.py)의 GPU 요청 Pod·완료 Job 근거를 연결합니다. |
| AI 해석 | [report_interpretation.py](src/ops_agent/report_interpretation.py)가 계산된 근거로 두 주제의 설명을 요청하고 검증합니다. 모델이 수치·품질을 계산하지 않습니다. |
| 공개·표시 | 기존 Worker/JC 공개 경로와 웹·HTML을 사용합니다. AI 문장과 계산 요약, 펼쳐 보는 상세 근거를 구분합니다. |

수집 누락·연결 모호성·잘림은 보고서 품질과 근거에 남깁니다. 응답 크기 한도는 프로세스 최대 메모리 보장이 아니며, 과거 큰 snapshot을 변환하는 migration은 없습니다.

### 주제별 AI 운영 해석 / Topic-level AI interpretation

`ops-interpretation-reason-action-v3`의 Namespace 후보는 아래 운영 제안 경로를 사용합니다. 후보·판단·수치·참조는 기존 코드가 결정하고 LLM은 관측의 의미와 판단 이유를 설명합니다. 후보가 없으면 기존 주제별 관측·의미·확인 경로를 유지합니다. 사건 해석의 참조·판단 범위는 유지하며 원인·반복 장애·복구를 확정하지 않습니다.

성공은 `narrative_status=complete`, `quality.report.method=llm_interpreted`로 식별합니다. 입력 상한은 32KB이며 기존 deadline·토큰 예산·최대 두 번의 해석 시도를 유지합니다. 잘못된 JSON 또는 지원되는 문장 오류는 한 번 보완하고 전체 응답을 재검증합니다. 구조·참조가 안전한 응답은 주제 순서에 관계없이 잘못된 Namespace 문장과 사건 주제를 함께 찾아 한 번에 보완합니다. 정상 주제·문장은 원문 그대로 보존하고 합친 전체 응답을 기존 검사로 재검증합니다. 최상위 키가 기대한 주제 ID와 정확히 같고 각 내용이 객체이며 내부 주제 ID가 충돌하지 않는 포장 오류는, 최초 구조 실패를 기록한 뒤 주제 배열로 묶어 기존 검사를 적용합니다. 같은 Namespace 주제의 내용 있는 항목이 별도로 존재할 때만 내용 없는 중복 표시(topic_id와 빈 advice 배열만 있는 객체)를 제거합니다. 정리한 전체 응답이 모든 기존 검사를 통과하면 추가 모델 재작성 없이 같은 원문을 채택하며 attempts는 실제 모델 호출 수를 유지합니다. 내용 오류가 남으면 그 항목만 한 번 보완하고 정상 문장은 보존하므로, 구조 수정 과정에서 정상 수치·길이를 새로 잘못 쓰는 일을 줄입니다. 내용 있는 중복·충돌 주제나 항목/참조를 안전하게 고정할 수 없는 구조·선별 오류는 기존 전체 보완을 사용합니다. 문장의 숫자를 제거하거나 길이를 자르는 자동 교정은 하지 않으며, 총예산·출력 설정·공통 전송 제한과 수치/길이/참조 검사는 유지합니다. 부분 보완은 시간별·비교 구간·판단 조건과 필수 참조를 생략하지 않고 최초 요청과 같은 32KB 상한 안에서 전송하며, 넘으면 계산 요약을 유지합니다. 사건 보완 예시에도 실제로 허용된 대상·기간·수치 참조를 넣어 응답 형식을 안내합니다. 두 번의 시도·최종 의미 검사는 유지합니다. 전송 오류·출력 잘림·예산/마감 소진은 추가 형식 보완을 유발하지 않습니다. 실패 시 계산 결과·요약을 유지하며, 시도별 `quality.report.failures`의 `attempt/reason`과 `Ops interpretation rejected` 로그로 구분합니다. HTTP 실패에는 최종 `http_status`를 저장하고, `namespace_summary_tokens_required`에는 `reference_errors`의 누락·중복된 허용 참조 이름과 사용 불가 참조 개수만 저장합니다. 사용 불가 참조 원문은 저장하지 않으며 과거 보고서에는 이 상세가 없을 수 있습니다. Namespace 최초·부분 보완 입력에는 `observed_values`와 판단 조건을 전달하고, 응답 구조의 `summary`는 판단 설명을 쓰는 빈 자리로 둡니다. 코드가 후보별 대상·기간·수치의 필수 근거를 붙인 뒤 기존 검증을 적용합니다. 원문·민감 예외는 로그에 남기지 않고 원격 종료 미확인·취소는 기존 Worker로 전파합니다.

Nemotron 3.5처럼 `chat_template_kwargs.medium_effort`를 지원하는 모델에서는 Ops Worker에 `OPS_LLM_MEDIUM_EFFORT=true`를 설정해 추론을 유지하면서 중간 수준으로 줄일 수 있습니다. 미설정 또는 `false`는 요청에 이 옵션을 추가하지 않아 서버 기본값을 유지합니다. GUI의 `auto-router` 별칭에도 전달되므로 실제 연결 모델과 LiteLLM의 전달 지원을 먼저 확인해야 합니다. Helm에서는 `components.ops-agent.env.OPS_LLM_MEDIUM_EFFORT: "true"`로 지정합니다. RCA 호출·출력 토큰 한도·후보 선정·참조/의미 검증·최대 한 번 보완은 유지합니다. 같은 저장 자료에서 해석 채택·문장 의미·전체 소요 시간을 확인한 뒤 적용합니다. 추론 완전 끄기는 운영 설정으로 제공하지 않습니다. Namespace에서는 LLM에 관측 현상과 판단 이유만 요청하고, 코드가 확인할 기록·목적과 조건부 제안을 연결합니다. 시간대 후보의 `확인한 뒤` 선행 조건과 `검토`는 최초·부분 보완 모두 같은 코드 행동에 보존하며 모델에게 조건을 채우도록 요구하지 않습니다. 검증 기준과 최대 두 번의 호출은 유지하고 탈락 원문은 로그·결과에 저장하지 않습니다.

웹과 HTML은 같은 저장 문장을 사용합니다. 과거 `llm_prioritized`는 AI가 고른 계산 문장으로 구분합니다. 참조·형식 검사 통과가 자연어 의미와 운영 유용성을 보장하지는 않습니다.

### GPU 메모리 보강

`DCGM_FI_DEV_FB_USED/FREE`를 현재 기간만 클러스터당 한 번 시간 집계해 GPU당 사용/여유 GiB와 비율을 저장합니다. 같은 GPU·시간·신원·표본 조건을 충족한 장치 관측이며 Namespace 독점 사용량이 아닙니다. 짧은 실행·연결 변경·결측·중복은 메모리 근거를 제한할 수 있으나 기존 활동률 계산은 바꾸지 않습니다. [메모리 수집·제외 조건](../docs/specs/ops-agent/aggregate-report-v1.md#namespace-gpu-메모리-보조-관측--optional-gpu-memory)을 따릅니다.

작업 라벨·일반 컨테이너 GPU 요청·노드/Pod 상태를 같은 UID와 시간대에 연결하는 보충 근거를 제공합니다. 테스트 유형과 실제 업무 목적, 요청과 실제 할당은 구분합니다. [연결 기준·한계](../docs/specs/ops-agent/aggregate-report-v1.md#저장된-작업-유형gpu-요청-연결)를 따르며 기존 계산·후보·검증 조건은 유지합니다.

### GPU 작업 대기·배치 완료 보조 관측

[workload_queries.py](src/ops_agent/workload_queries.py)는 일반 컨테이너의 GPU 요청과 Pod UID/Job owner를 연결해 시간별 최대 Pending·미배치·Running과 성공 완료 Job 표본을 수집합니다. 누락·모호한 이름 재사용은 제외하며, 외부 Alloy 전송 설정과 실제 저장 표본 확인은 별도입니다. [조회·근거·CSV·시간 의미](../docs/specs/ops-agent/aggregate-report-v1.md#ops-작업-대기배치-완료-보조-관측)를 따릅니다.

### Namespace별 조건부 운영 제안

[namespace_advice.py](src/ops_agent/namespace_advice.py)의 `namespace-pattern-advice-v3`는 저장된 활동·메모리·대기·완료로 후보를 만들고, 각 후보에 **운영 선택·그 이유·추가로 필요한 근거**를 연결합니다. `decision.scope`는 조건부 운영 선택, 구체적 점검, 관측 참고를 구분하며 원인 확정이나 조치 승인이 아닙니다. 종류별 고정 순위 대신 이 판단 범위와 연결된 근거를 비교합니다. 기존 최대 12개 중간 후보에서 대표 완료·클러스터를 확보한 뒤 서로 다른 운영 선택을 최대 5개로 좁힙니다. 대표 완료가 필수라는 사실을 높은 운영상 중요도로 읽지 않으며, 선택 종류만 바꾼 반복과 선택을 뒷받침하지 않는 일반 완료 조언을 추가로 채우지 않습니다. 세부 정렬·기존 계약 때문에 남는 반복은 [선별 명세](../docs/specs/ops-agent/aggregate-report-v1.md#조건부-운영-제안의-선별완료-연결)를 따릅니다.

LLM에는 관측 이유(`decision.reason`), 허용 판단(`scope/choice`), 연결 사실(`known`), 참고용 미확인 근거(`needed`, 조건·행동 작성 지시가 아님), 읽기용 관측값(`observed_values`)과 같은 대상의 `related_observations`를 전달합니다. 모델의 `summary`에는 수치·참조 없는 현상과 판단 이유만 작성하게 합니다. 작성용 `writing_decision.action`의 점검 목적·필수 조건·운영 행동과 `summary_start`의 대상·기간·수치 근거는 코드가 뒤에 한 번씩 붙입니다. 저장된 `decision_context`·후보·선별은 유지하며 작성용 `option/action`·`writing_focus`·치환 사전·`required_checks/required_prose_terms`는 모델 입력에서 제외합니다. 최초·부분 보완 모두 같은 이유 전용 계약을 사용하고, 행동·근거와 구분 공백을 뺀 기존 360자/참조 제외 220자 한도의 남은 길이를 후보별 `prose_max_chars`로 안내합니다. 이유 한 문장을 기본으로 요청하며 별도 최소 길이나 새 글자 수 상한은 두지 않습니다. 불완전한 미배치 영은 입력 관측값에 일부 표본·미배정 유무 미확인을 함께 표시하고 양수 근거는 보존합니다. 저장 수치·참조·근거 문장은 바꾸지 않습니다. `summary_source=llm`은 이유 설명의 작성 주체이며 최종 요약은 모델 설명과 코드 행동·근거의 결합입니다. 조립 변경은 기존 `interpretation_version`으로 구분하며 후보 기준 버전을 바꾸지 않습니다.

코드 행동은 모델 호출 전에 기존 완성 문장 검증기로 검사합니다. 코드의 조건 누락·길이 오류나 이유 예산 부족이면 `invalid_code_advice`로 계산 요약을 유지하며 모델 보완을 요청하지 않습니다. 모델 응답은 복사본에 행동을 붙여 기존 수치·참조·금지 주장·후보별 조건·확인 순서·길이 검사를 거칩니다. 미배정 부재 단정·관측되지 않은 대기 대상 지목·개별 작업의 GPU 활동률 귀속은 최종 조립 전에 원문에서도 검사합니다. 이 관측 검사 이동·중복 제거는 이유 전용 차단 추가와 별도의 정리이며 관측 패턴은 유지합니다. 코드만으로 기존 선택·포함 관계를 확인한 뒤 모델 원문의 직접 지시형, 운영 행동 서술, 권고·당위형과 검토 대상 분류를 `reason_only_namespace_summary_required`로 거절합니다. 원문만 옛 완성 문장 검사에 넣어 필수 조건을 요구하는 경로는 사용하지 않습니다. 큐·배치 점검 지시의 중복도 같은 이유 전용 검사로 막습니다. capacity 원문의 긍정형 자원 부족·부족 원인 단정은 `unsupported_resource_shortage_claim`으로 거절하며 부족 여부 미확인·판단 유보는 구분합니다. 오류 안내는 이유만 보완하도록 하며 조건·행동·참조를 모델에 채우라고 요구하지 않습니다. 부재의 직접 부정·없어도 조건형·미확인 자원 부족을 이어받는 질문과 정상 여러 단계 확인은 기존 허용 범위를 유지합니다. 정상 이유는 원문 그대로 보존하고 잘못된 항목·주제만 기존 한 번의 부분 보완으로 모읍니다. 구조·ID·개수·32KB 상한·JSON 모드·전송/토큰/시간 예산과 보완 실패 시 계산 요약 경로는 유지합니다. 행동 단어의 단순 등장만으로 거절하지 않으며 유한한 긍정형 서술·지시·권고 패턴을 검사합니다. 정상 부정·유보는 별도 표본으로 유지합니다. 검토 반복·선행 실행·부재 단정 검사는 유한 한국어 표현 검사이며 새로운 암시적 판단·접합부 자연스러움·운영 유용성은 별도 검수가 필요합니다. `present_advice`는 완성 요약의 정확한 경계에서 기존 `summary_parts.decision/evidence`로 나누며 decision에는 이유와 코드 행동이 함께 들어갑니다. UI·RCA와 저장 결과 읽기 계약은 유지합니다. 세부 조건과 검증 범위는 [집계 명세](../docs/specs/ops-agent/aggregate-report-v1.md#구현-범위와-결정-대기-항목)·[Agent QA](../agents/QA.md)를 따릅니다.

관측 활동률 0%는 미사용의 증거가 아닙니다. Pending은 대기 시간이 아니고 Job 경과는 대기·준비를 포함할 수 있습니다. GPU 연결은 실제 할당·보장량이 아니며, 미배치만으로 GPU 부족을 확정하지 않습니다. 원래 계산·품질·CSV·RCA를 유지합니다.

#### 운영 해석 개선 방향 (후속 개발 목표)

질문별 전체 보류 사유 표시·정책/실제 할당/실제 업무 목적/스케줄러 원인 연결은 미구현입니다. [반복 고활동·상대적 저부하 후보](../docs/specs/ops-agent/aggregate-report-v1.md#반복-고활동상대적-저부하-후보)는 기존 자격을 유지하는 별도 종류입니다. 떨어진 고활동·대기 구간은 자원 배분 점검 대상으로, 같은 날의 상대적 저활동 구간은 조건 확인 후 일부 작업의 시간 변경 시범 검토 대상으로 선별합니다. 시간대 변경은 확정 실행 권고가 아닌 시험 후보입니다. 대상 Namespace를 유지하고, 작업 준비·선행 작업 때문에 시작 시각을 바꿀 수 있는지와 마감·예약·가용 GPU·메모리 요구를 확인한 뒤 작업 일부의 시범 실행만 검토하도록 코드 행동을 구성합니다. 후보·비교 구간은 저장된 관측 날짜 그대로 표시하며 과거로 당겨 실행하거나 매일 같은 시간에 실행하라는 뜻이 아닙니다. 웹은 비교 구간과 낮은 활동 구간을 과거 관측으로 표시하고 이후 같은 시간대의 반복성·가용 GPU 확인이 필요함을 안내합니다. 하루의 상대적 활동 차이만으로 미래 실행 시간표를 제공하지 않습니다. 최종 문장은 관측 이유 뒤에 어떤 작업의 무엇을 왜 확인할지 코드 행동으로 연결합니다. 노드 배정 기록, 사용 가능한 GPU처럼 용어를 풀어 쓰고 메모리 수준을 증가 추세로 바꾸지 않도록 안내합니다. 떨어진 고활동·대기 후보의 목적은 대기 작업을 실행할 방법을 찾는 점검이며, 이 후보만으로 GPU 할당 확대를 제안하지 않습니다. 필수 근거·금지 주장·검증 조건은 유지하며 실제 응답의 준수 여부는 [Agent QA](../agents/QA.md)에서 관리합니다. 관측/비교 구간은 최초·보완 입력과 저장 근거에 보존합니다. 같은 저장 보고서의 실제 LLM 전후 비교에서는 새 운영 선택이 나왔지만 문장 유용성은 부분 개선이며 의미 오류도 남았습니다. 검증 범위와 미확인 운영 발행은 [Agent QA](../agents/QA.md)에서 관리합니다. 판단 범위에 따른 선별이 운영상 중요도나 문장 유용성을 보장하지 않습니다. 현재 전달 후보·필수 포함 조건과 별개이며, [구현 범위와 결정 대기 항목](../docs/specs/ops-agent/aggregate-report-v1.md#구현-범위와-결정-대기-항목)을 따릅니다.

## 기존 O계열 보고서

이전 요청 방식과 기존 일정은 [O계열 명세](../docs/specs/ops-agent/12_보고서_Agent_모듈_설계서.md)를 사용한다. `criteria 1.3`의 기본 주제는 O08/O01/O05/O11이며 현재 신규 화면의 기본 집계 계약과 구분한다.

- 공통 D binding과 query+CPC+기간 계획으로 조회한다. [collection.py](src/ops_agent/collection.py)가 의존성·예약 예산·병렬 수집·취소 회수를 처리한다. 실행별 관측 캐시는 같은 조회·기간의 근거를 재사용한다.
- O01 장비/Node 관측, O08 사용 패턴, O05 DB 사건·공개 RCA·조치 기록, O11 자료 신뢰도에 [operator_insights.py](src/ops_agent/operator_insights.py)의 확인 항목을 연결한다. 누적 상태와 현재 장애, 알람 해제와 복구 완료를 구분한다.
- 통합 binding과 criteria 1.3에서 O01은 불필요한 D06을, O05는 D10/D22를 조회하지 않는다. 계산에 쓰지 않는 보고서 D09/D13도 생략하며 `quality.omitted_queries`에 이유를 남긴다. 다른 계약의 조회를 임의로 줄이지 않는다.
- D06 범위 축소는 완전한 D02 신원·기간과 허용된 주제 조합에서만 적용한다. 신원 누락·공백·빈 후보·필터 한도 초과 시 넓은 기존 범위로 복귀한다. 최종 UID·Node·시간 연결 검사는 유지한다.
- O01 추가 관측은 대상별 고유 지표 ID를 사용한다. criteria 1.3은 D20 원본 구간을 결과 본문에 중복 저장하지 않고 계산 결과와 evidence refs를 유지한다. 구 결과 형식은 조회 호환용으로 유지한다.
- [report.py](src/ops_agent/report.py)는 코드가 만든 문장을 문장 ID 선택 LLM으로 편집한다. 새 수치·원인·조치를 생성하지 않으며 모델을 사용할 수 없으면 기본 보고서를 남긴다.

## 보고서 삭제와 파일 정리

사용자가 종료한 보고서를 삭제하면 JC가 DB 결과·근거를 삭제하고 `report_deletions`를 기록한다. [cleanup.py](src/ops_agent/cleanup.py)는 Worker 시작 시와 이후 30초마다 대상 1건을 처리한다. DB 행 잠금·`SKIP LOCKED`로 여러 Pod가 같은 대상을 동시에 맡지 않는다.

정규 UUID의 `ARTIFACT_DIR/<job_id>`만 처리하고 심볼릭 링크를 따라가지 않는다. 파일 삭제 후 0바이트 일반 파일로 표시해 늦게 끝난 저장 작업이 디렉터리를 다시 만들지 못하게 한다. `pending`/`failed`는 미완료, `complete`는 삭제 표시까지 생성한 상태다. 실패 시 재시도하며 DB에서 삭제한 본문이 복구되지는 않는다. migration 008 미적용 중에는 경고를 남기고 분석 루프를 유지한다. RCA에는 이 정리 루프가 없다.

### 설명의 길이와 기준별 적용 범위

Namespace 제안 7종에서 모델은 관측의 의미와 판단 이유를 설명하고 코드는 대상에 맞는 점검 목적·행동·필수 조건을 보존합니다. 대기 단계·완료 유형 확인 여부에 맞는 코드 문장은 기존 후보·판단 범위 안에서 구성합니다. 기존 360자/참조 제외 220자 한도와 참조를 유지하며 이유에 남는 분량은 후보마다 다릅니다. 설명이 길면 모델 이유만 부분 보완하고 코드 행동의 조건을 생략하지 않습니다. 같은 행동을 다른 대상에 제안하는 정상 반복을 억지로 다르게 쓰지 않습니다. 저장 응답 재생과 fixture 조립은 새로운 실제 모델의 자연스러움·판단 일관성을 입증하지 않습니다.

설명을 보강할 때는 현재 근거로 가능한 선택과 실행 전 확인 조건을 우선한다. 추가 GPU 수, 대기 원인, 다음날 같은 시간의 여유, 시간 변경의 성능 개선은 근거 없이 붙이지 않는다. 어떤 작업을 옮길지까지 특정하려면 작업 유형·마감·예약과 실제 할당/배치 가능 근거가 필요하다. [보고서 전용 토큰 예산](../job-controller/README.md#aggregate-report-token-allowance)은 입력·재작성 여유를 위한 한도이며 품질이나 발행 성공을 보장하지 않는다.
