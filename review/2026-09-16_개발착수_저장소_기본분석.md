기준일: 2026-09-16 · 최초 재검토: README 수정 `3f15ff0`, GitBook 설정 `d64e870` · 후속: `c2dd94e` 기준 자료 62개 정리

현재 저장소는 **DSX GPU Operations의 설계·명세·산출물 저장소**다. 기능별 책임과 데이터 계약은 상세하지만, 여러 개발자가 바로 실행하고 수정할 제품 코드는 아직 없다. 협업의 첫 단계는 공통 계약과 실행 기반을 맞추는 일이며, 그 뒤 관측·RCA·보고서·화면을 병행 개발할 수 있다.

원격 `main`을 fetch한 뒤 README 수정과 기존 분석 내용을 다시 대조했다. 링크 오류를 해결한 뒤 최신 Backend 구조도 v2와 개발 명세 v1.1을 기준으로 대체·중복 자료 62개를 정리했다. 정적 시안 복원은 현재 작업에서 제외한다. 테넌트·인증의 설계·연계 결정은 사용자 요청에 따라 후속 검토로 보류한다. 아래 분담과 착수 순서는 제안이며 담당자·기술 스택을 확정하지 않는다. GitHub 보호 규칙·실행 이력, 실클러스터·DB·모델 연결은 확인하지 않았다.

## 2. 문서상 제품 구조와 흐름

개발 기준은 [요구사항 01](<../output/deliverables-20260916-v1.1/01_요구사항_개발범위_정의서.md>), [API 02](<../output/deliverables-20260916-v1.1/02_백엔드_API_작업명세서.md>), [데이터 03](<../output/deliverables-20260916-v1.1/03_데이터_설계서.md>), [Agent 04](<../output/deliverables-20260916-v1.1/04_Agent_동작_판단_명세서.md>)다.

```text
CPC 관측 → Alloy → 관측 Gateway → Mimir / Loki
                                      ↑ 조회
Web → 사용자 Gateway → API → PostgreSQL 작업 원장
                              ↕ 점유·갱신·결과 확정
                        RCA Worker / 보고서 Worker
                              ↓ 공통 코드
                    조회·계산 / Knowledge / LLM 호출
                              ↓
                         사내 추론 Endpoint
```

- Backend 기능 8개를 **API 서버 1종·Worker 2종·공통 모듈**로 구현한다. 공통 모듈마다 서버를 만들지 않는다.
- 일반 조회·대화는 API에서 처리한다. 전문 작업은 DB 커밋 후 202와 `job_id`를 반환하고 Worker가 실행한다.
- `analysis_id`와 `report_id`는 해당 `job_id`다. 실행 상태 원장은 `jobs`, 시도 이력은 `job_attempts`, 최종 결과는 `job_results`다.
- Grafana Webhook은 Incident 갱신과 RCA 접수를 같은 트랜잭션으로 저장한다. 알림 해제·분석 성공·사건 종결은 서로 다르다.
- DB 점유·lease·attempt·취소·deadline 검사로 유효한 결과만 확정한다. 두 Worker가 별도의 작업 원장을 구현하면 안 된다.
- Mimir/Loki는 원시 관측, PostgreSQL은 업무·관계·결과·근거 참조를 맡는다. 전체 로그·시계열을 업무 DB에 복제하지 않는다.
- 수치는 코드가 계산하고 LLM은 조사 선택·해석·설명을 맡는다. LLM 실패 시에도 유효한 계산·근거를 보존한다.

범위는 F01~F14, N01~N05, RCA R01~R09, 보고서 O01~O11이다. **P1도 개발 범위이며 일·주·월 정기 보고서는 P0**다. 자동 장비 조치, 별도 브로커·그래프/벡터 DB, 제품 PDF/DOCX 보고서 엔진은 기본 범위에 없다.

## 5. 병행 개발 착수 순서

1. **기준 정리:** 링크는 해결 완료다. 다음으로 짧은 창의 판정 상태를 통일하고, API/Worker 언어·FE 기술, migration 도구·실행 명령·유효한 CI 범위를 정한다. 정적 시안 복원과 테넌트·인증 설계는 이번 선행 작업에서 제외한다.
2. **공통 계약을 실행 가능한 형태로 옮김:** 02·03·04의 DTO·enum과 최소 DB 스키마, 요청/응답 fixture를 만든다. OpenAPI 또는 선택한 프레임워크의 스키마를 계약 원본과 연결하고 별도 중복 수기 관리는 피한다.
3. **첫 통합 경로:** 로컬 고정 테스트 신원·범위 → 보고서 요청 → DB 접수 → Worker 점유 → 고정 관측 입력 계산 → 결과 저장 → UI 재조회. 실제 인증·LLM 연계 없이 작업·수치·저장 계약을 검증한다. 모의 검증임을 표시하고 실환경 인증·권한 검수 완료로 취급하지 않는다.
4. **독립 작업 병행:** 관측 담당은 실제 query/parser, RCA 담당은 사건·조사, 보고서 담당은 O 주제, FE 담당은 고정 응답으로 화면, Assistant/KB 담당은 발행·대화·모델 경로를 구현한다. 정기 일정은 공통 report 접수를 재사용한다.
5. **통합·환경 활성 검수:** 보류한 인증·테넌트 검토를 재개해 필요한 연계를 확정하고, 실제 관측·사내 모델·Webhook·정기 실행 연결 후 취소/재시작/권한 철회와 부족 입력을 검증한다. CPC별 정상 산출 가능 여부는 C04에 별도로 기록한다.

첫 통합 경로는 개발 순서를 위한 작은 검증 단위이며 전체 R/O·P1 범위를 줄이는 결정이 아니다. 기술 스택이 미정인 현재 단계에서 디렉터리 골격이나 새로운 서비스를 먼저 만들 필요는 없다.

## 6. 모든 작업자가 공유할 기준

- 기존 명세의 scope는 CPC별 Namespace 조합이다. 인증·테넌트 검토는 보류 중이며, 기존 계약을 임의로 변경하지 않는다. 후속 권한 구현에서는 다른 grant의 역할·범위를 교차 합성하지 않고 실행·결과·근거·출력에서도 현재 권한을 확인한다.
- 시간은 UTC 저장과 `[start,end)`; 이름만으로 자산을 식별하지 않고 CPC·GPU UUID·Pod UID와 시점을 함께 사용한다.
- `0`과 `null + 사유`, 현재 관계와 과거 관계, 전용 물리 GPU와 공유/MIG를 구분한다.
- `job.status`, `result_status`, 주제 상태, `quality`, `narrative_status`는 별개다. 작업 성공이 충분한 분석 근거를 뜻하지 않는다.
- 저활동 후보는 같은 전용 GPU–Pod–관측 episode의 60분 창, utilization <5%, 공동 관측률 ≥95%, 유효시간 중 저활동 ≥90%다. 짧은 서로 다른 할당을 합치지 않는다.
- 변경 PR은 F/N·R/O·S/AC·T ID를 연결한다. API/상태/scope는 02·03·07·08, 산식은 03·04·05를 함께 대조한다.
- 과거 PDF·ZIP·sources를 현행 명세처럼 덮어쓰지 않는다. 현재 편집 기준은 v1.1 Markdown이며 후속 결정의 적용 범위를 명시한다.
