# 처음 작업을 시작할 때 쓰는 담당별 코딩 에이전트 프롬프트

아래 네 가지는 **새 담당자가 참여하거나 새 작업을 처음 시작할 때** 쓰는 예시다. 같은 작업을 이어갈 때 매번 전체를 복사할 필요는 없다. 프로젝트 폴더에서 사용하는 코딩 에이전트를 열고 자기 담당에 맞는 예시 하나를 복사한다. 경로는 모두 **저장소 루트 기준**이다. `frontend/README.md`는 프로젝트 폴더 안의 `frontend` 폴더에 있는 문서를 뜻하며, 개인 PC의 사용자명이나 절대 경로를 넣을 필요는 없다. `[작업 내용]`, `[완료 조건]` 등을 실제 요청으로 바꾸고, 작업 유형은 하나만 선택한다.

## 작성 기준과 이 예시의 한계

2026-09-21 공식 가이드와 대조했다. OpenAI는 코딩 요청에 **목표·관련 맥락·제약·완료 조건**을 담고, 반복되는 공통 규칙은 `AGENTS.md`로 관리하도록 권장한다. [OpenAI 공식 가이드](https://learn.chatgpt.com/guides/best-practices)

Claude Code도 구체적인 파일·기존 구현·제약과 실행 가능한 검증 수단을 제공하고, 공통 규칙은 짧은 `CLAUDE.md`에 두도록 권장한다. [Claude Code 공식 가이드](https://code.claude.com/docs/en/best-practices)

**이 문서의 적용 판단은 “처음에는 공통 안내와 담당 문서로 맥락을 잡고, 일상 요청은 필요한 내용만 짧게 전달한다”는 것이다.** 아래 네 예시는 공식 템플릿을 복사한 것이 아니라 A/B/C-1/C-2의 담당 범위와 이 프로젝트의 계약·안전수칙에 맞춘 것이다. 네 개의 AI를 자동 실행하는 설정도 아니다. 문서·경로의 일치 여부를 확인했지만, 네 예시를 실제 Claude Code 개발 작업에 적용해 정확도·작업 시간·비용을 비교한 것은 아니다. 사용 중 반복되는 누락이 확인되면 그 원인에 맞춰 보완한다.

공통 규칙의 시작점은 [CLAUDE.md](../CLAUDE.md)이며, [작업 방식](../.claude/rules/workflow.md)·[안전수칙](../.claude/rules/safety.md)과 변경 경로에 해당하는 규칙을 함께 따른다. [AGENTS.md](../AGENTS.md)를 사용하는 다른 코딩 에이전트도 같은 영어 원본을 읽는다. 공통 원칙·검증 명령이 바뀌면 해당 영어 원본과 [시작 지침 번역](CLAUDE.ko.md)·[규칙 번역](rules.ko.md)을 함께 갱신한다. 사람이 읽는 현재 main 작업·향후 PR 절차는 [팀 협업 안내](team-development.md)에 있다.

## 처음 시작할 때와 이어서 작업할 때

- **새 담당자·새 작업**: 아래 공통 확인과 담당 문서를 읽고, 자기 담당의 예시 하나에 작업·허용 범위·완료 조건을 채운다. 설계와 접근 방식이 불명확하면 먼저 분석·계획을 요청한다. 작은 수정마다 긴 계획을 요구할 필요는 없다.
- **같은 작업을 이어갈 때**: 달라진 요구사항·남은 작업·추가 완료 조건을 전달한다. 관련 Issue나 기준 커밋을 알면 함께 적는다. 이미 확인한 설명을 매번 붙이지 않되, 바뀐 지침·코드·테스트는 다시 확인한다. 새 대화라면 이전 대화를 알고 있다고 가정하지 말고 담당 예시와 남은 작업을 전달한다.
- **버그 수정**: 재현 순서, 실제 오류나 증상, 기대 결과, 필요하면 민감정보를 제거한 로그·스크린샷을 추가한다. “잘 고쳐줘”보다 “같은 순서로 실행했을 때 이 오류가 재발하지 않아야 한다”가 확인하기 쉽다.

이 예시는 저장소를 읽고 검사할 수 있는 환경을 전제로 한다. 저장소 접근이 없는 일반 ChatGPT 대화에서는 경로만 적어도 파일을 읽을 수 있는 것이 아니므로 필요한 파일을 첨부하거나 접근 가능한 자료를 연결한다. 명령 실행 도구가 없다면 사용자가 검사 결과를 제공하며, 실행하지 않은 검사를 통과로 보고하지 않는다. [ChatGPT 자료 제공 안내](https://learn.chatgpt.com/docs/prompting#add-useful-context)

## 공통 확인: 문서 경로와 최신 변경사항

**공통 문서와 담당 모듈의 경로는 구체적으로 적고, 오늘의 작업·변경사항은 별도로 확인한다.** 변경사항만 보면 기존 계약이나 안전수칙을 놓칠 수 있다. 반대로 문서만 읽으면 아직 문서에 반영되지 않은 코드나 다른 사람이 수정 중인 내용을 놓칠 수 있다.

- 먼저 `CLAUDE.md`, `.claude/rules/workflow.md`, `.claude/rules/safety.md`와 `docs/team-development.md`의 현재 작업 규칙을 따른다. 새 작업에서는 `README.md`로 전체 흐름을, `docs/README.md`로 문서 목록을 확인하고 아래 담당 문서를 읽는다. 문서만으로 동작을 단정하지 말고 관련 코드·테스트와 대조한다. 담당별 주의점은 기존 공통 규칙을 대신하지 않는다.
- Frontend 작업은 `.claude/rules/frontend.md`, Go 서비스·계약·DB 작업은 `go-services.md`, RCA·Ops·공통 Python 작업은 `agents.md`를 `.claude/rules/`에서 읽는다. 공통 설정 원본·Helm·CI·배포를 다루면 `deployment.md`도 읽는다. 여러 경로에 걸치면 해당 규칙을 모두 적용한다.
- 날짜·버전이 붙은 설계서는 `docs/README.md`의 **현행 개발 문서** 링크에서 고른다. 프롬프트마다 날짜 폴더를 복제하지 않는다. 파일이 이동했다면 문서 목록과 `rg --files`로 실제 위치를 확인하고, 찾지 못하면 추측하지 말고 알린다. 문서를 옮기는 작업에서는 관련 링크와 이 예시도 함께 갱신한다.
- 에이전트는 현재 브랜치와 `git status --short --branch`, `git diff`, `git diff --cached`를 확인한다. 새 파일은 일반 diff에 나오지 않으므로 작업과 관련된 새 파일도 확인한다. 이미 커밋한 변경은 diff에 나오지 않으므로 필요한 최근 이력과 관련 코드·테스트도 읽는다. 기준 커밋이 있으면 그 이후 변경을 함께 확인한다.
- 작업 재개 시 바뀐 공통 지침·관련 문서도 다시 확인한다. 상태 확인만을 위해 자동으로 pull·브랜치 전환·변경 폐기를 하지 않는다. 원격 확인을 하지 않았다면 로컬의 `origin/main` 표시만 보고 원격 최신 상태라고 단정하지 않는다.
- **분석만 요청받으면 파일을 수정하지 않는다.** 구현·수정 요청은 범위 안에서 진행하고 경로별 규칙의 관련 검사와 영향받는 사용 경로를 검증한다. [공통 완료 기준](../.claude/rules/workflow.md#completion-criteria)과 [한국어 번역](rules.ko.md#공통-완료-기준)에 따라 검사 명령의 성공, 완료 조건의 실제 확인, 건너뛴 검사를 구분한다. 변경 결과·실행한 명령과 결과·미확인 항목을 보고하며, fixture 기반 검사와 실제 외부 연결·분석 품질 검증을 구분한다.

각 예시의 문서 목록은 출발점이지 수정 범위를 그 폴더 하나로 제한한다는 뜻은 아니다. 영향받는 사용 경로는 함께 확인하되, API·DB 계약 변경 등 요청 범위를 넓혀야 한다면 먼저 이유를 설명하고 합의한다. 아래 예시는 커밋·push·PR 생성·병합·배포를 허용하지 않는다. 필요할 때 해당 작업을 별도로 요청한다.

## C-2 — Ops Agent 담당

작업 예: 기간별 GPU 사용률 보고서에 관측 범위·누락 사유를 표시하거나, 공개 RCA 결과를 근거로 인용하는 부분을 개선하는 경우.
