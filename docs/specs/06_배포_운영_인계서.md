# 06. 배포·운영 인계서

버전 1.3 · 코드 대조 기준 `775ab2f` · 저장소의 현재 배포 설정과 운영 기준. 코드·QA 확인을 운영 배포/성능/복원 시험 완료로 간주하지 않는다.

## 실행 구성

Frontend, Backend(정기 일정 포함), Incident, Job Controller, RCA Agent, 보고서 Agent를 각각 기동한다. PostgreSQL·업무 파일 저장소·기존 Mimir/Loki·사내 추론 endpoint를 연결한다. 두 Agent 이미지에는 각각 NAT 워크플로와 공통 계산·정규화 라이브러리를 포함한다. Grafana MCP 서버는 별도 조회 연결 구성 요소로 기동하거나 기존 운영 endpoint에 연결한다. Agent별 업무 큐나 중앙 공통 업무 서버는 추가하지 않는다. 별도 Scheduler/Chatbot/HPA/큐 메트릭 어댑터는 배포하지 않는다.

GUI는 Backend, Grafana Webhook은 Incident, 생산자/Agent는 JC 내부 주소를 사용한다. 제품 인증은 이번 범위 밖이며 모듈 포트를 외부 GUI 경로로 임의 노출하지 않는다. 기존 관측 저장소·모델 접속에 필요한 환경 비밀은 secret_ref로 관리한다.

실제 값·담당·검증일·증거를 배포별 원장에 채운다. 문서의 예시는 운영 확정값이 아니다. 모듈 readiness는 DB/설정 준비와 Worker 실행 여유를 구분한다. Agent 부재 때문에 JC의 영속 접수를 불필요하게 막지 않는다.

### 현재 코드의 초기화·한도 설정

Backend는 migration과 선택적 데모 seed 뒤에 `EnsureDefaults`를 호출한다. `seedDemoData=false`에서도 API 필수 한도만 생성하며 예제 CPC는 등록하지 않는다. 기존 C07 행의 config·enabled·version은 덮어쓰지 않는다. 클러스터가 없어도 readiness는 통과하며 GUI 연결·설정의 클러스터 등록 또는 [02의 POST /clusters](backend/02_백엔드_API_작업명세서.md)로 실제 라벨 ID를 추가한다.

코드의 `service_profiles(kind=limits,name=C07)`은 Backend API 한도다. 위 원장의 C07에 함께 기재된 JC 용량·Agent 조회·LLM 예산은 별도 설정으로 관리되며 같은 DB 행을 공유하지 않는다.

| 설정 위치 | 현재 기본값·적용 범위 |
|---|---|
| Backend C07 | max_query_days=31, max_body_bytes=1,048,576, max_log_lines=1,000, max_requests_per_minute=120, max_text_length=16,000, max_inflight_requests=16, module_timeout_seconds=10 |
| JC 실행 프로필 local-v1 | max_attempts=3, attempt_budget=32,768, token_budget=98,304; 새 잡의 실행 snapshot에 고정 |
| Agent 관측 limits | max_queries=48, max_rows=5,000, max_bytes=2,097,152, chunk_seconds=3,600, max_range_seconds=2,678,400, deadline_seconds=900 |
| Agent LLM 출력 | 기본 출력 4,096, synthesis 출력 16,384 토큰; 실제 호출은 입력·출력을 포함하는 JC attempt 예산 안에서 제한 |

기본값의 원본: [Backend 초기화](../../backend/internal/store/store.go), [JC 설정](../../charts/gpu-ops-advisor/files/job-controller.json), [Agent 관측 설정](../../agents/config.example.json), [LLM 환경 설정](../../shared/python/src/agent_common/settings.py). 이 값은 운영 성능을 보장하는 수치가 아니다. 조회 한도와 토큰 예산은 별개이며, 한 CPC의 O02 하루 조회는 정상적인 1시간 구간 기준 4개 query × 24 = 96회가 필요해 기본 48회를 넘는다. 분할 재조회도 횟수를 소모하므로 기간 입력이 허용돼도 모든 구간을 확보한다는 뜻은 아니다.

`configuration.applyJobController`와 `applyIncident`는 현재 차트에서 기본 true다. 시작할 때 전달한 설정을 DB에 적용하므로 DB에서만 변경한 운영 설정은 다음 시작 시 values 값으로 갱신될 수 있다. Incident 분석 정책의 동일 revision 내용 변경은 여전히 거절한다. 이미 접수된 잡의 입력·실행 예산 snapshot과 저장 결과는 바꾸지 않는다. 이 동작은 기존 C07을 보존하는 Backend 초기화와 다르다. 실제 설치·기존 배포 업그레이드 명령은 [설치 안내](../helm-install.md)와 [기존 배포 안내](../helm-upgrade-existing.md)를 따른다.

## NAT·Grafana MCP 배포 설정

저장소는 NAT 1.5.0과 공식 Grafana MCP 1.4.2를 사용한다. 버전 원본과 시험 범위는 [Agent 안내](../../agents/README.md)와 [QA](../../agents/QA.md)에 있다. 문서의 latest URL을 자동 업그레이드 정책으로 쓰지 않는다. 두 Worker가 각자의 NAT MCP 클라이언트로 공통 Grafana MCP endpoint에 연결하며, 서버는 수동 배포·설정한다. Grafana MCP는 잡 배분·Agent 증설·달력 일정을 수행하지 않는다.

MCP는 Grafana의 등록 데이터소스로 Mimir·Loki를 읽는다. Grafana 연결 자격증명과 기존 관측 tenant/header는 운영 secret_ref로 관리하며 제품 사용자 인증을 추가하지 않는다. datasource UID, CPC selector, 원본 주기·보존과 C02/C03을 대조한다. Backend의 기존 관측 연결 설정은 유지한다.

서버는 읽기 전용으로 설정하고 필요한 Prometheus/Loki 조회 도구만 허용한다. Grafana MCP의 --disable-write 기능과 NAT의 include 목록을 사용하되 설치 버전의 실제 도구 목록으로 검증한다. --disable-query는 필요한 관측 조회까지 제거하므로 사용하지 않는다. 입력 scope·시간·query 제한은 별도로 14의 Agent 업무 함수가 강제한다. [Grafana 도구 활성화·읽기 전용 설정](https://grafana.com/docs/grafana/latest/developer-resources/mcp/configure/enable-and-disable-tools/), [NAT MCP 연결 설정](https://docs.nvidia.com/nemo/agent-toolkit/latest/build-workflows/mcp-client.html)을 참고한다.

검증 순서는 도구 목록·schema 확인 → 제한된 로그/지표 표본 조회 → 03의 원본 시각·단위·완전성 확인 → RCA Runbook/일반 조사와 보고서 사례 → 취소·timeout·재시도 시험이다. 단계별 결과와 버전 manifest를 인계한다. 기능 지원 여부를 확인하지 않은 설정 예시를 운영 확정값으로 사용하지 않는다.

## 수동 용량 조정

1. 큐 길이·최장 대기·실행 중 수·LLM 지연/격리 상태를 확인한다.
2. 운영자가 실제 서버/LLM 여유를 확인하고 Agent 배포 수와 C07을 결정한다.
3. 배포 도구로 RCA 또는 보고서 Agent를 수동 추가한다. 새 boot_id로 등록해 claim 가능한지 확인한다.
4. capacity 프로필 변경을 JC가 읽고 적용한 revision과 실제 점유를 확인한다. 클라이언트 요청으로 한도를 바꾸지 않는다.
5. 줄일 때 해당 Worker를 draining으로 전환해 새 인수를 멈추고 진행 잡 종료를 기다린다. 강제 종료 시 lease·원격 추론 상태를 확인한다.

한도보다 running이 많은 상태로 수동 축소하면 진행 잡을 강제 중단하지 않고 신규 claim만 제한한다. 큐 길이에 따른 자동 배포·replicas 변경은 없다. 모델 슬롯 부족을 Agent 수 증가만으로 해결된 것으로 판단하지 않는다.

## 기동·업데이트

현재 차트의 Backend startup/liveness는 `/api/v1/health/live`, readiness는 `/api/v1/health/ready`다. readiness는 DB·스키마·필수 API 한도를 확인하고 클러스터 등록이나 MCP 준비를 기다리지 않는다. DB 연결·migration은 HTTP 서버 시작 전에 수행하므로 이 단계의 실패는 프로세스 종료 로그로 확인한다.

MCP의 내부 Service DNS와 포트를 허용 Host에 넣고 probe에 Host 헤더를 지정한다. Worker는 JC·MCP 준비를 기다리고 MCP 연결 재시도를 수행한다. 상세 설정은 [차트](../../charts/gpu-ops-advisor/templates/deployments.yaml)와 [MCP 장애 확인](../helm-upgrade-existing.md)에 둔다.

DB/파일/관측·모델 준비 → Grafana MCP 연결·조회 확인 → migration/설정 검증 → JC → NAT 설정을 검증한 두 Agent → Incident·Backend → Frontend·Grafana 연결 순으로 확인한다. 대표 사건·즉시 보고서·정기 발생을 실행하고 저장 결과를 다시 읽는다.

업데이트는 신규 claim/생산 중단 또는 drain → 작업·outbox·일정 snapshot 보존 → 호환 DB 변경 → 소비자/생산자 순 배포 → 재전송/접수 확인으로 진행한다. rollback은 읽을 수 있는 이전 계약·이미지와 복원된 DB/파일 조합을 사용한다. 파괴적 migration은 별도 계획이 필요하다.

## 장애 대응

| 증상 | 확인·대응 |
|---|---|
| queued 증가 | 종류별 Worker 존재·freshness·slots·shared_limit·격리 확인, 필요 시 운영자가 수동 조정 |
| running 고착 | heartbeat/lease/원격 호출 확인, 무조건 슬롯 초기화하지 않음 |
| LLM timeout | 종료 불명이면 quarantine, 종료 증거/검증된 수명 없이 재사용 금지 |
| JC 장애 | 신규 접수/claim 중단, 생산자 outbox 보존, 같은 키 재전송 |
| Backend 일정 지연 | next_run/catch-up/missed 확인, 저장 pending은 별도 복구 |
| DB 장애 | 성공 확정 중단, 복구 후 attempt/final/receipt 대조 |
| 결과 불일치 | job·query·산식·evidence·candidate hash 추적, final 덮어쓰기 금지 |
| MCP 연결/도구 변경 | endpoint·transport·버전·allowlist·datasource 확인, 무제한 재연결·직접 조회 우회 금지 |
| 관측 부족 | 0으로 채우지 않고 데이터 품질·영향 주제·확인 시각 표시 |

## 백업·인계

DB·업무 파일·설정 revision을 함께 백업한다. 복원 후 final 파일 checksum, source_key/receipt 유일성, occurrence와 outbox 참조, 이전 Worker lease/격리 상태를 점검한다. 이전 프로세스가 살아 있는 환경에 복원 Worker를 병행 기동하지 않는다.

인계 증거: 각 이미지/공통코드 버전, migration, C01~C12, 05 실행 기록, 수동 증설/축소·DB/Worker 장애·정기 복구·백업 복원 결과, 담당자·미확인 항목. 제품 검수 완료 전 성능 수치·가용성·무손실을 보장하지 않는다.
