## 0. 현재 구현 분석과 업그레이드 작업

2026-09-23 · 코드 대조 기준 `d391f3d`. 아래는 코드에서 확인한 구현 차이이며 브라우저 재현 결과가 아니다. 본문의 화면 동작·완료 조건은 목표 기준이고, 구현·검수 완료 여부는 별도로 기록한다.

|---|---|---|---|
| FE-01 사건 상태 정합 | [Cases.tsx](../../../frontend/src/pages/Cases.tsx)와 [Results.tsx](../../../frontend/src/pages/Results.tsx)는 사건 배지를 `status`로 표시한다. 목록 선택지는 `investigating`을 포함하고 `acknowledged`가 없다 | Incident는 `state`를 쓰며 Backend 목록도 `state` 우선 필터다. 신규 행은 legacy `status`가 null일 수 있어 현재 상태를 배지에서 읽지 못한다 | 02의 사건 DTO에 맞춰 `state`와 legacy fallback을 처리한다. `open/acknowledged/closed`와 legacy resolved 조회를 구분하며 알람·검토·분석 상태를 분리하고 job의 `status`는 유지한다. `state=acknowledged,status=null` 사례를 목록·상세·필터에서 확인한다 |
| FE-02 종결·재발 흐름 | 사건 상세 폼은 `review_status`와 `memo`만 PATCH한다. 서버가 지원하는 `state=closed`를 보내는 UI는 없다 | 13의 재발 분석 여부는 이전 사건의 종결 상태와 연결된다. 검토 완료를 사건 종결로 혼동하면 이후 접수 판단을 이해할 수 없다 | 사람의 사건 종결을 기존 PATCH로 명시적으로 제공하고 검토·조치 기록과 구분한다. `If-Match`·멱등 재전송을 유지한다. 종결 후 재조회, `prior_incident_id` 이동, 분석 생략 사유를 표시하며 알람 해제·RCA 성공을 자동 종결로 바꾸지 않는다 |
| FE-03 RCA 근거·에피소드 표시 | [ResultContent](../../../frontend/src/components/live.tsx)는 RCA/사건의 필드를 일반 재귀 뷰로 표시한다. 보고서에는 별도 수치·품질 표시가 있다 | 필드가 출력되는 것과 사용자가 목적 선택·원인 지지/반박·분석 생략·관측 종료를 구분할 수 있는 것은 다르다 | 기존 결과 필드를 재사용해 목적별 판단, 근거와 한계, 에피소드·이전 사건·분석 상태를 구분해 보여준다. 1.4 목적은 공개 assessments/선택 근거에서 읽고 임의 기본값을 만들지 않는다. 구 결과·미발행·blocked·설명 실패도 확인한다 |

선행 계약은 [02](../backend/02_백엔드_API_작업명세서.md)의 BE-01/02와 [13](../incident/13_Incident_모듈_설계서.md)의 상태·에피소드 필드다. 개발 순서는 상태 정합 → 종결/재발 → RCA 근거 표시이며, [08](08_GUI_화면설계서.md)의 S05/S07에 반영한다. 직접 RCA 실행·자동 재분석 버튼은 추가하지 않는다.

1.4 사건 상태 선택지는 open/acknowledged/closed다. 기존 resolved 표시는 legacy에만 유지하고 신규 alarm_status=resolved와 분리한다. episode_started_at은 수신 시작, last_observed_at/count는 재시도를 포함한 수신 이력으로 표시한다. 관측 종료·사람 종결 시각과 이전 사건 링크, 분석 생략/수집 장애 사유를 별도로 보여준다. 종결 버튼은 RCA를 즉시 만들지 않으며 이후 새 증거가 확인되면 새 사건이 생성된다는 안내를 둔다. 보고서 요청·결과는 04 §5.5의 지원 그룹과 unsupported_group_by를 표시하고 criteria 1.1/1.2 수치를 동일 기준으로 비교하지 않는다.

검수 연결: [05](../05_테스트_검수_기준서.md)의 T28/T29/T48/T49~T52. [live.test.ts](../../../frontend/src/lib/live.test.ts)는 요청 계약의 일부를, [report.test.tsx](../../../frontend/src/lib/report.test.tsx)는 보고서 표시를 검사한다. 이들을 사건 화면의 검수 완료로 대체하지 않는다. **이번 상태: 정적 대조 완료, 신규 UI·브라우저/API 통합 검수 미실행.**

## 공통 상태·데이터

scope는 CPC별 Namespace 필터다. 로그인·역할 전환·권한 grant 기반 캐시·사용자 tenant UI는 이번 구현 기준에 포함하지 않는다. 입력/target/기간 검증과 모델 비밀 미노출은 유지한다.

캐시 키는 리소스·scope·기간·ID·revision을 포함한다. 범위 변경 시 이전 응답이 새 범위에 섞이지 않게 요청 취소 또는 응답 키 대조를 한다. 차트 간격 변경은 저장 분석 수치를 재계산하지 않는다.

job.status, result_status, topic/assessment status, quality, narrative_status를 각각 표시한다. queued의 capacity_wait는 '처리 자원 대기', worker_unavailable는 '실행 Agent 대기', inference_quarantined는 '추론 종료 확인 대기'로 구분한다. 0개 Agent에서도 접수된 잡을 실패로 바꾸지 않는다.

## 접수·폴링·명령

보고서 제출마다 멱등 키를 만들고 응답 확인 전까지 동일 요청에 재사용한다. 네트워크 실패 후 새 키로 다시 만들지 않는다. 202와 job_id를 받은 후 작업 상세로 이동한다. 입력을 수정해 의도적으로 다시 요청할 때만 새 키를 만든다.

queued/running/retry_wait를 운영 설정 간격으로 폴링하고 오류에는 backoff/Retry-After를 따른다. terminal이면 중단한다. 탭/화면 닫기는 잡 취소가 아니다. Backend의 can_cancel/can_retry를 표시하되 RCA에는 실행·재시도 버튼을 만들지 않는다. 명령은 별도 멱등 키+If-Match, 409면 상태 재조회·사유 표시다.

결과가 없으면 준비 중/종료 사유를 표시한다. succeeded+blocked도 가능하다. LLM 설명 실패만으로 수치·근거를 숨기지 않는다. 저장된 value_refs와 단위·기간을 사용하며 FE에서 같은 산식을 다시 구현하지 않는다.

## 정기 일정·출력·설정

정기 요청은 schedule_id/revision·시간대·다음 시각·실제 분석 기간을 보여준다. occurrence pending은 Backend 전달 대기, accepted는 JC job 연결, missed/failed는 사유와 함께 표시한다. 일정 일시중지는 이미 접수된 잡을 취소하지 않는다는 문구를 둔다.

보고서는 HTML/CSV를 Backend에서 다운로드한다. 지식의 검토/발행 상태와 content_hash 변경을 반영하고 발행본 직접 수정은 금지한다. 모델 라우팅은 rca/report만 표시한다. 연결 검사의 성공과 분석 품질 합격은 별개다. 용량/배포 수는 상태 조회만 제공하고 GUI 수정 버튼을 만들지 않는다.

## 클러스터 등록과 보고서 표시의 현재 구현

등록된 클러스터가 없으면 공통 화면은 등록 안내를 표시하고 `/settings/data`로 연결한다. 연결·설정 화면은 scope 선택 전에도 열 수 있다. 등록 모달은 실제 관측 라벨과 같은 cluster_id를 입력받아 멱등 키와 함께 `POST /clusters`를 호출한다. 중복/입력 오류는 서버 메시지를 표시하며 등록 성공을 수집 성공으로 표시하지 않는다. 구현: [Shell](../../../frontend/src/components/Shell.tsx), [설정](../../../frontend/src/pages/Settings.tsx).

보고서 상세는 기간·범위, 전체 수치 항목 중 산출 가능한 항목 수, 주제별 수치·대상·단위·부족 사유를 표시한다. null은 ‘산출 불가’이며 0과 구분한다. GPU–Pod 연결 관측 시간과 독점 할당 시간을 다른 이름으로 표시하고 원본 결과는 접을 수 있는 영역에 둔다.

수집 요약은 query_id·cluster_id별로 조회 구간의 상태·사유·표본 수를 묶고 여러 주제가 재사용한 동일 조회 묶음은 한 번 표시한다. 표본 수 표시는 원격 응답 건수의 합이며 경계 중복 제거 후 고유 표본 수와 다를 수 있다. LLM 설명이 failed/omitted여도 계산 수치와 근거는 유지한다.

발행 결과가 있으면 상세 상단에 HTML/CSV 다운로드 버튼을 표시한다. Backend 응답을 파일로 내려받고 오류는 화면에 표시한다. 수치 필드는 [03](../common/03_데이터_설계서.md), 다운로드 계약은 [02](../backend/02_백엔드_API_작업명세서.md)에 둔다. 구현: [보고서 표시](../../../frontend/src/components/ReportContent.tsx), [조회 품질 요약](../../../frontend/src/lib/report.ts), [결과 화면](../../../frontend/src/pages/Results.tsx).

일반 HTTP에서도 멱등 키·요청 hash 생성이 가능하도록 UUID는 getRandomValues, SHA-256은 설치된 해시 구현을 사용한다. 원본은 [browserCrypto](../../../frontend/src/lib/browserCrypto.ts)다. 기존 QA의 과거 데모 기록은 날짜별 현행 검증과 구분하며 이번 문서 갱신을 새 실행 시험으로 기록하지 않는다.

## 접근성·완료 조건

키보드 이동·포커스·폼 label·오류 연결·표/차트 대체 설명을 제공한다. 320px에서 핵심 입력·상태가 잘리지 않게 확인한다. 로딩/빈 목록/관측 부족/서버 장애를 서로 구분한다. 새로고침·직접 URL·뒤로 가기로 저장 결과와 occurrence를 다시 찾을 수 있어야 한다.
