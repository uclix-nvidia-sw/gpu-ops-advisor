# 14. 모듈 간 호출·공통 실행 계약

버전 1.3 · Backend / Incident / Job Controller / RCA / Report 공통

## 경계와 원장

Backend→JC는 report, Incident→JC는 rca만 접수한다. 두 Agent는 JC에서 claim하고 heartbeat/complete/fail을 보낸다. Agent별 접수 서버·개별 큐를 두지 않는다. 정기 발생은 Backend에 있다. 인증은 범위 밖이며 source_module은 신원 증명이 아니다. 배포 연결상 GUI의 업무 요청은 Backend만, Grafana 알람 Webhook은 Incident만 호출한다. Agent의 관측 조회는 반대 방향인 Agent → Grafana MCP → Grafana 데이터소스 경로다.

업무 데이터 소유권은 [03](03_데이터_설계서.md), 큐 선택 정책은 [10](../job-controller/10_Job_Controller_모듈_설계서.md)이 원본이다. 공통 라이브러리는 모듈별 저장 함수를 제공하고 jobs·attempts 직접 변경은 JC만 수행한다.

## 접수 DTO

`contract_version="1.3",source_module,source_key,kind,input,deadline_at,execution_profile_revision`을 사용한다. outbox 기반 자동 요청은 `dispatch_deadline`과 원본 snapshot 참조도 포함하며 재전송에서 바꾸지 않는다. rca는 source_module=incident와 실제 incident snapshot 연결, report는 source_module=backend가 필수다. source_key는 경로 사용을 위해 URL encode한다. input의 정규화 hash는 타임스탬프 UTC·정렬한 scope·주제 ID로 계산하되 뜻이 다른 요청을 합치지 않는다.

JC는 `(source_module,source_key)` 유일 키로 receipt와 job을 같은 트랜잭션에 커밋한다. 같은 키/같은 hash는 기존 job을, 다른 hash는 409 idempotency_conflict를 반환한다. 응답은 `{job_id,kind,status,version}`. 202는 영속 접수 확인이며 실행 시작 보장이 아니다.

Backend의 수동 보고서는 같은 클라이언트 멱등 키로 재확인한다. Incident와 정기 보고서는 생산자 DB의 outbox를 사용한다. outbox가 failed로 끝나기 전 receipt를 조회해 이미 접수된 job이 있는지 먼저 확인한다. 전송 경합 동안 expired outbox가 접수되는 것을 막도록 JC도 전달 snapshot의 dispatch_deadline을 검사한다. 마감 직전 접수 후 응답이 사라진 경우 receipt 확인 결과를 우선한다.

### RCA 접수 계약 1.4 변경 목표와 이행

2026-09-22 설계 변경이며 아직 구현되지 않았다. 위 1.3 DTO는 기존 잡에 유지한다. 신규 RCA는 `contract_version="1.4"`로 구분하며 보고서의 접수 계약과 결과 스키마 1.1은 이번 변경으로 바꾸지 않는다. API 경로·JC 큐·Worker 실행 프로토콜의 소유권은 유지한다.

| 항목 | 신규 RCA 계약 |
|---|---|
| 생산자·멱등 키 | Incident만 생성; `source_key=incident:<incident_id>:first`, 관측 에피소드당 최초 1회 |
| input | incident_id, evidence_version=1, scope, target 또는 확인된 사건 범위, incident_time, 절대 time_range, 있으면 prior_incident_id; DB의 최초 snapshot 연결·hash 검증 |
| 원문 | 최초 alert의 labels/annotations/status/startsAt 등을 snapshot에 고정. 알람의 코드를 검증된 fact로 승격하지 않음 |
| 제거되는 입력 | Incident가 정한 purpose_ids·analysis_profile_revision. 신규 스키마는 이 필드를 받지 않으며 R01/R02를 암묵 기본값으로 주입하지 않음 |
| 실행 설정 | 기존 execution_profile_revision 및 claim versions에 query/parser/선택 규칙·knowledge·예산을 고정 |
| 목적·경로 | Agent가 파싱·관측 근거로 선택, 기존 evidence에 추적 기록; 입력 snapshot은 변경하지 않음 |
| 결과 검증 | 1.4는 Agent의 목적 선택 trace와 assessments를 검증; 1.3은 기존 요청 목적 목록과 대조 |
| 중복 처리 | 관측이 이어지는 동안의 반복 firing·증거/설정 변화·resolved는 새 job 생성 없음. JC 기술 재시도만 같은 job의 새 attempt |
| 재발 처리 | 13 §2.3의 종료 후 새 증거 조건을 통과해야 새 사건이다. 직전 종결이면 새 job, open/acknowledged면 사건만 기록한다. 과거 payload 재전송과 resolved 선접수는 새 사건/job이 아니다. JC는 Incident의 에피소드 판정을 재수행하지 않는다 |

구현 순서는 ① [03 §6](03_데이터_설계서.md)의 생명주기 상태·nullable/제약·Worker 지원 계약 열과 부분 유일 인덱스를 추가 migration으로 준비하고 기존 생명주기의 다중 귀속을 점검 ② JC/shared·Worker 및 Backend/Frontend/Ops 호환 소비자 배포 ③ 기존 Incident 복제본 정지·drain 후 legacy 생명주기 귀속을 최종 반영하고 생산자·Helm 설정 전환이다. 알람 자연키 UNIQUE는 사건 테이블에 적용하지 않는다. 아래 지원 계약 필터가 혼합 Worker 시험을 통과한 뒤 신규 접수를 켠다.

전환 당시 이미 존재한 생명주기는 다시 전달하지 않는다. 기존 pending outbox는 원래 1.3 키·입력으로 완료하고, 기존 정책 미등록 사건을 자동 backfill하지 않는다. 과거 다중 evidence/job·정책 revision도 보존하며 새로운 최초 1회 제약을 과거 행에 일괄 강제하지 않는다. source_key·snapshot·hash를 재작성하지 않는다.

롤백은 신규 접수를 먼저 멈추고 1.4 pending/queued/running을 지원 소비자로 처리하거나 보존한 뒤 진행한다. 1.4 snapshot을 1.3으로 변환하거나 신규 사건을 구 정책으로 재접수하지 않는다. 구 생산자가 이미 기록된 생명주기를 재분석하지 않도록 검증하기 전에는 수신을 재개하지 않는다. DB 역마이그레이션·PVC 삭제는 롤백 절차가 아니다.

### 입력 계약 버전 전달·배분 — 1.4 추가 개발 목표

| 경계 | 확정 계약 |
|---|---|
| 접수 → 저장 | JC가 검증된 envelope.contract_version을 `jobs.versions.input_contract`에 고정. 새 RCA는 1.3/1.4, report는 1.3만 허용; 사용자가 versions를 덮어쓰지 못함 |
| 과거 job | 필드가 없는 기존 job만 소비 시 1.3으로 해석. 원래 input/hash/versions를 DB에서 재작성하지 않음. 명시된 알 수 없는 버전은 오류이며 1.3으로 강등하지 않음 |
| 등록 | `supported_contract_versions` 문자열 배열 추가. 생략은 `["1.3"]`, 빈 배열·미지원 버전·kind 불일치는 422. 같은 worker/boot 재등록은 같은 capability만 허용, 변경은 새 boot 필요 |
| 배분 | JC는 저장한 worker/boot의 kind와 지원 계약에 모두 맞는 job만 선택. 슬롯·공정성·Worker 가용성 계산도 호환 후보에 적용. claim 인자로 capability를 덮어쓰지 못함 |
| 호환 Worker 없음 | 접수된 job은 queued, 대기 사유는 기존 `worker_unavailable`. deadline은 계속 적용. 구 Worker에게 넘기거나 기술 실패로 소진하지 않음 |
| claim → 결과 | claim.versions의 input_contract를 Worker가 재검증하고 새 결과 versions에도 그대로 보존. Backend/Ops는 결과 스키마 1.1과 입력 계약 버전을 별도로 읽음 |

기존 profile·큐·Worker 등록 저장소를 확장한다. register의 capability는 배분 호환 정보이며 인증 수단이 아니다. 1.4 RCA Worker는 1.3/1.4 두 경로의 회귀 검수를 통과하고 두 버전을 등록한다. 구 JC는 이 필터를 모르므로 1.4를 허용하는 동안 구 JC 복제본을 혼재시키지 않는다.

### 현행 1.3 등록·claim DTO

register 입력은 `{worker_id,boot_id,kind,capacity_profile_id}`. 운영 설정에 없는 profile 또는 kind 불일치는 422다. profile의 slots와 한도는 서버 값만 쓴다. Agent 재시작마다 boot_id가 바뀌며 이전 boot의 점유는 종료 확인/lease 정책으로 회수한다.

claim 입력 `{worker_id,boot_id,kind}`. 응답 200은 `{job_id,kind,input,attempt_no,claim_token,lease_expires_at,deadline_at,versions,budget}`이며 하나의 잡만 반환한다. 204는 현재 배분 없음, 503은 큐 DB 일시 장애다. 같은 Agent가 동시에 여러 claim을 보내도 DB의 worker_slots를 넘지 않는다. 공통 capacity 잠금 → job → attempt/lease 순서로 잠가 교착 순서를 통일한다.

처리 여유가 없는 Agent는 claim하지 않는다. 모듈별 고정 concurrency와 JC의 서버 한도를 함께 적용한다. 실행 프로필은 한 job의 모델 호출을 직렬로 제한하고 실행 중 shared slot 하나를 보유한다.

## 실행·heartbeat·완료

heartbeat 입력 `{attempt_no,claim_token,stage,remote_call_state}`; 현재 attempt와 유효 lease일 때 갱신하며 `{lease_expires_at,cancel_requested,deadline_at}`를 반환한다. 만료 뒤 이전 토큰의 갱신은 409다. Agent는 lease 갱신 실패·취소·deadline을 확인하면 새 도구 호출을 멈춘다.

1. Agent는 고정 입력·버전으로 실행하고 evidence와 결과 candidate를 자기 저장 트랜잭션으로 쓴다. candidate는 아직 공개 final이 아니다.
2. complete에 `{attempt_no,claim_token,candidate_id,content_hash}`를 전달한다.
3. JC는 job 잠금 아래 attempt·토큰·lease·deadline·취소 여부, candidate의 kind/job/attempt/hash·schema 검증 결과를 확인한다.
4. 같은 트랜잭션에서 published_result_id 설정·succeeded·attempt 종료·슬롯 반환을 확정한다. 조회는 이 참조만 사용한다.
5. 같은 candidate/hash의 complete 재전송은 기존 성공 응답을 반환한다. 다른 후보나 늦은 attempt는 409다.

이 구조는 Agent의 후보 저장 후 JC 응답 전에 끊겨도 재시도로 복구된다. candidate를 저장한 것만으로 성공 표시하지 않는다. 이후 retry가 있더라도 과거 attempt 후보를 새 attempt의 final로 재활용하지 않는다. 근거·결과 파일 checksum을 확인하고 final 참조 뒤 파일을 덮어쓰지 않는다.

## 실패·취소·마감

fail 입력은 attempt/token, code, retryable, remote_call_state. 일시 오류만 backoff+jitter로 retry_wait, max_attempts/deadline/누적 예산 소진·영구 입력 오류는 failed다. 데이터 부족은 부분/보류 결과를 정상 저장할 수 있으며 실행 실패와 다르다.

cancel은 queued/retry_wait면 즉시 cancelled, running이면 cancel_requested_at을 먼저 기록한다. complete와 cancel이 경합하면 DB 잠금으로 먼저 확정된 상태를 따른다. final이 먼저 확정됐으면 취소 409다. 취소/만료 뒤 late 결과는 발행하지 않는다. report의 수동 retry는 남은 예산의 기술적 재시도에만 적용한다. 새로운 내용은 새 report job이다.

Worker lease 만료 시 새 attempt가 생겨도 이전 원격 LLM 호출이 실행 중일 수 있다. 종료가 불명확하면 공유 슬롯 reservation을 quarantined로 유지해 중복 추론 용량을 제한한다. 검증된 원격 수명 또는 운영 확인 전에는 반환하지 않는다. 이 동안 해당 잡은 inference_quarantined 사유로 대기한다. 단순 HTTP timeout을 종료 증거로 쓰지 않는다.

## 명령 멱등·예산·오류

cancel/retry는 `(operation,job_id,Idempotency-Key)` receipt와 request_hash를 사용한다. 같은 명령 재전송은 receipt를 먼저 확인하고 최초 요청에만 If-Match를 적용한다. 상태 변경·receipt 저장은 원자적이다. 수동 retry로 deadline·총 토큰 예산·max_attempts를 리셋하지 않는다.

| 오류 | 처리 |
|---|---|
| invalid_input/source_kind_mismatch | 422, 입력 수정 전 반복 금지 |
| stale_attempt/idempotency_conflict/version_conflict | 409, 상태 재확인 |
| capacity_wait/worker_unavailable | claim 204, 접수된 잡은 대기 |
| dependency_unavailable | 503 또는 실행 retry_wait, 제한 backoff |
| insufficient_data | result_status=blocked/partial, 정상 저장 가능 |
| narrative_failed | 계산·근거 보존, 설명만 failed/omitted |
| deadline_exceeded | expired, 새 호출/결과 발행 금지 |

버전 스냅샷에는 query/parser/criteria/result_schema/knowledge/model/execution profile을 고정하며 추가 개발 경로는 위 input_contract도 고정한다. DB/계약 변경은 추가 필드 → 호환 소비자 → 생산자 순으로 배포한다. 실행 중 잡을 새 설정으로 조용히 해석하지 않는다. RCA 1.4의 이력은 [03 §6](03_데이터_설계서.md)의 목적 선택 전 단일 DB snapshot으로 확보하며, 목적 추가 후 임의 재조회로 cutoff를 이동하지 않는다.

## NAT 워크플로와 Grafana MCP 실행 계약

NAT 도입 자체는 기존 접수·claim·heartbeat·complete/fail DTO와 소유권을 바꾸지 않는다. Incident 역할 변경에 따른 RCA 접수 1.4 차이는 위 이행 절을 따른다. NAT는 각 Worker 내부 실행 라이브러리이며 업무 접수 서버·추가 큐를 만들지 않는다. 아래 논리 계약은 Agent 내부 함수와 배포 설정에 적용하며 GUI API의 새 필드를 요구하지 않는다.

| 구간 | 고정·검증할 내용 | 실패 시 |
|---|---|---|
| Worker → NAT | job_id/attempt_no, 고정 입력·버전, deadline·남은 예산, 취소 상태 | 실행 불가/버전 불일치는 성공 처리하지 않음 |
| RCA → Runbook | 호환 범위·발행 revision·hash·적용 조건 | 미일치는 등록 일반 조사, 저장소 장애는 조회 실패로 구분 |
| Agent → MCP 업무 함수 | 등록 query ID/revision, scope·대상·절대 기간, datasource 매핑, 행/바이트·호출 한도 | 범위 밖 요청 차단, 제한 초과는 부분/보류 결과 |
| MCP → Agent | 원본·조회 시각, 단위·식별자·완전성·잘림·오류 | 03 정규화 후 tool_status·quality로 전달 |
| 보고서 → RCA DB | 공개 result ID/hash와 읽은 사건 snapshot 고정 | RCA 미완료 표시, 새 RCA 요청 없음 |
| NAT → Worker | 04 스키마의 결과와 evidence 참조, 종료 사유 | 검증 후 candidate 저장; NAT 반환만으로 succeeded 금지 |

### 도구 연결과 입력 통제

두 Agent는 각각 NAT MCP 클라이언트를 가지고 운영자가 설정한 같은 Grafana MCP endpoint를 사용할 수 있다. 기본 연결은 배포 프로필로 고정한 Streamable HTTP이며 endpoint·프로토콜·tool schema는 기동 시 확인한다. 필요한 조회 도구만 allowlist로 연결한다. 원격 tools/list에 새 도구가 추가돼도 자동으로 LLM에 노출하지 않는다.

초기 관측 도구는 query_prometheus와 query_loki_logs를 검증 대상으로 한다. 모델은 업무 도구에 query ID와 허용 인자를 전달하며 Python 함수가 등록된 PromQL/LogQL·datasource·selector를 구성한다. LLM이 원격 쿼리 도구에 자유 형식으로 직접 접근하는 경로는 두지 않는다. DB·Runbook 읽기는 별도 고정 함수이며 Grafana MCP를 통해 업무 DB를 수정하지 않는다.

운영 설정의 datasource UID/CPC 매핑, query revision과 호출 상한을 실행 동안 고정한다. MCP 응답의 잘림·최대 구간·시간 경계·중복은 03/04에서 검증한다. MCP 장애를 피하려고 Agent가 Mimir/Loki 직접 조회로 조용히 전환하지 않는다. 기존 Backend 조회 경로는 별개다.

### 시간 제한·취소·재시도·버전

- heartbeat는 NAT·MCP·LLM 호출과 독립적으로 진행한다. 각 호출 전 lease·취소·남은 deadline·예산을 확인하고 호출 timeout을 남은 실행 시간 이하로 제한한다.
- 취소나 lease 상실 시 새 도구·추론 호출을 중단하고 가능한 진행 요청의 취소를 전달한다. 로컬 coroutine 취소가 원격 종료 증거는 아니다. 원격 LLM 종료 불명은 기존 quarantine 규칙을 적용하고 MCP 조회 종료 불명도 기록하며 즉시 중복 재호출하지 않는다.
- 한 잡의 모델 호출은 직렬이며 기존 shared slot 하나를 유지한다. NAT의 병렬 도구 실행·자동 모델 재시도는 이 예산을 우회하지 못한다. 모델/도구 재시도와 MCP 재연결을 포함한 상한을 설정하고 실제 요청 재전송은 호출 예산에 합산한다. 작업 단위 새 attempt는 JC만 만든다.
- NAT 패키지·워크플로/프롬프트·도구 schema·MCP 서버 버전은 고정된 실행 프로필에 연결된 불변 배포 manifest로 보관하고 evidence snapshot에서 참조한다. query/parser/criteria/result_schema/knowledge/model/execution profile의 기존 고정 규칙을 유지한다. NAT 설정만을 위한 DTO·DB 열 확장은 하지 않는다. RCA 접수 1.4의 필드/제약 변경은 위 이행 절에 따른다.
- NAT trace를 job_id·attempt_no·도구 호출 ID에 연결한다. 로그에 비밀값을 기록하지 않으며 trace의 완료 표시는 JC의 업무 완료를 대신하지 않는다.

실환경 도구 스키마·원본 해상도·모델 tool calling·취소 동작은 C11/C12와 T33~T40에서 확인한다. NAT 자체만으로 DSX의 내구성·중복 방지·범위 제한이 보장된다고 간주하지 않는다.
