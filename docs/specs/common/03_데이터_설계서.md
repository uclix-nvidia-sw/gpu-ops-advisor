# 03. 데이터 설계서

## RCA 개별 관측과 기간 완전성 (2026-09-30)

Loki 밀리초 경계 축소 시 원본 `time_range`와 `quality.complete=false/reason=time_precision_reduced`를 보존하고 실제 범위는 `quality.request_time_range`에 기록한다. 경고·잘림 없는 성공 응답의 `observation_usable=true`는 실제 구간 안의 개별 health 관측을 RCA 해석에 사용할 수 있다는 뜻이다. 전 기간 무오류·지속 시간·Ops 집계를 완전한 것으로 바꾸지 않는다. 다른 partial은 제외한다.

Fleet 중첩 로그는 등록 adapter에서 machine/node/component, Loki ns 시각, reason과 XID/SXID 코드를 정규화한다. 기본 `time_basis=loki_recorded_at/fact_eligible=false`는 보고 관측이며 장비의 실제 관측 시각이나 현재 상태를 확정하지 않는다. [시각·freshness 승격 조건](../../../rcca-agent/README.md#2026-09-30-fleet-rca-수집분석-보완)을 별도로 검증해야 한다. 저장은 기존 evidence snapshot/result JSON이며 새 테이블·migration은 없다.

버전 1.3 · 신규 구현 모델. 실제 테이블 생성·적재 완료를 뜻하지 않는다.

## 1. 저장소와 소유권

| 저장소/데이터 | 쓰기 책임 | 읽기/사용 |
|---|---|---|
| Mimir·Loki 원본 | 기존 CPC 수집 기반 | Agent는 Grafana MCP, Backend는 기존 조회 경로 |
| 사건·알람·Incident outbox | Incident | Backend·RCA·보고서 |
| 일정·발생·Backend outbox·설정·지식·검토 | Backend | GUI·각 모듈의 고정 입력 |
| jobs·attempts·receipt·Worker·슬롯 예약 | Job Controller | Backend·Agent 내부 API |
| RCA candidate·근거 | RCA Agent | JC 검증 후 발행된 참조만 Backend·보고서 조회 |
| 보고서 candidate·근거·파일 | 보고서 Agent | JC 검증 후 발행된 참조만 Backend 조회 |
| Runbook 발행본 | Backend 지식 관리 | RCA가 호환 revision 검색·적용 조건 검사 |
| 관측 관계/품질 snapshot | 호출 모듈의 공통 저장 코드 | 결과 근거 재현 |

업무 DB는 초기 PostgreSQL 하나를 공유한다. 공통 라이브러리는 별도 서비스가 아니며 모듈 소유 함수를 제공한다. Agent는 jobs를 직접 갱신하지 않는다. JC는 candidate 내용을 수정하지 않고 jobs.published_result_id만 확정한다. 파일은 별도 업무 저장 경로와 checksum을 쓰며 Mimir/Loki 내부 블록을 직접 조작하지 않는다.

인증·대화·사용자 tenant용 테이블은 만들지 않는다. 기존 수집 저장소의 tenant 값은 연결 설정이며 제품 권한 모델이 아니다.

## 2. 수집·조회 경로 기준

| 범위 | 현재 자료 기준 | 적용 원칙 |
|---|---|---|
| 두 CPC 공통 | CSC 중앙 조회와 GPU↔Pod 활용 가능이라는 사용자 확인 | 기능을 두 CPC에 제공하되 대상별 실제 값·필터·기간 검증 |
| CPC-2 KSM/Exporter | Alloy EndpointSlice 발견·직접 scrape → Gateway → Mimir | 신규 GPU Ops 경로. 기존 Prometheus는 별도 모니터링으로 유지 |
| Fleet | Fleet → Alloy → Gateway → Mimir/Loki | 대표 필드와 로그 원문 계약은 각 생산자 기준 |
| CPC-1 직접 수집 | 후속 적용 확인 항목 | CPC-2 전환 완료를 그대로 복제하지 않음 |
| CPC-2 UID | Exporter 작업 라벨 + 같은 시점 KSM uid 조인 성공 기록 | Exporter UID 옵션 false 유지 기록 반영. 별도 Mapper 서비스 필수 아님 |
| 최신 로그 | CPC-2 최종 재배포 뒤 Loki 최신 도착 확인 대기 기록 | 기존 로그 전송 기반과 해당 재배포 검증을 구분 |

Mimir는 공통 tenant `cpc-1`에 대상 `cluster_id` 필터를 적용한다. CPC-2 Loki 표본은 tenant `cpc2`, 라벨 `cluster=cpc2`다. CPC-1 Loki 실제 값은 C02에 등록한다. 이 값은 과거 수집 환경의 연결 설정이며 현 배포에서 재확인한다. 제품 인증·tenant 설계를 추가하는 근거로 쓰지 않는다.

### 2.1 Agent의 관측 접근과 업무 DB 접근

관측 수집 경로는 유지한다. 두 Agent는 각각 NAT MCP 클라이언트로 운영자가 연결한 Grafana MCP 서버에 접근하고, MCP는 Grafana에 등록된 Mimir의 Prometheus 호환 데이터소스와 Loki 데이터소스를 조회한다. Grafana MCP는 조회 연결 구성 요소이며 DSX 잡 큐·지식·업무 결과를 소유하지 않는다. Backend의 기존 관측 조회까지 MCP로 일괄 전환하지 않는다.

| 접근 경로 | 범위·목적 |
|---|---|
| RCA → Runbook DB | 호환 published knowledge_revisions와 필수 증거·권고 검사 |
| RCA → Incident DB | 입력이 가리키는 불변 사건 증거 snapshot 읽기 |
| RCA → Grafana MCP | 사고 전후 로그·지표·관계 조회, 추가 조사 |
| 보고서 → Incident·RCA DB | 기간·scope 내 사건과 공개된 RCA 결과 읽기 |
| 보고서 → Grafana MCP | 확정 기간의 지표·관련 로그·매핑 이력 조회 |
| 각 Agent → 자기 결과·근거 저장 | 자기 job/attempt의 candidate·evidence 저장; 공개 확정은 JC |

이는 논리 데이터와 소유권의 구분이며 Runbook·RCA·보고서마다 물리 DB 서버를 추가하지 않는다. DB 읽기와 저장은 정해진 함수로 수행하고 LLM에 임의 SQL 도구를 제공하지 않는다. DSX Incident/RCA 이력은 이 업무 DB를 사용하며 Grafana Incident 제품의 이력과 혼동하지 않는다.

MCP 응답은 기존 §5의 정규화 계약으로 변환한다. datasource UID·CPC별 selector·query revision·단위·원본 시각·해상도·행/바이트 제한과 응답 잘림 여부를 확인한다. 분할 조회는 경계 중복을 제거하고 완전한 기간 확보에 실패하면 partial/unavailable로 보존한다. 빈 조회·조회 실패·실제 0을 구분한다. 필요한 원본 시각·해상도를 MCP가 보존하는지 실환경 검수하기 전에는 해당 계산의 준비 완료로 표시하지 않는다.

evidence.snapshot_ref가 가리키는 불변 문서에는 출처 종류, datasource UID 또는 지식/결과 ID·revision·hash, query ID/revision·정규화 인자, 대상·기간, 조회 시각, 완전성/잘림, 제한된 응답과 checksum을 기록한다. 기존 snapshot 저장 형식을 사용하고 이번 개정에서 새 DB 열·결과 최상위 필드를 요구하지 않는다. 비밀값과 인증 헤더는 저장하지 않는다.

보고서는 수집 기준 시각과 참조한 사건 상태·공개 RCA result ID/hash를 evidence로 고정한다. 후보·실패 attempt는 원인 분석 완료 자료로 읽지 않는다. 사건만 있고 공개 RCA가 없으면 미완료로 표시하며 사건 없음·관측 실패와 구분한다. 보고서에서 인용한 RCA 결과·근거는 해당 보고서의 보존 기간 동안 추적할 수 있도록 유지한다.

대표 소스는 의미 ID·모델·CPC·유효 기간별로 선택한다. Fleet/Exporter 어느 한쪽을 전역 우선으로 고정하지 않는다. 대소문자가 다른 이름은 생산자·정의 검증 없이 같은 시계열로 합치지 않는다. 소스 변경 전후의 `collection_path`·전환 시각·revision을 남긴다.

데이터 사전 revision에는 `meaning_id, source_name, source_version, raw_field, raw_unit, normalized_unit, value_type, entity_kind, supported_models, invalid_values, labels, query_id, original_period, max_age, valid_from/to, verification_scope, evidence_refs`를 기록한다. 미검증 원본 이름은 null이며 후보 이름을 실행 템플릿으로 발행하지 않는다.

### 3.2 장비 상태 정규화

`raw_health`는 원문 값 또는 null이며 `check_status=valid|unavailable|skipped|initializing|unknown`, `normalized_health=healthy|degraded|unhealthy|unknown`, `severity=info|warning|critical|unknown`은 등록 parser와 정책이 산출한다. `component`, 대상 키, 원본 시각, producer contract·parser revision·원문 근거를 함께 기록한다. 원문에 없는 필드·검사 성공을 추정하지 않는다. 실제 사건·회복 판정표는 11의 상태 판단 계약을 적용한다.

유효한 Degraded는 경고/이상 근거가 될 수 있으나 검사 불가 Healthy는 정상·회복 근거가 아니다. 의도적 제외·Initializing·로그 단절은 검사·수집 상태로 보존하고 그 사실만으로 장비 장애나 회복을 확정하지 않는다. 회복에는 C08의 승인된 유효 정상 연속 관측 조건이 필요하다.

원본의 `incidents` 등 배열은 전체 원문을 유지하고 모든 하위 GPU/항목을 정규화한다. 첫 항목만 처리하지 않는다. 항목별 식별자·경로와 parser 오류를 남겨 부분 성공도 추적한다.

### 3.3 D 정의·역할과 복수 관측 확장 — 2026-10-02

**상태: 기존 D 기준의 조사·후보 자료이며 최종 재설계 명세가 아니다. 현재 전체 메트릭의 실환경 확인은 미완료다.** 기존 분류 유지와 복수 하위 관측 구조 채택이라는 앞선 전제는 철회한다. D 번호·경계·구조는 [D 계약 재설계 개발 계획](d-contract-redesign-plan.md)의 P2에서 유지·분리·통합·폐기를 결정한다. 아래 표는 조사 근거를 재사용하기 위한 기존 D별 대조표다. 부서 데이터와 부서 매핑은 이번 범위에서 제외한다. 이 문서 개정은 실행 설정·Runbook·O·과거 결과의 의미를 변경하지 않는다.

#### D의 책임과 경계

재설계할 D는 RCA와 보고서가 공유하는 관측 데이터 계약이다. 단일 의미 관측으로 나눌지, 복수 관측을 묶을지는 미정이며 아래 복수 관측 설명은 검토할 한 가지 구조다. 개별 조회 결과의 식별, 단위·시간·대상 정규화, 등록된 파생 사실의 계산까지 D 계약에 포함한다. RCA Runbook은 그 사실로 원인 후보와 조사 분기를 판단하고, O는 기간 통계·비교·운영 결론을 구성한다. D 자체가 원인이나 업무 효과를 확정하지 않는다.

D01~D14와 `D03.used`, `D03.free`는 기존 대조 및 구조 예시일 뿐 유지하거나 채택할 식별자가 아니다. 새 D는 실제 데이터 의미와 소비 목적에 맞춰 정의하며, 개별 관측의 명시적 식별 원칙만 유지한다. 같은 원본이 여러 D에 필요하면 조회 응답을 재사용하되 논리 역할과 근거 참조를 보존한다. 예를 들어 D01의 신원 라벨, D02의 활동값, D08의 Pod 연결 라벨은 같은 원본을 활용할 수 있지만 같은 사실은 아니다.

Fleet와 DCGM Exporter의 동일 의미 관측을 합산하지 않는다. 원천 필드가 같아도 수집 주기·대상·단위·유효 구간을 검증한 후 대표 소스를 선택한다. 다른 소스는 교차 확인용으로 남길 수 있다. Kubernetes는 객체·배치 상태, DCGM은 장치 관측을 제공하므로 신원·시간이 맞는 구간에서만 연결한다.

| **D14 제품 업무 이력**: 과거 사건·분석·조치와 연결 | queries 밖의 DB context, report_db_snapshot | 기존 고정 DB 함수로 Incident·공개 RCA ID/hash·실제 조치·revision 조회. 신규 외부 metric 없음 | 사건 빈도·공개 판단·조치 사실. RCA 이력 조사, O05/O06/O10. 후보 결과를 공개 RCA로 읽지 않으며 새 SQL 실행 도구나 조회 서비스 추가 안 함 |

D02의 통신 활동과 D05의 통신 오류, D03의 용량과 D05의 메모리 오류는 관측 목적이 다르다. 동일 원본을 중복 합산하지 않는다. 새 관측을 기존 D에 억지로 배치하지 않는다. 새 경계와 배치는 P2에서 결정하고 의미 미확정 항목은 후보로 남긴다.

#### 개별 관측 정의와 결과 식별 검토안

개별 항목의 필수 정의는 다음과 같다. 모든 항목에 임의 PromQL/LogQL을 허용하는 범용 엔진을 먼저 만들지 않고, 검증한 source binding과 등록된 parser/calculation을 사용한다.

| 정의 | 필요한 내용 |
|---|---|
| 식별 | D ID, item ID, meaning ID, query/parser revision |
| 조회 | source·실제 metric/로그 필드, 고정 조건, 허용 scope·대상·기간 인자 |
| 대상 | entity kind, 신원 키, 지원 필터, 다른 D와의 연결 조건 |
| 값 | 원본/정규화 단위, gauge/counter/bitmask/info/event/relation, 오류값·리셋 처리 |
| 시간 | 원본 시각, 검증된 주기·유효 유지 상한, 발생/수신 시각 구분 |
| 출력 | 생산할 fact/metric 이름, 등록 parser·계산 함수, 근거 참조 |
| 의존성 | 다른 item 입력, 필수/선택 여부, 대체 소스의 의미 동등성 조건 |
| 가용성 | 확인한 환경·기간·생산자 버전·검증 근거, 미확보 사유 |

계획은 D와 필요한 item을 선택하고 의존 입력만 추가한다. D 전체를 선택할 수도 있지만 새 항목이 추가됐다는 이유로 모든 Runbook/O가 자동으로 전부 조회하지 않는다. Node 수준 데이터에 Namespace 필터를 무조건 붙이지 않는다. 허용 대상 관계를 확인해 투영하거나 지원 불가를 반환하며 권한 범위를 넓히지 않는다.

결과는 item별 상태·시계열/사건·단위·근거를 유지한다. `D03.used`와 `D03.free`를 같은 값 배열에 구분 없이 섞지 않는다. 같은 item 안에서도 cluster+대상 신원+원본 시각으로 구분한다. 소비자는 배열 순서가 아닌 item/출력 이름으로 입력을 선택한다. used 성공/free 실패이면 사용량은 보존하고 두 입력이 필요한 계산만 보류한다. 묶음의 성공 여부만으로 모든 입력을 정상 처리하지 않는다.

수집·단위 변환·신원/시간 조인·계산·품질 판정은 LLM 없이 코드로 수행한다. 예를 들어 메모리 비율은 같은 GPU·호환 생산자·겹치는 유효 구간·검증된 용량 정의·양의 분모일 때만 계산한다. 원인 해석과 운영 설명은 RCA/O에서 수행하며, 수집되지 않은 fact를 LLM이 보충하지 않는다.

#### 실환경 가용 목록 확인의 완료 조건

이번 개정에서는 아래 조사를 실행하지 않았다. 설정 이름·과거 표본·소스 목록의 확인만으로 완료 표시하지 않는다.

1. CPC별 현재 datasource와 producer/배포 버전·수집 경로를 확인한다. 인증 정보는 문서에 남기지 않는다.
2. 허용 범위·명시한 조회 기간에서 metric 이름·메타데이터·라벨과 Loki stream/구조화 필드를 페이지/조회 한도 내에서 조사한다. limit 초과·권한 제한·기간 제한을 기록한다.
3. 항목마다 대표 표본, 실제 중앙 이름, 단위/타입, 대상 신원, 원본 시각·주기·보존 범위, 의미 검증 근거를 기록한다. 빈 기간과 전역 미수집을 구분한다.
4. Fleet/Exporter 중복과 KSM 연결 가능성을 확인하고, 각 item을 확인됨/후보/미확보로 표시한다. 분석 적격성은 요청 기간마다 별도로 검사한다.
5. 산출 목록은 `cluster, source, producer/version, observed_window, raw_name/field, labels, type/unit, sample_time, D/item, verification, evidence_ref, limitation`을 포함한다. 이 목록이 D별 실제 실행 binding의 근거다.

후속 구현 검수에는 item 하나만 실패, 빈 결과와 0, 단위 불일치, counter reset, 겹치지 않는 시각, 같은 GPU의 중복 생산자, Namespace 없는 Host 관측, 불가능한 Runbook fact 요구, 기존 D revision 결과 열람을 포함한다. 두 Worker에서 사실·근거·보류 사유를 확인하며 fixture 통과와 운영 Grafana 의미 검증을 구분한다.

## 4. 식별·연결·시간

| 대상 | 기준 키 | 제한 |
|---|---|---|
| CPC | cluster_id | tenant 이름과 별개 |
| Node | cluster_id + node_uid 또는 검증된 node instance | 이름 재생성·장비 교체를 이름만으로 합치지 않음 |
| GPU | cluster_id + gpu_uuid | Node 관계는 시간별 관리. index·PCI는 보조 식별 |
| Pod | cluster_id + pod_uid | UID 미확인은 null, namespace/name은 표시·현재 조회용 |
| Container 실행 | Pod UID + container name + container ID/실행 구간 | 같은 Pod 재시작을 별도 Pod나 자동 할당 해제로 해석하지 않음 |
| MIG | 부모 UUID + 실제 instance ID + 구성 유효 구간 | 프로파일을 instance 영구 ID로 사용하지 않음 |
| Workload·소유권 | controller UID·owner chain / 명시 소유권·유효 구간 | Namespace·node_group만으로 팀·사람 추정 금지 |

CPC-2의 동시점 GPU 소스 결합 키는 `cluster_id+node+uuid`; UID 결합 키는 `cluster_id+namespace+pod+node`다. 원본 `uid`를 `pod_uid`로 정규화하고 출처를 보존한다. Exporter 자체 라벨은 `exporter_*`, 작업 라벨은 namespace/pod/container로 구분한다. 활동률 > 0으로 매핑을 사전 필터링하지 않는다.

모든 저장 시각은 timezone-aware UTC이며 기간은 `[start,end)`다. `occurred_at`(발생), `observed_at`(원본 관측), `ingested_at`(수신), `evaluated_at`(조회 평가), `data_cutoff_at`(입력 마감)을 별도 기록한다. 같은 평가 시각이어도 원본 시각·신선도가 맞아야 조인한다.

폴링 이력은 같은 관계가 인접 성공 관측에서 유지되고 간격이 검증된 원본 주기 T의 2배 이내인 구간만 관측 기반으로 연결한다. T 미확인·장기 공백·상충 UID·변경 경계는 기간 귀속 보류다. 마지막 값을 분석 종료까지 연장하지 않는다. `valid_to=null`은 무한히 유효한 할당을 뜻하지 않는다.

### 4.1 기간 이력 생성 책임

이번 구조는 **Mimir에 보존된 원본 이력에서 요청 기간의 관계를 복원**한다. Agent는 Grafana MCP, Backend는 기존 조회 경로로 표본을 확보하고 같은 관계 복원·계산 규칙을 적용한다. 실제 공유 가능한 Python 정규화·계산 함수는 두 Agent가 재사용하며 Go Backend에 Python 라이브러리 호출을 요구하지 않는다. 화면 접속·현재 매핑 저장 여부에 의존하지 않는다. 별도 주기적 Mapper나 원시 시계열 전량 복제를 추가하지 않는다.

등록 query는 GPU 작업 라벨, KSM UID, 수집 성공·완전성/기대 대상 이력을 같은 허용 scope·기간으로 조회한다. 지원되는 원본 range-vector 구간 조회 등 원본 표본 timestamp를 보존하는 방식을 검증해 등록한다. query_range의 평가 격자 표본 수를 원본 관측 수로 세지 않는다. 평가 시각마다 반복 표시된 값은 새로운 원본 표본으로 세지 않고 원본 timestamp로 중복 제거한다. 수집 성공만으로 전체 관계의 완전성을 확정하지 않는다. 원본 시각·검증된 주기·보존·품질 이력이 부족하면 영향을 받는 과거 구간만 unknown/blocked로 남긴다.

분석 입력 마감 시각과 query/parser/identity revision을 고정하고 사용한 제한된 원본·관계·품질 스냅샷을 evidence와 observation_snapshots에 보존한다. 재조회 시 동일 source·scope·원본 시각·내용·revision의 dedup_key를 재사용한다. 새 원본 정정·계약 변경은 기존 final 근거를 수정하지 않고 새 revision/근거로 보존한다. Mimir 원본이 만료된 뒤 보존된 업무 근거 이상의 전체 과거 이력을 복원할 수 있다고 표시하지 않는다.

### 4.2 계산 해상도

계산 query revision에는 원본 시각 취득 방식·검증된 원본 주기·값 유지 상한·조회 step·다운샘플링 허용 조건을 고정한다. 저활동 경계·짧은 급증·시간 가중 평균·P95를 손상하는 다운샘플 자료는 해당 계산에 사용하지 않는다. 화면 확대·축소용 간격은 저장 수치와 무관하다. 짧은 할당의 실제 관측시간과 장시간 후보 자격, A→B 교체 구간의 분모는 04의 고정 정책으로 각각 계산하고 근거 부족과 후보 미충족을 구분한다.

각 조회는 `tool_status=ok|partial|empty|unavailable|parse_error`를 반환한다. 각 분석 주제는 별도의 `status=ready|partial|blocked|not_applicable`을 사용한다. `job.status`는 10의 작업 실행 상태다. 이 상태들과 상세 `quality` 객체를 하나의 필드로 합치지 않는다. 결과 최상위 `result_status`는 04의 집계 규칙으로 서버가 확정하며 `narrative_status`는 설명 생성 상태를 별도 표시한다.

RCA·공통 도구의 수치는 `measurements`, 보고서 주제별 수치는 `topics[].metrics`에 한 번만 저장한다. 두 배열을 결과 전체에서 ID가 유일한 값 레지스트리로 취급하고 `facts[].value_refs` 등으로 참조한다. 자료형·단위·대상·기간/기준 시각·산식 revision·품질·근거를 함께 저장한다. evidence ID가 존재하는지만 검사하지 않고 문장 주장을 대조한다. 정확한 필드와 예시는 04가 원본이며 화면·파일에서 재계산하지 않는다.

Namespace 지표는 metric.quality에 요청/적용 그룹·observed_connections_only·제외 사유를 기록한다. topic.quality에는 같은 그룹·범위, 집계 단위, 해석 한계와 미귀속 원본 시계열 수를 보존한다. 전체 커버리지나 namespace 간 순위는 산출하지 않는다. 결과 전체의 evidence/value 참조 계약은 유지한다.

보고서 최상위 quality는 requested_group_by, collection(query_calls/query_limit/discovery_calls), 설명 생략·실패 시 narrative_reason을 추가로 기록한다. 사유는 모델 미설정·검증 사실 없음·토큰/시간 예산·HTTP 오류·출력 잘림·형식 오류를 구분하며 원본 오류/인증 정보를 넣지 않는다. llm_usage.request_attempts는 HTTP 요청 시도 수, 기존 calls는 성공 응답 수다. 이전 결과에 없는 진단은 추정하지 않고 기록 없음으로 표시한다.

`topics[].quality.observations[]`는 query_id·cluster_id·tool_status와 각 조회 구간의 quality를 담는다. 정상 응답에는 datasource_uid, query_revision, metric, unit, original_samples, max_hold_seconds, complete, sample_count, series_count를 기록한다. 실패·탐색/예산 부족 근거에는 일부 필드가 없을 수 있다. sample_count는 원격 응답의 표본 건수이며 분할 경계의 중복 제거 후 고유 표본 수를 뜻하지 않는다.

부분·실패 사유는 `source_warning`, `sample_limit_exceeded`, `response_byte_limit`, `budget_exhausted`, `query_failed` 등이다. 연결을 집계한 O02/O08은 `quality.mapping_basis="DCGM_Pod_UID_observation"`을 기록한다. 할당 계약 부재·불명확한 모드·Pod 신원 부족은 각각 `allocation_contract_missing`, `allocation_mode_unverified`, `gpu_pod_identity_missing`으로 구분한다.

산식·신원 제외 규칙은 [04](04_Agent_동작_판단_명세서.md), 조회 분할과 주제 처리는 [12](../ops-agent/12_보고서_Agent_모듈_설계서.md)를 따른다. 구현: [정규화](../../../shared/python/src/agent_common/normalize.py), [관측 조회](../../../shared/python/src/agent_common/observation.py), [보고서 계산](../../../ops-agent/src/ops_agent/workflow.py).

## 6. 업무 DB 물리 모델

### Incident 역할 변경의 데이터 영향 — 추가 개발 목표

2026-09-22 기준 아래 물리 모델은 현행 1.3을 기록한다. 2026-09-23에 사건 단위를 관측 에피소드로 확정했다. 신규 RCA 접수 1.4는 [13](../incident/13_Incident_모듈_설계서.md)의 4층 중복 제거·에피소드당 최초 1회와 [14](14_모듈간_호출과_공통실행_계약.md)의 이행 계약을 구현해야 한다.

- 알람 신원은 `(source, cluster_id, fingerprint, starts_at)`이며 해시 없는 자연키다. 기존 `event_key`는 `target`을 포함한 해시라 라벨 변화로 같은 firing이 분리됐다. 본문 hash는 전송 재시도 식별용으로 별도 유지한다.
- 사건 신원은 에피소드 ID이며, `dedup_group`은 source/cluster/machine/component의 충돌 없는 직렬화다. 신원 부족·분석 제외 그룹은 [13 §2.1](../incident/13_Incident_모듈_설계서.md)의 격리 규칙을 따른다. 한 그룹에 열린 에피소드는 최대 하나이며 그룹 잠금과 부분 유일 인덱스로 보장한다.
- 에피소드의 최초 snapshot은 evidence_version=1에 고정하고 outbox는 에피소드당 하나다. 후속 payload·반복 알람·정책 변화로 snapshot/revision/job을 추가하지 않는다. 반복 수신은 `observation_count`와 `last_observed_at`만 갱신한다.
- 종료는 `ended_at`/`ended_reason`(`alarm_resolved`·`observation_gap`·`closed_by_operator`)으로 기록한다. 종료는 회복이 아니다. resolved 선접수는 생명주기 해제 상태와 원문만 보존하고 사건을 만들지 않는다.
- `prior_incident_id`로 같은 그룹의 직전 에피소드를 연결한다. 13 §2.3의 새 증거 조건을 충족하고 직전이 `closed`면 신규 RCA를 발행하며, open/acknowledged면 사건만 기록하고 분석을 생략한다(`prior_analysis_open`). 과거 payload 재전송은 새 사건이 아니다. 유효 denylist 사건은 `analysis_excluded`로 보존하고 RCA를 발행하지 않는다.
- 최초 snapshot에는 원문·확인된 대상/범위·시각·입력을 보존하며 purpose_ids·analysis_profile_revision은 없다. 기존 incidents.analysis_profile_revision 등 필수 제약은 신규 입력을 지원하도록 추가 migration에서 완화/분기하고, 과거 정책·revision·snapshot은 유지한다.
- Agent가 선택한 목적·procedure·선택 근거·parser/규칙 revision은 Agent 소유 evidence와 기존 assessments에 기록한다. Incident 행이나 snapshot을 Agent가 수정하지 않는다.
- 기존 alert_events/receipt의 반복 접수 기록은 감사용이고 사건 수·재발 수가 아니다. `observation_count`는 Webhook 수신 횟수이며 원천 로그 건수가 아니다. 활성 그룹 키를 보존하며 종료 키는 허용 재전송 기간보다 먼저 삭제하지 않는다. 보고서 O05/O06은 중복 제거 사건·공개 RCA를 사용한다.

추가할 열과 인덱스는 다음과 같다. 기존 사건·snapshot·outbox·evidence를 재사용한다. 생명주기 해제 상태가 에피소드 경계를 넘어 유지되어야 하므로 `incident_alert_lifecycles` 하나만 추가한다. 이는 중복/해제 상태이며 별도 큐나 원문 복제 원장이 아니다.

`dedup_group`은 문자열 길이 상한을 두고 원본 라벨·K·설정 revision을 최초 snapshot에 보존한다. 기존 사건은 최초 alert event로 신원을 확인하되 dedup_group/episode_started_at을 추정해 backfill하지 않는다. legacy 생명주기의 다중 사건 귀속을 먼저 점검하고 자동 병합·삭제하지 않는다. migration은 기존 event_key 유일성, 필수 analysis_profile 제약 완화, 신규 생명주기 PK·열·인덱스를 함께 검수한다. ### RCA 1.4의 DB context 고정 — 추가 개발 목표

Worker는 입력/hash/scope 검사 후 **목적 선택 전에** 기존 `Store.read_context()`의 read-only repeatable-read 트랜잭션에서 이력을 확보한다. 1.4에서는 입력 purpose_ids로 이력 조회 여부를 결정하지 않는다. 같은 scope·입력 `[start,end)`의 사건, 그 사건의 공개 RCA ID/hash, 해당 기간의 실제 조치 기록과 발행 Runbook revision을 고정한다. 1.3과 보고서의 기존 읽기 계약은 유지한다.

`prior_incident_id`는 같은 scope·dedup_group임을 검증한 직전 사건 한 건만 기간 밖에서도 읽을 수 있다. 그 사건의 공개 RCA·연결 조치 기록은 `context_only`로 표시하고 기간 통계·현재 관측으로 합산하지 않는다. 연쇄 조상 조회나 관측 기간 확대는 하지 않는다. cutoff는 해당 트랜잭션의 DB 시각이며 각 행의 ID/version 또는 hash, 조회 범위·설정된 행/바이트 상한·잘림을 evidence에 보존한다. 예산 초과/누락은 context 불완전 사유다.

트랜잭션을 닫은 뒤 workflow가 목적을 선택·추가한다. 같은 attempt에서 DB를 다시 읽어 더 늦게 공개된 RCA·조치를 섞지 않는다. 고정 context로 R06/R07/R09를 판단할 수 없으면 부족을 남긴다. 새 attempt가 다시 읽으면 새 cutoff임을 기록하며 이전 attempt와 동일 snapshot이라고 주장하지 않는다. 외부 관측 조회는 별도 응답 시각/완전성을 갖는다.

### 현행 물리 모델

ID는 uuid, 시각은 timestamptz, 버전·attempt는 integer, 수량은 bigint, 계약 snapshot은 jsonb, hash는 text다. 결과 숫자에 NaN/Infinity는 허용하지 않는다. 공통 created_at/updated_at, 변경 레코드 version을 둔다. scope는 02의 CPC별 namespaces 객체이며 권한 정보가 아니다.

schedule_occurrences의 canonical=true 행에는 `(schedule_id,period_start,period_end)` 부분 유일 인덱스를 둔다. 중복 기간의 missed 행은 canonical=false와 기존 occurrence를 참조한다. occurrence와 outbox 생성은 동일 트랜잭션이다.

queued/retry_wait 검색은 `(kind,status,eligible_at,created_at,id)`, lease 회수는 미종료 attempt의 lease_expires_at, 사건 조회는 `(cluster_id,occurred_at)`, 에피소드 판정은 `(dedup_group)` 부분 유일과 `(dedup_group,episode_started_at DESC,id)`, 일정 발생은 `(enabled,next_run_at)`에 인덱스를 둔다. 1.4 기간 조회에는 episode_started_at을 사용한다. 인덱스 실제 선택은 구현 쿼리 계획으로 확인한다.

## 7. 원자성·발행·보존

접수 receipt는 jobs의 source_module/source_key/request_hash와 job ID로 표현하며 별도 접수 테이블을 만들지 않는다. 접수는 이 행의 유일 키 커밋, claim은 capacity 잠금+job+attempt+reservation, 완료는 유효 attempt 검사+jobs의 final 참조+상태+슬롯 반환을 각각 한 트랜잭션으로 수행한다. 장시간 조회/LLM 동안 DB 트랜잭션을 열어 두지 않는다.

유효 published_result_id만 정상 결과다. 후보 저장과 공개는 분리하며 후보의 job_id/attempt_no/kind/hash를 완료 시 다시 검증한다. 이전 attempt 후보는 진단 자료로만 보존한다. 완료·취소 경합 규칙은 14가 원본이다.

모든 원본 이력의 무기한 복제를 하지 않는다. final에서 인용하는 근거·파일·지식·설정 revision과 멱등 receipt는 해당 job보다 먼저 제거하지 않는다. 보존 기간·백업·원본 만료 후 재현 가능 범위는 06에서 운영값으로 확정한다. 과거 final을 새 산식으로 덮어쓰지 않는다.
