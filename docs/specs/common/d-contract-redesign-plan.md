# D 데이터 계약 재설계 개발 계획

기준일: 2026-10-02. 상태: 계획·문서 단계. 이번 작업은 문서 정정과 개발 계획 수립에 한정하며, 실환경 조회·제품 코드/설정·DB·Runbook 발행·배포를 수행하지 않는다. 아래 후속 단계는 실행 실적이나 구현 착수 권한을 뜻하지 않는다.

## 1. 목적과 정정

목표는 Fleet·Kubernetes·DCGM에서 확보할 수 있는 근거와 RCA/보고서의 질문을 연결하는 D 데이터 계약을 다시 설계하는 것이다. 기존 D의 잘못된 의미를 보존한 채 새 분류나 예외 처리를 덧붙이지 않는다. 필요한 경우 D의 번호·이름·경계·조회/출력 구조를 변경하고 소비자도 함께 수정한다.

앞선 [03 데이터 설계서 §3.3](03_데이터_설계서.md#33-d-정의역할과-복수-관측-확장--2026-10-02)의 ‘D01~D14 유지’와 ‘D03.used/free 구조 채택’은 확정 전제로 사용하지 않는다. 해당 절은 기존 D를 기준으로 한 조사 자료와 검토 후보로 정정했다. 메트릭 후보·코드 불일치·해석 제한은 재사용하지만 최종 분류는 본 계획의 결정 절차로 정한다.

다음은 확정 원칙이다.

- D는 관측·입력·출력 사실의 의미를 규정하고, RCA는 원인 판단, O는 기간 분석·운영 결론을 담당한다.
- 서로 다른 관측은 명시적 식별자·단위·대상·시간·품질·근거로 구분한다. 복수 조회를 한 배열에 섞지 않는다.
- 수집·파싱·정규화·계산·품질 검증은 코드로 수행한다. LLM을 데이터 해석 계약의 빈칸을 채우는 수단으로 사용하지 않는다.
- 부서 정보는 제외한다. 실제 Namespace·Pod·GPU 등의 식별 관계만 사용한다.
- 현재 데이터가 부족해도 필요한 관측 요구는 기록하되, 후보/미확보를 사용 가능한 입력으로 발행하지 않는다.
- 검증된 수집·계산 코드는 재사용한다. 기존 D 분류·번호와 직접 분기 코드는 보존 대상이 아니다.
- 과거 evidence/result/hash는 불변으로 보존한다. 과거 결과 읽기 호환성과 새 실행 구조를 구분한다.

## 2. 이미 확보한 근거와 조사 범위

[03 §3.3](03_데이터_설계서.md#33-d-정의역할과-복수-관측-확장--2026-10-02)의 source/metric 표를 시작 자료로 사용한다. 같은 자료 조사를 처음부터 반복하지 않는다.

| 구분 | 이미 확보한 내용 | 추가 확인이 필요한 내용 |
|---|---|---|
| 실행 설정 | agents/config.example.json과 Helm 사본의 D01~D13 정의 | 실제 배포된 설정·producer 버전 |
| 실행 코드 | 공통 조회·정규화, RCA/Runbook, Ops 계획·계산의 주요 소비 경로 대조 | 재설계에 영향받는 API·저장·표시·테스트 참조의 전수 목록 |
| Fleet | Host/GPU 필드·component 로그의 과거 표본과 소스/catalog 대조 | 현재 중앙 이름·실제 표본·단위·대상·시간·지원 범위 |
| Kubernetes/KSM | 과거 Pod info·Node condition·Container request 선별 전송 기록 | 다른 객체 상태·owner·제약의 현재 노출과 유효 요청 산식 입력 |
| DCGM Exporter | 과거 GPU_UTIL·FB_USED/FREE 수집, 전력·온도 등 설정/소스 후보 | 현재 전송 항목·장비 지원·실부하·보존기간·MIG/공유 의미 |
| D 정의 | 기존 D 목적·문제·수집 후보 표 | 새 D 경계·식별 방식·출력 계약·기존 D 처분 결정 |

현재 전체 가용 목록은 확인되지 않았다. ‘전체’는 접근 가능한 지정 datasource·cluster·조회 기간·생산자 범위 내의 목록을 뜻한다. 페이지 한도·권한·보존기간으로 누락될 수 있는 범위를 반드시 기록한다. metric 이름 발견, 의미 검증, 특정 기간의 분석 적격성은 서로 다른 상태다.

## 3. 단계별 산출물과 완료 기준

P0은 이번 문서 작업이고 P1 이후는 후속 작업이다. 설계 초안은 미확인 항목을 표시하면서 진행할 수 있으나, 실환경 근거가 없는 binding을 확정하거나 구현 준비 완료로 표시하지 않는다.

| 단계 | 작업 | 산출물과 보관 위치 | 완료 기준 |
|---|---|---|---|
| **P0 계획 정정** | 이전 유지 전제 정정, 범위·순서·결정 항목 명시 | 본 문서, 03 §3.3, 문서 목차 | 기존 유지안이 확정 명세로 읽히지 않고 후속 작업/완료 조건이 연결됨 |
| **P1 데이터 목록 확인** | 기존 근거 재사용, 지정 환경 읽기 전용 조사, 표본·metadata 대조 | docs/evidence/의 날짜·환경 명시 가용 데이터 원장. 원문은 비밀/운영 식별정보를 제거한 근거 참조로 관리 | 모든 조사 대상 source의 범위·누락 기록, 관측 항목별 검증 상태·근거·연결 키 확보 |
| **P2 D 계약 재정의** | 분석 질문과 가용 데이터로 경계 결정, 기존 D 처분 및 출력 정의 | 03 §3 데이터 사전 개정, 아래 결정 기록과 기존→신규 대응표 | 모든 새 D에 목적·입력·출력·조건·한계·소비 질문이 있고, 기존 D 전 항목의 처분 사유가 명시됨 |
| **P3 연계 개발 설계** | source부터 저장·RCA/O·UI까지 변경 경로 설계, 버전/전환 결정 | 본 문서 영향표 보완, 공통 04/14 및 모듈 02/07/10/11/12/13 중 실제 영향 문서 수정 | 모든 출력에 소비/검증 경로가 연결되고 직렬화·호환·발행·전환 미결정 사항 해소 |
| **P4 후속 구현** | 확정 계약에 따라 공통 실행·소비자·설정·테스트를 함께 변경 | 기존 소스 경로, 모듈 README/QA | 새 계약으로 두 Worker 경로가 연결되고 잘못된 D 의미·중복 우회 코드가 제거됨 |
| **P5 통합·운영 검수** | 격리 fixture/E2E와 실환경 의미·분석 품질을 구분 검증 | 05 검수 기준과 모듈 QA, 운영 확인 기록 | 지정 사례의 수치·판단·근거·실패 상태 검수. 배포는 별도 권한·복구 계획에 따름 |

P4/P5는 이번 요청에서 실행하지 않는다. P1도 이번에는 조사 절차만 문서화한다. 기간·정확도 목표·환경 정보가 없는데 임의로 수치를 확정하거나 운영 조회를 시작하지 않는다.

## 4. P1 데이터 원장 작성 방법

조사 시작 시 cluster·datasource·허용 범위·조회 기간·producer 버전·도구 기능·조회 한도를 명시한다. 등록된 읽기 경로로 metric 이름/metadata/label과 Loki stream·구조화 필드·표본을 확인한다. 인증 값·원본 민감 로그는 커밋하지 않는다. source 변경이나 새 exporter 배포는 조사와 별도 작업이다.

원장 한 행의 필수 항목:

`source / cluster / producer_version / observed_window / raw_metric_or_field / type / unit / entity_keys / timestamp_basis / sample_interval / retention_evidence / verification / evidence_ref / limitation / analysis_question`

검증 상태는 발견만 됨, 의미 검증됨, 미확보/접근 불가를 구분한다. 보존기간·주기는 표본만으로 보장하지 않고 근거 범위를 명시한다. 기간 분석 적격성은 별도 계산이며, 값이 없다는 이유로 0 또는 전역 미수집으로 기록하지 않는다.

출처별 시작 항목은 03 §3.3의 실제 이름 목록을 사용한다. 예: Fleet cpu_used_percent·cpu_load_average, KSM kube_pod_info·kube_node_status_condition·kube_pod_container_resource_requests, DCGM_FI_DEV_GPU_UTIL·DCGM_FI_DEV_FB_USED/FREE. 목록을 이 예시로 제한하지 않는다. Fleet/Exporter 중복은 실제 중앙 이름과 의미를 대조해 표시한다.

## 5. P2 D 정의의 결정 기준

먼저 RCA와 보고서의 질문을 작성한다. 예: 장비 오류 원문과 대상 확인, 메모리 여유와 활동 구분, 사건 당시 GPU–Pod 관계, 기간 전력 적분, 요청량과 배치 대기 구분. 질문→필요 사실→관측 원본을 연결하고 원본이 없는 사실은 미확보로 둔다. 기존 O/Runbook의 고정 D 목록을 새 설계의 상한으로 사용하지 않는다.

| 결정 항목 | 비교할 내용 | 결정 기록에 필요한 근거 |
|---|---|---|
| D의 단위 | 단일 의미 관측인가, 명시적 출력을 가진 목적 묶음인가 | 두 Worker의 재사용·개별 실패·계산 의존성·조회 중복 사례로 비교 |
| 식별 방식 | 의미 ID, D 코드, query ID, producer binding의 관계 | 번호 유지 강제 없음. 의미 변경 감지·추적·독립 결과 구분이 가능해야 함 |
| 복수 조회 | 묶음 내부 항목 또는 별도 관측 참조 | 필요한 관측만 실행, 실패가 독립, 출력 구분, 의존성 검사가 가능해야 함 |
| 파생 사실 경계 | D 정규화와 RCA/O 계산의 책임 | 공통 단위·신원·시간 처리는 공유하고 목적별 원인/정책 판단과 분리 |
| source 선택 | Fleet/Exporter의 대표·보조 관측 | 동일 의미 검증, 중복 합산 금지, 충돌·대체 시 품질 하락 처리 |
| 과거 계약 | 과거 결과 해석과 새 작업 실행 분리 | 잘못된 의미를 새 경로에 상속하지 않으며 기존 snapshot/hash 보존 |

`D03.used/free`는 비교할 구조의 예일 뿐 채택된 이름이나 스키마가 아니다. 위 항목은 P2에서 결론·이유·대안 기각 사유를 기록한다. ‘분류를 유지하기 위해’ 또는 ‘기존 코드가 편해서’만으로 경계를 정하지 않는다.

최종 D 정의 한 건은 다음 내용을 포함한다.

- 목적과 답할 수 있는 질문, 답할 수 없는 주장.
- 고유 식별자·revision·반환 대상과 시간 의미.
- source binding별 실제 metric/로그/DB 필드, 조회 조건·허용 인자·권한 투영.
- 타입·단위·오류값·counter reset·bitmask·중복·누락 처리.
- 필요한 다른 관측과 조인 키·유효시간, 필수/선택/대체 조건.
- 명시적 출력 이름·구조·등록 parser/calculation·evidence 참조.
- 관측별 상태와 집계 상태, 불가능한 계산의 보류 사유.
- 가용성 근거·지원 producer/장비·RCA/보고서 소비 예·검수 사례.

기존 D 처분표는 D01~D14 각 행에 `현재 의미/실제 동작 → 유지·분리·통합·폐기 → 신규 계약 → 변경 이유 → 소비자 → 과거 결과 처리`를 기록한다. 예를 들어 D04의 Host 정의/GPU 온도 실행 충돌은 확인된 문제이나, 온도를 D05로 옮기는 결론은 아직 고정하지 않는다. 연결 관측/할당, raw log/상태 fact, allocatable/배치 가능성도 분리 판단의 필수 사례다.

## 6. P3 연계 영향과 구현 작업 분할

| 영역·주요 위치 | 설계해야 할 변경·확인 | 확인 책임 영역 |
|---|---|---|
| agents/config.example.json, charts/gpu-ops-advisor/files/agents.json | 새 정의의 검증·source binding·두 사본 동기화 | 공통 Agent·배포 |
| shared/python/.../settings.py, observation.py, discovery.py, runtime.py | 입력 검사·계획·예산·대상 필터·독립 결과·근거 ID·조회 재사용 | 공통 Agent |
| shared/python/.../normalize.py, parsers.py, calculations.py | 식별자별 입력·등록 함수·단위/시간/품질·출력 fact | 공통 Agent |
| shared/python/.../store.py, contracts.py, shared/contract, shared/migrations | evidence/query revision 저장·검증·직렬화의 영향. DB 변경은 필요성 확인 전 확정하지 않음 | Agent·Backend/DB·JC |
| rcca-agent/src/rcca_agent/runbook_contract.py, workflow.py, runbooks | 요구 관측과 produces 검사, 분기·fact 구성·발행 revision | RCA·Runbook 관리·Backend |
| ops-agent/src/ops_agent/workflow.py, collection.py, namespace_usage.py | O별 질문과 필수 입력·산식·부분 결과·계획 재작성 | Ops |
| incident, job-controller | snapshot/profile/version/지원 계약과 발행 호환 영향 확인. 변경 필요가 없으면 근거 기록 | Incident·JC |
| backend/internal/api, frontend/src, Agent 보고서 생성 | 새 출력의 API·표시명·단위·상태·HTML/CSV·과거 결과 표시 | Backend·Frontend·Agent |
| agents/tests, 모듈별 테스트·CI, 문서 | 새 계약 사례와 기존 결과 읽기 회귀, 잘못된 기대값 교체 | 각 변경 모듈 |

위 표는 영향 확인 범위이며 모든 파일의 변경이나 migration을 미리 요구하지 않는다. P3에서 실제 참조를 검색하여 수정/영향 없음과 근거를 기록한다. 새 정의→조회→정규화→판단/계산→근거 저장→표시의 한 경로가 끊기지 않도록 작업을 나눈다. 공통 계약을 먼저 확정한 뒤 두 Worker와 표시 소비자를 전환한다.

메모리 사용/여유 같은 작은 사례는 새 계약의 전체 경로를 검증하는 첫 구현 사례로 사용할 수 있다. 이것을 구 D 구조 위의 영구 호환층으로 만들지 않는다. 전환은 작업에 고정된 계약 revision 기준으로 구분하고, 신규 Runbook 발행·실행 프로필·Worker 지원 버전의 적용 순서를 함께 정한다. 발행된 기존 Runbook revision을 덮어쓰지 않는다.

## 7. 검증 계획과 전환 조건

| 사례 | 기대 결과 |
|---|---|
| 같은 GPU의 사용량·여유량 입력 | 다른 관측으로 구분, 유효한 단위·시간일 때만 결합 |
| 입력 하나 실패·빈 응답·실제 0 | 독립 결과 보존, 의존 계산만 보류, 0과 미확인 구분 |
| counter reset·sentinel·단위 불일치 | 무효 증가량/계산 차단, 사유와 원본 근거 보존 |
| GPU 교체·Pod 이름 재사용·시간 불일치 | 신원/유효 구간이 맞지 않는 조인 차단 |
| Fleet/Exporter 동일 장비·상충 관측 | 이중 집계 금지, 검증된 source 선택 또는 충돌 보류 |
| Namespace 범위에서 Host 지표 필요 | 승인된 관계 기반 범위 투영 또는 불가 처리, 무단 범위 확장 없음 |
| Runbook이 생산 불가능한 fact 요구 | 등록/계획 검사에서 거부 또는 명시적 미지원 처리 |
| O가 추가 데이터를 조회 | 실제 계산 입력·근거로 연결됨을 검증, 조회 성공만으로 완료 표시 금지 |
| 예산 초과·취소·재시도·publication | 기존 JC lease/결과 발행·불변성·실패 격리 보존 |
| 기존 evidence/result 열람 | 당시 revision·의미·hash 유지, 새로운 단위/정의로 소급 해석 금지 |

후속 구현에서는 변경 모듈 규칙에 따른 정적·단위·통합/E2E 검사를 수행한다. 공통 Python 변경은 두 Worker를 검증한다. Go/API/DB·Frontend·Helm이 바뀌면 해당 소비자 검사를 포함한다. DB 테스트는 격리 대상으로 수행한다. fixture 결과와 실환경의 가용성·의미·LLM 분석 품질은 별도 증거로 기록한다.

운영 전환 전에 작업/Runbook/profile revision 호환, 저장 데이터 영향, 적용 순서, 실패 시 되돌릴 실행 버전을 정한다. DB 변경이 생기면 별도 데이터 보존·복구 절차가 필요하다. 배포 권한 없이 운영 상태를 변경하지 않는다.

## 8. 문서 관리와 다음 작업

본 문서는 개발 순서·결정·영향·검수 계획의 기준이다. 공통 D 의미와 최종 입출력은 03, 산식·판단은 04, 모듈 간 실행은 14에 단일 기준으로 반영한다. 새 분류 확정 전 03의 기존 D 표를 최종 계약으로 교체하거나 제품 설정을 수정하지 않는다. RCA 전용 참고 문서를 공통 데이터 가용성 원장으로 오인하지 않는다.

후속 작업의 첫 산출물은 P1의 가용 데이터 원장이다. 조사 환경·기간·접근이 확보되지 않으면 확인된 저장소 근거로 원장 초안을 작성하고 미확인 범위를 남긴다. 그 다음 P2에서 D별 처분표와 최종 정의를 작성한다. P2/P3의 미결정 항목이 남아 있으면 구현 준비 완료로 표시하지 않는다.
