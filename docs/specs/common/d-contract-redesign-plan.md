# D 쿼리 통합·확장 개발 계획

기준일: 2026-10-02. 상태: **설계 문서만 작성. 제품 코드·설정·DB·발행 Runbook·운영 환경은 변경하지 않았다.**

## 1. 목표와 확정 설계

**D 하나 = 하나의 논리 쿼리 정의를 유지한다. 중복 조회는 통합하고, 부족한 메트릭마다 독립 D를 추가하며, RCA/보고서의 기존 분석 기능과 결과는 보존한다.** 여러 메트릭을 D 내부 item으로 넣는 D03.used/free 구조는 채택하지 않는다. 한 D의 클러스터/기간 분할 호출은 허용되며 서로 다른 메트릭을 담는 것을 뜻하지 않는다.

실제 정의는 [메트릭·쿼리별 D 매핑 설계](d-query-mapping.md)에 있다. 이 문서는 작업 순서·영향·검수 기준을 관리한다. D별 metric/source/조건/단위/목적, O별 이전→이후 D, RCA 통합/확장 관계를 다른 문서에 중복 정의하지 않는다.

| 설계 결정 | 목적 | 기능 보존 조건 |
|---|---|---|
| 기본 D01/D08 조회를 D02로 통합 | 동일 GPU_UTIL 원본의 중복 query 정의 정리 | 신원·활동·관측 연결은 다른 코드 출력. 각 소비자의 필터·범위·단위·시각·observed 모드 보존 |
| D05 파생 보기를 D09 + health parser 처리로 통합 | 같은 로그를 상태 근거로 쓰는 관계를 명확히 함 | 상태 fact·producer·freshness 검증, Runbook 필수 fact와 evidence 연결 보존 |
| D03/D04 및 기타 독립 쿼리 유지 | 기존 실행 기능 유지 | D04는 실제 GPU 온도 의미로 정렬; Host 쿼리로 교체하지 않음 |
| D15~D49 35개 독립 쿼리 추가 | 메모리·Host·KSM·활동·통신·오류·전력 근거 확대 | 실환경 검증 전 후보 상태. 신규 실패가 기존 독립 결과를 지우지 않음 |
| Runbook/O의 입력·산식·출력 연결 변경 | 추가 수집을 실제 조사/보고서 결과로 활용 | 기존 산식·판정 gate 보존, 추가 출력·새 질문을 구분 |

기존 기능 + A는 모든 D 번호의 영구 보존을 뜻하지 않는다. 구현 중복은 통합하되 기존 관측·분석 능력을 잃지 않는다. 배포 override에서 D08이 실제 할당 원본이라면 DCGM 기본 설정과 다른 계약이므로 유지 또는 별도 할당 D를 정의한 뒤 전환한다. 번호만 일괄 치환하지 않는다.

수집·파싱·단위/시간/신원 정규화·계산·품질 판정은 코드로 수행한다. LLM은 이를 대신하지 않는다. 부서는 제외한다. 과거 evidence/result/hash와 발행 revision은 보존한다. 문서에 없는 신규 서비스·큐·DB·임의 쿼리 엔진을 도입하지 않는다.

## 2. 이전 문서에서 정정한 내용

초기 대화/문서의 ‘기존 D 분류 유지 + 복수 하위 관측’과 이후 ‘D 단위를 추후 결정’은 이번 명확한 요구로 대체한다. 확정된 단위는 단일 논리 쿼리이며, 전체 메트릭 목록을 D 안에 넣지 않는다. [03 데이터 설계서 §3.3](03_데이터_설계서.md#33-d-정의역할과-복수-관측-확장--2026-10-02)은 이 설계로 연결하는 요약으로 정정했다.

이미 조사한 저장소 설정·과거 수집 기록·Fleet/DCGM 카탈로그는 재사용한다. 신규 문서의 D 번호 매핑은 작성했지만 현재 운영 환경의 전체 메트릭·로그 확인을 완료했다고 주장하지 않는다. 번호/목적 매핑, 현재 가용성, 런타임 구현, 실제 분석 검수는 다른 단계다.

## 3. 단계·산출물·완료 기준

| 단계 | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| P0 설계·관계 작성 | D 쿼리 매핑과 목적, 기존 통합, 신규 D 및 O/RCA 사용 관계 정의 | 매핑 설계 §3~§7, 본 계획 | 모든 신규 D가 원본·목적·활용처에 연결되고 O01~O11 전환표가 있음. 이번 문서 단계 |
| P1 환경별 binding 검증 | 지정 환경의 실제 이름·타입·단위·대상·시간·필터 확인 | docs/evidence/의 날짜·환경별 데이터 원장 | 각 활성화 대상 D에 검증 근거 또는 미확보 사유. 페이지/권한/기간 한도와 누락 범위 기록 |
| P2 소비 계약 확정 | 각 신규 D의 정규화·fact, O 출력·산식·실패 상태, 모든 발행 Runbook 전환 대조 | 03 상세 데이터 계약, 04 판단/산식, 14 실행 계약 및 모듈 11/12 명세 | 실제 실행할 query binding·fact·계산·소비자·버전이 연결되고 미확정 입력으로 확정 판정하지 않음 |
| P3 구현 | 공통 실행·신규 정의·통합된 소비자·표시·설정 사본·테스트 변경 | 기존 코드 경로, 모듈 README/QA | 기존 기능 회귀 + 신규 관측/계산의 두 Worker 경로 완성 |
| P4 검수·전환 | 격리 테스트/E2E, 실환경 의미·품질, 버전 적용/복구 확인 | QA·운영 검수 기록 | fixture와 실환경 결과를 구분해 승인된 범위 통과. 배포는 별도 권한 |

이번 요청에서는 P0 문서만 수행한다. 운영 조회, 제품 구현, migration, Runbook 발행이나 배포는 실행하지 않는다. P1과 P2 설계 보완은 병행할 수 있으나 검증되지 않은 binding을 실행 준비 완료로 표시하지 않는다.

## 4. P1 데이터 원장과 활성 조건

원장 필드: `D / source / cluster / producer_version / observed_window / actual_metric_or_field / type / unit / entity_keys / filters / timestamp_basis / sample_interval / retention_evidence / verification / evidence_ref / limitation`.

Fleet는 source 이름과 중앙 변환 이름, DCGM은 장비 지원과 exporter 전송, KSM은 실제 선별 전송을 확인한다. metadata·label·원본 표본·Loki stream/필드의 조사 범위를 기록한다. 자료에 등장한 이름만으로 실수집을 확정하지 않으며, 빈 기간과 전역 미수집을 구분한다. 비밀값과 민감 원문은 커밋하지 않는다.

활성 조건은 정확한 metric/stream·selector·대상 키·단위/타입·원본 시간·invalid/reset 규칙이 검증되는 것이다. 미검증 D는 candidate/unavailable로 남기고 영향을 받는 신규 출력만 보류한다. 모든 D를 매번 조회하지 않고 O/Runbook의 선택·의존성과 예산에 따라 실행한다.

공통 Python 변경은 두 Worker의 정적·단위·통합/E2E 검사를 포함한다. Go/API/DB·Frontend·Helm 변경 시 실제 영향 모듈의 규칙을 적용한다. DB 테스트는 격리 환경에서 수행한다. 실제 Grafana의 의미/부하/기간과 LLM 분석 품질은 별도로 검증한다. 배포에는 적용 순서·복구 조건과 별도 권한이 필요하다.

## 7. 남은 구체 결정

D 형태를 다시 논의하는 단계는 아니다. 남은 결정은 후보 D의 환경별 binding·타입·단위·주기, 신규 출력의 정확한 직렬화/산식/필수성, 발행 Runbook 전수 대응, 구/신 실행 revision 전환이다. 전체 운영 가용 목록과 전용 Runbook의 내용·발행 revision 전수 전환은 미완료다. 저장소 초안 267개가 모두 D09/D05 필수·D02 선택을 사용하는 정적 대조는 매핑 §7.2에 기록했다. 비코드 사례의 조사 질문→D→계산 fact→판단/보류는 §7.1에 정의한다.

[매핑 설계](d-query-mapping.md)가 신규 D와 O/RCA 관계의 기준이며, 03은 공통 정의, 04는 판단·산식, 14는 모듈 실행 계약의 기준이다. 실제 구현 시 이들 문서와 해당 모듈 명세를 함께 갱신한다.
