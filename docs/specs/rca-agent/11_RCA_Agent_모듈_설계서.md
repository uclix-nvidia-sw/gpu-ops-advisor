# 11. RCA Agent 실행 계약과 평가 분리 설계·개발

현재 실행 설명은 [RCA README](../../../rcca-agent/README.md)가 소유한다. 이 문서는 현재 코드가 사용하는 계약과 판단 경계, RCA 평가 분리의 설계·개발 범위를 정리한다. **평가 분리의 코드·GUI 경로를 구현했다. 고정 응답 검증과 실제 모델의 평가 정확도·운영 배포는 구분하며, 실행 근거는 Agent QA에서 관리한다.** 입력/실행은 [실행 계약](../common/14_모듈간_호출과_공통실행_계약.md), 결과 필드는 [공통 판단·결과 계약](../common/04_Agent_동작_판단_명세서.md), DB 소유권은 [Shared](../../../shared/README.md)를 따른다.

## 구현 경계

| 영역 | 현재 코드 | 남은 검증·범위 |
|---|---|---|
| 핵심 LLM | `combined_synthesis.generate` 한 요청 + `review_analysis` 독립 검토. 같은 증거의 작성 HTTP 재전송·형식 복구·의미 재작성 없음 | 실제 모델의 의미 품질/비용 반복 비교 |
| Runbook | 1.1 코드 목표 유지, 1.2는 생산자·컴포넌트·비정상 보고 목표 추가. `assess_policies/finish_assessment`가 적용·필수 기준·차단·같은 초안 검토를 결합 | 신규 Fleet 원천 계약과 오류별 지침의 새 revision 발행·배포 필요. 모든 오류 지침의 작성 완료를 뜻하지 않음 |
| 자료 보존 | 해석만 유효하면 보존해 검토. 해석 영역 전체가 실패하면 그 영역을 임의 복구하지 않음 | 해석의 항목별 부분 채택은 후속 작업 |
| 최종 결과 | `rca_result_frozen`은 보고서용 구조화 근거 자료. `report_assembly`는 그 hash를 사용한 최종 보고서 구성 | 보고서 LLM은 고정 자료를 서술. 새 판단 금지·의미 일치는 배포 후 검수 |
| 소비자 | 평가 schema 1/2, rubric 1/2, 구형 3단계/신규 역할명 지원 | 실제 운영 데이터의 혼합 조회와 T79는 별도 확인 |

Runbook 1.1 첫 목적은 `identify_error_report`다. 코드 기준 `reported_error/scoped_source`, 필수 의미 기준, 네 차단 조건과 기존 `required_evidence`를 모두 검사한다. 정책 없는 지침과 섞이거나 조사 도중 지침 집합이 달라지면 새 목적 달성을 인정하지 않는다. 보완은 기존 조회 권한·selection 조건을 지키며 목적의 필수 링크만 사용한다. 미충족 시 실행 가능한 보완이 없으면 `goal_not_met`; 모든 기준과 같은 자료의 검토가 충족되면 `goal_achieved`다. 두 경우 모두 원인 확정과는 별개다. 여러 오류 코드가 함께 보고되면 단일 코드의 적용 범위를 확정하지 않고 `conflicting_reports=unknown`으로 남긴다. 코드 종류가 다르다는 이유만으로 모순이라고 확정하지 않는다.

한 attempt 안에서 `observation_hashes`가 원본 내용·대상 범위·기간을 비교한다. UUID, 조회 시도 시각, feedback, 모델 입력 샘플 변화는 작성 허가를 새로 만들지 않는다. 새 작업/attempt의 명시적 재평가는 별도 실행이며 이 변경은 DB 전역 모델 캐시를 만들지 않는다. 전체 호출 수에는 별도 품질 검토·선택·보고서 서술도 포함되므로 작성 횟수와 구별한다.

## 문서 관계와 읽는 순서

전체 방향을 함께 검토할 때는 [개선 목적](#평가-분리-설계개발) → 단계와 LLM 개입 → 사건 예시 → 함수별 변경 → 검수 기준 순으로 읽는다. 별도의 협의 항목이나 승인 절차를 만들지 않는다. 현재 동작과 목표를 비교할 때는 앞의 현행 계약 절과 RCA README를 함께 확인한다.

확인된 정보가 보고서와 다음 조사에 반영되지 않는 문제는 [확인된 증거와 후속 판단 연결 개선안](#확인된-증거와-후속-판단-연결-개선안)에서 검토한다. 해당 절은 구현된 표시·예약 보호와 **남은 개선 계획**을 구분한다. **해석·분석 호출 통합 + Runbook의 조사 판단 기준 추가**를 하나의 [구현 순서](#구현-순서와-변경-범위)로 구현했다. [단일 호출 설계](#증거-해석과-rca-분석의-단일-호출-설계)는 작성 방식을, [Runbook 판단 설계](#runbook-판단-기준과-품질-검토종료-설계)는 조사 목적·품질 검토·종료 결정을 다룬다. 핵심 코드·두 대표 Runbook·GUI는 구현했으며 실제 모델의 비교는 미실행이다. 효과는 따로 측정한다. 설계 작성만으로 현행 계약·운영 설정·발행 Runbook을 바꾸지 않는다.

## 입력과 실행 소유권

Grafana 알림은 Incident가 사건 snapshot으로 저장하고 JC에 RCA 작업을 접수한다. Worker는 JC claim의 입력·scope·기간·예산·지식 revision을 사용한다. Backend/GUI가 Worker를 직접 호출하지 않는다. lease·heartbeat·취소·원격 실행 종료 불명·공개는 공통 Worker와 JC의 계약이다.

RCA는 GPU·NVSwitch·노드 하드웨어 사건을 조사한다. 알람의 검색 단서, 보고된 상태, 검증된 현재 상태, 원인 판단은 별개다. 기존 입력·결과와 legacy Runbook 호환은 유지한다. 새 계약을 도입할 때 기존 snapshot을 조용히 재해석하지 않는다.

## Runbook 검색과 적용

[검색](../../../rcca-agent/src/rcca_agent/retrieval.py)은 오류 코드 namespace를 구분하는 결정적 순위 검색이다. 양수 점수의 후보를 제한된 수로 반환하며 점수는 관련도이지 진단 확률이 아니다. 코퍼스·tokenizer가 바뀌면 검색 품질도 다시 확인해야 한다.

[발행 계약 검증](../../../rcca-agent/src/rcca_agent/runbook_contract.py)은 scope·revision·reviewed content hash·내용 구조·등록 query를 확인한다. 구조 통과와 실제 적용 조건 충족은 별개다. `compatibility_status`는 입력 attribute의 known/unknown과 일치 여부를 확인하고, workflow가 scoped facts로 적용 가능 후보를 판단한다.

일반 조사 Runbook은 원인 확정을 위한 지식과 구분한다. 등록 일반 Runbook을 사용할 수 없으면 패키지의 조사 전용 템플릿이 fallback이며 `origin=builtin`으로 표시한다. 조사 지침은 관측 근거가 아니다.

`runbook_selection`은 검색·형식 검사 진단이고, 실제 사용할 `selected = applicable + pending`과 구분한다. `workflow.run()`은 selected 확정 뒤 `preserve_runbook()`으로 본문·revision·출처를 한 번 보존하고 최초 조사 계획과 수집으로 진행한다. `quality.selection_evidence_id`는 선택 진단, 계획의 `selection_evidence_id/evidence_refs`는 선택 진단과 사용 원문을 연결한다. 조사 확장에서 새로운 지침을 선택하면 해당 원문만 보존하고 확장 계획에 refs를 남긴다. `rule_refs`는 같은 revision의 중복을 막으며 `assemble_rca_draft`·평가의 `rule_sources`는 동일 ID를 재사용한다. 적용 조건·조회 허용 범위·본문은 바꾸지 않으며 fast path도 같은 보존 규칙을 따른다. 구 결과의 저장 시점은 재작성하지 않는다.

Runbook 작성 필드·등록·검토·발행 명령은 [작성 안내](../../../rcca-agent/runbooks/README.md)와 [DB workflow](../../../rcca-agent/runbooks/DB-WORKFLOW.md)를 따른다. 발행 revision을 덮어쓰지 않는다.

## 관측 계획과 보완 선택

`observation_plan`은 query ID·우선순위·필수 여부·목적·산출 fact·독립성을 정의한다. query는 profile에 등록되고 허용된 것이어야 하며 선언된 fact를 생산할 수 있는지 검증한다. 실제 대상·기간·데이터소스는 [공통 D binding](../common/d-binding-runtime.md)의 범위를 따른다.

| 선택 방식 | 현재 조건 |
|---|---|
| 필수 수집 | 선택된 Runbook이 요구하는 허용 조회 |
| 규칙 기반 보완 | `selection.missing_any`의 부족 조건이 있고 `requires_all` fact를 충족한 독립 보조 단계 |
| 명시적 정책 | `unexpected_evidence.additional_queries`; 단계의 selection 조건을 우회하지 않음 |
| 탐색 LLM | `exploratory_llm: true`인 독립 보조 단계만 JSON 선택 허용 |
| 선택 조건 없음 | `selection_conditions_missing`, `unconfigured_queries`로 기록. 암묵적 LLM fallback 없음 |

동일 query를 중복 선택하지 않고 priority/query ID 순서와 공유 예산을 적용한다. 최초 수집과 보완 수집 1회, 최대 2라운드다. 보완 배치는 최대 3개이며 이미 수집된 조회를 무조건 반복하지 않는다. 규칙으로 선택한 배치를 LLM으로 채우지 않는다.

매 라운드 `evidence_evaluation`은 가용 사실·부족 조건·상충/실패·정책과 규칙 판단·다음 조회·종료 이유를 저장한다. `sufficient`, `insufficient_actionable`, `insufficient_blocked`, `degraded`, `conflicted`를 구분한다. 다음 조회 없음, 예산/시간/라운드 소진은 근거 충분과 다르다.

## 관측의 판단 가능 범위

- 조회 성공은 응답 확보만 뜻한다. 값·단위·producer·대상·발생 시각·freshness가 해당 판단에 유효한지 별도 확인한다.
- Fleet 로그의 기록 시각은 장비 발생 시각이나 현재 상태를 자동으로 보증하지 않는다. `reported_error_code`와 현재 상태 fact를 분리한다. producer 시각 0은 유효한 사건 시각으로 승격하지 않는다.
- PCI 주소는 정규화한 후 제공된 인벤토리와 비교한다. 일치해도 후보 연결이며, 불일치는 제공된 목록에서 연결을 확인하지 못했다는 뜻이다. NVSwitch 주소는 GPU 인벤토리로 검증하지 않는다.
- GPU·Pod·Namespace 관계를 사용하는 기존 경로는 동일 대상·기간·UID 조건을 만족한 관측만 연결한다. 노드에 같은 시각 존재했다는 이유로 특정 GPU의 사용자나 업무 피해로 단정하지 않는다.
- 생산자가 같은 DCGM Field ID를 읽어도 표본을 합산하거나 독립된 장애 근거로 중복 가산하지 않는다. [생산자별 메트릭 의미](references/metric-meaning.md)와 [원천 검토 자료](references/README.md)를 따른다.

## 모델 입력과 원인 후보 검증

새 관측이 있는 라운드에서 해석·원인 분석을 한 번에 작성하고 Runbook 후보·권고를 결합한 구조화 자료를 별도로 검토한다. 같은 증거의 전체 RCA 재작성은 금지한다. fast path와 유효 근거 없음·모델 미설정은 별도 상태로 남긴다. [입력 구성](../../../rcca-agent/src/rcca_agent/synthesis_context.py)은 원본을 수정하지 않고 제한된 모델 뷰를 만든다. 입력 refs·원본/전달 크기·생략 수를 기록하고 수정 요청에서도 실제 입력 범위를 남긴다.

모델은 `hypotheses`와 `limitations`를 반환한다. 후보에는 주장·지지 refs·반박 refs·부족 입력이 필요하다. [검증기](../../../rcca-agent/src/rcca_agent/synthesis.py)는 구조, 허용된 관측 참조, 상충 참조, 숫자·한국어 표현과 특정 원인 주장 패턴을 검사한다. 신원 불확실성을 원인으로 제시하는 검사와 미확정 장치의 기전 주장은 표현 검사보다 먼저 확인한다.

같은 증거에서는 작성 1회만 허용한다. JSON 오류·출력 잘림·검토 지적도 재생성 사유가 아니다. 검토에서 특정 가능한 문제 주장을 제외하면 변경된 자료는 미검토로 남긴다. 유효한 부분만 남긴 `validated_subset`과 응답 전체를 채택한 `validated_response`를 구분한다. 거절 사유·위치·문장 hash를 진단에 저장하며 거절 원문 전체를 보관하지 않는다.

현재 검증은 원인 정확도나 확률을 산출하지 않는다. LLM 후보는 인과 확정으로 승격되지 않으며, 적용 가능한 Runbook에서 나온 후보와 관측 요약도 출처를 구분한다. 원인 후보가 없어도 보고된 증상과 부족한 근거를 보고할 수 있다.

## 결과·보고서·공개

RCA는 사실·추론·채택/보류·근거·한계·평가·종료 이유를 구조화한 자료를 생산한다. 조사 종료 후 `rca_result_frozen`에 분석과 최종 선택 발행 Runbook의 지침·출처·revision을 함께 고정한다. 보고서 LLM은 이 자료의 관측·분석 설명만 서술하며 원본 로그·Runbook을 재검색하거나 새 원인을 추가하지 않는다. 보고에 적용 가능한 지침은 코드가 판정하고, 오류 정의·대응 절차와 모델·버전·승인·조치 후 확인 조건은 원문으로 삽입한다. 오류 정의는 원인 추론과 분리해 원문 표시하고, 비정상 상태만으로 일반 원인 후보를 생성하지 않는다. 작성자의 미응답(`unknown`) 기준은 검토 입력의 `unresolved_assessments`에 분리한다. `method=llm` 완료 기준은 독립 검토의 판정·루브릭으로 평가하며 작성자의 미응답 자체를 목적 달성 근거로 사용하지 않는다. 원문 발췌의 로그 기록 시각은 생산자 상태 시각이나 회복 시각을 대체하지 않는다. 순서만 다른 동일 GPU 재고는 모델 입력에서 한 번 참조하되 저장 원본과 관측별 근거는 유지한다. 지침을 포함한 hash가 달라지면 공개하지 않는다. 작성 LLM 실패로 채택된 관측 해석이 없으면 대상·출처·시각 검증을 통과한 보고 사실(`reported_observations`)을 기존 자료 고정 단계에서 함께 저장하고 발생 내용에 원문 표시한다. XID·SXID·일반 Fleet 컴포넌트가 같은 경로를 사용한다. 이 요약은 LLM 입력에 추가하지 않으며, 분석 처리 상태와 구분하고 현재 상태·원인·회복 판정으로 승격하지 않는다. 별도 조회·LLM 호출·workflow 단계는 추가하지 않는다. 미설정·예산/입력 제한·검증 실패 시 동일 자료를 기본 표시하고 원격 실행 불명·취소는 기존 fencing을 따른다. 과거 보고서 계약과 별도 Ops 보고서는 유지한다.

본문은 “어디서 무엇이 보고됐고, 무엇을 알며, 다음에 무엇을 해야 하는지”에 답한다. `missing_inputs`를 행동 지시로 변환하지 않고 제한 상세에 보존한다. 근거 없는 확신으로 바꾸거나 unknown 판정을 삭제하지 않는다. 중요한 적용 조건은 대응 옆에 유지하고, 반복적인 부정 문구·개발자 코드는 본문의 중심으로 삼지 않는다. 빈 추가 확인 섹션은 만들지 않는다. 발생 시각 누락 시 이미 범위 검증된 로그 기록 시각을 보고 대조 기준으로 사용하되 장애 발생·회복 시각으로 해석하지 않는다.

Runbook 선택 → 등록된 근거 수집 → 기존 작성·코드 검증·독립 검토 → 목적 종료와 지침 고정 → 보고서의 실행 경로를 유지한다. 새로운 scoring LLM·최종 재검토·번역 단계는 없다. BM25 관련도, 코드의 자료 적합성 검사, 독립 검토의 기존 6개 척도를 구분한다. XID·SXID·비코드 Fleet 오류는 동일한 역할과 예산을 사용한다. 비코드 1.2 적용 조건, 원천 등록과 현재 카탈로그 경계는 [RCA README](../../../rcca-agent/README.md#비코드-fleet-오류와-평가)를 따른다.

현재 구현의 소유 문서는 [RCA 보고서·조회 계약](../../../rcca-agent/README.md#보고서와-조회-호환)이다. `report_assembly`의 작성 execution_status와 assembly_status를 분리하고 실제 호출 시간·usage·입력 hash·검증 위치를 보존한다. `source_items`는 GUI에서 원문 대조가 가능하다. 필수 섹션·출처·수치 검사는 의미 보존을 보장하지 않으므로 실제 모델 서술의 정확성은 배포 후 검수한다.

최적화는 기존 예산·검토 예약·출력 cap을 유지한 상태에서 진행한다. 동일 인벤토리만 참조 테이블로 공유하고 관측의 시각·값·출처를 합치지 않는다. 검토는 주장 표현을 한 번만 전달하며 작성 LLM과 검토 LLM이 원본을 각각 읽는 비용은 유지한다. Runbook 미확정 상태를 사실 주장과 구분하고 개별 지적은 관련 항목·의존 결론에만 적용한다. 전역 지적과 변경 초안 미검토 경계는 유지한다.

검수: 같은 XID/SXID fixture에서 작성·검토·보고서 서술 순서, D09 목적 종료, 추가 정렬 없음, 기본 32,768 예산에서 분석·검토 유지, 원본/고정 hash 불변, 반복 인벤토리 복원 일치, 잘림·입력 초과·알 수 없는 참조·새 수치·원격 실행 불명 경계를 검사한다. 보고서 실패에도 자료가 보존되어야 한다. 배포 후에는 사용자 제공 동일 사건의 원문과 보고서를 비교하여 사실·한계·반대 근거 손실, 가독성, 실제 전체 토큰·시간을 측정한다. fixture 토큰을 운영 절감률로 사용하지 않는다.

Runbook의 `operator_guidance`는 의미·주의·다음 확인·출처를 공통 형식으로 표시한다. 발행된 지침을 관측 사실로 간주하지 않고 다른 오류의 지침을 대신 붙이지 않는다. 권고는 전제 조건 충족 여부를 표시하며 실제 장비 조치를 수행하지 않는다.

| 결과 축 | 의미 |
|---|---|
| job 상태 | Worker 실행과 JC 공개 수명주기 |
| result_status / assessment | 근거에 따른 판단 가능 범위와 부족 입력 |
| analysis / synthesis 진단 | 모델 호출·응답 검사·수정·채택 상태 |
| narrative_status / quality.report | 보고서 구성·문장 편집 상태 |

evidence와 candidate를 저장한 뒤 JC가 실행권·계약·hash 등을 확인해 공개한다. 과거 결과의 `analysis.sufficiency`와 이전 평가 기록은 조회 호환용으로 유지한다. 원본 snapshot·결과 hash·발행 revision은 변경하지 않는다.

## 평가 분리 설계·개발

### 개선 목적과 현재의 차이

RCA는 장애 관련 로그·지표를 모아 원인을 조사하는 과정이다. 데이터를 받았는지, 데이터가 무엇을 뜻하는지, 결론이 근거에 맞는지는 서로 다른 질문이다. 모든 자료가 확보돼야만 조사를 완료하는 구조를 피하고, 확보한 증거가 허용하는 범위에서 결론과 한계를 남긴다. 자료 부족만 반복해서 설명하고 확보한 중요한 증거를 검토하지 않는 분석도 적절하다고 보지 않는다.

| 구분 | 질문 | 판단 주체 | 예시 |
|---|---|---|---|
| 수집 상태 | 데이터를 제대로 받아왔는가? | 코드 | 성공·빈 결과·부분 수집·실패 |
| 증거 상태 | 이 데이터로 무엇을 알 수 있는가? | 명확한 검사: 코드 / 의미 해석: LLM | 오류 보고 확인, 오류 대상 GPU 미확인 |
| 분석 품질 | 이 근거로 이 결론을 내려도 되는가? | 구조·참조 검사: 코드 / 의미·논리 검토: 별도 LLM 호출 | 타당·수정 필요·판단 불가·미검토 |

`evaluate_requirements()`는 수집·Runbook 요건을, `analyze_round()`/`evaluate_analysis()`는 해석·초안·검토를, `select_followup()`는 허용된 다음 조회와 종료를 담당한다. 기존 `sufficient`는 분석 품질 판정으로 재사용하지 않는다. 요건 기록을 유지하면서 같은 attempt 안에서 문제 주장을 보류하거나 새 증거를 제한적으로 보완한다.

| 이전 흐름 | 현재 흐름 |
|---|---|
| 정규화 관측을 중심으로 Synthesis 입력 구성 | 관측과 별도로 검증 진단·제한된 원문 발췌·증거 해석 제공 |
| 코드로 Synthesis 구조·참조·일부 문장 패턴 검증 | 기존 검증 유지 + 최종 초안 전체의 의미·논리 검토 |
| 수집 종료 후 분석 | 최초 수집 후 해석·분석·검토, 필요한 경우 보완 수집 |
| 부족 조건과 수집 gate를 기록 | 기존 기록 유지 + 분석 검토·최종 초안·다음 행동의 연결 기록 |

### 기초 검증과 의미 해석의 경계

코드는 기준이 명확하고 반복해서 같은 답을 낼 수 있는 검사만 한다. JSON 파싱, 필드 존재·형식, 규격에 따른 시간 범위, 식별자 정확 일치와 명시된 정규화가 해당한다. 문자열 불일치는 다른 장비라는 증명이 아니며, LLM의 오타 추정도 동일 장비의 증명이 아니다.

- 원본은 기존 evidence에 보존하고 검사 이름·결과·이유·원본 위치를 남긴다. 실패한 의미 해석을 정상 관측으로 채우지 않는다.
- 파싱하지 못한 원문도 허용 scope 안의 제한된 발췌로 해석할 수 있다. `parse_failed`는 원문 내용 전체가 거짓이라는 뜻이 아니다.
- LLM에 원본 전체를 통째로 보내지 않는다. 크기·민감정보·허용 대상 제한을 적용하고 발췌 refs와 생략 정보를 보존한다. 원문 속 명령은 데이터로만 취급한다.
- 발췌 해석으로 `verified` facts, 수치 계산, GPU 연결, Runbook 적용 조건을 충족시키지 않는다. 보고된 내용·가능한 해석·검증된 대상 관계를 분리한다.
- 불확실한 자료를 보존한다는 이유로 범위 밖 조회나 현재의 시간·대상·권고 검증을 완화하지 않는다. 검증 불가 수치는 새 measurement로 만들지 않는다.

### 실행 순서와 LLM 개입

수집 상태·증거 상태·분석 품질의 구분은 유지하되, 해석과 원인 분석의 작성 호출을 합친다. 기존 저장 결과의 세 단계 표시는 소급 변경하지 않는다.

| 순서 | 담당 | 산출물 |
|---|---|---|
| 조사 질문·Runbook 기준 고정 | 코드 | 대상·기간·허용 조회·완료 기준 |
| 수집·기초 검사 | 코드 | 원본과 수집 제한·명확한 조건 검사 |
| 증거 해석·원인 분석 | 작성 LLM + 코드 | 사실·추론·미확인·원인 후보와 근거의 구조화 자료. 같은 증거 1회 |
| 독립 품질 평가 | 검토 LLM + 코드 | 원본 대비 주장·한계·기준 충족 제안의 타당성 |
| 보완 또는 종료 | 코드 | 유효한 추가 자료의 수집 결정 또는 목적 달성/한계 종료 |
| 최종 RCA 자료 고정 | 코드 | 채택·보류·평가·종료 이유와 자료 hash |
| 최종 보고서 작성 | 보고서 LLM + 코드 검증 | 고정 자료를 읽기 좋은 보고서로 전달. 새로운 RCA 판단 금지 |
| 저장·공개 | Worker / JC | 실행권·계약·결과 hash 확인 후 공개 |

```text
질문·기준 → 수집·검사 → RCA 작성 1회 → 독립 품질 평가
                        ↑                   ↓
                 유효한 새 증거 ← 필요한 보완 또는 종료
                                            ↓
                         RCA 근거 자료 고정 → 최종 보고서 → 저장·공개
```

품질 지적은 같은 증거의 재작성·재검토 루프로 보내지 않는다. 문제 주장을 코드로 보류한 경우 변경 자료는 미검토이며 이전 지적은 보존한다. 최종 보고서는 평가 통과 여부와 관계없이 확정된 실행 범위의 자료·한계를 전달한다. 취소·원격 종료 불명까지 성공 공개를 보장하는 것은 아니다.

### 분석 품질 평가 척도 — rubric 1

평가 대상은 **최종 초안이 전달된 증거 범위에 맞는가**이다. 원인 정답률·수집량·문장 유창성의 점수가 아니다. 규칙은 출력의 구조·참조·판정 일관성을 검사하며, 아래 의미 판단은 별도 LLM 호출이 수행한다. 모델이 판단한 이유를 사람이 원본과 대조할 수 있어야 한다.

| 항목 / 코드 | 충족으로 볼 조건 | 수정 필요 사례 | 판단 불가 사례 |
|---|---|---|---|
| 근거와 결론의 연결 / `grounding` | 주요 주장·원인 배제·권고가 인용 증거의 범위를 지킴 | PCIe 일부 0값만으로 PCIe 원인 배제; 로그에 없는 고장 단정 | 판단에 필수인 인용 원문이 입력에서 빠져 확인 불가 |
| 대상·시각 구분 / `identity_time` | 보고 대상·실제 장치·사건/기록/현재 시각을 구분 | 이름의 마침표 차이를 같은 GPU로 확정; 기록 시각을 장애 발생 시각으로 확정 | 초안의 대상 연결을 검토할 식별 근거 자체가 전달되지 않음 |
| 반대 근거·모순 / `contradictions` | 서로 다른 관측을 함께 설명하거나 미해결로 표시 | 건강/이상 보고가 함께 있는데 한쪽만 채택 | 중요한 상충 자료의 세부 내용을 확인할 수 없음 |
| 중요한 대안 / `alternatives` | 현재 증거로 남는 주요 대안과 배제 범위를 설명 | 하드웨어 고장만 단정하고 설명 가능한 연결·관측 문제 누락 | 주요 대안을 비교할 근거의 의미가 불명확 |
| 수집·해석 한계 / `limitations` | 빈 결과·부분 수집·시간 공백·입력 생략이 결론을 어떻게 제한하는지 명시 | empty를 정상으로 처리; 검토하지 못한 기간까지 정상이라고 서술 | 제한이 결론에 미치는 영향을 판단할 문맥이 없음 |
| 중요한 증거 활용 / `evidence_use` | 확보한 핵심 보고를 사용하면서 미확인을 구분 | 유효한 오류 보고가 있는데 ‘자료 부족’만 반복 | 핵심 자료가 해석 불가능하거나 검토 입력에서 생략됨 |

항목마다 `pass/needs_revision/undetermined/not_applicable`, 이유, 실제 전달된 증거 ID를 기록한다. `not_applicable`에도 해당하지 않는 구체적 이유가 필요하다. 예컨대 반대 근거가 실제 제공되지 않은 경우와 반대 근거를 읽지 못한 경우를 혼동하지 않는다. 자료가 부족해도 ‘GPU 연결 미확인으로 해당 원인을 배제할 수 없다’는 설명은 충족일 수 있다.

종합 판정은 코드로 일관성을 확인한다. 하나라도 `needs_revision`이면 `revision_required`, 그것이 없고 `undetermined`가 있으면 `undetermined`, 나머지는 `acceptable`이다. 항목을 생략하거나 종합 판정과 모순되면 형식 복구를 한 번 요청하고, 다시 실패하면 **미검토**로 남긴다. 점수 평균이나 임의 가중치로 중요한 문제를 상쇄하지 않는다.

척도 자체를 검증할 기준 사례는 같은 자료에 대한 제한적 설명/과장된 설명 쌍, 식별자 오타, 관측 공백, 상충 보고, 핵심 증거 미사용이다. 기대 판정과 근거를 사람이 먼저 정하고 실제 모델 출력의 문제 누락·잘못된 지적·항목별 차이·호출 시간·토큰을 대조한다. 고정 응답 테스트는 이 평가의 저장·분기·참조 계약만 검증한다. 실제 모델의 의미 평가 정확도는 T79에서 별도로 검증한다.

### 다음 행동과 반복 제한

요건 미충족은 조사 제약이며 그 자체로 잘못된 분석이라는 뜻이 아니다. 반대로 기존 요건이 충족돼도 검토자가 중요한 보완 질문을 남겼다면 허용된 조회와 실행 조건을 다시 확인한다. `evaluate_requirements()`는 부족 조건과 정책 제안을 기록하고, `select_followup()`는 기존 Runbook 규칙·명시적 정책·허용 범위로 후보를 제한한다. `select_followup()`와 `evaluate_analysis()`의 결정이 `investigation_decision`에 실제 행동과 이유를 기록한다. LLM 제안은 등록 query ID와 목적·기대 효과만 포함하며 임의 조회식이나 새 Runbook 발행을 허용하지 않는다.

| 조건 | 행동 |
|---|---|
| 현재 자료를 과장함 | 특정 가능한 문제 주장을 코드로 보류하고 변경 자료는 미검토. 같은 증거 재작성 없음 |
| 중요한 결론을 바꿀 미확인 사항 + 허용된 미수행 조회 + 예산·범위 충족 | 보완 수집 후 해석·분석·검토 반복 |
| 근거 범위에서 타당하고 필요한 추가 조사가 없음 | 한계를 포함해 종료 |
| 원천 자료 부재·접근 불가·실행 가능한 조회 없음 | 판단할 수 없는 내용과 종료 사유를 남김 |
| 모델 미설정·확정된 호출 실패·유효 해석 자료 없음 | 가능한 코드 결과 보존, 단계 실패·생략 표시 |
| 예산 또는 라운드 소진 | 현재 검토 상태와 한계 기록. 미해결 초안을 정상 결론으로 승격하지 않음 |

추가 자료는 중요한 판단을 바꿀 수 있는지, 실제 확보 가능한지, 남은 예산 안에서 가치가 있는지 확인한다. 알려지지 않은 가용성을 ‘확보 가능’으로 단정하지 않으며 실패 이유를 기록한다. 같은 query/scope/기간/revision의 업무 재조회는 반복하지 않는다. 수집기의 기존 제한된 전송·분할 처리는 별도이며 전체 예산을 공유한다.

- 수집은 기존처럼 최초와 보완 1회, 최대 2라운드이며 보완 배치는 최대 3개다. 모델 토큰 부족만으로 명시적 Runbook 규칙의 읽기 전용 보완 조회를 차단하지 않는다. 조회 예산·deadline·계획 허용 범위는 유지하며 모델 탐색은 생략한다. 분석 실패와 수집 종료 사유를 각각 기록한다. 단순히 `causal_confirmation_evidence`가 없다는 이유로 모든 조회를 수행하지 않는다.
- 같은 증거의 작성은 attempt 안에서 최대 1회다. 새 UUID·중복 응답·feedback·입력 축약은 새로운 증거로 세지 않는다. 보완 수집으로 유효한 원본이 추가된 경우에만 다음 작성을 허용한다.
- 작성은 형식 실패·출력 잘림·HTTP 오류에도 한 번만 전송한다. 독립 검토의 형식 검사·제한된 응답 복구와 보고서 서술은 별도 역할이며 원인 재작성으로 연결하지 않는다.
- 모든 LLM 호출은 같은 attempt에서 직렬로 실행하고 같은 token budget·deadline을 사용한다. 수집 예산·원격 실행 상태·취소 처리를 재설정하지 않는다.
- 초안 생성·수정 전에 bounded 입력과 기존 출력 cap으로 다음 검토에 필요한 토큰을 예약한다. 최초 분석 작성에서 예약량이 사용 가능한 원문 근거를 모두 제외하면, 기존 호출자 예약량을 하한으로 예약량을 줄인다. `rca_synthesis.diagnostics.budget_allocation`에 요청·적용 예약량과 원문 수용 여부를 기록한다. 이는 분석 호출 전 근거 소실을 막는 부분 개선이며 후속 검토 성공을 보장하지 않는다. 현재는 생성 실패 후에도 코드 후보 조립·검토를 시도할 수 있다. 검토 자체를 수용하지 못할 때 새 초안 시작까지 차단하는 사전 검사는 남은 예산 개선(F2) 범위다. 시간은 호출마다 남은 deadline을 확인하며 추정 시간만으로 검토 완료를 보장하지 않는다.

### 실패와 최종 초안 처리

#### 모델 요청 제한 진단 (F0)

`evidence_interpretation.call_stage()`는 해석·검토의 요청 본문 크기와 사용 가능한 토큰 예산을 독립적으로 검사한다. 입력 상한 초과는 `llm_input_size_exceeded`, 예산 부족은 `llm_token_budget_exhausted`다. 둘 다 해당하면 입력 상한 초과를 주 사유로 기록하고 두 조건을 모두 남긴다. 본문 크기가 상한과 같으면 허용하며, 기존의 보수적 필요량 이하인 예산은 거절한다. 상한·예약·기본 출력 cap은 확대하지 않는다.

최초 요청과 형식 복구 요청마다 `request_checks`를 기록한다. 크기·예산·예약량·최초 출력 상한 계산값과 실제 논리 호출 여부는 [04의 중간 기록 계약](../common/04_Agent_동작_판단_명세서.md#기록의-관계와-검증)을 따른다. 복구 입력이 한도를 넘으면 첫 호출·검증 실패 기록을 보존하고 추가 호출을 하지 않는다. 이전 결과에 이 진단이 없으면 원인을 새로 추정하지 않는다.

검토가 입력 상한으로 중단되면 `evaluate_analysis()`가 `analysis_unresolved`, 토큰 부족이면 `llm_budget_exhausted`로 종료 결정을 전달한다. `workflow.select_followup()`는 이 결정을 우선 적용하므로 입력을 줄이거나 모델 예산을 보충하려는 추가 조회는 발생하지 않는다. 검토는 `verdict=null`이며 수집·원인 상태를 정상으로 승격하지 않는다. 문제 주장 제거 후 재검토가 실패하면 기존 `draft_changed_after_review`와 별도로 `failure_reason`을 보존한다.

모델 미설정·HTTP 오류·출력 검증 실패는 기존 사유를 유지한다. 취소·deadline·원격 종료 불명은 기존 예외/Worker 수명주기를 따르며 입력 제한 결과로 바꿔 공개하지 않는다. 공통 `LLM.request_budget()`은 기존 전송 cap 계산을 공유하고, 모델 보고 토큰과 usage 누락에 따른 보수적 예산 차감을 구분한다. 새 모델 호출·외부 서비스·DB 변경은 없다.

#### 최종 결과 처리

| 실패·생략 | 처리 |
|---|---|
| 증거 해석 실패 | 실패 기록과 기존 정규화 관측으로 분석 가능 범위를 판단. 원문 추정을 검증 사실로 대체하지 않음 |
| RCA 생성 실패·사용 가능한 자료 없음 | 코드로 확인 가능한 내용과 한계 제공. 무근거 후보를 생성하지 않음 |
| 검토 실패·생략 | 미검토. 검토 실행 성공과 타당 판정을 구분 |
| 검토 완료지만 판단 어려움 | `undetermined`, 확정 원인으로 승격하지 않음 |
| 수정 필요를 해결하지 못함 | 문제가 지적된 주장·연관 권고를 정식 결과에서 제외/보류. 의존성을 안전하게 분리하지 못하면 코드 기반 관측·한계만으로 대체 |
| fast path | 기존 규칙 경로 유지, 새 해석·분석·검토 생략 사유 기록. 최종 편집 호출과 구분 |
| 원격 종료 불명·취소·lease 상실·실행 deadline 초과 | [14 실행 계약](../common/14_모듈간_호출과_공통실행_계약.md) 우선. 부분 결과 공개로 우회하지 않음 |

검토한 초안은 정규화한 claims/recommendations/limitations와 입력 뷰 hash를 묶은 `analysis_id`로 고정한다. 기존 `content_hash()`를 재사용하며 job 전체 content_hash와 구분한다. LLM·Runbook 출처는 유지하고 권고에도 초안 내 local claim ID를 연결한다. 원인 후보·권고·한계를 변경하면 새 ID를 만들고 재검토해야 한다.

제외·보류로 최종 초안이 달라지면 재검토 호출은 하지 않는다. 지적된 주장만 제외한 초안은 검토한 초안의 부분집합이므로 최종 review를 `complete`·`verdict=acceptable_after_feedback`로 기록하고 이전 검토 ID와 기준을 함께 연결한다. 특정 주장을 가리키지 않는 전체 지적은 `grounding`·`identity_time`이 모두 `pass`이면 주장을 무효화하지 않는 피드백으로 보존한다. 그렇지 않은 전체 지적으로 해석 전체를 제외한 경우에만 **최종 초안의 review는 skipped/verdict=null**, 사유는 `draft_changed_after_review`로 남긴다. (2026-10-19 변경: 이전에는 모든 주장 제외 뒤 검토 판정을 승계하지 않아, 대안·누락 맥락 같은 전체 지적만으로도 목적 달성이 불가능했다.) 기존 assessment/result_status는 최종 유효 근거와 기존 규칙으로 다시 계산하며 검토 통과로 상향하지 않는다.

형식 검증을 통과한 초안·구조화 검토는 기존 evidence에 저장하되, 거절된 원시 모델 응답 전체를 새로 저장하지 않는다. 기존 사유·위치·hash 진단 및 민감정보 제한을 유지한다. 보류된 내용은 일반 보고서·Ops의 정상 후보로 인용하지 않는다.

### 사건 예시와 결과 추적

예시 입력은 XID 오류 보고 로그, 정확히 연결되지 않은 GPU 식별자, 일부 값이 0이지만 시간 공백이 있는 PCIe 지표다. 실제 환경의 검증 결과가 아닌 설계 설명용 사례다.

| 단계 | 처리 예시 |
|---|---|
| 코드 검사 | 조회 성공·지표 공백·식별자 불일치 기록. 다른 장비라고 확정하지 않음 |
| LLM ① | 오류 보고 확인, GPU 연결과 공백 시간 상태는 미확인 |
| LLM ② 초안 | 만약 ‘PCIe 지표가 0이므로 PCIe 원인은 아니다’라고 서술하면 검토 대상 |
| LLM ③ | 대상 연결과 관측 공백 때문에 원인 배제가 과도하다고 지적 |
| 수정 | ‘오류 보고는 확인했으나 GPU 연결·시간대 관측이 부족하여 PCIe 원인을 배제할 수 없다’ |
| 코드 결정 | 신뢰할 연결 자료가 조회 가능하고 중요하면 보완, 없으면 한계를 남기고 종료 |

가능한 최종 조합은 **부분 수집 / 오류 보고 확인·GPU 미확인 / 제한된 근거 안에서 타당 / 원인 미확정 / 조사 종료 / 추가 자료 확보 불가**다. 검토 LLM이 실패한 같은 사건은 ‘타당’ 대신 ‘미검토’다. 모든 조회에 성공했어도 근거 없는 단정이면 ‘수정 필요’다.

기록은 `D09 → 해석 → 초안 → 검토 → 추가 확인 필요 → D44`처럼 인과 연결을 제공한다. D 번호는 조회 식별자이지 실행 순서가 아니다. 실제 선택 이유·입력 refs·라운드·초안 ID·결정 기록으로 순서를 설명하며 생성 시각만으로 시작 순서·소요시간을 추정하지 않는다. 표시 기준은 [07](../frontend/07_프론트엔드_개발명세서.md#rca-평가-분리-표시)을 따른다.

### 함수별 개발 내용과 유지 범위

기존 공개 ID/hash·과거 snapshot·입력 계약·DB 소유권을 바꾸지 않는다. Backend/JC는 RCA 의미를 재평가하지 않으며 공개 계약 검증을 계속 맡는다. 정책·설정 revision 변경이 필요한 구현에서는 해당 revision과 fixture를 함께 갱신하되 이 설계 작성으로 배포 설정을 변경하지 않는다.

개발 순서는 결과/trace 호환 → 기초 검증 진단·해석 → 초안 전체 검토 → 제한된 반복 → 보고서·Ops·UI 통합이다. 이는 코드 의존 순서이며 별도의 협의·승인 단계를 추가하는 것이 아니다. 실제 적용 순서와 롤백 경계는 14를 따른다.

[05의 T66~T79](../05_테스트_검수_기준서.md#rca-평가-분리-검수)를 구현 검수 기준으로 사용한다. 현재 [test_rca_analysis](../../../agents/tests/test_rca_analysis.py), [test_rca_repairs](../../../agents/tests/test_rca_repairs.py), [test_synthesis_context](../../../agents/tests/test_synthesis_context.py), [test_rca_rule_selection](../../../agents/tests/test_rca_rule_selection.py), [test_rca_batch_selection](../../../agents/tests/test_rca_batch_selection.py), [test_rca_parallel](../../../agents/tests/test_rca_parallel.py), [test_e2e](../../../agents/tests/test_e2e.py)를 회귀 대상으로 유지한다. 신규 해석·검토 단위 테스트와 Frontend 표시 테스트를 추가한다.

공통 Python 변경은 RCA/Ops 양쪽, 결과 변경은 Backend·Frontend·Ops와 Worker→JC 공개 경로를 함께 검사한다. 고정 LLM 응답으로 분기·참조·예산을 검증한 결과와 실제 모델이 과장·누락을 찾아낸 결과는 구분한다. 실제 사례는 같은 증거의 적절한 설명과 과장된 설명, 상충·대상 미확인·관측 공백을 포함하고 사람이 원본 근거와 비교한다. 호출 시간·토큰·검토 누락/오검출을 기록하며 보편적인 정확도 목표나 검토 점수를 임의로 만들지 않는다. 실행 증거가 생기기 전에는 Agent QA를 통과 기록으로 갱신하지 않는다.

## 확인된 증거와 후속 판단 연결 개선안

**통합 개선 계획 · 핵심 작성/검토·목적 종료·GUI 구현, 실측과 후속 개선은 별도.** 문제 진단의 비교 기준은 `3b76899`이다. 평가 분리·F0·워크플로우 팝업은 이 기준에 구현돼 있으며, 아래 계획은 확보한 정보를 보고서와 다음 조사에 연결하고 검토 입력·실패 진단·평가 방법을 보완한다. 현재 GUI는 저장된 상세 실패 사유와 호출 이력을 분리하고, 오류 이벤트의 시각·보고된 GPU 연결 후보·근거 ID 및 상태 보고의 재고 관계를 표시한다. Agent의 예약량·추론·후속 선택은 이 표시 변경으로 수정되지 않는다. F 번호는 항목 식별자이며 실행 순서는 [구현 순서](#구현-순서와-변경-범위)를 따른다. 운영 배포 여부와 실제 모델 품질은 코드 구현 상태와 구분한다.

### 해결하려는 문제

현재 RCA는 오류 이벤트와 장치 재고의 연결을 저장하고도 화면에는 “오류 장치 확정 불가”라고 표시할 수 있다. 필요한 조회를 수행한 뒤에도 같은 일반 지침을 다시 안내하며, 복구 조치 목록이 비어 있는 이유도 구분하지 않는다. 사용자는 조사로 무엇을 알아냈고 무엇이 남았는지 판단하기 어렵다.

개선 목표는 **확인한 내용을 그 범위 안에서 인정하고, 남은 질문에 필요한 다음 행동을 연결하는 것**이다. 증거가 충분해야만 좋은 분석이라는 전제는 두지 않는다. 원인이 미확정이어도 오류 보고·재고 연결·발생 시각처럼 확인한 정보는 명확히 보여준다.

여기서 “재고 연결 확인”은 이벤트 주소와 보고된 재고가 일치한다는 뜻이다. 실제 장치 신원의 독립 검증, 현재 장애 지속 여부, 근본 원인 확정과 구분한다. `fact_eligible=False`를 일괄 해제해서 해결하지 않는다.

| 문제 | 기준 코드에서 확인한 원인 | 개선 방향 |
|---|---|---|
| XID 재고 일치와 연결 UUID가 화면에 드러나지 않음 | `RcaObservations`는 `device_observations`만 읽음. `inventory_candidate_only` 표시 분기가 없고 `error_events`를 별도로 표시하지 않음 | 오류 이벤트와 상태 보고를 나누고, 보고된 재고 연결·독립 검증·현재 상태를 각각 표시 |
| 생산자 시각 누락이 사건 전체의 문제처럼 보임 | 상태 보고의 시각 누락은 표시하지만 보고서 기본 시각 문장은 사건 기준 시각만 사용 | 사건 기준 시각·생산자 이벤트 시각·로그 기록 시각을 출처와 함께 구분 |
| 이미 수행한 확인을 계속 안내 | `project_guidance`는 발행 지침을 복사하고 `StructuredGuidance`는 `next_checks`를 그대로 출력 | 확인 질문마다 현재 결과·근거·남은 조건을 연결하고, 완료 항목과 다음 확인을 분리 |
| 복구 조치가 없는 이유가 불명확 | 조사 전용 Runbook은 `assemble_rca_draft`의 일반 조치 생성에서 제외. 빈 `recommendations`에는 동일 문구 사용 | 조사 권고와 복구 후보를 구분하고 미정의·평가 생략·입력 부족·조건 불충족을 명시 |
| 표현 수정 중 분석 근거가 줄어들 수 있음 | `synthesize`가 남은 예산으로 `bounded_context`를 다시 구성 | 단순 표현 수정은 주장에 사용한 입력을 유지. 유지할 수 없으면 축소와 영향·수정 중단을 명시 |
| 증상 요약이 원인 후보로 들어감 | `observed_device_symptom`을 `cause_candidates`에 추가하고 보고서가 후보로 표시 | 관측된 증상과 원인 가설을 분리. 유효한 가설이 없으면 없다고 표시 |
| SXID 장치 연결이 계속 미해소 | GPU 재고로 NVSwitch를 매핑하지 않으며 별도 스위치 재고 소비 경로가 없음 | 우선 미지원 범위를 명시하고, 실제 원천 계약이 확보된 뒤 스위치·포트 연결을 추가 |

근거 코드: [관측 화면](../../../frontend/src/components/RcaObservations.tsx), [고정 지침 화면](../../../frontend/src/components/StructuredGuidance.tsx), [이벤트·재고 처리](../../../rcca-agent/src/rcca_agent/fleet_events.py), [지침 투영](../../../rcca-agent/src/rcca_agent/operator_guidance.py), [판단·조치 조립](../../../rcca-agent/src/rcca_agent/workflow.py), [보고서 생성](../../../rcca-agent/src/rcca_agent/report.py), [수정 요청](../../../rcca-agent/src/rcca_agent/synthesis.py), [입력 제한](../../../rcca-agent/src/rcca_agent/synthesis_context.py).

오류 이벤트는 이미 LLM 분석 입력에 전달된다. 따라서 “분석이 이벤트를 전혀 읽지 않는다”는 설명은 맞지 않는다. 조사 권고도 발행 Runbook의 별도 지침으로 남는다. 부족한 부분은 **확인한 정보와 사건별 진행 상태를 연결하여 일관되게 전달하는 처리**다.

### 코드로 확인된 입력·진단 문제

다음은 기준 코드에서 확인한 동작이다. 이 경로가 존재한다는 사실과 운영에서 얼마나 자주 발생하는지는 구분한다. 입력 차단과 보수적 예산 산정은 F0 이전에도 있었으며, F0가 새로 만든 문제로 보지 않는다.

| 확인된 동작 | 현재 한계 | 개선 항목 |
|---|---|---|
| `evaluate_analysis()`는 6,000바이트 기준 뷰를 만들고 `rule_sources`를 추가할 때 **전체 뷰**를 10,000바이트와 비교 | 6,000+10,000바이트가 아니다. `review_analysis()`의 24,000바이트 한도는 초안·rubric·허용 조회 등을 포함한 요청 본문에 적용하며 초안 전체 크기는 별도로 제한하지 않음 | F4에서 실제 구성 요소와 생략을 추적하고 중복 표현부터 축소 |
| `analysis_draft()`의 `claims`에는 후보·권고 문장이 들어가며 원래 `cause_candidates`·`recommendations`도 함께 전송 | 같은 문장·근거가 중복되어 검토 요청을 키움. 입력 초과 후 재구성 경로가 없음 | 주장을 삭제하지 않는 검토 전용 표현과 호출 전 크기 검사 |

### 운영 사례와 예약량 조정안을 연결한 문제 범위

배포 화면에서 확인한 경로와 아직 적용하지 않은 수정 후보를 구분한다. 아래 사례는 문제를 재현할 기준이며 전체 운영 실패율이나 실제 장비 상태의 정답은 아니다. 제안된 `synthesis_view()`·`reserve_review_budget()`·`budget_allocation`은 기준 코드에 없는 **구현 후보**다. 제안 설명만으로 함수의 정확성이나 회귀검사 통과를 인정하지 않는다.

| 확인한 문제 | 해결 범위 | 함께 해결했다고 간주하면 안 되는 것 |
|---|---|---|
| 최신 XID·SXID에서 ②의 `input_evidence_refs=[]`, `request_attempts=0`, `llm_context_budget_exhausted` 기록 | F2-A에서 검토 예약이 분석용 입력을 비우는 경로를 재현하고, 하한을 보존한 배분 조정 가능성 검사 | 수집 원본 부재, 전체 토큰 소진, 연결 실패로 단정하지 않음. 빈 refs만으로 예약 과다가 유일 원인이라고 확정하지 않음 |
| XID 재검토는 9,134/24,000바이트로 입력 검사를 통과했지만 출력 4,096토큰에서 잘림 | F2-B에서 실제 출력 길이·상한·재시도 비용과 검토 예약을 함께 비교 | 입력 중복 제거만으로 출력 잘림이 해결됐다고 보지 않음 |
| SXID 재검토는 9,192/24,000바이트였지만 가용 11,211이 보수적 필요량 12,001 이하라 호출 차단 | F2-B에서 실제 입력·예산 산정·단계별 소비를 대조 | F2-A가 ②를 호출하게 만들었다고 ③까지 완료된 것으로 보지 않음 |
| XID의 앞선 정상 보고와 뒤의 오류 보고를 시각 차이 설명 없이 상충으로 해석 | F1-A·F4에서 기록 시각별 순서와 생산자 시각의 한계를 함께 전달·평가 | 상태 변화, 동시 모순, 실제 복구 중 어느 하나를 자동 확정하지 않음 |
| SXID 검토가 ‘원인과 현재 상태는 추가 확인 필요’라는 한계 설명을 근거 없는 주장으로 지적 | F1-A에서 적절한 불확실성 표현의 오검출을 검사 | 후보 제거·미검토 종료가 안전하게 동작했다고 검토 판단까지 정확하다고 보지 않음 |
| XID 검토가 D02로 드라이버 로그·펌웨어 정보를 얻는 질문을 제안 | F3-A에서 query ID와 조회 목적·제공 정보·한계를 함께 연결 | 등록된 query ID라는 형식 검사만으로 질문의 해결 가능성을 인정하지 않음 |
| ② 팝업의 대표 사유가 `실패 failed`, 호출한 재검토가 최종 `생략` 상태로 표시됨 | F0·GUI에서 호출 전 차단/호출 후 실패와 최종 미검토를 분리하고 구체적 오류를 우선 설명 | 저장된 과거 상태를 덮어쓰거나, 실행 횟수가 있는데 미호출로 설명하지 않음 |
| 이전 XID의 이벤트 시각·보고된 재고 일치가 저장돼 있지만 관측 요약에 드러나지 않음 | 기존 근거 표시 단계에서 상태 보고·이벤트·연결 확인을 별도로 표시 | 재고 일치를 독립 신원·현재 건강·원인 확인으로 승격하지 않음 |

`llm_context_budget_exhausted`의 상세 해설은 기존 분석 요약에도 있다. 문제는 해당 설명의 부재만이 아니라 **결과 요약·팝업의 대표 사유·중첩 진단이 같은 실행을 일관되게 설명하는가**이다. 관측 자료는 남았지만 입력에 담지 못한 경우, 입력 자체가 없는 경우, 모델 응답을 받은 뒤 검증에서 거절한 경우를 분리한다. [② 입력 검사](../../../rcca-agent/src/rcca_agent/synthesis.py), [팝업 사유 선택](../../../frontend/src/components/RcaWorkflow.tsx), [검토 후 종료 처리](../../../rcca-agent/src/rcca_agent/evaluation.py)를 함께 변경 대상으로 본다.

### 측정이 필요한 가설과 판단 기준

| 아직 확인하지 않은 주장 | 필요한 측정 | 판단에 사용할 결과 |
|---|---|---|
| Runbook 후보·권고가 많을수록 검토가 빈번하게 생략됨 | 초안·증거·rubric 등 구성별 바이트, 후보/권고 수, 검토 필요 단계의 실행/생략 사유 | 입력 초과 빈도와 원인별 분포. 일부 큰 사례만으로 운영 전반을 단정하지 않음 |
| 바이트 기반 산정이 실제 토큰의 2~3배이며 조기 종료의 주원인임 | 동일 payload의 사전 추정·예약·출력 cap, 모델 보고 prompt/completion/total tokens, 실제 모델 tokenizer를 사용할 수 있으면 별도 추정 | 언어·로그·식별자 혼합 입력별 차이. 실행하지 않은 요청의 usage를 0이나 실측으로 채우지 않음 |
| 기본 attempt 예산이 실제 RCA에 부족함 | 고정 사례의 단계·수정·복구·라운드별 비용, 검토 완료 여부, 지연·잘림·최대값과 분포 | 입력 구성 개선 전후를 같은 모델·설정으로 비교한 뒤 F2 조정 판단. 예제 설정을 운영 설정으로 간주하지 않음 |
| 검토 LLM이 과장·누락을 잘 찾으며 입력 축소 후에도 품질이 유지됨 | 사람이 사전에 정한 항목별 기대 판정과 실제 출력, 보류 사례·반복 실행 | 중대한 과장 통과·누락·오검출을 사례별 보고. 검토 완료율만으로 의미 품질을 평가하지 않음 |
| 동일 입력 재사용·JSON 모드·단계별 모델이 유리함 | 동일 사례의 비용·지연·파싱/구조/의미 실패 비교와 서버 지원 확인 | 효과가 확인된 항목만 후속 구현. 호출 수 감소를 품질 향상으로 간주하지 않음 |

한국어의 고정 토큰 비율이나 보편적 정확도 목표를 가정하지 않는다. 저장소 Runbook과 운영 발행 revision·실행 profile도 구분한다. 운영 사례는 비식별화된 원본과 연결 정보를 확보한 뒤 재생하며, 특정 사건의 시각·UUID나 원인을 합성 사례의 정답으로 옮기지 않는다.

### 기존 설계 및 구현과의 관계

기준 커밋에는 평가 분리·F0·워크플로우 팝업이 구현돼 있다. F1~F8은 이 절에 통합한 개선 항목의 식별자이며, 현재 완성된 기능으로 간주하지 않는다. F0의 적용 단계 확대도 아래에 별도로 제안한다.

| 기존 항목 | 유지할 역할 | 이번 제안에서 보완할 내용 |
|---|---|---|
| 수집 상태·증거 상태·분석 품질 분리 | 수집 성공과 결론의 타당성을 별도로 판단 | 증거 상태에서 확인한 내용을 최종 보고서와 후속 확인까지 연결 |
| F0 실패 사유 분리 | 입력 크기 초과·토큰 부족·미검토를 구분 | 이 진단을 유지하며 정보 누락을 예산 부족으로 숨기지 않음 |
| 개발측 워크플로우 팝업 | 단계별 무엇·왜·어떻게·입력·결과 확인 | 확인 항목의 이전/현재 상태와 변경 근거, 실행·보류 이유 표시 |
| F3 보완 질문 연결 | 검토 질문을 기존 조회 권한 안에서 다룸 | 미충족 질문을 어떤 조회 또는 사람의 확인으로 해결할지 연결 |
| F4 실제 입력과 주장 근거 연결 | 작성·수정·검토가 본 발췌·표본과 출처를 추적 | 표현 수정에서 근거를 유지했는지 검증하는 기반으로 함께 구현 |
| F1 평가 사례 및 F2 예산 조정 | 의미 품질을 측정하고 측정 후 예산 조정 | 아래 사례를 평가에 포함. 입력 상한·토큰을 늘리는 것만으로 해결하지 않음 |

새 결과 필드의 계약은 구현 시 [04 공통 판단](../common/04_Agent_동작_판단_명세서.md)에 반영한다. 화면 계약은 [07 Frontend](../frontend/07_프론트엔드_개발명세서.md), 실행 가능한 검수 항목은 [05 검수](../05_테스트_검수_기준서.md)가 소유한다. 이 절의 제안 상태를 구현 완료나 검수 통과로 옮겨 적지 않는다.

### 사용자가 보게 될 결과

다음은 보고된 XID 이벤트의 PCI 주소가 같은 노드의 보고된 GPU 재고와 일치한 **설명용 예시**다. 특정 운영 사건의 현재 상태를 판정한 결과가 아니다.

| 판단 항목 | 개선 후 표시 예시 | 이 정보로 확정하지 않는 것 |
|---|---|---|
| 오류 보고 | XID 79 오류 이벤트를 수집함 | 현재도 오류가 지속되는지 |
| 이벤트 시각 | 생산자 보고 기준 시각과 원본 근거 표시 | 생산자 시계가 독립 검증되었다는 주장 |
| 보고된 재고 연결 | 오류 PCI와 GPU UUID가 재고에서 일치 | 실제 장치 신원·현재 접근 가능 여부 |
| 현재 상태 | 사건 이후 접근 가능 여부 미확인 | 정상·복구 완료 |
| 근본 원인 | 유효한 원인 가설 없음 또는 근거가 있는 미확정 가설 | 재고 일치만으로 물리 고장 확정 |
| 시험 주입 여부 | 관련 근거 미확보 | 실제 고장 또는 시험 로그라고 단정 |

> **확인한 내용:** 오류 이벤트의 PCI 주소와 보고된 GPU 재고가 일치합니다. 연결된 UUID와 근거를 확인할 수 있습니다.
>
> **다음 확인:** 해당 GPU의 사건 이후 접근 상태를 확인해야 합니다. 수집한 PCIe replay는 대상·기간·관측 공백·counter reset을 확인한 뒤 해석합니다. 별도의 AER·커널 근거가 필요한지도 구분합니다.
>
> **판단 한계:** 재고 일치와 replay 관측만으로 물리 연결·전원 고장을 확정하거나 배제할 수 없습니다.

화면은 ‘확인한 내용 → 남은 질문 → 다음 행동 → 판단 한계’ 순서로 읽게 한다. 완료된 확인도 근거와 함께 남기되 다음 행동 목록에서는 반복하지 않는다. 독립적인 장치 검증이 남았다면 기존 PCI 문자열 대조와 다른 확인임을 명시한다.

다음은 구현할 정보의 논리 구조다. 기존 `quality.rca_evaluation`과 evidence 기록을 확장하고, 별도 서비스나 DB 테이블을 먼저 만들지 않는다.

| 기록 단위 | 담을 정보 | 의미 경계 |
|---|---|---|
| 관측된 내용 | 이벤트/상태 보고 구분, 값, 대상, 기간, 시각 기준, evidence 참조·원본 위치 | 원문에서 읽은 사실과 LLM 해석을 분리 |
| 연결·검증 결과 | 비교한 값과 규격, 일치/불일치/미확인/상충, 적용 범위, 제한 | 같은 생산자 재고의 일치를 독립 검증으로 승격하지 않음 |
| 확인 질문 | 안정적인 항목 ID, 질문, 대상·기간, 필요한 근거, 결과, 남은 조건 | D-query 성공 자체를 질문 해결로 간주하지 않음 |
| 다음 행동 | 연결 질문, 기대 효과, 허용 조회 또는 수동 확인, 실행 가능성, 실행/보류 이유 | LLM 제안이 조회 권한이나 장비 조치 승인을 만들지 않음 |
| 조치 평가 | 조사 권고/복구 후보 구분, 출처, 평가 여부, 적용 조건별 결과·근거, 최종 사유 | 원천의 재부팅 제안과 검증된 복구 권고를 분리 |
| 입력 이력 | attempt·round·stage, source ID, 발췌 위치/표본, 실제 입력 hash, 생략 항목·이유 | 같은 evidence ID 또는 같은 바이트 상한만으로 동일 입력을 주장하지 않음 |

확인 질문의 상태는 **완료 / 부분 확인 / 미수행 / 판단 불가**를 기본으로 한다. 수집원 미지원·권한 부족·예산 부족·상충 등은 그 이유로 함께 기록한다. 질문을 완료하려면 해당 대상·기간·질문 범위의 근거가 있어야 한다. 이후 새로운 반대 근거가 나오면 부분 확인 또는 판단 불가로 바꾸고 이전 판단과 변경 근거를 남긴다.

기존 `operator_guidance.next_checks`에는 제목·설명만 있고 완료 조건이 없다. 이 문장만 보고 코드가 완료 여부를 추정하지 않는다. 새 확인 질문에는 출처·적용 범위·완료 조건을 정의하고, 기존 지침은 일반 안내로 유지한다. Runbook 작성 계약을 확장할 경우 `validate_operator_guidance`와 소비 화면의 버전 호환을 함께 처리하고 새 revision으로 발행하며 기존 revision은 유지한다.

예를 들어 D44 조회가 성공했다면 ‘replay 자료 수집’은 완료할 수 있다. ‘해당 GPU에서 사건 중 replay가 증가했는가’는 대상·기간·reset·표본 공백 확인이 필요하고, ‘PCIe가 장애 원인인가’는 별도의 질문이다. 한 질문의 완료를 다른 질문의 완료로 복사하지 않는다.

복구 후보는 ‘정의 없음’, ‘평가 생략’, ‘필요 입력 부족’, ‘조건 불충족’, ‘정의된 조건 충족’을 구분한다. 정의된 복구 후보가 없다면 목록 수준의 사유를 남기고 가상의 조치를 만들지 않는다. 값이 없어서 평가하지 못한 조건과 실제 비교 결과가 불충족인 조건도 구별한다. 정의된 조건이 충족돼도 실행은 운영자의 판단으로 남는다.

| PR #133의 Ops 보고서 보강 | 그대로 보존하며 RCA 결과를 읽는 Ops의 호환만 검증 |

**이번 구현 대상은 RCA의 작성·평가·후속 조사·종료 판단이다.** PR #134의 보고서 본문 생성·편집·조치 유형별 표현과 Ops 보고서는 보존·호환 확인 대상으로 둔다. 보고서 재구성이나 보고서 생성 단계를 RCA 검토 앞으로 옮기는 작업은 포함하지 않는다. 다만 중간 분석의 언어 거절을 없애면서 최종 한국어 표시를 유지하는 최소 연결은 아래 [내용 검증과 표현 정리 분리](#중간-rca-내용-검증과-한국어-표현-정리-분리)에 포함한다. 품질 검토는 실제 검토한 RCA 초안·근거에 연결하고, 그 판정을 검토하지 않은 별도 생성 문장 전체의 품질 보증으로 확대하지 않는다.

| 작업 축 | 바꾸는 것 | 유지하는 것 |
|---|---|---|
| LLM 작업 통합 | 증거 해석과 원인 분석을 한 작성 응답으로 받음 | 사실/추론 구분, 두 참조 영역, 부분 성공 보존, 별도 검토 LLM |
| Runbook 판단 기준 | 이번 조사의 목적, 목적 달성 조건, 계속 조사할 조건, 남겨도 되는 미확인 항목을 구조화 | 공통 품질 척도·조회 권한·필수 근거·원인/조치 적격성 경계 |
| 둘을 연결하는 결정·표시 | 설명 수정 / 보완 수집 / 목적 달성 종료 / 한계 종료의 이유를 기록 | 과거 결과, 명시된 호출·라운드 한도, JC 공개 소유권 |

통합은 호출을 줄이는 변경이고, Runbook 기준은 무엇을 확인하면 조사를 끝낼지 정하는 변경이다. 호출 통합의 효과가 부족해 분리 구조를 유지하더라도 Runbook 기준은 별도로 검증·채택할 수 있다. 두 가지를 한 번에 바꾼 뒤 비용이나 종료율 개선을 어느 한쪽의 효과로 설명하지 않는다.

### 증거 해석과 RCA 분석의 단일 호출 설계

**핵심 구현 완료 · 실제 모델 비교 미실행.** 증거의 의미를 해석하는 일은 유지하되, 그 결과를 별도 LLM 요청으로 만든 뒤 다시 분석 모델에 넘기는 방식을 합친다. 한 응답에서 확인 내용과 원인 가설을 구조적으로 구분하고, 별도 호출의 검토자가 원본과 전체 초안을 대조한다. 단계 수를 줄인 것만으로 비용 절감이나 품질 개선을 주장하지 않는다.

기존 separate 경로에서는 `evaluate_analysis()`가 `interpret_evidence()` 응답을 `interpretation_*`로 넣어 `synthesize()`를 호출한다. 기본 combined 경로는 `combined_synthesis.generate()`가 두 영역을 한 번에 받는다. 확인된 실행에서는 해석 결과가 분석에 전달됐지만 근거가 부족한 가설과 수정 실패가 발생했다. 이는 분리 호출의 효과가 없다는 증명이 아니며, 통합하면 더 좋아진다는 증명도 아니다. 같은 사건·예산으로 전체 결과를 비교해 채택한다. 별도 모델 설정·서비스·새 큐는 추가하지 않는다.

예산 비율은 같은 실행의 저장 설정과 사용량으로 계산한다. 대화에서 대조한 2026-10-15 저장 실행 두 건의 제한적 관측은 아래와 같다. 운영 원본은 저장소에 포함하지 않으며, 이 수치는 통합 재생 결과나 전체 운영 분포가 아니다.

| 저장 실행 표본 | 증거 해석 차감량(복구 포함) | 해당 `attempt_budget` | 예산 대비 비율 |
|---|---:|---:|---:|
| 통합 논의의 최근 사례 | 9,088토큰 · 응답 2건 | 65,536 | **13.9%** |
| 앞서 확인한 별도 사례 | 4,708토큰 · 응답 1건 | 32,768 | 14.4% |

분자는 해당 단계 `usage.charged_tokens`, 분모는 같은 결과 `versions.execution.attempt_budget`이다. 두 사례에서는 모델 보고량과 차감량이 같았지만 usage 미보고 사례는 추정 차감을 별도 표시한다. 9,088을 다른 사례의 32,768로 나눈 약 28%는 잘못된 비교다. 여러 attempt의 전체 `token_budget`이나 기본 설정을 분모로 대신 쓰지 않는다. 통합해도 해석 작업·출력은 필요하므로 **13.9%를 예상 절감률로 사용하지 않는다.** 추가 표본을 조사할 때는 선택 기간·표본 수·실행 profile/모델·복구 여부·실패/생략을 함께 기록하고, 기록 누락을 사용량 0으로 채우지 않는다.

#### 바꿀 것과 유지할 것

| 구분 | 종전 분리 구조 | 현재 통합 구조 |
|---|---|---|
| 작성 호출 | 증거 해석 → RCA 분석, 각각 별도 호출 | **증거 해석·RCA 분석** 한 논리 호출에서 구조화 응답 생성 |
| 작성 결과 | 해석 응답을 다음 분석 입력에 다시 포함 | 한 응답 안의 `interpretation`과 `hypotheses`를 구분. 같은 응답의 해석이 독립 검증된 사실처럼 취급되지 않음 |
| 품질 검토 | 결합된 초안에 별도 LLM 호출 | 유지. 원본·수집 제한·입력 생략과 해석·원인·Runbook 권고 전체를 검토 |
| 수집·기초 검사 | 기존 조회·파싱·명시된 조건 비교 | 유지. 해석 통합을 이유로 대상·기간·권한·fact 조건을 완화하지 않음 |
| 반복 | 형식 복구, 의미 수정, 보완 라운드 제한 | 동일 증거의 형식 복구·의미 재작성 없음. 수집은 최대 2라운드·보완 3개 유지 |
| 결과·공개 | 수집/증거/분석 품질과 원인 확정·작업 상태 구분 | 유지. 원인 미확정과 분석 실패를 구분하고 기존 JC 공개 경계 유지 |
| 최종 표현·조회 선택 | 문장 ID 편집, 허가된 탐색 선택 | ID 정렬·조회 권한 유지. 한국어 표시 연결은 아래 공통 선행 변경으로 검증. 작성은 전송 1회. 별도 검토의 형식 복구·전송 재시도, 편집·선택 호출은 별개여서 총 호출 2회를 보장하지 않음 |

**통합 대상은 작성 과정의 두 호출뿐이다.** 검토를 작성 응답 안의 자기평가로 바꾸지 않는다. 숨겨진 사고 과정이나 단계별 장문 독백을 요구하지 않고, 사람이 확인할 수 있는 주장·출처·한계만 구조화한다.

#### 한 번의 응답에 담을 내용과 검증

다음은 구현할 내부 응답의 설계다. 외부 결과/중간 기록의 정식 계약은 구현 시 04에서 버전을 나눠 정의한다.

| 항목 | 담을 내용 | 코드와 검토자가 확인할 것 |
|---|---|---|
| `interpretation.findings` | 기존 id/statement/kind/evidence_refs. `observed`는 원문에 보고된 내용, `inferred`는 해석 | 실제 전달된 자료의 `input_evidence_refs`만 허용. 조회 실패·검사 결과도 그 제한을 설명하는 데 사용하며 실제 고장·현재 상태·검증 fact로 승격하지 않음 |
| `interpretation.unknowns/conflicts/limitations` | 아직 알 수 없는 것, 상충 보고, 해석 범위 | 시각 차이에 따른 보고와 같은 시점의 모순을 구분. 빈 목록을 자료 완전성으로 해석하지 않음 |
| `hypotheses` | 기존 주장·지지/반박 refs·value refs·missing inputs와, 의존한 해석의 `finding_refs` | 원문 refs가 직접 필요하며 finding ID만으로 원인을 지지하지 못함. 참조한 해석이 제외되면 의존 가설도 재검사 |
| `limitations` | 결론의 범위, 원인 구분에 필요한 추가 확인 | 자료 부재·대상 연결 미확인·모델 입력 생략·처리 실패를 구분. 코드가 확정한 수집 제한은 모델이 삭제할 수 없음 |

빈 원인 후보는 유효한 응답일 수 있다. 이때 확보한 사실·확인되지 않은 연결·판단 한계를 설명하며 관측된 증상을 가상의 원인 후보로 채우지 않는다. 추가 확인은 기존 missing inputs와 별도 검토의 질문 연결을 활용한다. 이 변경만으로 새 질문 실행 권한을 만들지 않는다.

- `validate_interpretation()`과 `validate_synthesis()`의 구조·참조·수치·인과 제한을 재사용하되, **각 영역에 다른 허용 참조 집합**을 전달한다. 아래 집합은 최초/복구 요청마다 실제 전송한 뷰에서 계산하며, 수집한 모든 evidence ID로 확대하지 않는다.

| 검사 영역 | 허용 참조 집합 | 거절·보존 기준 |
|---|---|---|
| 해석의 `evidence_refs` | `input_evidence_refs`: 전달된 관측뿐 아니라 `evidence_checks`·조회 품질/실패 자료의 refs 포함 | 실패 기록은 자료 확보 제한을 설명할 수 있음. unknowns의 빈 refs는 기존처럼 명시적 이유가 있을 때만 허용 |
| 가설의 `supporting_refs/contradicting_refs` | `observation_refs`: 전달된 오류 이벤트·장비 관측·Pod 관계·지표·원문 발췌의 refs | supporting은 비어 있으면 안 되며 지지/반박 교집합 금지. 진단·조회 실패·Runbook·생성 해석에만 있는 refs를 원인 근거로 채택하지 않음 |
| 가설의 `finding_refs` | 같은 채택 응답에 남은 해석 finding ID | 해석과의 의존 관계만 나타냄. 관측 refs를 대신하거나 진단을 관측 근거로 승격하지 못함 |

관측 집합은 `OBSERVATION_SECTIONS`로 명시한다. 입력 배정 순서와 관측 승격을 분리해 Runbook 지침이 관측이 되지 않게 한다. 같은 evidence ID에 관측과 진단이 함께 있을 수 있으므로 ID 허용만으로 주장의 타당성을 보증하지 않는다. F4의 실제 섹션·발췌 위치·표본 연결과 별도 의미 검토를 함께 사용한다. 진단 전용 ref를 가설에 사용한 응답, 입력에서 빠진 관측, 같은 ID의 다른 발췌를 검수 사례로 둔다.

- 두 영역을 독립 검증하며 유효한 해석은 보존한다. **형식 복구를 포함해 같은 증거의 작성 재호출은 하지 않는다.**
- JSON 파싱 실패는 임의 부분 추출로 성공 처리하지 않는다. 해석 보존과 의존 가설 처리의 구체적 경계는 아래 부분 성공 기준을 따른다.
- `validated_response/validated_subset`과 영역별 채택/제외 사유를 구분한다. 해석 일부 채택이 분석 전체 완료·품질 통과를 뜻하지 않는다. 여러 응답의 일부를 합치면 응답별 입력과 채택 위치를 연결하며 충돌·의존 검사를 다시 한다.
- 표현 문제와 의미 문제는 구분한다. 중간 언어 거절의 분리는 아래 공통 선행 변경으로 검증한 뒤 분리/통합 양쪽에 동일하게 적용한다. 언어 정책 변경의 효과와 호출 통합의 효과는 별도로 측정하며 구조·근거·수치 검사를 함께 해제하지 않는다.
- 검토 대상에 해석의 주장도 포함한다. `analysis_draft()`는 해석 주장에 구별되는 claim ID를 부여하고 원문 refs를 연결한다. 검토에는 동일한 해석을 독립 원천 근거처럼 중복 넣지 않는다. 해석·후보·한계·실제 입력의 변경은 새 `analysis_id`와 재검토 대상이다.

#### 부분 성공의 보존과 비교

분리 구조에서는 분석 호출이 실패해도 앞선 해석 응답이 남을 수 있다. 통합 응답 전체의 JSON이 깨지면 그 응답의 해석도 채택할 수 없으므로, 호출 감소와 함께 **유용한 중간 결과를 잃는 비용**을 측정한다.

| 응답·검증 결과 | 보존할 내용 | 최종 표시·검토 |
|---|---|---|
| 해석·분석이 모두 유효 | 원문 연결과 함께 양쪽 결과 보존 | 원인 후보가 빈 배열이어도 명시적으로 판단을 보류한 유효 분석이면 작성 완료로 취급. 원인 미확정과 생성 실패 구분 |
| JSON은 유효하고 해석은 통과했지만 분석은 실패 | 채택된 해석·한계와 분석 실패 사유 보존 | ‘해석 보존·원인 분석 미채택’. 해석을 검토할 초안과 보고서에 연결하고 검토되지 않았으면 미검토 표시 |
| 일부 해석·가설만 유효 | 채택 항목과 제외 이유·원문·응답 출처 보존 | 제외된 해석·상충·한계에 의존하는 가설은 보류. 의존성을 분리하지 못하면 가설은 채택하지 않고 유효한 해석 및 코드 관측·한계만 보존 |
| 전체 JSON 파싱 실패 | 그 응답에서는 해석·가설 모두 미채택 | 정규식이나 추정으로 부분 성공을 만들지 않음. 같은 논리 요청의 앞선 응답에서 검증된 부분이 있으면 그 출처로 보존하되, 새 원문에 대한 분석·검토 완료로 승계하지 않음 |

보존은 코드 검증을 통과한 모델 해석이라는 뜻이며 사실 확정이나 품질 검토 통과가 아니다. 보완 라운드의 새 증거가 앞선 해석과 충돌할 수 있으면 이전 해석은 이력으로 남기고 현재 결론에 무조건 합치지 않는다.

비교는 작성 응답 채택 직후와 최종 보고서 반영 후를 각각 본다. 사례·attempt·라운드별 해석/분석의 전체·일부·미채택 상태를 교차 집계하고, **해석만 남은 사례 수**, **해석·분석 모두 잃은 사례 수**, 최종 보고서에 남은 유용한 사실·한계와 검토 여부를 기록한다. 형식 실패·출력 잘림·의도적 원인 보류를 섞지 않는다. 기준선에는 해석이 남았는데 통합 후 소실된 쌍을 사람이 확인하며, 중대한 정보 손실을 비용 절감으로 상쇄하지 않는다. 영역별 중첩 지표를 더해 전체 성공률로 계산하지 않는다.

#### 출력 상한과 잘림 측정

현행 validator의 허용 최대 길이는 해석의 네 목록(findings/unknowns/conflicts/limitations) 각각 16개 × statement 800자, 가설 8개 × claim 2,000자, 분석 limitations 32개 × 2,000자다. 이 주요 문장 상한만 합쳐도 131,200자이며 reason·missing inputs·ID·refs·JSON 구조는 별도다. 이는 생성해야 할 분량이나 실제 토큰 수가 아니다. 한국어·영문·식별자 혼합 비율과 모델에 따라 토큰 수가 달라지므로 고정 문자/토큰 환산으로 수용 가능성을 보장하지 않는다.

`Settings.llm_synthesis_max_tokens`의 기본값 16,384는 설정 상한이다. 실제 요청은 공통 `LLM.request_budget()`이 남은 예산·예약·프롬프트 상한을 반영한 `output_token_cap`을 쓰며, 전송 재시도에서 cap이 달라질 수 있다. 최초 요청의 설정값만으로 모든 응답이 16,384토큰까지 생성 가능했다고 설명하지 않는다.

| 측정 항목 | 기록·판정 기준 |
|---|---|
| 요청별 실제 출력 상한 | 설정 상한, 가용 cap, 실제 전송한 `max_tokens`, 남은/예약 예산. 최초·복구·전송 재시도 각각 기록 |
| 실제 응답 길이와 종료 | 모델 completion tokens·문자/바이트 길이·제공된 종료 사유. 미보고는 미기록으로 남기고 빈 응답/수치 0과 구분 |
| 잘림과 검증 실패 | 출력 상한 종료, 전송 중단, JSON 파싱 실패, 영역별 필수 필드/참조 오류를 별도 기록. JSON 오류만으로 잘림을 확정하지 않음 |
| 보존과 복구 비용 | 잘림/형식 실패 후 해석·가설 채택 범위, 필수 한계·반대 근거 누락, 복구 횟수·토큰·시간과 최종 검토 완료 |

첫 비교는 같은 설정 상한과 기존 제한을 기준으로 수행한다. 긴 로그·한국어 설명·다수 상충 근거와 작은 가용 cap 사례를 포함하고 최초 요청뿐 아니라 복구 후 실패도 센다. cap과 종료 사유를 저장하지 못하는 구 기록은 추정 대신 측정 불가로 남긴다. 이후 응답 간결화가 필요하면 영역별 개수·문장 길이 제한을 프롬프트와 validator에 함께 적용하고 별도 버전으로 비교한다. 상한을 낮춰 중요한 반대 근거·한계를 빠뜨리거나 총예산을 늘린 효과를 통합 효과로 계산하지 않는다.

#### 실제 입력과 실행 기록

`inspection_context()`의 기초 진단·발췌와 `synthesis_input()`의 관측·Runbook을 합쳐 `bounded_context()`로 작성 입력을 만든다. 별도 해석 응답을 사전 입력으로 요구하지 않는다. 원본 전달 개선(F4)과 호출 통합의 효과를 섞지 않도록 비교 시 같은 입력 구성 정책을 사용한다. 현재 앞부분 발췌·Healthy 의미 매핑·핵심 메시지 누락은 통합 자체로 해결되지 않는다.

통합 호출은 기존 모델 stage `synthesis`와 실행 기록 `rca_synthesis`를 재사용하고, 새 응답 버전과 `generation_mode=combined`를 명시한다. `evidence_validation`은 코드 검사로 별도 보존한다. 신규 통합 실행에서 호출하지 않은 `evidence_interpretation` 완료 기록을 만들어 호환을 가장하지 않는다. 단일 작성 호출 외에 독립 품질 검토와 기존 선택·편집 호출이 남을 수 있으므로 전체 작업의 LLM 호출 수가 항상 2회라고 설명하지 않는다. 기존 stage별 모델 설정은 읽을 수 있게 유지하며, 통합 모드에서는 `evidence_interpretation` 모델을 호출하지 않았음을 표시한다.

호출별로 작성/복구/의미 수정, round, 실제 입력 hash·refs·발췌/표본 위치·생략 내역, 응답별 채택 항목, 모델/설정, 요청 사전 검사, 전송 횟수·usage·시간을 연결한다. 같은 evidence ID라는 이유로 같은 원문을 읽었다고 주장하지 않는다. 통합 입력 크기는 해석·분석 두 번에 중복 계상하지 않는다. 입력 상세 추적은 F4와 같은 구현을 사용하며 민감정보와 거절된 원시 응답 전체의 저장 제한은 유지한다.

`validate_evaluation/source_evaluation`은 schema 1/2를 지원한다. schema 2의 combined evidence 완료는 `rca_synthesis.interpretation_status`와 실제 해석에 연결한다. 가짜 독립 해석 기록은 만들지 않는다. schema 1의 의미는 유지한다. 최상위 `result_schema_version=1.1`은 기존 필드의 의미·필수성을 유지하는 범위에서 보존한다.

| 계약 영향 | 구현할 호환 처리 |
|---|---|
| `quality.rca_evaluation` schema 2 | collection/review/investigation 축 유지. evidence는 작성 모드에 따라 독립 해석 기록 또는 통합 응답의 해석 채택 영역을 참조. 목적·기준별 상태·종료 근거도 이 버전에서 확장하며, schema 2 사용을 통합 호출 성공과 동일시하지 않음 |
| 초안 hash | schema 2에서 목적·정책 revision/hash, 검토 대상 RCA 해석·원인·권고·한계와 실제 입력 연결까지 포함. rubric 버전은 검토 입력 hash에도 연결. schema 1의 hash 산식과 과거 기록은 변경하지 않음 |
| 최종 검토 | 같은 최종 초안·목적·정책·rubric/검토 입력만 연결. 내용이나 판단 범위가 바뀐 후 이전 통과 승계 금지. 보완 수집 후 검토 실패도 이력의 통과로 대체하지 않음 |
| 과거/알 수 없는 버전 | schema 1과 평가 필드 없는 결과는 기존대로 열람. 알 수 없는 버전은 미지원·미검증으로 표시하고 정상 판정을 추정하지 않음 |
| 배포 순서 | 공통 validator·JC 공개 검사·Backend·Ops·GUI의 1/2 읽기 지원을 먼저 검증하고 새 producer를 활성화. 되돌릴 때도 schema 2 읽기 지원은 남겨 이미 저장한 결과를 보존 |

필드·enum·hash의 정식 정의는 04, 실행 전환은 14, 표시 계약은 07, 실행 가능한 검수 항목은 05가 소유한다. 공통 Python·Ops·GUI가 schema 2를 읽고 Backend/JC는 기존 JSON 저장·공개 경로를 재사용한다. 실행 검증 범위와 배포는 QA에서 구분한다. 새 DB 테이블이나 과거 데이터 변환은 요구하지 않는다.

#### 실패·수정·보완 수집과 예산

- 통합 작성 → 코드 검증·규칙 조립 → 별도 품질 검토가 기본이다. 통합 출력 실패를 이유로 같은 attempt에서 예전 해석+분석 경로를 자동 호출하지 않는다. 비교용 구 경로와 런타임 fallback은 구분한다.
- 검토 지적을 저장하고 특정 가능한 문제 주장만 보류한다. 같은 증거의 재작성·수정·재검토 루프는 수행하지 않는다. 변경 자료에 기존 검토 통과를 재사용하지 않으며 null verdict와 미검토 이유를 남긴다. 유효한 새 원본 관측이 추가된 경우에만 다음 작성·독립 검토를 수행한다.
- 새 증거의 작성 전에 실제 입력 및 후속 검토에 필요한 예약을 계산한다. 기존 총예산·외부 예약·검토 보호 하한·deadline을 유지하고, 길어진 통합 응답과 별도 검토의 비용을 전체 루프에서 측정한다. 작성 오류에는 같은 증거의 복구 요청을 하지 않는다. 출력 상한·총예산을 동시에 늘려 통합의 효과로 계산하지 않는다.
- 작성 실패 뒤 코드 기반 초안을 검토할 수 있는 기존 경로도 비용에 포함한다. 생성 실패·대체 초안·대체 초안 검토를 분리 기록하고 검토 통과를 원인 분석 성공으로 표시하지 않는다. 해당 검토를 줄이거나 생략하는 정책은 F2-B의 별도 비교 대상이며, 통합 첫 구현에서 암묵적으로 바꾸지 않는다.
- 보완 수집 후에는 누적 원본과 새 근거로 통합 작성·검토를 다시 수행한다. 이전 해석+새 refs만 넘기거나 이전 검토를 새 근거의 검토로 복사하지 않는다. 호출 통합만 비교하는 단계와 정책 없는 구 Runbook은 기존 명시적 보완 수집 동작을 유지한다. 새 판단 기준 채택 후에는 [목적별 종료 조건](#다음-행동과-종료-조건)을 먼저 적용한다. LLM 예산만 부족하고 독립 수집이 필요·허용된 경우에는 **수집 완료·추가 분석 미수행**으로 남긴다. 조회 예산·deadline·횟수 제한은 계속 적용한다.
- 원본 부재, 원본은 있지만 입력 예산 때문에 제외됨, 모델 전송 실패, 응답 구조/내용 검증 실패를 구분한다. 입력 관측이 비었다는 사실만으로 `no_usable_evidence`를 ‘원본 없음’으로 번역하지 않는다. 취소·원격 종료 불명은 기존 Worker/JC 경계를 따른다.

#### GUI에서 보여줄 내용

기존 개발측 RCA의 **워크플로우 디버깅** 버튼과 근거 상세 화면을 재사용한다. 기본 흐름은 `수집·기초 확인 → RCA 작성 → 독립 품질 검토 → 추가 수집/종료 → RCA 근거 자료 고정 → 최종 보고서 작성 → 저장/공개`으로 읽히게 한다. 수집·검증의 개별 기록은 접어서 볼 수 있게 유지하고 실제 호출 수를 화면 구획 수로 계산하지 않는다.

#### 최소 재생 도구의 선행 조건

**통합 작성 경로의 코드 구현에 앞서, 기존 분리 경로를 고정 입력으로 재생하고 기준선을 저장할 최소 F1-B 도구를 준비한다.** 최소 고정 응답 재생 도구는 [오프라인 RCA 재생](../../../rcca-agent/README.md#오프라인-rca-재생)에 구현했다. `workflow.run()`이 기존 `evaluate_analysis()`·조립·선택·종료를 호출하며 공통 LLM의 실제 예산 차감·출력 잘림·형식 검사를 통과한다. 원래 main `bf85dfd`의 분리 경로를 기준으로 입력과 소스 hash를 보존한다. 실제 모델의 의미 품질 비교는 미실행이다. 통합 결과까지 비교하는 전체 F1-B 완료를 착수 조건으로 삼지는 않는다. 도구 없이 먼저 통합한 뒤 이전 동작을 추정해 비교하지 않기 위한 구현 순서이며, 별도 협의·승인 단계를 추가하는 요구가 아니다.

| 최소 준비 항목 | 통합 작성 구현에 착수할 수 있는 조건 |
|---|---|
| 고정 재생 입력 | 사건·evidence 묶음/hash·Runbook/profile·모델/예산과 보완 조회 fixture를 읽고, 누락된 자료는 부분 재생으로 표시 |
| 기존 경로 실행 | `evaluate_analysis()`와 기존 조립/선택 흐름을 재사용. 실시간 수집·운영 DB 쓰기·결과 발행 없이 최초 및 보완 라운드 재생 가능 |
| 측정 저장 | 실제 입력/설정·응답 채택 영역·검토 대상·다음 행동·실패/생략·usage와 위 출력 상한/잘림 항목 저장. 관측하지 못한 값은 미기록으로 구분 |
| 기준선 자체 검증 | 고정 응답으로 충분 예산, 의도적 부족, 해석 성공 후 분석 실패, 보완 후 판단 변경의 결과를 검사하고 재현 가능한 기준선 저장 |
| 비교 준비 | 사람 기대 판정·중대한 손실 기준·반복 수·비교 설정을 실행 전에 고정하고, 같은 입력을 통합 경로에도 공급할 수 있는 실행 진입점 확보 |

순서는 **최소 도구·분리 기준선 → 통합 경로 구현 → 실제 모델로 양쪽 반복 비교 → 채택 판단**이다. fixture 기준선은 도구와 분기 검증이며 실제 모델 품질의 기준선을 대신하지 않는다. 실제 모델의 분리/통합 기준선은 동일 비교 환경에서 확보한 뒤 채택을 판단한다. 계약·GUI 설계 검토는 도구 준비와 병행할 수 있고, 비교 도구를 위해 새 운영 API나 영구 이중 실행 경로를 만들지 않는다.

#### 분리 호출과 통합 호출의 비교 검증

F1-B 재생 도구의 두 실행 경로로 비교한다. 운영 작업을 중복 접수하거나 운영 DB를 수정하지 않는다. 사건·원본 묶음/hash·대상·기간·Runbook/profile revision·모델 및 생성 설정·총예산·입력 선택 정책·검토 rubric·수정 한도를 고정한다. 이 비교에서는 기존 Runbook 종료 정책과 rubric 1을 유지하고, 새 판단 정책·rubric 2의 효과는 이후 선택된 작성 구조에서 따로 비교한다. 구조상 프롬프트·응답 형식이 달라지는 부분은 버전과 차이를 기록한다. RCA 해석을 초안 claim으로 연결하는 공통 변경은 양쪽에 동일하게 적용한다. 원래 main의 기준선도 별도로 보존해, 공통 검토 범위 확대 효과를 호출 통합 효과로 계산하지 않는다. 현재 단계별 모델이 다르면 우선 작성 모델을 같게 맞춘 구조 비교를 하고, 실제 운영 조합 비교는 별도로 표시한다.

호출 구조 비교에서는 Healthy 매핑, 원문 선택, 질문 선택, 총예산 증액을 동시에 변경하지 않는다. 언어 거절 분리의 전후를 먼저 비교하고 채택한 동일 정책을 분리/통합 양쪽에 적용한다. F4 같은 선행 변경이 필요하면 분리 호출 쪽에도 동일하게 적용해 새 기준선을 만든다. 모델 변동을 고려해 실행 전에 사례별 반복 수·실행 순서·완료 기대 조건을 정하고 양쪽을 같은 횟수 실행한다. 유리한 응답만 고르지 않고 실패·생략·재시도까지 남긴다.

| 사례 | 사람이 먼저 정할 기대 결과 |
|---|---|
| Healthy 다수·오류 소수, 정상 보고 뒤 오류 보고 | 중요한 오류와 전후 보고를 설명하되 실제 복구·동시 모순을 단정하지 않음 |
| 이벤트 원문만 존재, 긴 JSON의 핵심 메시지·9번째 이후 반대 근거 | 전달/생략 범위를 드러내고 핵심 근거 누락을 ‘원본 없음’으로 바꾸지 않음 |
| 식별자 오타·GPU 연결 미확인·같은 주소의 상충 UUID | 문자열 일치/불일치와 실제 장비 신원 확정을 구분 |
| PCIe 0값·관측 공백·reset, SXID와 GPU 재고만 존재 | 원인 배제·NVSwitch 신원 확정으로 확대하지 않음 |
| 증거 부족하지만 유효한 제한적 설명 / 과장된 설명의 쌍 | 적절한 불확실성은 허용하고 무근거 원인 단정은 거절 |
| 형식 오류·영문 인용 거절·일부 채택·출력 잘림·한 영역만 유효 | 복구 상한과 의존성 보존. 제외 때문에 반대 근거가 사라진 결과를 정상 완료로 표시하지 않음 |

| fast path·모델 미설정·구 결과·다른 attempt | 기존 경계와 조회 호환 유지. 다른 실행의 근거·판정 혼합 금지 |

먼저 fixture로 호출 수·구조·복구·계약을 확인하고, 같은 자료로 실제 모델 비교를 수행한다. 실제 모델 결과는 사례·반복 수와 원본/입력 생략 한계를 명시하며 일반적인 정답률로 확대하지 않는다. 중대한 오류가 한 건이라도 새로 생기면 해당 원인을 해결하고 다시 비교한다. 차이가 불명확하거나 품질·완료 조건을 지키지 못하면 분리 호출을 유지한다. 성공/실패/미실행·미검증을 구분하고 실제 결과만 Agent QA에 남긴다.

개발 후보의 기본 경로는 combined이며 profile의 명시적 separate는 비교·회귀 경로다. 자동 이중 실행이나 통합 실패 후 구 경로 재호출은 없다. 실제 운영 채택 효과는 모델 재생 전까지 미검증으로 남긴다. 운영 반영은 별도 배포 단계이며, 되돌려도 저장 원본·기존/신규 결과는 보존한다.

### 중간 RCA 내용 검증과 한국어 표현 정리 분리

**이번 RCA 계획에 포함하는 미구현 변경.** 영문 혼용 때문에 근거 있는 후보나 중요한 한계를 버리지 않고, 내용의 유효성과 사용자에게 읽기 쉬운 표현을 따로 처리한다. 기존 보고서의 구조·조치 문구를 개편하는 작업은 아니다.

현행 [synthesis.py](../../../rcca-agent/src/rcca_agent/synthesis.py)의 `validate_synthesis()` 안 `language_diagnostic()`은 식별자를 마스킹한 뒤 한글 유무와 고정 기술용어 목록 밖 영문을 검사한다. `non_korean`은 가설·한계의 거절 사유가 되고, `synthesize()` 내부 복구 호출이나 `validated_subset`의 항목 제외로 이어질 수 있다. 이는 별도 `analysis_review`의 근거 지적에 따른 의미 수정과 다른 경로다. 코드상 경로는 확인했지만 특정 운영 응답에서 거절된 실제 영문은 원본 재조회 전까지 미확인으로 둔다.

| 처리 | 변경·유지할 기준 |
|---|---|
| 중간 분석 채택 | 영문 혼용·한글 부재만으로 항목을 거절하거나 재호출하지 않음. 한국어 작성 지침은 유지하되 표현 진단은 비차단 정보로 분리 |
| 내용 검증 | 구조·길이·허용 refs·두 참조 영역·수치·대상/신원·불확실성·과장 검사는 유지. `non_korean`만을 이유로 한 fallback 제외·복구를 제거 |
| 언어 의존 검사 | 숫자 단어·확정 표현 등의 기존 정규식도 점검. 한국어/영문/혼용의 동일 의미 사례가 같은 결과를 내야 함. 코드가 확인할 수 있는 값은 구조화 값과 대조하고 의미는 독립 품질 검토로 확인. 영문이면 내용 검사를 통과하는 우회 금지 |
| 의미 문제 | 근거 부족·모순은 특정 가능한 주장을 보류하고 미검토로 남김. 동일 증거 재작성·재검토 없음. 영문으로 썼다는 이유만으로 의미 수정 횟수 소비 금지 |
| 최종 한국어 표시 | 채택한 RCA 내용은 원본으로 보존하고 한국어 표시문은 문장 ID·원본 hash와 연결한 별도 표현으로 관리. 표현이 RCA 주장·근거·원인 상태를 다시 쓰지 않음 |
| 표현 실패 | 원본 후보·반대 근거·한계 보존. 한국어 고정 안내와 원문 보기로 제공하며 ‘한국어 표현 정리 미완료’ 표시. 분석 실패·항목 삭제·추가 조사로 전환하지 않음 |

현재 [report_editor.py](../../../rcca-agent/src/rcca_agent/report_editor.py)의 `prioritize()`는 문장 ID를 정렬할 뿐 번역하지 않는다. 입력 미리보기도 잘리므로 이 함수가 이미 한국어 정리를 한다고 가정하면 안 된다. 먼저 기존 한국어 고정 문장과 작성 지침을 활용하고, 정리가 필요한 채택 문장에 한해서 **기존 최종 편집 요청을 확장하는 최소 방식**을 검증한다. 구조·검증·소비 계약을 함께 변경하며 일반 보고서 재작성 모델을 추가하지 않는다. 이미 한국어인 문장은 불필요하게 다시 쓰지 않는다.

표현 요청에는 해당 문장의 전체 내용과 보존할 수치·단위·식별자·근거·불확실성을 전달한다. 잘린 미리보기로 번역하지 않는다. 고정 ID 밖 문장·새 숫자/식별자·누락된 필수 한계 등은 채택하지 않고 원본으로 되돌린다. 코드 비교만으로 의미 동등성이 보장되지는 않으므로 부정·인과·가능성 보존을 사람 기준의 실제 모델 검수에 포함한다. 신뢰할 수 없는 표현은 적용하지 않고 미완료를 표시한다. 원문 로그 인용은 출처와 함께 보존하며 번역문을 새 관측으로 승격하지 않는다.

표현 정리는 RCA의 독립 품질 검토 뒤 남은 예산 안에서만 수행한다. 기존 편집 호출·복구 상한을 늘리지 않고, 언어 문제를 원인으로 중간 분석이나 조사를 다시 실행하지 않는다. 표현 비용도 전체 비용에 포함하며 **중간 언어 복구 0회**와 전체 비용 감소는 다른 검수 항목이다. 예산 부족·모델 미설정·출력 잘림이면 정보 보존 경로를 사용하고 번역 성공을 만들지 않는다.

개발측 GUI의 `RcaWorkflow`·`RcaDebug`는 **내용 검증 / 형식·수치 복구 / 의미 수정 / 한국어 표현 정리**를 구분한다. 각 항목에 실제 호출 여부·횟수·비용, 비차단 표현 진단, 내용 거절·표현 미적용 이유를 저장된 값으로 표시한다. 구 `non_korean` 기록은 당시 동작 그대로 읽고, 원문이 없으면 거절 단어를 추정하지 않는다. 표현 완료 여부는 분석 품질 판정·조사 종료와 별도로 표시한다.

| 회귀·비교 사례 | 통과 기준 |
|---|---|
| 내용이 동일한 한국어·영문 혼용·영문 가설과 한계 | 내용 채택과 refs 동일, 언어만을 이유로 한 중간 재호출·항목 탈락 0건 |
| 영문과 잘못된 refs·수치·신원·근거 없는 단정이 함께 있음 | 내용 문제는 계속 거절·수정. 영문 허용이 검증 우회가 되지 않음 |
| 중요한 반대 근거·한계에만 영문 포함 | 후보만 남기고 한계를 없애는 결과 금지. 독립 검토 입력에도 보존 |
| 한국어 정리에서 숫자·부정·인과·불확실성 변경 | 변형 표현은 미채택, 원래 RCA 내용과 근거 보존. 사람이 의미를 대조 |
| 표현 요청 실패·예산 부족·출력 잘림·문장 누락 | 한국어 상태 안내와 원문 열람 가능, 실제 실패/호출 표시. RCA 재실행·내용 삭제 없음 |
| 이미 한국어인 결과·기존 문장 ID 정렬·구 기록 | 기존 출력/순서와 구 기록 조회 유지, 불필요한 표현 호출 없음 |

`test_rca_repairs`·합성 검증·`test_rca_evaluation`·편집/보고서 소비·`RcaDebug/RcaWorkflow` 테스트에 위 사례를 추가한다. 04에는 원본/표현·진단 참조, 07에는 구분 표시, 05에는 언어별 동일 판정·정보 보존 검수를 반영한다. 이번에는 11의 구현 계획과 검수 요구만 갱신하며 코드와 해당 계약 문서의 구현 완료를 주장하지 않는다.

### Runbook 판단 기준과 품질 검토·종료 설계

**핵심 구현 완료·실제 모델 검증 전.** Runbook에는 오류별 조사 목적과 증거 조건을 넣고, 공통 코드는 실행 경계와 다음 행동을 결정한다. LLM은 자료의 의미와 설명의 타당성을 판단한다. Runbook의 자연어 지침이나 로그 문자열 하나를 곧바로 ‘원인 확정·검토 통과·조사 종료’로 바꾸지 않는다.

#### 왜 품질 검토와 별도로 종료 기준이 필요한가

기준 코드 `8da8e73`의 `evaluate_requirements()`는 `applicable`에 **일반 조사(`general_investigation`)도 아니고 조사 전용(`investigation_only`)도 아닌 Runbook**이 하나도 없으면 `causal_confirmation_evidence` gap을 남긴다. `rule_followup()`은 이 gap으로 선택 조회를 제안할 수 있다. `select_followup()`의 `review_accepted` 분기는 **`acceptable`이고, `followup_questions`가 비어 있고, `ruled`도 비어 있을 때** 성립한다. 따라서 단순히 미실행 조회 `remaining`이 있다는 이유로 계속 조사하지는 않지만, 규칙에 따라 선택된 후보 `ruled`가 있으면 검토 질문이 없어도 이 종료 분기는 막힌다. 그때도 다른 종료 override·조회/시간/라운드 한도가 있으면 수집하지 않을 수 있다. 따라서 이번 문제를 ‘검토자가 엄격해서 계속 돈다’로만 설명할 수 없다. **주장의 품질 문제와 조사 목적을 달성한 뒤에도 조회하는 문제를 각각 고쳐야 한다.**

XID 79 보고만으로 ‘펌웨어/드라이버가 가짜 XID 79를 만들었다’고 우선 주장한 것은 수정 대상이다. 반면 ‘XID 79 보고와 장치 연결 범위를 확인했고 물리 원인은 미확정’이라는 설명은 제한된 조사 목적의 유효한 결과일 수 있다. 원인 미확정은 그 자체로 반대 증거가 아니며, 모든 하드웨어·전원·드라이버 가능성을 나열해야 품질 검토를 통과하는 규칙을 만들지 않는다.

#### Runbook에 추가할 판단 기준

첫 구현은 **알려진 오류 보고의 식별과 조건부 안내**를 목적으로 하는 대표 Runbook부터 적용한다. 현재 상태·실제 영향 확인이나 근본 원인 규명은 별도의 더 강한 증거가 필요한 목적이다. 조사 도중 데이터가 부족하다는 이유로 원래 목적을 더 쉬운 목적으로 자동 변경하지 않는다. 목적의 출처·대상·기간을 수집 전에 고정한다.

다음은 첫 구현이 지원하는 `decision_policy` 구조다. 새 동작이 명시된 콘텐츠는 `gpu-rca-runbook/1.1`로 구분하고, 1.0과 legacy는 기존 선택·종료 동작을 유지한다. Python·Go validator가 1.0/1.1을 검사한다. 기존 발행 revision은 그대로 보존하며 1.1은 새 revision으로 발행한다. 세부 계약은 [작성·발행 안내](../../../rcca-agent/runbooks/DB-WORKFLOW.md)에 반영한다.

| 항목 | 넣을 내용 | 검사·판단 책임 |
|---|---|---|
| `goal` | 안정적인 목적 ID, 사람이 읽는 질문, 결론의 범위. 첫 적용은 오류 보고 식별·안내 | 코드가 선택된 발행 revision과 사건 범위에 고정. LLM이 목적 변경 불가 |
| `applies_when` | 보고된 오류 코드·생산자·대상·기간 등 이 기준을 적용할 조건 | 명시된 규격으로 코드 검사. 검색 점수·`applicable` 포함 여부만으로 대체하지 않음 |
| `completion_criteria` | ID, 질문, 필요한 관측/출처·범위, 검사 방식, 완료 조건 | 명확한 값은 코드, 의미 질문은 작성 LLM이 근거와 함께 제안하고 별도 검토자가 확인 |
| `blocking_conditions` | 다른 대상/시간의 오류, 관련 신원 충돌, 필수 자료 부재, 적용 제외 조건 등 완료를 막는 항목 | 관련 조건의 미확정도 안전하게 통과시키지 않음. 실제 충돌과 단순 미확인을 구분 |
| `non_blocking_unknowns` | 해당 목적에서는 남겨도 되는 항목과 허용되는 설명 범위 | 근본 원인·현재 접근 가능 여부 등을 한계로 보존. 구체적 복구 권고의 전제까지 면제하지 않음 |
| `followup_links` | 기준 ID와 기존 observation plan 단계/query ID의 연결, 이 목적의 필수/선택 여부·기대 정보 | 기존 required/권한/선택 조건을 약화하지 않음. Runbook에 없는 새 조회를 허용하지 않음 |

`method=llm` 완료 기준(`bounded_conclusion`)은 작성 LLM의 자기평가가 아니라 독립 검토 루브릭으로 판정한다(`agent_common.rca_evaluation.review_scope_status`). 검토가 완료되어 `acceptable`/`acceptable_after_feedback`이고 `grounding`·`identity_time`·`limitations`가 `pass`/`not_applicable`이면 `satisfied`다. `needs_revision`은 모든 지적이 특정 주장을 가리켜 코드가 그 주장을 제외한 경우(`unattributed_issues=false`)에만 해소로 본다. 채택된 해석에 남은 finding이 없거나 형식 복구로 caveat이 빠진 경우(`criterion_withheld`)는 `unknown`이다. 작성 LLM의 답은 `author_status`로만 보존하고 검토 대상 주장으로 보내지 않는다. 결과 검증기도 같은 함수로 완료 기준과 검토 근거 ID의 일치를 확인한다. (2026-10-19 변경: SXID 11001 `b5ba138e`에서 작성 LLM이 자기 결론을 `unknown`으로 답해 검토 통과와 무관하게 목적이 미달되던 문제.)

기존 조건 검사와 등록된 증거 이름을 재사용하고 임의 Python·SQL·쿼리 표현식을 평가하는 새 규칙 언어는 만들지 않는다. `analysis_guidance`·`operator_guidance`의 자유 문장을 코드 조건으로 추정하지 않는다. 문자열 비교도 명시된 파서·정규화 규격에 한정하며 오타 추측으로 장비를 합치지 않는다. `reported_error_code=xid:79` 확인은 보고 사실의 조건이며 검증된 `error_code`나 실제 고장 원인을 생성하지 않는다.

조건별 실행 결과는 **충족 / 불충족 / 미확정**으로 저장한다. 각 항목에 기준 ID, 판단 담당(코드/LLM), 비교한 값 또는 설명, 원본 refs·위치, 제한, Runbook revision/hash를 남긴다. 근거 없음·해석 실패·생략은 미확정이며 false나 충족으로 바꾸지 않는다. LLM이 완료라고 제안해도 코드상 불충족·미확정인 필수 항목을 덮어쓸 수 없다.

의미 판단은 작성 응답의 `interpretation.criterion_assessments`에 기준 ID·제안 상태·기존 finding 참조·원본 참조로 연결하며 긴 근거 문장을 중복 저장하지 않는다. 새 정책을 적용한 경로에만 이 응답 영역을 요구하고, 분리 작성을 채택하면 기존 해석 호출에서 같은 구조를 받는다. 기준 평가를 위한 세 번째 새 모델 호출은 만들지 않는다. 허용 기준 ID·참조 영역·code 검사와의 모순은 validator가 검사하고, 의미 판단은 별도 검토자가 원본과 대조한다. 진단 refs는 미확인의 설명에는 쓸 수 있지만 관측을 요구하는 완료 조건의 근거로 대체할 수 없다. 새 영역도 출력 상한·잘림·부분 성공 검수에 포함한다.

`investigation_only=true`는 유지한다. 새 기준은 제한된 조사 완료를 허용하는 별도 계약이지 `fast_path`, `causal_status=supported`, 건강 상태나 권고 적격성을 얻는 우회 경로가 아니다. 여러 Runbook이 선택되면 고정된 목적에 필요한 기준을 함께 확인하고, 더 엄격한 필수 조건·적용 제외를 쉬운 Runbook 하나의 충족으로 덮지 않는다. 목적을 일관되게 정할 수 없거나 지원하지 않는 정책 버전이면 새 완료 판정을 하지 않고 이유를 남긴다. 정책 없는 구 revision에는 새 조기 종료를 소급하지 않는다.

#### 품질 검토는 목적에 맞게 하되 근거 기준은 유지

6개 공통 척도 키는 유지한다. 목적·적용 범위를 반영하는 검토 규칙은 **rubric 2**로 버전 관리하고 rubric 1 기록의 뜻을 바꾸지 않는다. Runbook에는 척도별 면제나 ‘무조건 통과’를 넣지 않는다. 검토 입력은 고정 목적·기준별 상태·발행 지침, 원본과 실제 발췌·생략, 수집 제한, 작성 해석과 전체 주장이다. 통합 응답의 해석과 코드 요약도 원본과 대조할 검토 대상이며 독립된 원인 증거로 중복 계산하지 않는다.

| 척도 | 목적에 맞는 검토 기준 |
|---|---|
| 근거와 결론의 연결 | 오류 보고·장치 연결·가능 원인·확정 원인을 구분. ‘가능성’이라는 표현만으로 근거 없는 특정 원인 우선화를 허용하지 않음 |
| 대상·시각의 구분 | 목표 범위에서 필요한 연결을 확인하고 불확실성 표시. 노드의 오류 보고 식별에 장비 독립 신원 확정을 무조건 요구하지 않지만, 장비를 특정한 조치에는 해당 전제 필요 |
| 반대 근거·모순 | 실제 반대 관측·동일 범위의 충돌을 설명. ‘원인 미확정’과 ‘가설 존재’만으로 모순 판정 금지 |
| 중요한 대안 | 원인을 선택·배제하거나 원인별 조치를 주장할 때 중요한 대안 검토. 오류 보고만 확인하고 원인을 보류한 경우에는 구체적 이유로 해당 없음 가능. 알려진 반대 근거를 숨기는 면제는 불가 |
| 수집·해석 한계 | 목적 달성에 필요한 부족과 목적 밖 미확인을 구별. 미확정 원인·현재 상태·수집 공백은 계속 보존 |
| 중요한 증거 활용 | 확보한 사건별 근거를 사용. 선택 조회 미수행만으로 감점하지 않으며 이미 확보한 중요한 반증·적용 제외는 무시하지 않음 |

지적에는 claim/기준 ID와 **설명 수정 / 판단을 바꿀 추가 정보 필요**를 구분해 남긴다. 조회 질문에는 무엇을 구별할지, 어떤 정보가 필요한지, 허용 조회가 그 정보를 제공하는지를 연결한다. 최종 실행은 코드가 판단한다. D44의 PCIe replay를 드라이버 버전 조회로, D02의 활동 지표를 커널 로그 조회로 제안하면 그 목적의 실행 근거로 쓰지 않는다. 다만 최신 D02 계획의 지표 라벨에 실제로 포함된 모델·드라이버 정보는 원본 범위 내에서 활용한다.

#### 다음 행동과 종료 조건

판단의 우선순위는 아래 표를 따른다. 먼저 실행 제한을 확인하고, 이어 현재 초안의 문제와 조사 목적의 필수 조건을 확인한다. ‘선택 조회가 남아 있다’, ‘원인이 미확정이다’, ‘검토 질문이 있다’만으로 추가 수집을 결정하지 않는다. 조회·라운드·수정 예산은 추가 작업이 필요한 분기에서 검사한다. 이미 목적과 최종 검토를 충족한 결과를 남은 조회 예산이 0이라는 이유로 실패 처리하지 않는다.

| 상황 | 다음 행동 | 결과에 남길 이유 |
|---|---|---|
| 취소·deadline 도달, 원격 종료 불명 | 기존 Worker/JC 종료·격리 처리 | 기존 판단 기록은 보존하되 실제 실행 종료 사유를 목적 달성으로 바꾸지 않음 |
| 근거 없는 단정·한계 누락 등 현재 자료의 문제 | 특정 가능한 문제 주장을 코드로 보류. 같은 증거의 재작성·재검토 없음 | 검토 지적과 변경 자료의 미검토 상태 보존. 자동 추가 수집 없음 |
| 목적의 필수 항목이 미충족/미확정이거나 중요한 반증이 있고, 이를 해결할 허용 조회가 실행 가능 | 그 항목에 연결된 보완 수집 → 다시 작성·검토 | 필요성, 제공 가능한 정보, 대상·기간·조건·예산 |
| 적용 조건과 목적의 모든 필수 기준 충족, 관련 차단 조건 없음, **같은 최종 초안** 검토 `acceptable` | 목적 달성으로 조사 종료 | 완료한 목적·근거·남은 한계. 목적 밖 선택 조회는 미수행 이유를 남기고 종료 |
| 필수 자료가 원천에 없음·권한/조건 부족, 수정 한도 도달, 재검토 불가 등 더 진행할 수 없음 | 한계를 기록하고 종료 | 목적 미달/판단 불가와 미검토/수정 필요를 보존. 원인 확정이나 품질 통과로 표시하지 않음 |

명시된 필수 조회와 공통 적용 제외·관련 신원 충돌은 선택 조회보다 우선한다. 새 정책이 선언한 **목적 밖 선택 항목**에 한해서만 `causal_confirmation_evidence` 등의 일반 gap이 반복 조회를 유발하지 않게 한다. gap 자체는 삭제하지 않고 `필수 미충족 / 목적 밖 미확인`의 이유를 덧붙인다. 정책 없는 구 revision과 호출 통합만 비교하는 단계에서는 기존 명시적 보완 조회 우선 동작을 유지한다.

LLM 토큰 부족과 조회 예산 부족은 계속 구분한다. 토큰만 부족해도 기존 정책 또는 새 목적에 필요한 허용된 독립 수집은 수행할 수 있고, 수집 후 모델을 실행하지 못하면 미분석으로 남긴다. 코드 기준이 충족됐더라도 필수 품질 검토가 실패·생략되면 ‘목적 달성·검토 통과’로 종료하지 않는다. 한도 내에서 해결하지 못한 문제는 같은 요청을 반복하는 대신 한계 종료로 기록한다.

예를 들어 노드·기간이 맞는 XID 79 보고와 출처를 확보했고 선택한 목적이 오류 식별·안내라면, ‘XID 79 보고를 확인했다. 근본 원인과 현재 접근 가능 여부는 미확인이다’라는 최종 설명이 검토를 통과한 뒤 종료할 수 있다. D44·D11이 그 목적에서 선택 사항이면 전부 채울 필요가 없다. 반대로 PCI 주소·UUID가 충돌하는데 특정 GPU를 고장 장치로 단정하거나, 물리 원인 규명이 목적인데 보고 코드만 확보했다면 목적 달성으로 끝내지 않는다. 시험 주입임을 아는 경우에는 시험임을 표시하고 실제 장애·복구를 주장하지 않는다.

#### 결과·GUI와 함수별 변경

평가 schema 2의 investigation 축에 목적·정책 revision, 기준별 상태/근거, 필요한 보완과 보류 이유, 최종 초안/검토 참조, 다음 행동·종료 사유를 연결한다. **실행 종료, 목적 달성, 품질 검토, 원인 상태는 별개**다. `result_status`·`missing_inputs`·`fact_eligible`·권고 적격성은 목적 달성 때문에 성공/충족으로 덮어쓰지 않는다. 새 reason/enum은 04의 공통 계약과 소비 validator에 함께 정의한다.

개발측 RCA의 기존 **워크플로우 디버깅** 버튼에서 ‘이번 조사 목적 → 무엇을 확인했나 → 왜 수정/추가 조회/종료했나’를 먼저 보여준다. 기본 화면은 쉬운 문장과 표로, 기술 ID·전체 원문은 펼쳐 보기로 제공한다.

| GUI 위치 | 먼저 보여줄 내용 | 펼치면 확인할 근거 |
|---|---|---|
| 최종 요약 | ‘오류 보고 식별 완료 / 분석 품질 타당 / 원인 미확정 / 조사 종료’처럼 축별 표시 | 목적, Runbook revision, 최종 초안·검토 ID, 제한 |
| 조사 기준 | 사람이 읽는 질문별 충족·불충족·미확정과 필수/선택 구분 | 비교 값, 코드/LLM 담당, 원문 위치, 입력 생략 |
| 통합 작성 | 한 호출에서 해석·원인 분석을 했다는 표시와 부분 채택 상태 | 실제 입력·응답 채택·검증 실패·호출/비용 |
| 품질 검토 | 목적에 따른 6개 척도와 해당 없음의 이유, 설명 수정과 추가 정보 요구 구분 | rubric 버전, 검토한 원문/주장, 반증·대안 판단 |
| 다음 행동 | ‘보고 식별은 완료되어 전력 조회는 생략했습니다’, ‘장치 연결이 충돌해 추가 확인합니다’ 등 저장된 사건별 이유 | 실행/보류 query, 연결 기준, 조건·예산, 종료 reason |

구 기록에는 목적·기준이 없다고 표시하고 지금 규칙을 대입해 과거의 종료 이유를 만들지 않는다. `RcaNarrative`의 `incident-first/1`·`/2`와 기존 노드 범위·조치 유형별 표현을 유지한다. RCA 품질 표시는 검토 대상 초안에 한정하고 기존 보고서 전체가 새로 검토됐다는 표시를 만들지 않는다.

초안 등록·발행은 기존 Backend 절차와 compatibility 검사를 따른다. 런타임에서 구조를 지원하기 전에 신규 revision을 발행하지 않는다. 되돌릴 때 이전 발행 revision과 검증된 작성 구조를 선택하며, 이미 생성된 schema 2 결과의 읽기 지원은 유지한다. 문서 작성·코드 구현·실제 발행·배포 검증은 각각 따로 기록한다.

### 워크플로우와 LLM 개입

다음 표는 **호출 통합과 Runbook 판단 기준을 함께 적용한 미구현 목표 흐름**이다. 현행 3단계 호출은 앞의 [현재 실행 순서](#실행-순서와-llm-개입)에 남긴다. F0~F8의 ①/②/③ 표기는 종전 분리 단계의 식별이며 현재 통합 경로는 작성/검토 역할로 읽는다.

| 순서 | 담당 | 수행 내용 | 남길 판단 근거 |
|---|---|---|---|
| 1. 사건·목적·기준 설정 | 코드 | 사건 snapshot, 대상·기간, 선택 Runbook의 조사 목적·판단 기준 고정. 구 revision은 기존 정책 | 목적·기준의 출처와 revision/hash, 필수/선택 구분 |
| 2. 수집·기초 확인 | 코드 | 기존 필수 조회와 형식·시각·식별자 검사, 목적 기준 중 명확한 항목 확인 | 원본, 요청 결과·제한, 비교 규격, 기준별 상태 |
| 3. 증거 해석·RCA 분석 | **작성 LLM 한 호출** | 확인 내용·추론·상충·미확인, 목적 기준의 의미 판단, 필요한 원인 후보·지지/반박·다음 확인 작성 | 같은 응답 안의 구분된 결과와 실제 입력 근거 |
| 4. 검증·초안 조립 | 코드 | 영역별 참조 검사, 질문/목적 기준 갱신 검사, RCA 해석·Runbook 후보·권고 결합 | 채택/제외 사유, 기준별 근거, 검토 대상 RCA 초안 ID |
| 5. 분석 품질 검토 | **별도 검토 LLM** + 코드 | 목적·기준과 원본을 보고 RCA 해석·원인·권고의 과장·누락·한계 검토 | rubric 버전, 척도별 이유·근거, 수정/추가 정보 요구, 검토 대상 ID |
| 6. 수정·수집·종료 | 코드 | 설명 수정 / 필수 보완 수집 / 목적 달성 종료 / 한계 종료를 구분. 필요한 경로만 반복 | 목적 기준·검토 결과·실행 가능성과 다음 행동의 연결 |
| 7. RCA 결과·디버깅 GUI | 코드 | 목적 달성·품질·원인·종료 이유를 저장하고 워크플로우 디버깅 버튼으로 확인. 이후 기존 결과 소비 경로 유지 | RCA 초안/검토/원본 연결, 단계별 무엇·왜·어떻게·한계 |

통합 출력의 질문 상태 제안도 코드의 참조·대상·기간·명확한 완료 조건 검사를 거친다. 코드 통과를 의미 정확성 보증으로 표시하지 않는다. 전체 자료 확보를 종료 조건으로 삼지 않으며, 기존 조회 권한·수정 횟수·deadline·예산을 유지한다.

### 개선 항목별 구현 원칙

**F0 진단 보완 — 모든 단계에서 실패를 비교할 수 있게 한다.** ② 초안 작성과 선택·편집 호출의 진단을 기존 공통 LLM 계산과 연결한다. 입력 크기, 가용 예산, 사용할 증거 없음, 전송 실패, 출력 검증 실패를 구분하고 기존 상세 reason은 보존한다. 서로 다른 원인을 하나의 이름으로 바꾸지 않는다. 시도·라운드·단계·복구 요청별 한도/필요량/예약량·호출 여부와 실측/추정 usage를 GUI에 표시한다. 구 기록의 원인은 추정하지 않는다. `call_stage`, `synthesize`, 공통 `request_budget`·`complete`, 선택·편집 호출자와 `RcaWorkflow`가 변경 대상이다. 진단 보완만으로 재시도 횟수나 종료 정책을 바꾸지 않는다. `failed` 같은 포괄적 상태가 `diagnostics.error_code`의 상세 사유를 가리지 않게 한다. 최종 초안이 미검토여도 실제 모델 호출·출력 잘림 이력은 별도로 표시하며, 호출 전 차단을 ‘모델 응답 검증 실패’로 설명하지 않는다.

**F1-A 검토자 단독 평가 — 평가기부터 시험한다.** [오프라인 도구](../../../agents/tests/rca_replay.py)는 기존 `review_analysis()`를 재사용한다. 고정 응답 사례는 실행·참조 계약 검사용으로 구현했으며 아래 실제 모델 평가와 사람의 기대 판정 합의는 남은 작업이다. 사람이 작성한 초안, 실제 전달할 증거와 수집 제한, rubric·모델·요청 설정을 고정한다. 같은 증거의 적절/과장 쌍, 식별자 오타, 관측 공백, 상충 보고, 핵심 증거 미사용의 다섯 유형을 준비한다. 모델 실행 전에 항목별 기대 판정·이유·근거와 중대한 오류 기준을 정하고 사람이 합의하지 못한 사례는 보류한다. 유형별 한 사례는 도구 동작 확인용이며 일반 정확도나 T79 전체 통과의 근거가 아니다.

**F1-B 전체 루프 재생 — 입력 구성과 결정을 함께 시험한다.** 최소 도구는 실제 `workflow.run()`을 통해 `evaluate_analysis()`와 현재 호출자의 문맥·조립·선택 코드를 재사용한다. 고정 조회·모델 응답으로 충분/부족 예산, 해석만 보존, 보완 후 검토 변경, 검토 수락 후 명시 규칙 조회를 검사한다. 조회는 도구 이름·전체 인자를 대조하고 누락 또는 응답 바인딩 실패는 부분 재생으로 기록한다. 아래 운영 입력 추출과 실제 모델 비교는 미완료다. 사건 범위·기간, 고정 evidence, 발행 Runbook·실행 profile, 예산을 입력으로 받고 보완 조회는 준비한 fixture를 공급한다. 실시간 MCP 조회나 운영 발행은 하지 않는다. Backend에서 자료를 추출할 때 목록의 모든 페이지와 원문·job/attempt·snapshot/revision 연결을 확인하고 묶음 hash·누락·비식별화 여부를 기록한다. 자료가 부족하면 부분 재생으로 표시한다.

F1-A에는 정상 보고 뒤 오류 보고가 이어지는 경우와 동일 시점의 모순 보고를 따로 넣는다. 생산자 시각이 없으면 Loki 기록 순서를 실제 장비 상태 변화로 단정하지 않는 설명을 기대한다. ‘원인은 미확정이며 현재 상태는 추가 확인 필요’처럼 적절한 한계 설명을 실패 처리하지 않는지 검사한다. 원인 가설이 없는 초안에 근거 없는 대안 나열을 강제하지 않도록 rubric·프롬프트를 보완하고, 구체적 원인을 단정하면서 반대 근거를 누락한 분석은 계속 거절해야 한다. 평가기 지적 때문에 유효한 내용이 제외되는 경우도 추적한다.

두 모드는 코드·프롬프트·rubric·모델/설정 버전, 입력·초안 hash, 항목별 기대/실제 판정, 호출·시간·토큰·실패/생략을 JSONL로 남긴다. 보류 사례와 반복 수는 실행 전에 고정한다. 모델이 보고하지 않은 usage와 실행 전 차단은 별도로 기록하며 비밀값·거절 원문 전체를 저장하지 않는다. 도구의 계약 검사와 실제 모델 평가는 각각 통과/실패를 판단한다. 기존 허용 연결을 사용하며 벤치마크용 RCA 로직을 복제하지 않는다.

**F4 입력 연결과 검토 입력 구성 — 무엇을 읽었는지 보존한다.** `bounded_context`, `synthesize`, `evaluate_analysis`, `analysis_draft`, `review_analysis`에서 호출·복구별 실제 입력 hash, source ID, 발췌 위치/표본, 생략 이유를 연결한다. 후보를 어느 응답에서 채택했는지 기록하고 유효 부분을 여러 응답에서 합쳤다면 각 입력으로 추적한다. 작성 입력과 검토 입력은 별개로 남긴다. 동일 ID·동일 크기 상한을 동일 내용의 증거로 사용하지 않는다.

검토 요청은 전체 주장 목록과 근거·반대 근거·수집 제한을 유지하되 `claims`와 후보·권고의 반복 전송을 줄인다. 코드가 결합한 Runbook 후보·권고, 작성에 쓰이지 않은 중요 자료도 검토 범위에 포함한다. 초안의 저장 형식과 ID는 유지하면서 검토용 표현을 조립하고 claim ID와의 대응을 검증한다. 실제 요청 내용의 hash는 별도로 연결한다. 입력을 줄이기 위해 주장·한계·반대 근거를 조용히 삭제하지 않는다.

호출 전에 전체 요청 크기를 계산하고, 중복 제거로 들어가지 않으면 미검토 주장·필수 자료·사유를 남긴다. 첫 구현은 동일 입력의 반복 호출이나 자동 분할 검토를 추가하지 않는다. 검토 전체가 불가능하면 skipped/null, 일부 항목 판단만 불가능하면 해당 한계를 유지한다. 이미 입증한 수정 필요는 보존하되 미열람 영역까지 전체 통과로 표시하지 않는다. 초안·입력 변경 후 이전 통과를 승계하지 않는다. 표현 수정 시 실제 근거를 유지할 수 없으면 중단하며, 축소 입력의 새 작성은 의미 재분석과 재검토로 다룬다.

**F3-A 질문과 후속 결정 — 기존 조회 권한 안에서 연결한다.** `rule_followup`, `select_followup`에서 기존 규칙·정책으로 실행 가능한 후보를 구한다. 새 판단 기준이 있는 revision은 [목적별 종료 조건](#다음-행동과-종료-조건)을 함께 적용하고, 목적 밖 선택 조회의 보류를 기존 규칙 위반이나 수집 실패로 표시하지 않는다. 구 revision은 기존 동작을 유지한다. `missing_any ∩ gaps`, `requires_all`, 대상·기간·신선도·중복·예산·라운드 조건을 그대로 적용한다. LLM 질문은 정책 우선순위와 명시 priority를 바꾸지 않고 같은 priority의 규칙 후보 사이에서 관련성을 반영한다. 질문이 없는 후보는 기존 순서를 유지한다. `exploratory_llm: true` 경로만 탐색을 허용하고 규칙 배치의 빈자리를 탐색 LLM으로 채우지 않는다.

검토 입력에는 허용 query ID뿐 아니라 기존 D 계약·선택 Runbook의 목적, 제공하는 관측과 한계를 전달한다. D02는 GPU 활동과 실제 제공된 장치 라벨, D44는 PCIe replay 관측이다. D02의 모델·드라이버 라벨이 있으면 활용하되 커널 로그·펌웨어 상태나 물리 원인 확정을 제공한다고 설명하지 않는다. 코드는 등록 ID·권한·명시 계약을 확인하고, 의미의 관련성은 LLM 제안과 사람 평가로 검증한다. 목적을 벗어난 질문은 실행으로 바로 연결하지 않고 부적합/판단 불가 이유를 남긴다.

모든 질문에 검토 evidence와 질문 위치/ID, 관련 query·적용 규칙·충족/부족 조건, 실행·수동 확인·보류 이유를 남긴다. 조건 부족·권한 없음·이미 수행·범위 밖·배치 제한·예산 부족을 구분한다. 질문은 허가를 만들지 않으며 명시된 규칙 실패를 정책·탐색 경로로 우회하지 않는다. `operator_guidance`의 일반 문장을 자동 완료 조건으로 해석하지 않고 앞 절의 질문 구조와 GUI를 사용한다.

**F2-A 분석 입력을 남기는 예약량 조정 — 구현과 검증 범위.** 총예산을 늘리지 않고 현재 남은 예산 안의 분석·검토 배분을 조정한다. main에 반영된 `synthesis_view()`·`reserve_review_budget()`를 기준으로 검토 보호 하한을 보완한다. 예약 결정과 실제 `synthesize()`는 같은 입력 선택 계산을 사용한다. 현재 예약에서도 근거를 담을 수 있으면 배분을 유지하고, 근거가 모두 빠질 때만 하한 이상의 범위에서 가능한 가장 큰 예약을 선택한다. 아래는 로컬 구현 계약이며 운영 효과는 별도 실측 대상이다.

| 변경 대상 | 구현 동작 | 보존 조건 |
|---|---|---|
| `synthesis.synthesis_view()` | 남은 예산·예약량으로 입력 상한·출력 여유와 실제 선택 뷰를 함께 계산. 예측 뷰와 전송 뷰의 차이 기록 | 원본 불변, 사건 범위·입력 상한·수치/참조 검사 유지. refs가 한 개 남았다는 사실을 의미상 충분함으로 해석하지 않음 |
| `synthesis.reserve_review_budget()` | 현재 예약으로 근거가 모두 빠지는 경우에만 제한된 배분 조정을 검토 | 호출자가 이미 확보한 예약량을 침범하지 않음. 조정 가능한 검토 예약과 유지할 하한을 분리해 명시. 검토 필수 입력·출력 최소 여유를 확보할 수 없으면 중단 |
| `evaluation.evaluate_analysis()` | 기존 예약 설정 지점에서 조정 함수를 사용하고 `synthesis.budget_allocation`에 전후 배분·이유 기록 | `finally`의 이전 예약 복원, 공유 attempt 예산·deadline·예외 처리 유지. 분석 호출 성공을 검토 성공으로 승격하지 않음 |
| `test_rca_budget_allocation.py`와 GUI 소비자 | 고정 예약·외부 예약만 보호한 조정·검토 하한을 보호한 조정을 동일 fixture로 비교. 실제 공통 LLM의 HTTP 경계와 예산 차감을 사용 | 사용량 보고/미보고, 작은/큰 규칙 초안, 예산 18,000~40,000, 출력 잘림을 검사. 실제 모델 정확도와 실패율은 별도 |

하한은 `기존 외부 예약 + encoded_size(review_payload(규칙 기반 초안, 보존된 검토 뷰, 허용 조회)) + REVIEW 프롬프트 바이트 + 기본 검토 출력 상한 + 512`다. 실제 검토와 같은 `review_payload()`를 재사용하며 규칙 후보·권고와 기본 한계를 포함한다. 모델이 앞으로 작성할 주장·한계나 재시도 비용의 상한은 아니다. **현재 근거를 담는 데 필요한 예산과 이 검토 하한을 동시에 확보할 수 없으면 기존 예약과 차단을 유지**한다. 외부 예약은 `finally`에서 복원한다. 고정 응답 비교에서 ②만 성공하고 ③이 실패하는 사례가 증가하면 불합격이며, 이 통과를 실제 모델의 모든 응답에 대한 검토 완료 보장으로 해석하지 않는다.

`budget_allocation`은 기존 `requested_review_reserve/applied_review_reserve/remaining_tokens/synthesis_sources_fit/review_reserve_reduced`를 유지한다. 여기에 `previous_reserved_tokens/review_floor_tokens/review_floor_basis/review_baseline_input_bytes/review_output_tokens`, 입력 상한·선택 바이트·refs·`context_selection`, 조정 사유 `reservation_unchanged/analysis_input_preserved/analysis_review_budget_insufficient`를 추가한다. 생략은 뷰의 기존 섹션별 개수 진단이며 완전한 생략 ID 목록은 아니다. 실제 전송 내용의 완전한 추적은 F4 범위다. 예약 조정은 원문 전체 보존, 검토 출력 잘림 해결, 의미 품질 보장의 대체물이 아니다. 구 기록에는 하한과 사유를 소급 주입하지 않는다.

**F2-B 전체 루프의 예산·출력 상한 개선 — F1-B 실측 뒤 적용한다.** `review_reserve`, 공통 LLM·Settings를 대상으로 F2-A 적용 전후를 비교한다. 출력 cap, 다음 검토 예약, 현재 입력 상한은 서로 다른 제약이다. 새 모델 초안/의미 수정을 시작하기 전에 다음 검토 여유를 확인하되 합성 실패 후 코드 후보를 검토하는 경로와 구분한다. 바이트 기반 상한과 실제 모델 토큰 차이는 모델별 자료로 판단하며 관측된 평균이나 소수 표본 P95만으로 예약량을 확정하지 않는다.

기존 고정 예약을 그대로 적용한 재현 기준: `REVIEW`는 UTF-8 2,297바이트, `SYNTHESIS`는 5,550바이트다. 기본 출력 설정 4,096에서 `review_reserve = encoded_size(view) + 2,297 + 4,096 + 4,096 + 512`이며 뷰가 6,000~10,000바이트일 때만 예약량이 17,001~21,001이다. 6,000바이트는 최소 뷰 크기가 아니므로 이를 전체 예약 범위로 일반화하지 않는다. ① 이후 잔여 예산 21,000을 가정하면 ② 유효 예산은 -1~3,999이고 입력 상한은 0이 된다. 실제 `review_reserve`·`synthesize`에 같은 합성 조건을 넣어 두 경우 모두 호출 0회·빈 refs·`llm_context_budget_exhausted` 반환을 확인했다(외부 모델 호출 없음). 이는 해당 조건의 재현이며, 실제 ① 소비량·예약량·선택 뷰를 기록하지 않은 운영 결과의 유일 원인을 확정하는 증거는 아니다.

검토 출력의 허용량도 측정한다. `validate_review`는 척도 6개 이유 각 800자, issue 최대 16개의 이유·수정안 각 800자, 질문 최대 3개의 질문·기대 효과 각 800자를 허용한다. 텍스트 상한 합계는 35,200자이며 ID·refs·JSON 구조는 별도다. 이 상한은 필수 출력 길이가 아니다. 기본 4,096토큰은 실제 고정 cap도 아니며 공통 LLM이 잔여 예산으로 낮추고, 첫 응답 잘림 뒤 여유가 있으면 늘려 재시도할 수 있다. 따라서 특정 응답의 잘림을 구조적으로 필연 또는 모델과 무관하다고 단정하지 않는다. F1-A/B에서 실제 전송 cap·완료 사유·출력 길이·재시도와 척도 누락을 측정한 뒤, 짧은 이유·중복 제거·단계별 cap을 비교한다. 상한을 줄여 필수 이유나 반대 근거가 사라지는 변경은 불합격이다.

입력 초과, 입력 근거 없음, 토큰 사전 차단, 출력 잘림을 따로 세고 검토 재전송·형식 복구·의미 수정의 비용도 포함한다. 입력 중복 제거·검토 출력의 간결화·단계별 상한을 같은 사례에서 비교하되 필수 척도·이유·근거를 삭제하지 않는다. 필요한 경우에만 산정식·cap·입력 상한·attempt 예산을 바꾼다. 설정 추가 시 미지정 동작, 환경 변수·JC 예제·Helm 미러와 양 Worker 검사를 함께 정의한다. 검토 불가 시 기존 유효 결과·한계를 보존하고 성공을 만들지 않는다. 모든 사건의 검토 완료나 전체 증거 확보를 목표로 삼지 않는다.

F8은 논리 단계 실행·형식 복구·전송 시도, 모델 보고/추정 usage를 따로 센다. 수정 후 통과 전환은 초안 ID와 의미 수정 전후 검토 쌍으로 계산하고 보완 수집 후 새 분석과 구분한다. 중간 경로는 최종 결과만으로 추정하지 않는다. 구 기록의 누락을 0회·통과로 채우지 않으며 수계산 사례와 일치해야 한다. 집계값은 원인 정확도 점수가 아니다.

### 독립 채택 범위와 계약 영향 공유

한 계획으로 관리하되 모든 기능의 동시 채택·배포를 요구하지 않는다. 아래 의존성이 실제 착수·활성화 조건이며, 다음 구현 순서표는 권장 진행 순서다. 특정 개선이 보류돼도 그 개선에 의존하지 않는 항목은 진행할 수 있다.

| 중간 언어 거절·최종 표현 분리 | 내용 검사 유지, 기존 표현/진단 계약의 최소 확장과 소비·정보 보존 검수 | 호출 통합·Runbook 1.1·rubric 2·평가 schema 2. 분리 호출/schema 1의 기존 진단 확장으로도 적용 가능하도록 설계 |

| Runbook 판단·종료 정책 | Runbook 1.1 작성/발행/소비, schema 2의 목적·기준·종료 기록, 목적에 맞는 rubric 2와 검수 | 호출 통합·언어 개선. 분리 호출을 유지한 schema 2 결과에서도 적용 가능 |
| 목적에 맞는 rubric 2 | 목적·기준·원본을 전달하는 검토 계약 | 호출 통합. 단독 F1-A 평가 가능하되 첫 운영 적용은 Runbook 판단·종료 정책과 한 단위로 검증 |

schema 2는 **공유 호환 기반이라는 의존성은 있지만 두 기능을 동시에 켜야 하는 계약은 아니다.** 최소 공통 상태·참조와 작성 모드를 정의하고, 분리 작성은 기존 독립 해석 기록을, 통합 작성은 통합 응답의 채택 영역을 참조한다. 목적 정책 미적용은 기존 종료 동작과 명시적인 미적용 상태로 표현하고, 정책이 적용된 경우에만 목적·기준·revision을 필수 검증한다. 미적용 기능의 가짜 기록이나 빈 완료 판정을 요구하지 않는다. 이 구분은 저장 결과의 의미이며 영구 운영 토글을 추가하라는 요구가 아니다.

계약 fixture는 최소한 **schema 1 기존 결과 / schema 2 통합+기존 Runbook / schema 2 분리+새 Runbook 정책 / schema 2 통합+새 정책**을 각각 검사한다. 새 정책은 있으나 필수 목적·revision·검토 참조가 없는 결과는 거절한다. 알려진 미적용 상태와 알 수 없는 버전은 다르게 처리하며, 한 기능을 되돌려도 다른 기능의 결과 읽기를 유지한다.

계약 변경의 공유는 [팀 가이드의 모듈별 담당과 계약 영향](../../team-development.md#1-담당-범위와-리뷰)을 따른다. C-1이 RCA 실행·검증을 담당하고 **B는 Runbook 1.1 Go validator·발행 API·JC/Backend 공개 계약**, A는 GUI, C-2는 RCA 결과의 Ops 소비 영향을 확인한다. 구현 전에 같은 PR/연결 작업에 변경 필드·버전·필수성, 정상/실패/근거 부족 fixture, 적용 순서·되돌리기와 검증 담당을 공유한다. 불명확한 호환 요구는 해당 담당과 확인하며 동료 Approve를 별도 필수 관문으로 만들지 않는다.

설계 기준은 PR #135가 반영된 main이다. 현재 변경은 재생 도구, 통합 작성, Runbook 1.1 Python/Go 검사와 목적 종료, schema 2·Ops·GUI, 최종 자료 고정을 포함한다. DB 스키마 변경은 없다. 실행한 검사와 미실행 실환경 검증은 QA에서 구분하며 개별 담당자의 검토 완료를 대신 주장하지 않는다.

먼저 4단계에서 언어 거절 분리 전후를 비교한다. 이후 비교군은 A=공통 입력·채택된 언어 정책의 분리 호출+기존 Runbook 정책, B=통합 호출+같은 정책, C=5단계에서 선택한 작성 구조+새 Runbook 기준·rubric 2·종료 정책이다. A↔B는 호출 구조 효과, 선택된 A 또는 B↔C는 판단 정책 효과를 비교한다. 각 비교에서 원본·모델·총예산·나머지 콘텐츠는 고정하며 새 revision의 실제 변경 내용을 기록한다. 통합 불채택이 Runbook 개선의 자동 중단을 의미하지 않으며 두 변경의 채택 결과를 따로 남긴다.

구현 시 04는 결과/중간 기록 계약, 14는 적용 순서, 07은 화면 계약, 05는 실행 가능한 검수 기준, Runbook 작성 안내는 콘텐츠 계약, QA는 실제 검증 증거를 갱신한다. 새 필드/enum은 Backend·Frontend·Ops와 Worker→JC 공개를 함께 검사한다. 공통 Python·설정 변경은 양 Worker와 필요한 환경 예제·Helm 미러에 도달한다. 입력 계약 1.3/1.5와 평가 schema 1 구 결과에 새 필수값을 요구하지 않으며, 새 서비스·테이블·큐나 GUI의 Worker 직접 실행은 추가하지 않는다.

실제 저장 사례는 사건·attempt·발행 Runbook·실행 profile과 원본 hash를 함께 고정해 재생한다. XID 79·SXID 11001 운영 회귀 사례는 원본과 연결 정보를 확보한 뒤 사용한다. 합성 사례는 구조 검증용이며 운영 시각·UUID·원인의 정답을 대신하지 않는다. 민감한 운영 원본을 저장소에 넣지 않고 비식별화 범위와 재현 한계를 명시한다.

### Runbook 기준·종료·GUI의 추가 검수

실행에 고정된 **발행 revision**을 기준으로 검사한다. 최신 XID 79·SXID 11001의 비교 수집 계획은 필수 지표를 먼저 모으며, 아래 선택 조회 종료 설명은 선택 계획을 가진 구 발행본에 적용한다. 저장소 XID 79·SXID 11001 원본의 1.1 정책과 운영 발행본 1.0을 혼동하지 않는다. 새 수집 평가·다음 행동 기록은 `decision_policy_status=applied/mixed/not_configured`로 적용 여부를 남기고, 다음 행동 기록의 `collected_queries/deferred_queries`로 목표 확인에 사용한 조회와 목적 밖 선택 조회를 구분한다. LLM 잔여 예산은 선택 조회의 실행 근거가 아니다. 필수 조회 뒤 기존 목적·후속 조회 판정을 수행하며 충족한 오류 보고 식별 목적의 선택 조회는 보류한다. 목적 없는 기존 Runbook의 규칙 기반 후속 조회는 유지한다. GUI는 목적 달성 시 D09 등 실제 수집과 생략한 선택 조회를 설명하고, 정책 미설정 시 새 Runbook revision 발행이 필요함을 표시한다. 정책 없는 과거 기록에 적용 상태를 소급 추정하지 않는다. 기존 1.0의 규칙을 변경하는 대신 [새 revision 적용 절차](../../../rcca-agent/runbooks/DB-WORKFLOW.md#기존-발행본에-종료-기준-적용)를 따른다.

아래는 유지할 검수 기준이다. 코드·fixture에서 확인한 항목은 QA와 05의 T80~T86에 기록하며 실제 모델의 의미 품질은 아직 통과로 표시하지 않는다. 고정 응답은 계약·분기, 실제 모델 재생은 의미 판단을 검사한다. 기존 테스트에 사례를 추가하고 실행 가능한 항목은 05에 반영한다. 호출 통합의 참조 영역·부분 성공·출력 잘림 기준은 앞 절을 그대로 적용한다.

정책 비교에서는 **목적에 불필요한 추가 조회 수, 필요한 추가 조회 누락 수, 잘못된 목적 달성 종료 수, 한계 종료 수와 이유, 타당한 제한 설명의 거절 수, 과장 통과 수**를 같은 사례·반복 수로 센다. 비용·지연·검토 완료·부분 성공 손실도 함께 보고한다. 고정 검수 사례에서 신규 오종료·필수 조회 누락·원인/조치 승격이 한 건이라도 생기면 채택하지 않는다. 필요한 조사와 품질을 유지하면서 불필요한 반복이 줄었는지 사례별로 대조하며 종료율 증가만으로 성공을 주장하지 않는다.

실제 모델 의미 검증 전 기대 판정·중대한 오류·반복 수를 고정한다. 모델 응답의 통과와 사람이 원본을 대조한 판단을 각각 기록한다. 검토 실패를 숨기려고 목적을 낮추거나 답하기 쉬운 사례만 남기지 않는다. 운영 원본 확보·재생이 안 된 부분은 미검증으로 남기며 코드/GUI 검수로 대신하지 않는다.

| F2-B | 입력 상한 이내의 출력 잘림, 재검토 사전 차단, ② 비용 증가 후 ③ 실패, 복구·의미 수정·보완 라운드 | 선정한 완료 사례의 검토 완료, 부족 사례의 정확한 제한·미검토. 전체 비용 누적, 초안/수정 전 여유 검사. ② 성공률만 높아지고 ③ 실패가 악화되면 채택하지 않음 | T69·T73·T74 |

실행 결과는 **통과 / 실패 / 미실행·미검증 / 해당 없음(이유)**으로 기록한다. 실제 모델 평가에는 코드·모델·자료 버전, 환경, 표본·반복 수, 실패/생략 수와 사람이 원본에 대조한 차이를 남긴다. 기대와 다른 결과를 감추기 위해 실행 후 기대값을 바꾸거나 사례를 제외하지 않는다. 한 변경의 효과를 비교할 때 다른 입력·모델·설정은 고정한다.

중대한 과장 통과, 실행 조건 우회, 원본 연결 손실, 추론의 사실 승격이 발견되면 확대 적용을 중단한다. 도구 테스트·fixture E2E·CI 통과는 실제 모델의 의미 품질이나 운영 배포를 보장하지 않는다. F5~F8과 F3-B의 선택 항목도 위 구현 원칙의 비교·호환 조건을 충족해야 하며 실제 결과는 [Agent QA](../../../agents/QA.md)에 검증 범위를 명시한다.

### 적용 범위와 보존할 기능

기존 사건 snapshot, 증거 원본, 발행 Runbook revision, 과거 결과는 덮어쓰지 않는다. 구 결과에서 읽을 수 있는 이벤트 정보는 출처와 함께 표시하되 당시 실행하지 않은 평가를 소급해 완료로 만들지 않는다. 새 표시/판단 필드가 없는 결과는 기존 화면과 미기록 표시로 열 수 있어야 한다.

결과 확장은 Backend 조회·공통 validator·Ops 소비·Worker→JC 공개 경로를 함께 검사한다. 장비 자동 조치, 자유로운 추가 쿼리, 새 수집원 도입, 모델 예산 일괄 증가는 이 제안의 첫 구현 범위에 포함하지 않는다. 목표는 조사 종료나 원인 확정 수를 늘리는 것이 아니라, **무엇을 확인했고 무엇이 남았는지 근거에 맞게 전달하는 것**이다.
