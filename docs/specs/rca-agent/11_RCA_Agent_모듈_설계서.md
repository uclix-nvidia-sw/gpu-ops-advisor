# 11. RCA Agent 실행 계약과 평가 분리 설계·개발

## 이번 개발 기준

**작업: 판단 기준 구체화, Runbook 기반 일괄 보완 수집·재분석과 판단·실행의 재생 검수. 상태: 설계, 미구현.** 코드 비교 기준은 `7b95d6a`(2026-10-19 조회한 main, PR #158 병합 포함)다. 실제 실행 설명은 [RCA README](../../../rcca-agent/README.md), 실행한 검증의 범위는 [Agent QA](../../../agents/QA.md)가 소유한다. 이 문서는 이번에 구현할 기준과 유지할 계약을 정의하며 배포 완료를 뜻하지 않는다.

목표는 **부족한 판단을 어떤 증거로 보완할지 설명하고, 그 계획대로 조사·수정·종료하는 RCA**다. 현재는 `model_assessment()`가 선택 followup 설명을 제외하고 `select_followup()`도 필수 링크 중심으로 후보를 줄인다. 검토자는 D의 의미를 충분히 받지 못하며, 구체적 오해를 발견해도 동일 증거 재작성 제한 때문에 수정할 수 없다. 이 세 부분을 연결해서 고친다.

- **유지:** 통합 작성 LLM → 독립 검토 LLM → 종료 후 보고서 LLM, 코드의 쿼리 생성, 원본·revision·hash 보존, 조회 권한·공유 예산·취소·JC 공개, 발행 revision과 과거 결과의 추적·읽기.
- **변경:** 선택 D 정보 준비, 기준별 부족 내용과 다음 계획, optional 전면 제외를 없애고 기본 수집 + 선택 D 일괄 보완 1회로 실행, 기존 Runbook 실행 규칙의 대체·폐기 검토, 동일 증거에 대한 제한된 의미 수정, 회차/수정/종료의 GUI 근거 연결.
- **제외:** 평가 점수·통과 점수, Ops 개편, 자유로운 쿼리 생성, Runbook 무조건 순회, 새 수집원, 총예산 일괄 증액, 자동 하드웨어 조치. 기존 O계열의 공통 D 사용은 호환 유지 대상이다.

**이 문서의 목표 워크플로우와 R/V의 결과 조건이 필수 개발 기준이다.** 통합 작성 → 독립 검토 → 종료 후 보고서의 역할·순서는 유지하고, 기존의 필수 링크 중심 보완 선택을 Runbook별 일괄 보완 정책으로 대체한다. main은 구현·비교의 출발점이다. 사건 장치 우선 정렬·`context_only`·보고서 섹션·GUI 접힘은 교체 가능한 구현 예이며 존속 자체를 검수하지 않는다. 유지하면 해당 분류/표시의 오해 가능성을 검사하고, 교체·제거해도 중요 근거 보존·정확한 판단/종료 표시라는 같은 결과 조건을 검사한다. 구현 PR에는 선택한 방식과 R/V 대응을 남긴다. 원본·출처·과거 결과 보존은 구현 교체와 무관하게 필수이며, 구 실행 정책 전환은 [Runbook 정책 전환](#runbook-정책-전환과-종료-조건)을 따른다.

**개발 순서:** 아래 요구사항 표 → 전체 워크플로우 → 해당 상세 규칙 → 단계별 구현/검수 순서로 읽는다. 요구사항 ID를 구현·테스트·PR 설명에 함께 사용한다. 같은 사실은 한 곳에서 정의한다.

**활성화 조건:** 입력 예산과 LLM 평가 정확도는 아직 입증되지 않았다. 아래 단계의 확인 조건을 만족해야 새 정책을 활성화한다. 기준을 낮추거나 사례를 빼서 검토 통과율을 높이지 않는다.

## Runbook 기반 검토·계획과 RCA 반복 설계

아래 상세 규칙은 R01~R12의 구현 기준이다. 현행 동작과의 차이는 요구사항 표에, 필수 판단·데이터 경계는 뒤의 해당 절에 모았다.

### 전체 워크플로우와 호출 경계

```text
사건 접수 → Runbook 선택(목적·판단 기준·기본 D·선택 D)
    ↓
기본 D 수집 [코드] → 원본·수집 상태 보존
    ↓
┌─ RCA Agent Loop: Runbook별 수집 기반 분석 최대 2회 ──────
│ ① 누적 증거 RCA 분석 [작성 LLM] ◀───────────────────┐
│    ↓                                                │
│ ② 검토 입력 준비 [코드]                             │
│    • 초안·원본·판단 기준·선택 D 공통 정의             │
│    • 기본/일괄 보완 상태·D별 결과·실행 가능 범위      │
│    ↓                                                │
│ ③ 독립 검토·계획 [검토 LLM]                         │
│    • 부족한 기준·영향·일괄 보완으로 확인할 내용       │
│    • 보완 수집 / 같은 증거 수정 / 종료 제안           │
│    ↓                                                │
│ ④ 검증·실행 분기 [코드]                             │
│    ├─ A. 보완 필요 + 아직 일괄 보완하지 않음          │
│    │   → 남은 선택 D 전체 수집(보완 1회)              │
│    │   → 전체 배치 완료/실패·거절 결과 확정           │
│    │   → 새 관측 누적 → 두 번째 ①로 복귀 ──────────┤
│    │     새 관측 없음: 작성 반복 없이 수정/한계 종료 │
│    ├─ B. 기존 증거만으로 분석 수정 가능              │
│    │   → 구체적 지적 + 같은 증거로 ① 복귀 ─────────┘
│    │     attempt당 의미 수정 최대 1회, 이후 재검토
│    ├─ C. 목적·품질 충족 → 목표 달성 종료
│    └─ D. 보완 불가 / 보완 완료 후 미충족 / 실행 제한·실패
│        → 미충족 기준·수집 결과·한계를 남기고 종료
│        검토 실패 시 추가 실행 중단, 원인 확정으로 표시 금지
└──────────────────────────────────────────────────────
    ↓
최종 RCA 자료·검토 상태·종료 이유 고정
    ↓
보고서 LLM: 고정 자료를 읽기 좋게 서술 → 저장·JC 공개 → GUI
```

**A는 일괄 보완 후 RCA 재분석, B는 동일 증거의 분석 수정이다.** 수집 단계는 Runbook당 기본 1회와 보완 최대 1회다. 작성·검토 각각 최대 2회의 수집 기반 실행을 뜻하며 LLM 총 호출이 2회라는 뜻은 아니다. 의미 수정·형식 복구·보고서는 별도 기록한다. 보고서 LLM은 종료 뒤에만 호출한다.

XID 79는 기본 D09 후 첫 검토에서 보완을 승인하면 D44·D02·D11을 한 묶음으로 처리하고, D09와 확보한 전체 보완 증거로 한 번 재분석·재검토한다. SXID 11001은 같은 방식으로 D02·D13을 보완한다. 실행 병렬도 때문에 묶음을 나누더라도 그 사이에는 작성·검토 LLM을 호출하지 않는다.

일괄 보완에서 일부 조회가 실패해도 실행 가능한 나머지는 처리한다. 새 관측이 전혀 없으면 기존 분석·검토의 적용 범위를 보존하고 수집 실패/동일 결과를 별도 기록하며, 유효한 수정이 있으면 B, 없으면 한계 종료한다. 두 번째 검토가 미충족이어도 같은 Runbook의 세 번째 수집은 시작하지 않는다. 실패한 수집·미검토를 보완 불필요나 목적 달성으로 바꾸지 않는다. 검토 자체 실패는 아래 [실패 분기](#검토-실패와-종료-제안-오류)가 우선이다.

새 관측으로 다른 Runbook이 적용되는 확장은 별도 정책 전이이므로 작업 전체가 항상 2회로 끝난다는 보장은 아니다. 같은 Runbook의 횟수를 확장·재선택으로 초기화하지 않으며 구체 경계는 아래 전환 절을 따른다.

### D 정보 준비와 컨텍스트 계약

준비 위치는 `evaluate_analysis()`의 검토 입력 조립 직전이다. 전체 설명은 Runbook 선택 뒤 한 번 해석·고정해 재사용할 수 있지만, 실제 검토 요청을 만들 때 조회 결과·부족 조건·미실행 계획·실행 가능 상태를 갱신한다. Runbook별 기본/일괄 보완 상태와 보완 가능 횟수(0 또는 1)를 제공한다. 보완 완료 후에는 collect를 허용하지 않고 revise/finish만 제공한다. 예산·deadline 등으로 collect가 실제 불가능하면 allowed_actions와 사유를 제공하고, 실행 계획과 보고서에 남길 추가 확인을 구분한다. 예약량 산정에도 같은 결정용 카탈로그를 반영해, 작성 뒤 예상 밖의 검토 입력 증가가 생기지 않게 한다.

초기 새 루프 적용 대상은 **RB-XID-79와 RB-SXID-11001**이다. D 설명은 두 지침이 사용하는 **D09·D02·D44·D11·D13의 5개 공통 정의**부터 준비한다. XID 79는 기본 D09/선택 D44·D02·D11, SXID 11001은 기본 D09/선택 D02·D13이다. 전체 D 일괄 작성은 선행 조건이 아니다. D09도 수집 결과의 의미를 검토하는 기준으로 작성하며, 기본 D 실행에 별도 LLM 선택 호출을 넣지 않는다.

C-1(RCA)이 Runbook 목적·기준과 D 설명을 작성하고 실제 binding·원천 표본과 대조할 책임을 진다. 공통 D/설정 변경의 영향은 C-2(기존 O계열 소비자), B(계약/설정 소비자), A(표시)와 연결하며 역할별 범위는 팀 가이드를 따른다. 실명 담당자는 구현 PR에 기록하고 별도 필수 승인 절차를 추가하지 않는다. S1의 콘텐츠 산출물은 D별 의미·확인 가능한 정보·한계·필수 인자·scope/단위/producer·binding revision/출처·Runbook 기준 연결·기존 성공/실패 예시다. D02의 실제 제공 라벨, D13의 실제 로그 원천처럼 환경 의존 능력은 배포 binding에서 확인한 범위만 적는다. 정적 문서만으로 관측 가능성을 확정하지 않는다.

초기 대상의 모든 선택 D 설명이 준비되고 V01/V02/V23의 정의·binding 대조 및 오선택 사례를 검수하기 전에는 해당 새 정책을 활성화하지 않는다. 이후 누락/충돌이 발견되면 `definition_incomplete`와 제외된 D/기준을 GUI·검토 입력에 남기고 추정 추천·실행하지 않는다. 확장 Runbook의 D도 같은 요건을 충족해야 후보가 된다.

공통 profile의 각 `queries[D].decision_support`를 선택용 설명의 추가 필드 후보로 둔다. 필드 누락이 기존 D 실행/O계열을 실패시키지 않도록 하되, 새 검토·계획 모드에서 설명 없는 D를 모델이 추정해서 추천하게 하지 않는다. producer별 의미·단위·scope·필수 인자는 검증된 binding에서 가져와 일반 설명을 제한한다. 설명과 binding이 충돌하면 해당 D는 `definition_incomplete`로 보이고 자동 실행 후보에서 제외한다. 문서 설명은 관측 사실이 아니다.

| 검토용 `query_catalog` 항목 제안 | 의미·출처 |
|---|---|
| `query_id`, `definition_revision`, `binding_id/revision`, `catalog_entry_hash` | 고정한 D 설명·실행 계약의 출처. 새 schema에서 이름 확정 |
| `observes`, `can_inform`, `cannot_establish` | 무엇을 관측하고 어떤 질문에 도움을 주며 무엇은 확정할 수 없는지. 검토된 공통 정의 |
| `runbook_refs`, `purpose`, `criterion_links` | 이 사건에서 해당 D를 선택지로 둔 이유. Runbook revision과 기준 key 연결 |
| `requirements`, `availability` | 필요 대상·시간·식별 정보, binding 가용 여부와 미확정/차단 사유. 알 수 없는 가용성을 가능으로 단정하지 않음 |
| `history` | 동일 요청의 실행 여부, evidence refs, 성공/빈 결과/부분/실패/미실행 구분, 이미 얻은 정보 |

카탈로그는 현재 선택한 Runbook들의 기본/선택 D를 ID와 definition revision별로 중복 제거한다. 기본 D의 설명은 증거 의미를 이해할 정도로 재사용하고, **모든 선택 D의 결정용 설명**을 제공한다. 긴 PromQL/LogQL, 인증·URL·데이터 소스 상세, 전체 인벤토리를 반복해서 붙이지 않는다. Raw 실행 설정은 코드만 사용한다. `can_inform`은 관련 가능성이지 원인 증명이나 조회 성공 보장이 아니다. `criterion_links`는 관련성 안내·정렬에 쓰되 연결이 없다는 이유만으로 후보를 숨기지 않는다. 의미·한계·필수 인자·이력은 짧은 구조로 제공하고 중복과 부가 설명부터 제거한다. 실제 collect 불가 상태에는 계획 전용 설명을 생략할 수 있으나 기존 증거의 D 의미·한계와 평가 기준은 유지하고 생략 이유를 기록한다. 새 경로는 GOAL_REVIEW의 D02/D44 개별 설명을 검증된 공통 정의로 대체하며 정의 없이 하드코딩만 먼저 삭제하지 않는다.

모델에 전달된 카탈로그 hash·각 항목 revision·정의 누락 목록·원본/전달 바이트·근거 refs·생략 범위·전체 요청 hash를 저장한다. 카탈로그 refs는 `input_evidence_refs`/`observation_refs`와 별도 영역이며 원인 후보의 지지 근거로 인용할 수 없다. 작성자의 해석과 Runbook 지침도 독립 관측으로 승격하지 않는다.

작성 입력과 채택 결과는 다음 참조 경계를 지킨다. 작성 결과는 사실·추론·미확정과 원인 후보이며 완성된 보고서가 아니다. 빈 원인 후보는 허용하고, 호출하지 않은 해석 단계의 완료 기록을 만들지 않는다. 관측 역할은 입력 정렬 순서와 무관하며 같은 evidence ID나 바이트 상한만으로 실제 입력이 같다고 보지 않는다.

| 영역 | 허용 참조·보존 규칙 |
|---|---|
| 해석 evidence refs | 실제 전달된 `input_evidence_refs`; 진단/실패도 한계 설명에 사용 가능. 근거 없는 unknown은 명시적 이유 필요 |
| 가설 supporting/contradicting refs | 전달된 `observation_refs`만. 지지 근거 필수, 지지/반박 교집합 금지. Runbook·진단·생성 해석·D 정의는 원인 관측이 아님 |
| `finding_refs` | 같은 채택 응답의 해석 의존 관계. 원문 refs를 대신하지 못하며 해석 제외 시 의존 가설 보류 |
| 부분 성공 | 검증된 항목과 제외 위치/code/hash 보존. 전체 JSON 실패는 임의 추출하지 않음. unknown/conflict/limitation 또는 의미 기준 오류가 목적 달성을 만들지 못하게 보호 |

컨텍스트의 충분성은 아직 입증되지 않았다. 다음 순서로 판단한다.

1. 실제 Runbook별 선택 D 수, 설명 크기, 초안·원본 근거 크기 분포를 측정한다. 단일 오류뿐 아니라 다중 Runbook·많은 증거·긴 한국어 응답 사례를 포함한다.
2. 기존 모델/출력 cap/총예산과 검토 예약 하한을 유지한 실제 전체 요청으로 사전 검사한다. 카탈로그를 포함한 동일 payload builder로 예약을 산정하고 임의 비율·새 환산식으로 완화하지 않는다. 분석 관측이 모두 빠질 때만 하한 안에서 조정하며 작성·검토 최소 필요량을 함께 확보하지 못하면 차단한다. 외부 예약은 실패 시에도 복원한다. `budget_allocation`의 요청/적용/이전 예약·잔여량·수용 여부·하한/산정 근거·실제 cap·조정 사유를 보존한다. UTF-8 바이트, 보수적 차감, 실제 토큰과 미보고를 구분한다. 규칙 초안의 예약은 생성 초안·복구 비용 상한이나 검토 성공 보장이 아니다. 실제 cap·출력 길이/finish reason·부분 채택·usage를 전송별 검사하고 작은/큰 초안·usage 유무·예산 경계는 V04/V22/V28로 검수한다.
3. 중복 설명 제거는 허용하되 판단에 필요한 한계·반대 근거·선택 D를 조용히 삭제하지 않는다. 중요 관측을 선택하는 방식은 교체 가능하다. `bounded_context`의 같은 cluster/target/component 내 유효 이벤트 장치 우선 배치를 유지한다면 정렬을 동일 장치 확정이나 중요도 판정으로 사용하지 않는다. 주소 미지정 상태·정상 전후·다른 장치의 관련 반대 근거도 평가 대상으로 남긴다. 원본은 보존하고 실제 입력의 선택·생략을 대조하며 중요 근거를 담지 못한 입력을 전체 검토로 표시하지 않는다.
4. 필요한 입력과 검토 출력 여유를 확보할 수 없으면 `review_context_insufficient` 등 명시적 사유로 검토/계획 미완료 처리한다. 이번 첫 구현에서 자동 분할 검토나 별도 계획 호출은 추가하지 않는다. 기존에 검토되던 사건이 카탈로그 추가 때문에 미해결로 바뀌는 회귀도 측정하고 적용을 보류한다. 생략 이력만으로 의미 손실이 해소됐다고 판단하지 않는다. 불충분 사례가 확인되면 호출 분리와 비용을 재비교한 뒤 설계를 갱신한다.

### 평가 기준과 부족한 내용의 표현

**점수·합계·가중치·통과 점수는 사용하지 않는다.** 공통 품질 기준과 Runbook의 조사 목적 기준을 구분한다. 자료를 적게 모았어도 제한된 결론이 타당할 수 있고, 문장이 신중해도 조사 목적에 필요한 관측이 없으면 목적은 미달이다. 검토자는 두 축을 각각 답한다.

사람에게 설명할 다섯 관점과 현재 6개 rubric의 연결은 다음과 같다. 새 형식에서 항목을 합쳐 세부 검사를 잃지 않으며, 현재 key를 보존해 비교할 수 있도록 한다.

| 설명 관점 | 기존 기준/관련 판단 | 반드시 설명할 내용 |
|---|---|---|
| 사건 파악 | `identity_time` + Runbook 코드 기준 | 오류 보고·대상·시각의 연결 범위, 보고 시각과 실제 발생 시각의 차이 |
| 목적에 필요한 증거 | `evidence_use` + Runbook 필수 기준 | 목적에 필요한 관측, 확보/미확보 내역, 확보된 중요한 증거 활용 여부 |
| 분석의 타당성 | `grounding` | 어떤 주장에 어떤 근거가 연결되고 어디서 비약했는지 |
| 반대 근거와 대안 | `contradictions`, `alternatives` | 중요한 반대 관측·다른 설명. 미확정 자체를 모순이라고 하지 않음 |
| 판단 범위 | `limitations` | 관측 사실·추론·미확정·수집 제한의 구분 |

각 품질 기준과 Runbook의 의미 기준에 `status`, `reason`, `evidence_refs`, `confirmed`, `missing`, `impact`, `resolution`, `completion_condition`을 제안한다. `missing`은 부족 없음이면 빈 목록이며, `resolution`은 수정/수집/수동 확인/보완 불가를 구분한다. 실제 코드 필드명·한도는 04 결과 계약에서 확정한다.

- 사용자 상태는 충족/보완 필요/판단 불가이며 `not_applicable`은 기존 호환과 목적상 적용 제외를 위해 별도로 유지한다. 적용 제외에는 이유가 필수이고 자동 충족으로 변환하지 않는다. 새 Runbook의 필수 기준에는 적용 제외를 허용하지 않는다.
- ‘충족’은 전체 데이터 확보나 실제 원인 확정이 아니라 명시된 조건을 해당 근거 범위에서 만족했다는 뜻이다. 코드가 검사하는 식별자·시각·필수 자료 조건을 LLM이 무시하거나 변경할 수 없다.
- 작성 LLM의 `criterion_assessments`는 제안이다. 새 정책에서 검토자는 원본을 보고 별도 평가하고, `finish_assessment()`는 검증된 검토 평가와 코드 기준을 결합한다. 작성자 자기평가를 검토의 근거로 중복 가산하지 않는다.
- 근거가 없는 주장을 철회하는 것은 수정이고, 빠진 관측을 얻는 것은 수집이다. 문장을 신중하게 바꾸는 것만으로 미충족된 필수 관측을 충족시킬 수 없다.
- Runbook의 조사 목적과 필수 조건을 평가 기준으로 고정하며 종료를 위해 목적을 낮추지 않는다. 시험 주입 추정은 해당 사건의 원문/필드 근거·반대 관측·남은 의문과 영향을 함께 설명해야 한다. 오류 코드만 존재, 로그 부재, 정상 지표 또는 특이한 패턴만으로 시험이나 장비 정상을 확정하지 않는다. 원인 미확정 자체는 품질 실패가 아니며 ‘D09로 충분’은 해당 목적과 근거 범위에서만 성립한다. 복수 코드·다른 PCI/시각·입력 생략만으로 모순을 확정하지 않고 상태 보고의 반복을 오류 이벤트 반복으로 세지 않는다. 오류 식별 목적을 모든 사건의 원인 조사 목적 대신 적용하지 않는다.

**첫 검토의 핵심은 개별 D 선별이 아니라 일괄 보완의 필요성 판단이다.** Runbook에는 기본 D로 충족할 수 있는 목적 조건, 추가 관측이 필요한 조건, 선택 D 전체의 보완 범위와 한계를 적는다. D의 실제 의미·인자·원천은 공통 정의를 참조한다. 기본 D에서 무엇이 확인됐는지, 어떤 중요한 조건이 부족한지, 묶음 안의 어떤 D가 그 판단을 지지·반박·범위 한정하는 데 도움이 되는지와 예상 결과 활용을 필수로 설명한다. 일부 D가 직접 관련되지 않아도 collect 승인 시 전체 묶음에 포함되며, 각 D가 모두 필수 근거인 것처럼 이유를 만들어 쓰지 않는다.

| 첫 검토의 판단 | 결정 근거와 다음 행동 |
|---|---|
| 목적·품질 충족 | 필수 조건별 근거와 반대 관측 검토 후 종료. 선택 D가 있다는 이유로 조회하지 않음 |
| 중요한 관측 부족 + 선택 묶음으로 보완 가능 | 부족 기준·D 정의·예상 판단 변화를 연결해 collect. 코드가 남은 선택 D 전체를 실행 목록으로 구성 |
| 증거는 있으나 추론·표현에 오류 | 해당 claim·원본·수정 요구를 제시해 revise. 수집도 필요하면 일괄 수집 후 재분석에 함께 반영 |
| 부족하나 선택 묶음으로도 보완 불가 | 관련 D의 제공 정보·한계와 대조한 이유를 남겨 한계 종료. 정의 누락·실행 불가는 별도 제한으로 표시 |

‘자료 부족’이라는 문구만으로 전체 수집을 승인하거나 ‘시험 주입 같다’는 추측만으로 생략하지 않는다. Runbook에 잘못 포함된 선택 D는 실행 때 모델이 몰래 빼는 대신 콘텐츠 검수에서 수정하고 새 revision으로 발행한다. 첫 검토의 성급한 생략과 불필요한 일괄 수집을 모두 V05/V06/V07/V16의 실제 모델 재생으로 검사한다. 두 번째 검토는 추가 수집 계획 대신 같은 목적의 충족·미충족과 한계, 유효한 수정 필요성을 판단한다.

### 검토·계획 응답과 실행 검증

새 응답은 기존 검토 결과에 아래 구조를 추가하는 방식으로 설계한다. 이는 필드 예시이며 현행 validator가 이미 허용한다는 뜻이 아니다.

```text
review_schema_version / rubric_version
analysis_id / input_hash / catalog_hash / batch_version
criteria                      기준별 품질 평가
objective_assessments         Runbook revision별 의미 기준 평가
issues                        claim·근거·수정 요구·동일 증거 수정 가능 여부
next_action                   revise | collect | finish
collection_assessment         대상 Runbook·부족 기준·일괄 보완 이유
    criterion_keys / issue_ids / catalog_refs
    expected_effect / result_usage   관측·미관측·불완전 결과의 활용
    request_scope_ref         고정 대상·기간
    repeat_reason             기존 실패 요청 재조회가 필요할 때 이유
finish                        종료 제안·미충족 기준·한계·보완 생략 근거
```

검토 LLM은 실행할 D 부분집합이나 pending 변경 목록을 출력하지 않는다. `collect`는 해당 Runbook 선택 D 전체 묶음에 대한 제안이며, 코드가 고정 카탈로그와 기존 결과에서 전체 실행 목록을 만든다. 완결된 동일 요청은 재사용하고 정의/인자/전제/권한·예산 때문에 실행할 수 없는 D는 제외 이유를 보존한다. ‘관련성이 낮다’는 모델 의견만으로 묶음에서 일부를 빼지 않는다. 보완 완료 후 collect 제안, 빈 묶음 승인 또는 수정 지적 없는 revise는 아래 3번의 행동 오류로 처리하고 진단을 남긴다. 필수 근거·설명이 누락된 불완전 응답은 2번의 검토 실패다. 기존 주장 수정 요구는 collect와 함께 전달해 재분석 때 반영한다.

최종 실행 기록은 모델의 제안과 분리한다. `plan_id`, review evidence ID, 대상 초안, 각 D의 `proposed/accepted/rejected/executed` 상태, 실제 evidence refs, 불가 사유를 남긴다. 모델이 종료를 제안해도 목적 달성 여부는 같은 초안의 유효 검토·필수 기준·차단 조건을 코드가 다시 확인한다. 존재하지 않는 인자나 대상을 모델이 생성해 쿼리 범위를 넓힐 수 없다.

| 판단 | 주체와 경계 |
|---|---|
| 어떤 조건이 부족하며 왜 중요한가 | 검토 LLM, 원본 근거와 조건을 명시 |
| 수정으로 해결되는가, 추가 관측이 필요한가 | 검토 LLM, 둘 다 필요하면 collect에 수정 요구 포함 |
| 선택 D 전체 묶음이 부족한 판단을 보완할 수 있는가 | 검토 LLM. 기여할 D의 공통 정의·예상 판단 변화 제시; 개별 D 실행 선별은 하지 않음 |
| 같은 요청을 다시 할 이유가 있는가 | 검토 LLM이 이전 실패/부분 결과와 이유 설명. 코드는 이력 제공 |
| ID·revision·참조·요청 형식·허용 scope·명시 필수 전제 | 코드 검증. 의미 평가를 문자열 일치 점수로 대체하지 않음 |
| Runbook당 일괄 보완 1회·조회·토큰·시간·의미 수정 한도 | 코드 통제. 모델이 사유를 바꿔 한도를 초기화하지 못함 |

부분 실행 가능한 계획은 허용된 항목만 실행하고 거절 사유를 다음 회차의 검토 입력에 포함한다. 모든 항목이 거절됐다고 다른 D를 코드가 임의 대체하지 않는다. 수집 항목이 전부 거절되어도 검토 LLM이 기존 증거만으로 가능하다고 명시한 구체적 수정 요구가 있고, R08의 수정·재검토 예산과 횟수가 남으면 revise로 전환한다. 코드가 새 수정 방안을 추론하지 않는다. 이 조건도 없으면 불가 사유와 남은 조건을 기록해 종료하며, 같은 자료로 계획 재작성 LLM을 반복 호출하지 않는다. 실제 조회 실패도 분석 품질 충족이나 ‘보완 불필요’로 바꾸지 않는다.

### 검토 실패와 종료 제안 오류

**평가 결과가 미충족인 것과 평가를 수행하지 못한 것은 다르다.** 다음 순서로 검사하며, 첫 적용 분기를 실행한다. 현재 코드의 일부 예산 오류별 stop_override만으로 새 루프의 실패 처리를 대신하지 않는다.

| 순서·상황 | 채택·상태 | 다음 행동 |
|---|---|---|
| 1. 취소·hard deadline·원격 실행 불명 | 기존 Worker/JC 상태와 fencing 우선 | 새 수집·수정·보고서 호출 금지. 가능한 진단만 보존하며 정상 완료/공개로 우회하지 않음 |
| 2. 입력/예산 차단, 호출 실패, 잘림·JSON·필수 기준·형식·참조·버전 검증 실패가 복구 후에도 남음 | 최신 초안은 미검토. 실패 응답의 평가·보완 제안 모두 미적용 | RCA 루프 종료. 기존 미실행 배치도 `최신 검토 실패로 실행 보류`로 보존하고 재수집/의미 수정/새 계획 호출 금지 |
| 3. 응답 구조·필수 평가·근거 참조·초안/정책/카탈로그/배치 버전은 유효하지만 종료가 필수 코드 기준/기존 승인 배치와 충돌하거나 허용되지 않는 collect/revise를 제안 | 행동 제안만 거절. 코드 기준은 코드 결과 유지, 나머지 유효 평가·issue 채택. 해당 응답으로 새 배치 승인 없음 | 기존 유효 승인 배치가 아직 시작되지 않았고 보완 권한이 있을 때만 실행. 없으면 유효 수정 또는 미해결/제한 종료. 세 번째 수집·재계획 호출 없음 |
| 4. 정상 평가·계획 | 기준별 평가와 검증된 계획 채택 | collect/revise/finish의 기존 분기 실행 |

검토 형식 복구는 기존 call_stage의 최초 요청+최대 1회 복구 상한을 유지한다. 입력/예산 차단·통신 오류·원격 불명에는 복구 호출을 만들지 않고, 잘림(`llm_output_truncated`)은 기존 정책대로 재전송하지 않는다. JSON/형식·참조 검증 오류는 기존 재시도 가능 조건·토큰·deadline 안에서만 복구한다. 의미 수정 1회와 별도 기록하며 새 정책용 무한 재검토/재계획을 추가하지 않는다. 3번의 행동 제안 충돌은 모델 재호출 없이 처리한다.

형식·참조가 유효한 계획의 개별 요청이 scope·필수 인자·실행 전제·예산 검사에서 거절되는 것은 검토 전체 실패가 아니다. 그 경우는 앞 절의 부분 실행/전부 거절 처리에 따른다. 실행 가능한 D 전체를 처리하고 묶음이 끝나기 전에 분석을 시작하지 않는다.

2번은 종료 구분 `분석 미해결`을 기본으로 하되 실제 토큰 소진 등은 기존 실행 제한 reason을 보존한다. 두 경우 모두 최신 검토는 실패/생략이며, `보완 불필요`나 목적 달성으로 바꾸지 않는다. 마지막 유효 초안·검토와 최신 미검토 초안을 각각 ID/근거 범위로 보존하고 이전 통과를 승계하지 않는다. 남은 실행 여유가 있으면 채택 자료·미검토 상태·실패 이유·미실행 요청을 고정해 기존 보고서 경로로 전달한다. 보고서 모델로 재평가하지 않으며 실패/예산 부족이면 같은 고정 자료의 기본 표시를 사용한다. hard deadline 이후 저장·공개를 보장한다는 뜻은 아니다.

3번은 **완전한 응답에서 확인된 행동 제안의 일관성 오류에만 허용하는 예외**다. LLM의 목적 달성/충족 주장이 코드 담당 기준(명시된 식별자·시각·필수 자료 등)의 결과와 충돌하면 모델 주장은 이력으로 보존하고 충족 판정으로 채택하지 않는다. 코드도 문자열 차이만으로 실제 장비 불일치를 추론하지 않고 해당 계약이 정의한 검사 결과만 적용한다. 충돌 기준 ID·코드 관측 refs·모델 판단·최종 채택 범위를 따로 저장한다. 잘린 JSON, 필수 평가 항목 누락, 틀린 근거 참조·버전은 이 예외가 아니라 2번이다.

기존 승인된 일괄 배치의 필요성과 보완 권한은 충돌하지 않는 최신 평가와 우선 적용한 코드 기준을 함께 사용해 확인한다. 해당 부족에 연결된 실행 가능한 요청이 처음부터 없거나 실행 직전에 모두 불가로 바뀌면 현재 유효 issue의 기존 증거 수정 가능 여부·수정 예산을 검사한다. 가능하면 revise, 불가하면 미충족 기준·유효 계획 부재/실행 불가 사유를 남기고 분석 미해결 또는 실제 실행 제한으로 종료한다. 코드가 다른 D나 수정 내용을 발명하거나 모델 재계획을 추가하지 않는다. 목표 미달을 보완 불필요로 바꾸지 않는다.

### 일괄 실행 목록과 검토 출력

**실행 목록은 코드가 고정 Runbook·카탈로그에서 만든다.** Runbook ID/revision·catalog hash·batch ID/version·승인 review ID와 전체 선택 D를 한 번 고정하고, D별 재사용/대기/실행/성공/실패/거절/미실행 상태와 근거를 보존한다. 일부 D만 출력한 모델 목록을 실행 원본으로 삼지 않는다. 승인한 배치 버전과 실행 대상이 다르면 실행을 막고 진단을 남긴다. 일괄 보완은 스케줄링 시작 전에 사용 처리하며 일부 실패나 ID 변경으로 새 배치를 열지 않는다.

동일 묶음의 독립 D는 실행 한도 내에서 병렬 또는 여러 실행 묶음으로 처리한다. 모든 D의 결과·실행 불가 상태를 확정한 뒤 누적 재분석을 한 번 수행한다. 전제 자료가 필요한 D는 같은 배치 안에서 순서를 지키고, 선행 실패 시 dependent D를 미실행 사유와 함께 남긴다. 모델이 다음 검토에서 대기 항목을 유지/취소/교체하는 별도 프로토콜은 두지 않는다. hard deadline·취소·원격 불명은 배치 완료보다 우선한다.

**입력뿐 아니라 출력도 S2 통과 조건이다.** 현재 기본 검토 출력 cap은 4,096토큰이며 실제 설정값으로 측정한다. 모든 기준 key의 판단은 필수다. 충족 기준은 짧은 reason·refs·부족 없음 표시, 미충족/판단 불가 기준은 부족·영향·해결·완료 조건, 적용 제외는 이유를 요구한다. S1에서 프롬프트·validator의 조건부 필드와 길이 상한을 함께 확정한다. 코드는 판단 근거를 만들어 넣지 않는다.

검토 응답은 실행 목록을 반복하지 않고 배치·기준·D 정의 참조로 설명한다. S2에서 긴 한국어·다수 미충족·전체 보완 증거가 포함된 두 번째 입력/출력의 실제 토큰·잘림·JSON 완결성·refs·총비용을 측정한다. 기존 성공 사례의 검토 실패 회귀가 있으면 활성화를 보류하며 cap 증액·근거 삭제로 통과시켰다고 보지 않는다.

### 분석 수정과 추가 수집의 별도 반복 계약

| 항목 | 분석 수정 반복 | 추가 수집 RCA 반복 |
|---|---|---|
| 시작 조건 | 유효한 검토의 구체적 issue·근거·수정 요구 | 부족한 조건과 이를 보완할 허용 선택 D 계획 |
| 증거 집합 | 동일 source version | 기존 원본 + 새 조회 원본·진단 |
| 작성 요청 | 원본 근거·이전 초안·관련 검토 지적 | 누적 근거·수집 결과·관련 검토 지적 |
| 결과 | 새 `analysis_id`, parent 연결, 같은 회차의 수정본 | 새 수집 회차의 분석본 |
| 후속 검토 | 수정본에 대한 독립 검토 필수 | 재분석본에 대한 독립 검토 필수 |
| 실패 시 | 원래 지적 보존, 문제 주장 보류, 미검토 표시 | 조회 실패/동일 응답/새 관측 유무를 구분해 제한 종료 또는 결과 검토 |

**새 정책은 Runbook당 기본 수집 1회 + 선택 D 일괄 보완 최대 1회다.** 첫 검토가 보완 필요성을 승인하면 남은 선택 D 전체를 조회하고 누적 재분석·독립 검토를 한 번 수행한다. 목적 달성이면 첫 분석에서도 종료한다. 보완 뒤 미충족이어도 같은 Runbook의 추가 수집은 반복하지 않고 수정 또는 한계 종료한다. 정상 경로는 작성·검토 1쌍 또는 2쌍과 종료 후 보고서이며 의미 수정·형식 복구는 별도다.

- **일괄과 동시 실행을 구분한다.** 기존 실행 묶음 최대 3개 같은 제한은 병렬도/스케줄링 제한으로만 사용한다. 선택 D가 4개 이상이어도 전체를 같은 보완 배치로 처리하고 실행 묶음 사이 작성/검토 호출은 없다. 일부 실패가 독립 D를 중단시키지 않으며 hard deadline·취소는 우선한다. 배치 완료 후 새 관측이 있을 때 한 번 재분석한다. 결과가 모두 동일/실패이면 불필요한 작성 호출 없이 유효 수정 또는 한계 종료한다.
- **재사용·재조회:** 요청 키는 D·binding/revision·고정 대상/기간·인자를 정규화한다. 완결된 동일 결과는 재사용한다. 실패/부분 결과의 재조회는 첫 검토에서 이유·예상 새 정보가 승인된 경우에만 보완 배치 안에 포함하고, 같은 키의 논리 재조회는 attempt당 최대 1회다. 기본 D 실패 보완도 이 배치 안에 명시적으로 포함할 수 있다. 보완 중 새 실패는 기존 전송 재시도 계약만 적용하며 추가 LLM 계획·세 번째 수집을 만들지 않는다. 사유/UUID/Runbook·revision 변경으로 이력과 한도를 초기화하지 않는다.
- **의미 수정:** 같은 증거의 의미 수정은 attempt당 최대 1회다. collect와 수정이 함께 필요하면 일괄 수집 뒤 재분석에 함께 반영한다. 두 번째 검토 후에도 유효한 수정 권한이 남으면 동일 증거 수정·독립 재검토는 가능하며 이는 세 번째 수집 회차가 아니다. 수정 실패·한도 소진으로 문제 주장을 자동 채택하지 않는다.
- **토큰·조회 예산:** 전체 보완 묶음과 누적 작성·검토·보고서가 기존 예산 안에 들어가는지 실제 요청 크기·cap·예약 보호로 검사한다. 임의 비율·총예산 증액은 하지 않는다. 부족하면 실제 거절/미실행 D와 한계를 남기며 일부 수집을 전체 확보로 표시하지 않는다. 후속 초안 크기는 추정과 실측을 구분하고 사전 검사를 완료 보장으로 표현하지 않는다.
- **시간·종료:** 각 실행 전 deadline·취소·timeout을 검사한다. 미측정 예상 시간 예약은 이번 범위 밖이다. 원격 불명·hard deadline은 Worker/JC 경계가 우선이며 보고서/저장을 보장하지 않는다. 빈 반복이나 재계획 전용 호출을 하지 않는다. Runbook별 사용 상태, 요청별 재조회 한도와 공유 조회·토큰·deadline은 확장에도 유지한다.

Runbook에 포함된 선택 D는 collect 승인 시 전체 실행 대상이 되므로 구성·의미·자료량이 실행 비용을 직접 결정한다. S1에서 각 D의 포함 이유·보완할 기준·의존성·중복·원천과 전체 묶음의 처리 가능성을 검수한다. S2/V22/V25에서 한꺼번에 들어온 증거가 핵심/반대 근거를 밀어내거나 작성만 성공하고 검토가 실패하는지 확인한다. 루프 분기 감소만으로 비용·품질 개선을 주장하지 않는다.

**S2/V25의 활성화 차단 기준:** 같은 재생 사례·원본/Runbook·모델/설정·조회/토큰 예산·deadline·실행 환경에서 기존 경로와 새 루프를 비교한다. 조건과 반복 횟수를 함께 남기고 deadline 실패 건수/비율(전체 시도 수 포함), 결과 저장 여부, 소요 시간과 추가 수집의 판단 개선을 사례별로 기록한다. 기존에 저장되던 사례가 새 흐름에서 저장되지 않거나 deadline 실패가 증가하면 원인을 확인·해결하고 같은 조건으로 재검수할 때까지 활성화를 보류한다. 환경 변동으로 비교가 불가능한 경우는 통과가 아닌 미검증이다. 다른 사건 구성의 운영 비율만 비교하거나 성공한 결과만 분모로 삼지 않는다. 이 검수는 기존 attempt 상태·저장 결과·재생 실행 기록으로 수행하며 T1~T3의 GUI 시간 진단을 기다리지 않는다. 예상 시간 기반 조기 종료·deadline 확대를 도입하는 규칙도 아니다.

`source_version`, `analysis_id`, `review_id`, `collection_round`, `revision_no`, `parent_analysis_id`, `trigger`를 분리한다. 동일 증거가 돌아왔는데 UUID나 입력 뷰만 바뀐 경우 새 수집 근거로 재작성을 허용하지 않는다. 검토 issue가 수정 경로의 명시적 예외이며, HTTP 오류·JSON 실패·출력 잘림은 의미 수정 권한을 만들지 않는다. 기존 형식 복구 정책과 이 의미 수정 1회는 별도 횟수로 저장한다.

재조회는 같은 ID를 다시 실행할 수 있으므로 `collected.update()`로 과거 query 결과를 덮어쓰지 않고 요청별 evidence를 append/merge한다. 원본과 모델 입력 뷰는 분리하고 새 관측으로 hash를 속이지 않는다. 새 관측이 없고 수정 예외도 없으면 이전 분석을 재사용한다. `remaining`은 D ID가 collected에 있다는 이유만으로 제거하지 않고, 요청별 결과·미실행 계획·유효 재조회 사유를 구분한다. 누적 observation_refs와 hash는 실제 원본에 연결하고 실패 진단을 원인 지지 관측으로 승격하지 않는다. 수집 상태만 달라졌다면 그 사실과 근거를 새 결정 기록에 남기고 이전 검토의 읽은 범위를 확장해 표시하지 않는다.

현행 `acceptable_after_feedback`는 구 결과 읽기와 비교 기준으로 보존한다. 새 경로에서는 주장 삭제도 해석·대안·목적 판단을 바꿀 수 있으므로 재검토 없는 통과 승계를 적용하지 않는다. 수정한 초안에 이전 검토 통과를 승계하지 않는다. 수정본 검토가 실패/생략되면 해당 초안은 미검토이며, 이전에 지적된 주장을 정상 결론으로 복구하지 않는다. 기초 형식/참조 검사 통과를 의미 품질 통과로 표시하지 않는다. 후속 조회를 더 해도 같은 결론일 수 있고, 반대 근거가 나와 가설을 철회할 수도 있다.

### Runbook 정책 전환과 종료 조건

#152의 Runbook 1.2는 생산자·컴포넌트·비정상 상태·선택적 reason으로 오류 보고 목표를 판별하는 현재 계약이다. 새 검토·계획 계약은 **`gpu-rca-runbook/1.3` 제안**으로 분리한다. 단, 구 JSON을 그대로 복사하고 planning_mode만 추가하는 것을 구현 목표로 삼지 않는다. Runbook은 조사 목적·판단 기준·기본/선택 D·기준과 D의 관계·명시적 실행 전제·출처/적용 조건을 제공하고, 검토 LLM은 그 안에서 일괄 보완의 필요성과 결과 활용을 판단한다. D 의미·조회 구현은 공통 정의와 binding에서 제공한다.

| 현행 구조/행동 | 새 방향에 따른 처리 |
|---|---|
| 1.1 오류 코드 / 1.2 component·health·reason 적용 조건 | 검증 가능한 사건 구분 근거는 활용하되 새 목적 구조에 맞춰 재설계 가능. 보고 사실을 실제 고장·회복으로 승격하지 않음 |
| identify_error_report 고정 목적 | 사건별 실제 조사 목적·충족 기준으로 검토. 오류 보고 확인만 필요한 경우에만 유지하며 부족한 분석을 종료하려고 목적을 낮추지 않음 |
| required/basic D와 optional D | 기본 수집과 조건부 일괄 보완을 구분. collect 승인 전에는 선택 묶음, 승인 뒤에는 남은 선택 D 전체가 실행 대상. 기존 optional 제외 규칙은 대체 |
| selection.missing_any / exploratory_llm | 새 검토·계획 LLM과 중복되는 의미 판단/별도 선택 호출은 대체·제거. 이 규칙을 그대로 보존하기 위해 새 흐름을 제한하지 않음 |
| requires_all | 권한·대상·명시적 선행 자료 같은 실행 전제만 코드 검증으로 유지. 의미상 필요한지는 검토 기준으로 옮김 |
| operator_guidance와 보고서의 고정 절차 삽입 | 참고 지침이며 조사 증거나 실행 지시가 아님. 보고서 역할에 맞는 적용성·조건·출처만 전달하며 현재의 자동 삽입·섹션 구성은 재설계/삭제 가능 |
| 기존 Runbook 파일·실행 경로 | 일괄 보존을 전제하지 않음. 항목별 유지/재작성/대체/폐기를 결정하고 전환 완료한 중복 실행 코드·저작 파일은 소비자 확인 후 제거 가능 |

S1에서 대상 Runbook별 목적, 기본/선택 D, 기준, 적용 조건의 전환 대응표를 만든다. #152의 작성자와 RCA·보고서/GUI·Backend 담당자에게 지침 자동 삽입의 유지/대체/삭제안, 근거, 소비자 영향, 검수·되돌리기 방안을 공유하고 구현 전에 대응표의 결정을 확정한다. 기존 설계를 보존해야 한다는 전제나 별도 필수 Approve 절차를 추가하지 않는다. 1.3의 필드 후보는 `decision_policy.planning_mode=review_guided_batch`, `observation_plan[].execution_preconditions.requires_all`이며 정확한 구조는 Python/Go 공통 fixture와 함께 확정한다. 구 selection 의미 규칙과 새 계획을 동시에 실행하지 않는다. 1.0/1.1/1.2 발행본을 같은 revision에서 새 의미로 해석하거나 덮어쓰지 않는다.

전환은 새 구조 검증·읽기 지원→새 Runbook 작성/검수→새 revision 발행·선택 전환→구 정책 퇴역 순서다. 병행 지원은 전환 수단이며 영구 요구가 아니다. 초기 두 Runbook 밖 미전환 사건은 기존 발행 revision/실행 경로를 유지하고 실행 기록에 구 정책임을 명시한다. 새 모드로 선택된 revision의 결함은 구 경로로 자동 우회하지 않는다. 새/구 지침 혼합은 단일 새 정책으로 검증되지 않으면 새 루프를 실행하지 않고 미지원/미해결 이유를 남긴다. 되돌릴 대상 revision을 명시하고, 완료 후 구 실행 경로의 제거 범위와 검수를 확정한다. 새 요청이 조용히 구 규칙으로 우회하지 않게 한다. 과거 결과가 참조하는 발행본·출처·hash와 조회 기능은 유지하며, 이번 문서 작업에서 DB/파일 삭제나 운영 발행을 수행하지 않는다.

선택 D의 `required=false`는 첫 검토 전에는 항상 실행하지 않는다는 뜻이다. 검토 LLM이 중요한 부족을 보완할 수 있다고 판단해 collect를 승인하면 현재 Runbook의 남은 선택 D 전체를 수집한다. 적어도 하나 이상의 D가 부족 기준의 지지·반박·범위 한정에 기여할 근거가 있어야 하며, 묶음의 다른 D는 함께 수집하는 배경 관측일 수 있다. 실행 범위·정의·완결 결과 재사용·명시적 전제·예산 외의 이유로 일부를 선별하지 않는다. 첫 단계에서 보완을 생략하려면 목적·품질 충족 또는 선택 묶음으로 보완할 수 없다는 근거를 남긴다. 시험 추정·원인 미확정만으로 수집/종료를 자동 결정하지 않는다. 보완 뒤 원인 미확정이면 조사 범위의 한계를 설명하며, 모든 D 조회 성공을 품질 통과로 취급하지 않는다.

| 종료 상태 | 필수 조건 | 사용자 설명 |
|---|---|---|
| 목적 달성 | 호환·적용 가능한 Runbook, 필수 코드/의미 기준 충족, 차단 없음, 같은 최종 초안 검토 통과 | 어떤 조건을 어떤 관측으로 충족했는지. 원인 확정 여부는 별도 |
| 보완 가능한 조회 없음 | 첫 단계에서 관련 선택 D로 중요한 부족을 보완할 수 없음을 유효 검토로 설명. 해결할 분석 수정 문제 없음 | 원인 미확정·목적 미달·보완 생략 근거. 실행 불가를 도움 없음으로 바꾸지 않음 |
| 실행 제한 | 조회/모델 예산·deadline·입력 한도·전제 부족 등으로 계획 전체를 수행하지 못함 | 미실행/실패 D와 영향. 전체 보완 완료나 목적 달성으로 표시하지 않음 |
| 보완 완료 후 미충족 | 일괄 보완이 끝나고 유효한 최종 검토에도 필수 기준 미달, 추가 수정으로 해결 불가 | 현재 Runbook 자료로 확인한 범위와 남은 의문. 전체 수집 성공과 분석 품질·원인 확정은 별개; 실패/미실행이 있으면 그 제한을 우선 설명 |
| 분석 미해결 | 모델/응답 검증 실패, 수정 실패 또는 검토 미완료 | 채택 가능한 사실과 미채택 분석, 실패 위치. 정상 검토로 표시하지 않음 |

기존 `goal_not_met`는 호환용으로 유지하되 새 결과에 `termination_detail`을 붙여 `no_helpful_query`, `definition_incomplete`, `request_unavailable`, `plan_rejected`, `review_context_insufficient`, `no_new_evidence`, `supplement_completed_unresolved`, `supplement_already_used` 등 구체적 원인을 제안한다. 최종 reason enum과 기존 STOP_REASONS 매핑은 04 결과 계약에서 확정하고 validator와 GUI를 함께 갱신한다. `insufficient_actionable` 같은 수집 gate가 존재해도 실제 계획이 실행되지 않았으면 이유를 같은 화면에서 연결한다. 단순히 ‘추가 조회 없음’만 표시하지 않는다. 정의 누락·실행 불가·예산 부족은 D가 도움이 없다는 의미 판단과 구분하고 실제 제한 reason을 남긴다. 원인 미확정이어도 한계를 정확히 설명한 분석은 품질 통과가 가능하지만 목적 미달 상태는 유지한다. 종료의 근거 필드·선택지 누락·refs/버전은 코드가 검사하고, D의 유용성/시험 추정의 의미 타당성은 검토 LLM과 실제 모델 검수로 확인한다. 근거가 없는 일반 문구만으로 보완 불가를 채택하지 않는다. 형식/참조/필수 설명 실패는 기존 검토 실패 분기, 유효 승인 배치와 종료 충돌은 기존 종료 제안 거절 분기를 따른다.

현재 Runbook의 보완이 끝났다는 이유만으로 다른 Runbook을 자동 순회하지 않는다. unexpected-evidence 확장은 새 관측 단서·오류 namespace·적용 조건으로 새 Runbook이 검증·선택될 때만 허용한다. 새 revision·선택 이유·기본/선택 D·목적·카탈로그 hash를 고정하고 새 검토 승인을 받는다. 새 Runbook은 기본/보완 단계를 따르되 이미 확보한 동일 요청을 재사용하고 공유 예산·재조회 이력은 유지한다. 따라서 다중 Runbook 사건 전체의 수집 기반 분석은 2회를 넘을 수 있다. 같은 Runbook 재선택·revision 변경·집합 변경으로 기존 보완 권한을 다시 만들지 않는다. 여러 Runbook을 함께 검토할 때는 묶음별 승인·생략 근거와 사용 상태를 따로 기록하고, 동시에 승인된 묶음은 공통 요청을 중복 제거해 수집한 뒤 함께 재분석한다. 적용성이 바뀐 미실행 배치는 보류하고 구 검토를 새 목적에 승계하지 않는다. 새/구 정책 혼합이나 적용 불확정은 명시적 미지원/한계로 남긴다. 조사 종료는 사건 해소나 복구 완료가 아니다.

### GUI와 보고서에 남길 근거

현재 개발용 RCA의 [RcaWorkflow](../../../frontend/src/components/RcaWorkflow.tsx), [RcaEvaluationTrace](../../../frontend/src/components/RcaEvaluationTrace.tsx), [RcaEvaluation](../../../frontend/src/components/RcaEvaluation.tsx)를 확장한다. 흐름을 감추지 않으면서 코드 기록을 LLM 호출처럼 보이지 않게 한다.

- ‘기본 D 수집 → 1차 분석·검토 → 선택 D 일괄 보완 → 2차 분석·검토 → 종료’로 표시한다. Runbook별 보완 사용 여부와 배치 내 D별 실제 호출을 연결한다. 의미 수정/재시도/Runbook 확장은 별도 표시하며 작업 전체의 LLM 호출이 최대 2회인 것처럼 표현하지 않는다.
- 입력 준비 상세는 D별 의미·한계·실행 가능 상태·기존 결과·실제 모델 전달 여부를 보여준다. 원문 전체가 아니라 선택용 정의를 읽었다면 그 범위를 표시한다.
- 기준별로 판단 조건·사용 근거·확인한 사실·부족 내용·영향·보완 방법을 보여준다. 6개 기존 rubric과 Runbook 목적 기준을 구분하고 점수는 표시하지 않는다.
- 보완 결정은 ‘부족한 기준 → 전체 선택 묶음으로 기대하는 판단 변화 → 일괄 승인/생략 이유 → D별 실행·재사용·실패·미실행 → 두 번째 판단 → 종료’로 연결한다. Runbook에 포함돼 함께 조회한 D와 부족에 직접 기여한 D를 구분한다. 일부 실패를 보완 불필요로 번역하지 않고, 2차 미충족 종료에서는 조사 범위 소진과 실행 제한을 구분한다.
- 수정은 지적 대상과 이전/새 초안, 재검토 결과를 연결한다. 입력 초과·근거 없음·토큰 차단·전송 실패/원격 불명·응답 형식/참조 실패·출력 잘림·의미 수정·코드 보류·미검토를 code/path·요청 한도·usage와 함께 구분한다. `invalid_author_response`를 연결 실패로 표시하거나 구 기록에 없는 세부 원인을 추정하지 않는다. 실행 0회 기록을 추가 LLM 호출로 표시하지 않는다.
- 종료는 목적 달성/제한 종료와 원인 확정 여부를 분리한다. 화면의 요약과 상세는 모두 termination_detail과 유효한 최종 초안·검토/목적 ID를 확인하며 `goal_not_met`만으로 보완 불가를 표시하지 않는다. 결과 화면과 작업 디버깅 모두 개발자 관점의 상세 접근을 연결한다. UUID·hash·원시 enum은 상세에 두고 사람이 이해할 수 있는 이유를 먼저 표시한다.
- 보고서 모델은 채택된 사실·한계·종료 이유를 설명한다. 고정 지침 삽입을 의무화하지 않고, 조사 결과에 적용 가능한 참고 설명/조건부 대응을 구분하며 새 조사·판단은 수행하지 않는다. 실행하지 않은 계획은 ‘수행 결과’가 아니라 ‘남은 확인’이다. 보고서 실패 시 동일 자료의 기본 표시를 유지한다.

### 결과·보고서·공개

**R11의 구현 계약:** RCA 루프는 근거·분석·채택 범위·종료 이유를 확정하고, 보고서 LLM은 그 자료만 읽기 좋게 서술한다. 조사와 평가를 보고서 단계에서 다시 수행하지 않는다. 필수 섹션·출처·수치 검증은 유지하되 이를 의미 일치의 증명으로 간주하지 않는다. 현재 구현 설명은 [RCA 보고서 계약](../../../rcca-agent/README.md#보고서와-조회-호환)이 소유한다.

| 처리 위치 | 구현할 규칙 | 검수 |
|---|---|---|
| `summarize_reports`와 누적 관측 조립 | 구현 방식에 관계없이 수집 사실을 보존한다. 검증된 대상·출처·시각 범위의 보고만 요약하며 작성/검토 실패가 원본 사실을 삭제하지 않음. 정상/오류 보고를 회복·실제 원인으로 승격하지 않음 | V15·V20·V34 |
| `collected`·관측 집계 | 조회 요청·원천 레코드·의미상 이벤트를 구분해 이력과 집계 단위를 보존. 재조회/기간 겹침의 동일 레코드 제거와 여러 레코드의 같은 이벤트 재보고 병합은 별도 규칙이며 S1에서 기존 파서와 대조. 같은 레코드의 수집 상태·해석 계약별 검증 결과는 합쳐 없애지 않음. 원천 식별자와 출처·시각·내용 등 검증된 레코드 식별 계약으로 동일성을 판정하며 evidence UUID·문구 동일만으로 합치지 않음. 동일성 불명은 수집 레코드 수와 중복 여부 미확정으로 표시하고 고유 사건 건수로 단정하지 않음 | V11·V34 |

| 보고서 구성 후 hash 재검사·저장/조회 | 보고서 전후 같은 고정 자료의 hash를 검사하고 변화 시 공개 거절. 보고서 실패/예산 부족은 같은 사실·한계·종료 이유의 기본 표시. Backend/Ops/GUI가 이를 검토 완료·복구 완료로 바꾸지 않음. 구 결과의 필드 누락은 그대로 읽고 소급 생성하지 않음 | V20·V21 |

Runbook 지침은 조건부 참고 자료다. 포함 여부와 섹션은 새 조사 목적·적용성에 맞게 정하며 기존의 자동 원문 삽입을 의무화하지 않는다. 포함한 지침의 출처·revision·모델/버전·승인 조건을 보존하고 실제 수행 조치나 관측 근거로 바꾸지 않는다. 테스트 주입·실제 장애, GPU·NVSwitch의 적용 범위를 구분한 최신 지침은 전환 대응표에서 검토한다. 목적·기준 문구를 바꾸면 새 revision/fixture로 검수하며, 저장소 JSON 수정과 DB 발행은 별개다.

원본 사실 보존은 hard deadline·취소·원격 실행 불명에서 정상 저장·공개를 보장하는 우회 경로가 아니다. 공통 Worker/JC 경계가 우선한다. 과거 결과·발행 revision·hash는 수정하지 않는다. 구체적인 저장/채택 필드는 [04 채택 계약](../common/04_Agent_동작_판단_명세서.md#검토-평가와-행동-제안의-채택--개발-목표), 화면은 [07 실패 표시](../frontend/07_프론트엔드_개발명세서.md#검토-실패와-종료-제안-오류-표시--개발-목표), 실행 검사는 [05](../05_테스트_검수_기준서.md#runbook-기반-루프의-실패콘텐츠-검수--개발-목표)에 연결한다.

### 실행 종료 후 소요 시간 디버깅 — 개발 목표

**성공·실패·취소·시간 초과 등 실행이 끝난 뒤 개발용 RCA에서 확인한다. 진행 중 실시간 표시·타이머·추가 polling은 이번 범위가 아니다.** 우선 지연 위치를 측정하고 이후 최적화한다. 900초 실행 제한이나 요청 timeout은 성능 목표가 아니며, 이번 작업에서 늘리거나 임의의 단계별 시간 배분을 도입하지 않는다. 기존 deadline·취소·원격 종료 불명 경계는 유지한다.

- 전체 attempt 경과와 단계별 소요 시간을 구분한다. 수집(D별/배치), RCA 작성, 검토 입력 준비·검토, 다음 행동 결정, 보고서 작성, 결과 저장, JC 완료·공개를 실제 기록 범위에서 연결한다. 대기/초기 준비 등 포함 범위를 표시하고 전체 경과를 단계 합계로 대신하지 않는다.
- 회차·의미 수정·논리 호출·전송 재시도별 시간을 구분한다. 병렬 D의 개별 시간 합과 배치 경과를 중복 가산하지 않는다. 오래 걸린 단계는 같은 계층의 실측 시간 기준으로 보여주고 요청·응답·토큰·실패 사유를 기존 상세에 연결한다.
- 성공 결과가 없는 실패 attempt도 남은 진단으로 열 수 있어야 한다. 시간 기록 없음은 미기록, 시작만 있음은 종료 미기록, 미실행은 미실행으로 표시하며 0초·진행 중·성공으로 추정하지 않는다. 측정되지 않은 서버 대기/생성 시간이나 단계 사이 공백을 원인으로 단정하지 않는다.
- 구현은 GUI만의 변경이 아니다. RCA의 단계 계측, 공통 LLM/Worker의 호출·저장 기록, JC 완료 상태, Backend 조회 및 GUI 조립을 함께 확인한다. 제품 결과의 불변 hash와 저장·공개 소유권은 유지한다. 데이터 의미는 [04 시간 진단](../common/04_Agent_동작_판단_명세서.md#rca-종료-후-시간-진단--개발-목표), 종료/저장 경계는 [14 실행 계측](../common/14_모듈간_호출과_공통실행_계약.md#rca-종료-후-시간-계측--개발-목표), 표시와 화면은 [07](../frontend/07_프론트엔드_개발명세서.md#rca-종료-후-시간-진단-표시--개발-목표)·[08](../frontend/08_GUI_화면설계서.md#종료된-rca의-시간-진단--개발-목표)을 따른다.

시간 진단은 아래 T1~T3의 별도 구현 단위로 진행한다. T1에서 기존 실행/진단 저장·조회 경로와 누락 구간을 확인하고 최소 추가 계약을 확정한다. 특히 메모리 evidence만 남는 실패 경로, 결과 저장 완료 후에야 알 수 있는 저장/JC 완료 시간을 어디서 보존·조회할지 확정해야 한다. T3에서는 [05 시간 검수](../05_테스트_검수_기준서.md#rca-종료-후-시간-진단-검수--개발-목표)까지 확인한다. 계측 추가를 실제 속도 개선이나 모든 장애에서 진단 저장이 보장된다는 주장으로 바꾸지 않는다.

### 데이터 계약과 버전 전환

현재 1.2와 구별한 제안 버전은 Runbook 1.3, 평가 `schema_version=3`, `rubric_version=3`, 검토 응답 `review_schema_version=2`다. 현재 지원 버전과 구분하고 실제 개발 첫 단계에서 [04 결과 계약](../common/04_Agent_동작_판단_명세서.md), [14 실행 계약](../common/14_모듈간_호출과_공통실행_계약.md)에 필드/enum/한도를 확정한다. 기존 schema 1/2·rubric 1/2와 구형 결과를 계속 읽는다. DB 컬럼/새 테이블 필요성은 기존 evidence/result JSON으로 표현 가능한지 먼저 확인하며 이 설계로 migration을 전제하지 않는다. 최상위 `result_schema_version=1.1`은 기존 필드의 의미·필수성을 보존하는 범위에서 유지한다. 바뀌는 경우에는 외부 결과 버전도 별도 전환한다. 평가 필드 없는 구 결과는 기존대로 읽고, 알 수 없는 버전은 미지원으로 표시하며 정상 상태를 추정하지 않는다.

### 검증 방법과 평가의 불확실성

기존 `test_synthesis_context`·`RcaNarrative.test`의 사건 장치 선택/구 요약 검사와 `test_rca_failure_facts`, `test_rca_llm_roles`, `test_rca_combined_policy`, `test_rca_rule_selection`, `test_rca_budget_allocation`, `test_rca_validation_details`, `test_runbook_contract` 및 관련 소비자/E2E 테스트에 사례를 연결한다. `test_rca_failure_facts`의 호출 기대값은 최신 main·profile의 구 경로 회귀로만 사용한다. `test_rca_clear_report`의 피드백 채택·첫 선택 조회 기대값도 구 모드에 한정하며 새 모드는 독립된 fixture로 검사한다. 새 루프는 계획에 따른 실제 호출을 검증하며 총 호출 수를 3회로 고정하지 않는다. 사실 보존 때문에 추가 조회·모델 호출이 생기지 않는 성질을 양 경로에서 검사한다. 구 결과 읽기 기대값을 일괄 새 동작으로 바꾸지 않는다. 실행 정책의 의도된 전환·퇴역은 별도 fixture로 검증한다. 공통/Go 계약 변경은 양 Worker·JC/Backend·Ops 소비를, GUI는 정상·실패·빈 결과·구 버전을 검사한다.

최소 재생은 두 방식이다. **검토자 단독:** 동일 증거의 적절/과장 초안을 비교한다. **전체 루프:** 실제 `workflow.run()`과 공통 LLM accounting을 사용하고 조회 도구명·전체 인자를 고정 응답과 대조한다. 전체 페이지·job/attempt·revision·원문 연결이 없으면 부분 재생이며 운영 정확도 증거가 아니다. 합성 사례의 시각/UUID를 운영 원본 정답으로 대체하지 않는다.

실제 모델 비교 전에 기대 행동·금지 주장·중대한 오류·반복 수를 고정한다. 원인 미확정이 타당한 사례, 정상→오류 시간 순서와 동시 상충, 9번째 줄의 반대 근거, 생산자 시각 없음, 같은 ID의 다른 발췌를 포함한다. 같은 모델 계열의 독립 호출도 같은 오해를 반복할 수 있으며 refs가 있다는 사실은 의미 정확도를 증명하지 않는다.

기록은 코드/프롬프트/rubric/모델·설정/Runbook/profile 버전, 원본·실제 요청·초안 hash, 기대/실제 판정, 호출·시간·usage·잘림·생략·부분 채택이다. 해석만 남은 사례, 해석/분석 모두 소실된 사례와 최종 반영을 구분한다. 전송하지 않은 자료를 읽었다고 표시하지 않는다. 보수적 추정·미보고는 실측과 분리하고 비밀값·거절 원문 전체를 저장하지 않는다.

**활성화 차단 조건:** 검수 사례에서 근거 없는 목적 달성/원인 확정, 필요한 조회 누락, 조회 scope 우회, 원본/최종 검토 연결 손실, 잘림 은폐가 재현되면 활성화하지 않는다. 의미 평가가 흔들리면 성공 기준을 낮추지 않고 기준/입력을 보완한다. 사람 간 합의가 없는 사례는 미확정으로 남기고 자동 종료의 정답 사례에서 구분한다. 새 수정 경로는 오류 수정 효과와 비용을 함께 비교하며 작성 성공률만으로 채택하지 않는다.

불필요한 조회·부당한 수정·잘못된 D 선택·과장 통과·미달 종료·판단 변동을 사례별로 센다. 이는 RCA 점수가 아니라 개발 검수 결과다. 실제 모델 평가, fixture, CI, 배포 후 확인을 각각 기록한다. 문서 정리만으로 어느 항목도 통과로 바꾸지 않는다.

## 변경하지 않는 판단·데이터 경계

현재 실행 설명은 [RCA README](../../../rcca-agent/README.md), 결과 필드·구 버전 호환은 [04 공통 판단](../common/04_Agent_동작_판단_명세서.md#81-rca-평가-분리-결과-확장)이 소유한다. 아래 조건은 구현 교체 여부와 관계없이 지킨다. 입력·참조·부분 채택·예약은 R02, 평가·계획은 R03/R04, 수정은 R08, 종료는 R09, 최종 자료는 R11의 상세 규칙을 따른다.

### 평가 분리 설계·개발

| 축 | 담당·의미 | 혼동하면 안 되는 것 |
|---|---|---|
| 수집 상태 | 코드: 성공/빈 결과/부분/실패/미실행 | 조회 성공은 필요한 관측 확보나 의미 검증이 아님 |
| 증거 상태 | 코드의 명확한 검사 + LLM 해석: 사실/추론/미확정 | 문자열 불일치는 다른 장비의 증명도, 오타 추정은 동일 장비의 증명도 아님 |
| 분석 품질 | 코드 구조/참조 검사 + 독립 LLM 검토 | 검토 완료·acceptable은 원인 확정/복구 완료가 아님 |

- Incident snapshot→JC claim→Worker 실행·저장→JC 공개 소유권과 scope/기간/revision·hash·lease/취소/원격 불명·idempotency를 보존한다. GUI 직접 Worker 실행은 없다. 작업 성공·판단 가능 범위·모델 채택·보고서 상태를 구분한다.
- Runbook의 검색 일치/순위는 원인 확률이나 적용 확정이 아니다. 오류 namespace와 실제 적용 여부를 구분하고 본문/revision/출처·확장 이유를 보존한다. 일반 조사/fallback 지침은 관측이나 원인 확정 근거가 아니다. 정책 적용/혼합/미설정 상태를 구분하고 과거 결과에 새 적용 상태를 추정하지 않는다. 저장소 파일과 실제 발행본을 구분하며 변경은 새 revision으로 발행한다.
- Fleet의 보고와 현재 상태는 다르다. 생산자 시각 0·로그 기록 시각을 발생/회복 시각으로 승격하지 않는다. 재고 일치는 연결 후보이며 독립 신원 검증이 아니다. GPU 재고로 NVSwitch 신원을 대신하거나 같은 노드의 GPU/Pod만으로 업무 피해를 확정하지 않는다. GPU 노드 RCA에 작업 연결을 일괄 필수화하지 않으며 같은 DCGM field의 생산자들을 독립 근거로 중복 가산하거나 `fact_eligible`을 일괄 해제하지 않는다.
