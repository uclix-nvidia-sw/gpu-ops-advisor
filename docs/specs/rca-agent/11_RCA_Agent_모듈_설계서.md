# 11. RCA Agent 실행 계약과 평가 분리 설계·개발

## 이번 개발 기준

**작업: Runbook 기반 검토·계획과 필요한 증거의 반복 수집·재분석. 상태: 설계, 미구현.** 코드 비교 기준은 `2994570`(2026-10-19 조회한 main, PR #152 병합 포함)다. 실제 실행 설명은 [RCA README](../../../rcca-agent/README.md), 실행한 검증의 범위는 [Agent QA](../../../agents/QA.md)가 소유한다. 이 문서는 이번에 구현할 기준과 유지할 계약을 정의하며 배포 완료를 뜻하지 않는다.

목표는 **부족한 판단을 어떤 증거로 보완할지 설명하고, 그 계획대로 조사·수정·종료하는 RCA**다. 현재는 `model_assessment()`가 선택 followup 설명을 제외하고 `select_followup()`도 필수 링크 중심으로 후보를 줄인다. 검토자는 D의 의미를 충분히 받지 못하며, 구체적 오해를 발견해도 동일 증거 재작성 제한 때문에 수정할 수 없다. 이 세 부분을 연결해서 고친다.

- **유지:** 통합 작성 LLM → 독립 검토 LLM → 종료 후 보고서 LLM, 코드의 쿼리 생성, 원본·revision·hash 보존, 조회 권한·공유 예산·취소·JC 공개, 발행 revision과 과거 결과의 추적·읽기.
- **변경:** 선택 D 정보 준비, 기준별 부족 내용과 다음 계획, optional 전면 제외와 고정 수집 회차 상한 제거, 기존 Runbook 실행 규칙의 대체·폐기 검토, 동일 증거에 대한 제한된 의미 수정, 회차/수정/종료의 GUI 근거 연결.
- **제외:** 평가 점수·통과 점수, Ops 개편, 자유로운 쿼리 생성, Runbook 무조건 순회, 새 수집원, 총예산 일괄 증액, 자동 하드웨어 조치. 기존 O계열의 공통 D 사용은 호환 유지 대상이다.

**기준선과 목표 설계를 구분한다.** #152 병합은 현재 코드 비교의 출발점이지 그 Runbook 계약·보고서 구성을 반드시 유지한다는 결정이 아니다. 합의한 조사 흐름에 맞지 않는 기존 Runbook 구조·규칙·코드 경로는 대체하거나 폐기한다. 과거 발행본·원본·결과를 보존하는 것과 구 실행 정책을 영구 유지하는 것은 별개다. 전환 기준은 [Runbook 정책 전환](#runbook-정책-전환과-종료-조건)에 둔다.

**개발 순서:** 아래 요구사항 표 → 전체 워크플로우 → 해당 상세 규칙 → 단계별 구현/검수 순서로 읽는다. 요구사항 ID를 구현·테스트·PR 설명에 함께 사용한다. 같은 사실은 한 곳에서 정의하며 과거 F 번호의 별도 실행 순서는 사용하지 않는다.

**방향의 타당성과 성공 여부를 구분한다.** 현재 빠져 있는 ‘부족 기준→D 의미→실행→재평가’ 연결을 만드는 방향은 문제에 맞는다. 그러나 입력 예산과 LLM 평가 정확도는 아직 입증되지 않았다. 아래 단계의 확인 조건을 만족해야 새 정책을 활성화한다. 기준을 낮추거나 사례를 빼서 검토 통과율을 높이지 않는다.

## Runbook 기반 검토·계획과 RCA 반복 설계

아래 상세 규칙은 R01~R12의 구현 기준이다. 현행 동작과의 차이는 요구사항 표에, 실제 유지 계약은 뒤의 현행 계약 절에 모았다.

### 전체 워크플로우와 호출 경계

```text
사건 접수 → Runbook 선택·revision 고정
    • 조사 목적·필수 기준·기본 D·선택 D 확인
        ↓
기본 D 조회 [코드]
    • 공통 binding으로 쿼리 구성·대상·기간 적용
    • 원본·수집 상태·명확한 기초 검증 결과 보존
        ↓
┌──────────────── RCA 조사 루프 ────────────────┐
│ ① 증거 해석·RCA 분석 [작성 LLM]              │
│    현재 증거 → 사실·후보·반대 근거·한계        │
│          ↓                                   │
│ ② 검토·계획 입력 준비 [코드]                │
│    초안·원본 근거·수집 제한·평가 기준          │
│    + 선택 D의 의미·한계·인자·실행 이력        │
│    + 실제 입력 범위·예산 검사                 │
│          ↓                                   │
│ ③ 분석 검토·다음 계획 [독립 검토 LLM]       │
│    기준별 판단·부족 내용·수정/조회/종료 제안   │
│          ↓                                   │
│ ④ 다음 행동 검증·분기 [코드]                │
│    ├─ 수정: 동일 증거 + 구체적 지적 → ①     │
│    │        같은 수집 회차의 수정·재검토      │
│    ├─ 수집: 실행 가능 → 선택 D 조회          │
│    │        기존 + 새 증거 → 다음 회차 ①    │
│    ├─ 실행 불가: 사유 보존                   │
│    │        잔여 계획 실행 / 조건부 수정 / 종료│
│    └─ 종료: 목적 달성 / 보완 불가 / 제한 도달│
└──────────────────┬───────────────────────────┘
                   ↓
최종 RCA 자료·채택 상태·미확정 사항·종료 이유 고정
                   ↓
보고서 LLM: 고정된 자료를 읽기 좋은 문장으로 구성
                   ↓
기존 저장·JC 공개 → GUI 실제 호출 흐름과 판단 근거 표시
```

**고정된 마지막 수집 회차는 없다.** 조건이 부족하고 현재 Runbook 안에 도움이 되는 실행 가능한 D가 있으면 위 루프를 계속한다. 기본 D→선택 D 한 번으로 끝내지 않으며 회차 수 자체를 종료 조건으로 쓰지 않는다.

추가 조회는 검토 LLM의 하위 도구 호출이 아니라 워크플로우가 실행하는 **다음 수집 회차**다. 코드는 입력/계획 검증을 위해 별도 LLM을 부르지 않는다. 형식 복구 호출과 실제 의미 재검토, 코드 기록을 구별한다. 검토 입력 부족이나 모델 실패를 ‘검토 통과’ 또는 ‘추가 자료 불필요’로 처리하지 않는다.

### D 정보 준비와 컨텍스트 계약

준비 위치는 `evaluate_analysis()`의 검토 입력 조립 직전이다. 전체 설명은 Runbook 선택 뒤 한 번 해석·고정해 재사용할 수 있지만, 실제 검토 요청을 만들 때 조회 결과·부족 조건·미실행 계획·실행 가능 상태를 갱신한다. 수집 회차 잔여 횟수는 제공하지 않는다. 예산·deadline 등으로 collect가 실제 불가능하면 allowed_actions와 사유를 제공하고, 실행 계획과 보고서에 남길 추가 확인을 구분한다. 예약량 산정에도 같은 결정용 카탈로그를 반영해, 작성 뒤 예상 밖의 검토 입력 증가가 생기지 않게 한다.

공통 profile의 각 `queries[D].decision_support`를 선택용 설명의 추가 필드 후보로 둔다. 필드 누락이 기존 D 실행/O계열을 실패시키지 않도록 하되, 새 검토·계획 모드에서 설명 없는 D를 모델이 추정해서 추천하게 하지 않는다. producer별 의미·단위·scope·필수 인자는 검증된 binding에서 가져와 일반 설명을 제한한다. 설명과 binding이 충돌하면 해당 D는 `definition_incomplete`로 보이고 자동 실행 후보에서 제외한다. 문서 설명은 관측 사실이 아니다.

| 검토용 `query_catalog` 항목 제안 | 의미·출처 |
|---|---|
| `query_id`, `definition_revision`, `binding_id/revision`, `catalog_entry_hash` | 고정한 D 설명·실행 계약의 출처. 새 schema에서 이름 확정 |
| `observes`, `can_inform`, `cannot_establish` | 무엇을 관측하고 어떤 질문에 도움을 주며 무엇은 확정할 수 없는지. 검토된 공통 정의 |
| `runbook_refs`, `purpose`, `criterion_links` | 이 사건에서 해당 D를 선택지로 둔 이유. Runbook revision과 기준 key 연결 |
| `requirements`, `availability` | 필요 대상·시간·식별 정보, binding 가용 여부와 미확정/차단 사유. 알 수 없는 가용성을 가능으로 단정하지 않음 |
| `history` | 동일 요청의 실행 여부, evidence refs, 성공/빈 결과/부분/실패/미실행 구분, 이미 얻은 정보 |

카탈로그는 현재 선택한 Runbook들의 기본/선택 D를 ID와 definition revision별로 중복 제거한다. 기본 D의 설명은 증거 의미를 이해할 정도로 재사용하고, **모든 선택 D의 결정용 설명**을 제공한다. 긴 PromQL/LogQL, 인증·URL·데이터 소스 상세, 전체 인벤토리를 반복해서 붙이지 않는다. Raw 실행 설정은 코드만 사용한다. `can_inform`은 관련 가능성이지 원인 증명이나 조회 성공 보장이 아니다. `criterion_links`는 관련성 안내·정렬에 쓰되 연결이 없다는 이유만으로 후보를 숨기지 않는다. 의미·한계·필수 인자·이력은 짧은 구조로 제공하고 중복과 부가 설명부터 제거한다. 실제 collect 불가 상태에는 계획 전용 설명을 생략할 수 있으나 기존 증거의 D 의미·한계와 평가 기준은 유지하고 생략 이유를 기록한다. 새 경로는 GOAL_REVIEW의 D02/D44 개별 설명을 검증된 공통 정의로 대체하며 정의 없이 하드코딩만 먼저 삭제하지 않는다.

모델에 전달된 카탈로그 hash·각 항목 revision·정의 누락 목록·원본/전달 바이트·근거 refs·생략 범위·전체 요청 hash를 저장한다. 카탈로그 refs는 `input_evidence_refs`/`observation_refs`와 별도 영역이며 원인 후보의 지지 근거로 인용할 수 없다. 작성자의 해석과 Runbook 지침도 독립 관측으로 승격하지 않는다.

컨텍스트의 충분성은 아직 입증되지 않았다. 다음 순서로 판단한다.

1. 실제 Runbook별 선택 D 수, 설명 크기, 초안·원본 근거 크기 분포를 측정한다. 단일 오류뿐 아니라 다중 Runbook·많은 증거·긴 한국어 응답 사례를 포함한다.
2. 기존 모델/출력 cap/총예산/예약 보호를 유지한 전체 요청으로 사전 검사한다. UTF-8 바이트 한도와 토큰 예산을 별도로 기록하고, 현재 보수적 차감값을 실제 토큰과 동일시하지 않는다.
3. 중복 설명 제거는 허용하되 판단에 필요한 한계·반대 근거·선택 D를 조용히 삭제하지 않는다. 현재 bounded evidence 선택은 유지하고 무엇을 읽지 못했는지 드러낸다.
4. 필요한 입력과 검토 출력 여유를 확보할 수 없으면 `review_context_insufficient` 등 명시적 사유로 검토/계획 미완료 처리한다. 이번 첫 구현에서 자동 분할 검토나 별도 계획 호출은 추가하지 않는다. 기존에 검토되던 사건이 카탈로그 추가 때문에 미해결로 바뀌는 회귀도 측정하고 적용을 보류한다. 생략 이력만으로 의미 손실이 해소됐다고 판단하지 않는다. 불충분 사례가 확인되면 호출 분리와 비용을 재비교한 뒤 설계를 갱신한다.

### 평가 기준과 부족한 내용의 표현

**점수·합계·가중치·통과 점수는 사용하지 않는다.** 공통 품질 기준과 Runbook의 조사 목적 기준을 구분한다. 자료를 적게 모았어도 제한된 결론이 타당할 수 있고, 문장이 신중해도 조사 목적에 필요한 관측이 없으면 목적은 미달이다. 검토자는 두 축을 각각 답한다.

사람에게 설명할 다섯 관점과 현재 6개 rubric의 연결은 다음과 같다. 새 형식에서 항목을 합쳐 세부 검사를 잃지 않으며, 현재 key를 보존해 비교할 수 있도록 한다.

| 설명 관점 | 기존 기준/관련 판단 | 반드시 설명할 내용 |
|---|---|---|
| 사건 파악 | `identity_time` + Runbook 코드 기준 | 오류 보고·대상·시각의 연결 범위, 보고 시각과 실제 발생 시각의 차이 |
| 목적에 필요한 증거 | `evidence_use` + Runbook 필수 기준 | 목적에 필요한 관측, 확보/미확보 내역, 확보된 중요한 증거 활용 여부 |
| 분석의 타당성 | `grounding` | 어떤 주장에 어떤 근거가 연결되고 어디서 비약했는지 |
| 반대 근거와 대안 | `contradictions`, `alternatives` | 중요한 반대 관측·다른 설명. 미확정 자체를 모순이라고 하지 않음 |
| 판단 범위 | `limitations` | 관측 사실·추론·미확정·수집 제한의 구분 |

각 품질 기준과 Runbook의 의미 기준에 `status`, `reason`, `evidence_refs`, `confirmed`, `missing`, `impact`, `resolution`, `completion_condition`을 제안한다. `missing`은 부족 없음이면 빈 목록이며, `resolution`은 수정/수집/수동 확인/보완 불가를 구분한다. 실제 코드 필드명·한도는 04 결과 계약에서 확정한다.

- 사용자 상태는 충족/보완 필요/판단 불가이며 `not_applicable`은 기존 호환과 목적상 적용 제외를 위해 별도로 유지한다. 적용 제외에는 이유가 필수이고 자동 충족으로 변환하지 않는다. 새 Runbook의 필수 기준에는 적용 제외를 허용하지 않는다.
- ‘충족’은 전체 데이터 확보나 실제 원인 확정이 아니라 명시된 조건을 해당 근거 범위에서 만족했다는 뜻이다. 코드가 검사하는 식별자·시각·필수 자료 조건을 LLM이 무시하거나 변경할 수 없다.
- 작성 LLM의 `criterion_assessments`는 제안이다. 새 정책에서 검토자는 원본을 보고 별도 평가하고, `finish_assessment()`는 검증된 검토 평가와 코드 기준을 결합한다. 작성자 자기평가를 검토의 근거로 중복 가산하지 않는다.
- 근거가 없는 주장을 철회하는 것은 수정이고, 빠진 관측을 얻는 것은 수집이다. 문장을 신중하게 바꾸는 것만으로 미충족된 필수 관측을 충족시킬 수 없다.
- 오류 보고 식별이 목적이면 그 목적의 조건만 검사한다. 물리 원인이나 회복 확인을 목적으로 추가하려면 Runbook 목적·조건을 새 revision으로 명시해야 한다. ‘D09로 충분’은 모든 원인 조사에 대한 결론이 아니다.

### 검토·계획 응답과 실행 검증

새 응답은 기존 검토 결과에 아래 구조를 추가하는 방식으로 설계한다. 이는 필드 예시이며 현행 validator가 이미 허용한다는 뜻이 아니다.

```text
review_schema_version / rubric_version
analysis_id / input_hash / catalog_hash
criteria                      기준별 품질 평가
objective_assessments         Runbook revision별 의미 기준 평가
issues                        claim ID·근거·수정 요구·기존 증거만으로 수정 가능한지
next_action                   revise | collect | finish
collection_plan[]
    query_id / catalog_entry_hash
    criterion_keys / issue_ids
    reason / expected_effect
    result_usage              관측·미관측·불완전 결과를 각각 어떻게 사용할지
    request_scope_ref         고정된 대상·기간 참조
    repeat_reason             동일 요청 재조회 시 필수
finish                        proposed_reason / unresolved_criteria / limits
```

`next_action=collect`이면 기존 주장 수정 요구를 함께 보낼 수 있다. 추가 자료를 받아 재분석할 때 같이 수정하므로 별도의 선행 수정 호출을 강제하지 않는다. 의미 있는 수집 없이 해결할 수 있는 과장·누락만 있으면 `revise`를 선택한다. 조회 목록을 비운 채 collect를 반환하거나, 수정 지적 없이 revise를 반환하거나, 필수 기준 미달인데 goal_achieved를 제안하면 구조/일관성 검증에서 거절한다.

최종 실행 기록은 모델의 제안과 분리한다. `plan_id`, review evidence ID, 대상 초안, 각 D의 `proposed/accepted/rejected/executed` 상태, 실제 evidence refs, 불가 사유를 남긴다. 모델이 종료를 제안해도 목적 달성 여부는 같은 초안의 유효 검토·필수 기준·차단 조건을 코드가 다시 확인한다. 존재하지 않는 인자나 대상을 모델이 생성해 쿼리 범위를 넓힐 수 없다.

| 판단 | 주체와 경계 |
|---|---|
| 어떤 조건이 부족하며 왜 중요한가 | 검토 LLM, 원본 근거와 조건을 명시 |
| 수정으로 해결되는가, 추가 관측이 필요한가 | 검토 LLM, 둘 다 필요하면 collect에 수정 요구 포함 |
| 어떤 선택 D가 도움을 주는가 | 검토 LLM, 제공된 Runbook 후보와 D 정의 안에서만 제안 |
| 같은 요청을 다시 할 이유가 있는가 | 검토 LLM이 이전 실패/부분 결과와 이유 설명. 코드는 이력 제공 |
| ID·revision·참조·요청 형식·허용 scope·명시 필수 전제 | 코드 검증. 의미 평가를 문자열 일치 점수로 대체하지 않음 |
| 조회·토큰·시간·의미 수정 한도(고정 수집 회차 제한 없음) | 코드 통제. 사유가 타당해도 한도를 늘리지 않음 |

부분 실행 가능한 계획은 허용된 항목만 실행하고 거절 사유를 다음 회차의 검토 입력에 포함한다. 모든 항목이 거절됐다고 다른 D를 코드가 임의 대체하지 않는다. 수집 항목이 전부 거절되어도 검토 LLM이 기존 증거만으로 가능하다고 명시한 구체적 수정 요구가 있고, R08의 수정·재검토 예산과 횟수가 남으면 revise로 전환한다. 코드가 새 수정 방안을 추론하지 않는다. 이 조건도 없으면 불가 사유와 남은 조건을 기록해 종료하며, 같은 자료로 계획 재작성 LLM을 반복 호출하지 않는다. 실제 조회 실패도 분석 품질 충족이나 ‘보완 불필요’로 바꾸지 않는다.

### 분석 수정과 추가 수집의 별도 반복 계약

| 항목 | 분석 수정 반복 | 추가 수집 RCA 반복 |
|---|---|---|
| 시작 조건 | 유효한 검토의 구체적 issue·근거·수정 요구 | 부족한 조건과 이를 보완할 허용 선택 D 계획 |
| 증거 집합 | 동일 source version | 기존 원본 + 새 조회 원본·진단 |
| 작성 요청 | 원본 근거·이전 초안·관련 검토 지적 | 누적 근거·수집 결과·관련 검토 지적 |
| 결과 | 새 `analysis_id`, parent 연결, 같은 회차의 수정본 | 새 수집 회차의 분석본 |
| 후속 검토 | 수정본에 대한 독립 검토 필수 | 재분석본에 대한 독립 검토 필수 |
| 실패 시 | 원래 지적 보존, 문제 주장 보류, 미검토 표시 | 조회 실패/동일 응답/새 관측 유무를 구분해 제한 종료 또는 결과 검토 |

**새 정책은 고정 수집 회차 상한을 제거한다.** 기본 수집 이후에도 미충족 조건을 보완할 D를 검토 LLM이 요청하면 현재 Runbook의 허용 범위 안에서 수집·누적 재분석·독립 검토를 반복한다. 조건을 충족하면 즉시 종료하고, 모든 D를 기계적으로 소진하지 않는다. 조건이 부족하면 회차 수만으로 유효 요청을 버리지 않는다.

- **배치와 회차를 구분한다.** 한 수집 배치 최대 3개는 실행 묶음 크기이며 전체 보완 기회를 1회로 제한하지 않는다. 검토 응답의 전체 요청 목록은 현재 Runbook의 유효 후보 집합을 표현할 수 있어야 하며 응답 validator가 3개만 허용해 요청을 누락시키지 않는다. 실제 목록 길이·입력/출력 상한은 S1에서 확정하고 S2에서 검사한다. 남은 요청은 pending으로 보존하고 이후 검토에서 유지·취소·수정 이유를 명시한다. 목적 달성, 새 근거에 따른 불필요 판단, 실행 불가 외에는 조용히 취소하지 않는다.
- **누적 분석:** 한 배치에서 새 관측을 얻으면 기존+새 증거로 재분석한다. 새 관측 없이 실패/동일 결과만 나온 경우 작성 LLM을 다시 부르지 않고, 같은 검토에서 이미 승인한 독립적인 pending 요청이 있으면 그 요청을 실행한다. 새 자료에 의존하는 요청은 선행 조건을 확인한다. 한 D의 실패가 다른 유효 요청의 중단 근거가 되지 않는다.
- **진행 없는 반복 차단:** 요청 키는 D·binding/revision·대상·기간·실행 인자를 포함한다. 기존 성공 결과의 재사용, 실패/부분 결과 재조회, 새로운 요청을 구분한다. 재조회에는 검토자의 이유와 예상되는 새 정보가 필요하다. 표현·UUID만 다른 같은 요청/같은 결과는 진행으로 세지 않으며, 반복 차단은 해당 요청에 적용한다. 실행 가능한 다른 계획과 유효 수정도 없을 때만 no_new_evidence 등으로 종료한다. HTTP 재시도·취소·deadline 규칙을 우회하지 않는다.
- **의미 수정:** 동일 증거의 의미 수정은 attempt 전체 최대 1회를 별도로 유지한다. 이는 수집 회차 상한이 아니다. 수집과 수정이 모두 필요하면 수집 후 재분석에 함께 반영해 선행 수정 호출을 줄인다. 수정 한도 소진만으로 도움이 되는 새 D 수집을 막지 않는다.
- **실행 예산:** 조회·토큰·deadline·전송 제한은 유지하되 회차 상한을 다른 고정 호출 수로 대체하지 않는다. 새 수집 전에 후속 작성·검토와 보고서 작성 여유를 같은 accounting으로 확인한다. 실제 요청 크기·설정 cap·기존 예약 보호를 사용하고 임의 토큰 비율로 배정하지 않는다. 아직 생성되지 않은 초안/응답 비용은 추정·실측을 구분하며 사전 검사를 완료 보장으로 표현하지 않는다. 수정도 작성+재검토 비용을 함께 검사한다. 한도를 넘으면 필요한 미실행 D를 기록해 실행 제한으로 종료한다. 보고서 호출 실패 시 기존 고정 자료 기본 표시를 유지한다.

이 계약은 무제한 호출이나 모든 원천의 수집 성공을 보장하지 않는다. 실행 가능한 요청을 회차 수로 막지 않는다는 뜻이다. S2/V22/V25에서 Runbook의 필요한 D를 연속 수집하는 전체 경로가 현 예산으로 가능한지 확인한다. 필요한 조회가 반복해서 예산으로 중단되면 새 흐름의 완료 조건을 충족한 것으로 보고하지 않고 배치·입력·예약 설계를 재검토한다. 임의 증액이나 실패 사례 제외로 통과시키지 않는다.

`source_version`, `analysis_id`, `review_id`, `collection_round`, `revision_no`, `parent_analysis_id`, `trigger`를 분리한다. 동일 증거가 돌아왔는데 UUID나 입력 뷰만 바뀐 경우 새 수집 근거로 재작성을 허용하지 않는다. 검토 issue가 수정 경로의 명시적 예외이며, HTTP 오류·JSON 실패·출력 잘림은 의미 수정 권한을 만들지 않는다. 기존 형식 복구 정책과 이 의미 수정 1회는 별도 횟수로 저장한다.

재조회는 같은 ID를 다시 실행할 수 있으므로 `collected.update()`로 과거 query 결과를 덮어쓰지 않고 요청별 evidence를 append/merge한다. 원본과 모델 입력 뷰는 분리하고 새 관측으로 hash를 속이지 않는다. 새 관측이 없고 수정 예외도 없으면 이전 분석을 재사용한다. `remaining`은 D ID가 collected에 있다는 이유만으로 제거하지 않고, 요청별 결과·미실행 계획·유효 재조회 사유를 구분한다. 누적 observation_refs와 hash는 실제 원본에 연결하고 실패 진단을 원인 지지 관측으로 승격하지 않는다. 수집 상태만 달라졌다면 그 사실과 근거를 새 결정 기록에 남기고 이전 검토의 읽은 범위를 확장해 표시하지 않는다.

수정한 초안에 이전 검토 통과를 승계하지 않는다. 수정본 검토가 실패/생략되면 해당 초안은 미검토이며, 이전에 지적된 주장을 정상 결론으로 복구하지 않는다. 기초 형식/참조 검사 통과를 의미 품질 통과로 표시하지 않는다. 후속 조회를 더 해도 같은 결론일 수 있고, 반대 근거가 나와 가설을 철회할 수도 있다.

### Runbook 정책 전환과 종료 조건

#152의 Runbook 1.2는 생산자·컴포넌트·비정상 상태·선택적 reason으로 오류 보고 목표를 판별하는 현재 계약이다. 새 검토·계획 계약은 **`gpu-rca-runbook/1.3` 제안**으로 분리한다. 단, 구 JSON을 그대로 복사하고 planning_mode만 추가하는 것을 구현 목표로 삼지 않는다. Runbook은 조사 목적·판단 기준·기본/선택 D·기준과 D의 관계·명시적 실행 전제·출처/적용 조건을 제공하고, 검토 LLM은 그 안에서 보완 필요성과 다음 D를 판단한다. D 의미·조회 구현은 공통 정의와 binding에서 제공한다.

| 현행 구조/행동 | 새 방향에 따른 처리 |
|---|---|
| 1.1 오류 코드 / 1.2 component·health·reason 적용 조건 | 검증 가능한 사건 구분 근거는 활용하되 새 목적 구조에 맞춰 재설계 가능. 보고 사실을 실제 고장·회복으로 승격하지 않음 |
| identify_error_report 고정 목적 | 사건별 실제 조사 목적·충족 기준으로 검토. 오류 보고 확인만 필요한 경우에만 유지하며 부족한 분석을 종료하려고 목적을 낮추지 않음 |
| required/basic D와 optional D | 시작 근거와 보완 후보 구분은 유지. optional 제외와 고정 2회차 종료는 새 실행 경로에서 제거 |
| selection.missing_any / exploratory_llm | 새 검토·계획 LLM과 중복되는 의미 판단/별도 선택 호출은 대체·제거. 이 규칙을 그대로 보존하기 위해 새 흐름을 제한하지 않음 |
| requires_all | 권한·대상·명시적 선행 자료 같은 실행 전제만 코드 검증으로 유지. 의미상 필요한지는 검토 기준으로 옮김 |
| operator_guidance와 보고서의 고정 절차 삽입 | 참고 지침이며 조사 증거나 실행 지시가 아님. 보고서 역할에 맞는 적용성·조건·출처만 전달하며 현재의 자동 삽입·섹션 구성은 재설계/삭제 가능 |
| 기존 Runbook 파일·실행 경로 | 일괄 보존을 전제하지 않음. 항목별 유지/재작성/대체/폐기를 결정하고 전환 완료한 중복 실행 코드·저작 파일은 소비자 확인 후 제거 가능 |

S1에서 대상 Runbook별 목적, 기본/선택 D, 기준, 적용 조건의 전환 대응표를 만든다. 1.3의 필드 후보는 `decision_policy.planning_mode=review_guided`, `observation_plan[].execution_preconditions.requires_all`이며 정확한 구조는 Python/Go 공통 fixture와 함께 확정한다. 구 selection 의미 규칙과 새 계획을 동시에 실행하지 않는다. 1.0/1.1/1.2 발행본을 같은 revision에서 새 의미로 해석하거나 덮어쓰지 않는다.

전환은 새 구조 검증·읽기 지원→새 Runbook 작성/검수→새 revision 발행·선택 전환→구 정책 퇴역 순서다. 병행 지원은 전환 수단이며 영구 요구가 아니다. 전환 중 정책 혼합 처리·미전환 항목의 구 경로 또는 명시적 미지원 처리·되돌릴 대상 revision을 정하고, 완료 후 구 실행 경로의 제거 범위와 검수를 확정한다. 새 요청이 조용히 구 규칙으로 우회하지 않게 한다. 과거 결과가 참조하는 발행본·출처·hash와 조회 기능은 유지하며, 이번 문서 작업에서 DB/파일 삭제나 운영 발행을 수행하지 않는다.

선택 D의 `required=false`는 항상 실행해야 하는 조회가 아니라는 뜻이다. 새 정책에서는 도움 되는 선택 조회를 금지한다는 뜻으로 사용하지 않는다. `followup_links`는 어떤 기준과 관련되는지 알려주는 지침이며 필수/선택 여부로 모델 입력에서 링크를 삭제하지 않는다. 목적을 달성했고 중요한 품질 문제가 없으면 남은 선택 D를 소진하지 않고 종료한다.

| 종료 상태 | 필수 조건 | 사용자 설명 |
|---|---|---|
| 목적 달성 | 호환·적용 가능한 Runbook, 필수 코드/의미 기준 충족, 차단 없음, 같은 최종 초안 검토 통과 | 어떤 조건을 어떤 관측으로 충족했는지. 원인 확정 여부는 별도 |
| 보완 가능한 조회 없음 | 미달 기준과 모든 관련 선택지의 부적합/자료 부재/미지원 이유 기록 | 현재 Runbook과 확보 가능한 자료로 판단할 수 없는 내용 |
| 실행 제한 | 조회/모델 예산·deadline·입력 한도 또는 유효 수집이 없는 상태의 수정 한도 도달. 고정 회차 종료 없음 | 도움이 될 수 있는 계획이 남았는지와 왜 실행하지 못했는지 |
| 분석 미해결 | 모델/응답 검증 실패, 수정 실패 또는 검토 미완료 | 채택 가능한 사실과 미채택 분석, 실패 위치. 정상 검토로 표시하지 않음 |

기존 `goal_not_met`는 호환용으로 유지하되 새 결과에 `termination_detail`을 붙여 `no_helpful_query`, `definition_incomplete`, `request_unavailable`, `plan_rejected`, `review_context_insufficient`, `no_new_evidence` 등 구체적 원인을 제안한다. 최종 reason enum과 기존 STOP_REASONS 매핑은 04 결과 계약에서 확정하고 validator와 GUI를 함께 갱신한다. `insufficient_actionable` 같은 수집 gate가 존재해도 실제 계획이 실행되지 않았으면 이유를 같은 화면에서 연결한다. 단순히 ‘추가 조회 없음’만 표시하지 않는다.

현재 Runbook을 다 조회했다는 이유만으로 다른 Runbook을 자동 순회하지 않는다. 기존 unexpected-evidence 확장은 보존하되 새로운 관측 단서·오류 namespace·적용 조건과 선택 원문을 기록해야 한다. 초기 구현의 선택 카탈로그는 현재 선택된 지침에 한정한다. 여러 정책이 섞이거나 새로운 지침 집합의 적용을 확정할 수 없으면 목적 달성을 자동 승계하지 않고 한계를 남긴다. 조사 종료는 사건 해소나 복구 완료가 아니다.

### GUI와 보고서에 남길 근거

현재 개발용 RCA의 [RcaWorkflow](../../../frontend/src/components/RcaWorkflow.tsx), [RcaEvaluationTrace](../../../frontend/src/components/RcaEvaluationTrace.tsx), [RcaEvaluation](../../../frontend/src/components/RcaEvaluation.tsx)를 확장한다. 흐름을 감추지 않으면서 코드 기록을 LLM 호출처럼 보이지 않게 한다.

- ‘1회차 분석 → 검토 입력 준비 → 검토·계획 → 추가 조회 → 2회차 분석 → …’으로 실제 반복을 표시하고 최대 2회차 진행률을 쓰지 않는다. ‘1회차 분석 수정 1 → 수정본 검토’는 수집 회차와 구분한다.
- 입력 준비 상세는 D별 의미·한계·실행 가능 상태·기존 결과·실제 모델 전달 여부를 보여준다. 원문 전체가 아니라 선택용 정의를 읽었다면 그 범위를 표시한다.
- 기준별로 판단 조건·사용 근거·확인한 사실·부족 내용·영향·보완 방법을 보여준다. 6개 기존 rubric과 Runbook 목적 기준을 구분하고 점수는 표시하지 않는다.
- 각 계획은 ‘부족한 기준 → D가 제공할 관측 → 선택 이유 → 실행/대기/거절/취소 → 새 근거 → 후속 판단’으로 연결한다. 실행 배치와 전체 요청 목록을 구분하고 취소·남은 요청의 이유를 표시한다. 실패나 거절을 ‘필요 없음’으로 번역하지 않는다.
- 수정은 지적 대상과 이전/새 초안, 재검토 결과를 연결한다. 통신 실패·응답 형식 실패·의미 수정 필요·코드 보류·미검토를 구분한다. 실행 0회 기록을 추가 LLM 호출로 표시하지 않는다.
- 종료는 목적 달성/제한 종료와 원인 확정 여부를 분리한다. UUID·hash·원시 enum은 상세에 두고 기본 화면에는 사람이 이해할 수 있는 이유를 먼저 표시한다.
- 보고서 모델은 채택된 사실·한계·종료 이유를 설명한다. #152의 고정 지침을 무조건 붙이지 않고, 조사 결과에 적용 가능한 참고 설명/조건부 대응을 구분하며 새 조사·판단은 수행하지 않는다. 실행하지 않은 계획은 ‘수행 결과’가 아니라 ‘남은 확인’이다. 보고서 실패 시 동일 자료의 기본 표시를 유지한다.

### 데이터 계약과 버전 전환

현재 1.2와 구별한 제안 버전은 Runbook 1.3, 평가 `schema_version=3`, `rubric_version=3`, 검토 응답 `review_schema_version=2`다. 현재 지원 버전과 구분하고 실제 개발 첫 단계에서 [04 결과 계약](../common/04_Agent_동작_판단_명세서.md), [14 실행 계약](../common/14_모듈간_호출과_공통실행_계약.md)에 필드/enum/한도를 확정한다. 기존 schema 1/2·rubric 1/2와 구형 결과를 계속 읽는다. DB 컬럼/새 테이블 필요성은 기존 evidence/result JSON으로 표현 가능한지 먼저 확인하며 이 설계로 migration을 전제하지 않는다. 최상위 `result_schema_version=1.1`은 기존 필드의 의미·필수성을 보존하는 범위에서 유지한다. 바뀌는 경우에는 외부 결과 버전도 별도 전환한다. 평가 필드 없는 구 결과는 기존대로 읽고, 알 수 없는 버전은 미지원으로 표시하며 정상 상태를 추정하지 않는다.

### 검증 방법과 평가의 불확실성

기존 `test_rca_llm_roles`, `test_rca_combined_policy`, `test_rca_rule_selection`, `test_rca_budget_allocation`, `test_rca_validation_details`, `test_runbook_contract` 및 관련 소비자/E2E 테스트에 사례를 연결한다. 구 결과 읽기 기대값을 일괄 새 동작으로 바꾸지 않는다. 실행 정책의 의도된 전환·퇴역은 별도 fixture로 검증한다. 공통/Go 계약 변경은 양 Worker·JC/Backend·Ops 소비를, GUI는 정상·실패·빈 결과·구 버전을 검사한다.

최소 재생은 두 방식이다. **검토자 단독:** 동일 증거의 적절/과장 초안을 비교한다. **전체 루프:** 실제 `workflow.run()`과 공통 LLM accounting을 사용하고 조회 도구명·전체 인자를 고정 응답과 대조한다. 전체 페이지·job/attempt·revision·원문 연결이 없으면 부분 재생이며 운영 정확도 증거가 아니다. 합성 사례의 시각/UUID를 운영 원본 정답으로 대체하지 않는다.

실제 모델 비교 전에 기대 행동·금지 주장·중대한 오류·반복 수를 고정한다. 원인 미확정이 타당한 사례, 정상→오류 시간 순서와 동시 상충, 9번째 줄의 반대 근거, 생산자 시각 없음, 같은 ID의 다른 발췌를 포함한다. 같은 모델 계열의 독립 호출도 같은 오해를 반복할 수 있으며 refs가 있다는 사실은 의미 정확도를 증명하지 않는다.

기록은 코드/프롬프트/rubric/모델·설정/Runbook/profile 버전, 원본·실제 요청·초안 hash, 기대/실제 판정, 호출·시간·usage·잘림·생략·부분 채택이다. 해석만 남은 사례, 해석/분석 모두 소실된 사례와 최종 반영을 구분한다. 전송하지 않은 자료를 읽었다고 표시하지 않는다. 보수적 추정·미보고는 실측과 분리하고 비밀값·거절 원문 전체를 저장하지 않는다.

**활성화 차단 조건:** 검수 사례에서 근거 없는 목적 달성/원인 확정, 필요한 조회 누락, 조회 scope 우회, 원본/최종 검토 연결 손실, 잘림 은폐가 재현되면 활성화하지 않는다. 의미 평가가 흔들리면 성공 기준을 낮추지 않고 기준/입력을 보완한다. 사람 간 합의가 없는 사례는 미확정으로 남기고 자동 종료의 정답 사례에서 구분한다. 새 수정 경로는 오류 수정 효과와 비용을 함께 비교하며 작성 성공률만으로 채택하지 않는다.

불필요한 조회·부당한 수정·잘못된 D 선택·과장 통과·미달 종료·판단 변동을 사례별로 센다. 이는 RCA 점수가 아니라 개발 검수 결과다. 실제 모델 평가, fixture, CI, 배포 후 확인을 각각 기록한다. 문서 정리만으로 어느 항목도 통과로 바꾸지 않는다.

## 현행 계약과 유지 근거

아래는 `2994570`의 현재 동작과 판단 경계다. 이번 새 정책의 요구사항은 앞의 R01~R12이며, 아래의 현재 실행 구조를 전부 보존해야 한다는 뜻은 아니다. 대체/폐기 판단은 Runbook 전환 표를 따른다. 과거 개발 계획을 별도 실행 목록으로 유지하지 않는다.

### 평가 분리 설계·개발

| 축 | 담당·의미 | 혼동하면 안 되는 것 |
|---|---|---|
| 수집 상태 | 코드: 성공/빈 결과/부분/실패/미실행 | 조회 성공은 필요한 관측 확보나 의미 검증이 아님 |
| 증거 상태 | 코드의 명확한 검사 + LLM 해석: 사실/추론/미확정 | 문자열 불일치는 다른 장비의 증명도, 오타 추정은 동일 장비의 증명도 아님 |
| 분석 품질 | 코드 구조/참조 검사 + 독립 LLM 검토 | 검토 완료·acceptable은 원인 확정/복구 완료가 아님 |

Incident snapshot→JC claim→Worker 실행·저장→JC 공개 소유권을 유지한다. scope/기간/지식 revision·원문 hash·lease/취소/원격 불명·idempotency를 보존하고 GUI가 Worker를 직접 실행하지 않는다. 결과의 job 상태, 판단 가능 범위, 모델 채택, 보고서 구성 상태는 별개다.

Runbook 검색은 오류 namespace를 구분하는 결정적 관련도 검색이며 점수는 진단 확률이 아니다. `selected=applicable+pending`, 선택 진단과 실제 적용을 구분하고 본문/revision/출처를 보존한다. 일반 조사/내장 fallback은 원인 확정 지식이 아니며 관측으로 인용하지 않는다. 확장 시 새 지침 원문과 적용 이유를 연결한다.

Fleet의 보고된 오류와 현재 상태는 다르다. 생산자 시각 0·로그 기록 시각을 실제 발생 시각으로 승격하지 않는다. PCI/UUID 재고 일치는 보고된 연결 후보이지 독립 장치 검증이 아니다. GPU 재고를 NVSwitch 신원으로 대체하지 않는다. GPU–Pod가 같은 노드에 있다는 이유로 사용자/업무 피해를 확정하지 않고 GPU 노드 RCA에 작업 연결을 필수로 되살리지 않는다. 같은 DCGM field를 읽는 두 생산자를 독립 장애 근거로 중복 가산하지 않는다. `fact_eligible`를 일괄 풀지 않는다.

### 분석 품질 평가 척도 — rubric 1

과거 rubric 1은 grounding·identity_time·contradictions·alternatives·limitations·evidence_use의 6개 기준과 pass/needs_revision/undetermined/not_applicable을 사용한다. rubric 2는 목적에 맞게 적용 범위를 설명하며, 과거 판정을 새 기준으로 다시 쓰지 않는다. 이번 R03의 상세화와 사용자 설명의 대응은 [평가 기준](#평가-기준과-부족한-내용의-표현)에 한 번만 정의한다. QA의 과거 척도 검증 범위를 새 정책의 검증 완료로 해석하지 않는다.

### 증거 해석과 RCA 분석의 단일 호출 설계

현재 기본은 `combined_synthesis.generate` 한 작성 요청 + 독립 검토이며 비교용 `separate`를 유지한다. 작성 결과는 보고서가 아닌 findings/unknowns/conflicts/limitations, hypotheses와 원문/해석 의존 refs다. 빈 원인 후보는 타당한 유보일 수 있다. 호출하지 않은 독립 해석 완료 기록을 만들어 schema 호환을 가장하지 않는다.

| 영역 | 허용 참조·보존 규칙 |
|---|---|
| 해석 evidence refs | 실제 전달된 `input_evidence_refs`; 진단/실패도 한계 설명에 사용 가능. 근거 없는 unknown은 명시적 이유 필요 |
| 가설 supporting/contradicting refs | 전달된 `observation_refs`만. 지지 근거 필수, 지지/반박 교집합 금지. Runbook·진단·생성 해석·D 정의는 원인 관측이 아님 |
| `finding_refs` | 같은 채택 응답의 해석 의존 관계. 원문 refs를 대신하지 못하며 해석 제외 시 의존 가설 보류 |
| 부분 성공 | 검증된 항목과 제외 위치/code/hash 보존. 전체 JSON 실패는 임의 추출하지 않음. unknown/conflict/limitation 또는 의미 기준 오류가 목적 달성을 만들지 못하게 보호 |

현재 항목별 채택·제외와 의존 가설 보류가 구현되어 있다. 이를 ‘향후 구현’으로 다시 적지 않는다. observation 역할은 입력 섹션 우선순위와 분리하며, 실제 입력의 발췌/표본·생략까지 확인한다. 같은 ID/바이트 상한은 같은 모델 입력을 보장하지 않는다.

현행은 새 원본 hash가 없으면 작성 재호출을 막고 검토 지적 항목을 보류한다. 변경 초안의 `draft_changed_after_review`·호출 0회는 추가 검토가 아니다. **R08을 켠 새 정책만** 유효한 의미 지적에 대해 1회 수정·새 검토 예외를 갖는다. HTTP/JSON/잘림은 이 예외 사유가 아니다. 검토가 차단됐다고 새 수집으로 반복 우회하지 않는다.

### Runbook 판단 기준과 품질 검토·종료 설계

현행 1.1의 첫 목적은 `identify_error_report`다. `reported_error/scoped_source`, 필수 의미 기준, 필수 근거와 차단 조건, 적용 호환성, **같은 초안의 acceptable 검토**가 모두 필요하다. 복수 오류 코드라는 이유만으로 모순을 확정하지 않는다. 정책 혼합·지침 집합 변화는 목적 달성을 자동 승계하지 않는다.

현행 `model_assessment`는 optional followup을 제외하고 `select_followup`는 required 링크와 미수집 필수 D 중심으로 후보를 제한한다. 목적 미달이고 후보가 없으면 `goal_not_met`다. 구 정책의 `rule_followup`는 missing_any/requires_all과 명시 우선순위를 따르고, `exploratory_llm=true`일 때만 별도 선택 모델을 쓴다. 정책 없는 경우 acceptable·질문 없음·ruled 없음이면 review_accepted 종료가 가능하다. 현행 수집은 최대 2회차·보완 배치 최대 3개다. R05/R07/R12는 새 1.3 실행에서 optional 제외와 고정 회차 종료를 대체하고, 구 정책의 지원 종료는 전환 계획으로 관리한다.

현행 1.2는 생산자·컴포넌트·비정상 보고와 선택적 정확한 reason으로 코드 없는 Fleet 사건을 구분한다. 이것은 보고 식별 조건이며 현재 건강·실제 원인 판정이 아니다. 원천 등록·지침 발행 범위는 [비코드 Fleet 계약](../../../rcca-agent/README.md#비코드-fleet-오류와-평가)을 따른다.

Runbook 작성/검토/발행은 [DB workflow](../../../rcca-agent/runbooks/DB-WORKFLOW.md)를 따른다. 저장소 JSON은 운영 발행본이 아니며 새 revision을 사용한다. `decision_policy_status=applied/mixed/not_configured`를 유지하고 과거 결과에 새 정책 적용 상태를 추정하지 않는다. 목표 달성은 원인/조치 적격성과 별개다.

### 모델 요청 제한 진단과 예약 보호

F0 진단의 단계별 code/path·한도·필요량·호출 여부·usage 보존을 유지한다. 입력 초과, 근거 없음, 토큰 사전 차단, 전송 실패/원격 불명, 응답 형식/참조 실패, 출력 잘림을 구분한다. `invalid_author_response`는 응답 채택 실패이며 연결 실패가 아니다. 예전 포괄 코드만 있는 기록의 상세 원인은 복원한 것처럼 표시하지 않는다. 진단 보완 자체로 재시도/종료 정책을 바꾸지 않는다.

현행 F2-A 하한은 `외부 예약 + encoded_size(review_payload(규칙 기반 초안, 검토 뷰, 허용 조회)) + review_prompt 바이트 + 기본 검토 출력 상한 + 512`다. 실제 payload builder를 재사용한다. 현재 예약으로 관측이 모두 빠질 때만 하한을 지키는 범위에서 조정하며 양쪽 최소 필요량을 함께 확보하지 못하면 차단을 유지한다. 외부 예약은 finally에서 복원한다. R02는 여기에 실제 카탈로그 baseline을 포함하며 산식을 임의 완화하지 않는다.

`budget_allocation`의 requested/applied reserve, remaining tokens, source fit, reduced 여부, previous reserve, floor/basis, baseline bytes/output cap과 조정 사유를 유지한다. 기존 사유는 `reservation_unchanged/analysis_input_preserved/analysis_review_budget_insufficient`다. 섹션별 생략 개수와 모든 생략 ID 목록을 혼동하지 않는다. 규칙 초안 하한은 앞으로 생성할 전체 초안/복구 비용의 상한이 아니며 모델 검토 완료를 보장하지 않는다.

검토의 24,000바이트는 초안/rubric/선택지를 포함한 본문 한도다. 초기 6,000바이트 뷰에 rule_sources를 붙일 때 전체 뷰를 10,000과 비교하는 코드와, combined에서 실제 작성 뷰를 넘기는 경로를 구별한다. 6,000+10,000으로 더하지 않는다. 현재 review payload는 claims와 후보/권고/해석의 중복 본문을 줄이므로 이전의 중복 전송 진단을 현행 사실로 재사용하지 않는다.

validator의 최대 허용 문장 합계는 실제 생성량/토큰이 아니다. 기본 synthesis 출력 16,384·검토 4,096은 실제 request cap과 다를 수 있다. actual cap, response length/finish reason, 부분 채택과 사용량을 단계·전송별 측정한다. 과거 2~3배 바이트/토큰 주장과 고정 프롬프트 바이트 산식은 현행 보편값으로 사용하지 않는다. 작은/큰 규칙 초안, usage 보고/미보고, 예산 18,000~40,000 경계 fixture와 실제 모델을 분리해 검수한다.

### 결과·보고서·공개

현재 #152는 최종 선택 발행 Runbook의 지침·출처·revision을 분석과 함께 `rca_result_frozen`에 고정한다. 적용성은 코드로 판정하고 보고서 LLM은 관측·분석을 서술하며 대응 절차·모델/버전·승인·조치 후 확인 조건은 원문으로 삽입한다. `missing_inputs`·미확인은 한계 상세로 보내고 빈 추가 확인 섹션은 생략한다. 생산자 시각이 없으면 범위 검증된 로그 기록 시각으로 사건과 대조하지만 장애 발생·회복 시각으로 승격하지 않는다. 이는 현재 동작 설명이며 자동 지침 삽입/섹션 배치를 새 설계의 필수 요구로 고정하지 않는다.

새 R11에서는 RCA의 구조화 근거·독립 검토·미충족 조건·실행/미실행 계획·종료 이유가 보고서의 입력이다. Runbook 지침의 포함 여부는 조사 목적과 적용성으로 결정하며, 관련 없는 고정 절차는 제거할 수 있다. 포함한 지침의 출처·revision·조건과 모든 보고서 입력 hash는 추적 가능해야 한다. 보고서 LLM은 이 자료로 읽기 좋은 문장을 작성하고 원문/Runbook 재조사·새 판단·추가 정렬 LLM을 수행하지 않는다. 필수 섹션/출처/수치 검사는 유지하되 의미 일치의 증명으로 간주하지 않는다. 실패/예산 부족은 동일 자료 기본 표시, 원격 불명·취소는 공통 실행 계약을 따른다. 과거 결과·발행 revision을 수정하지 않는다. 현재 구현의 소유 문서는 [RCA 보고서 계약](../../../rcca-agent/README.md#보고서와-조회-호환)이다.

## 이번 범위 밖의 남은 과제

과거 계획의 고유 과제를 아래에 보존한다. **별도 확대 구현을 약속한 목록이 아니며**, 재착수 시 최신 코드와 실제 원천을 다시 대조한다. 이미 구현된 표시/호출 통합/예약 보호를 미구현으로 중복 등록하지 않는다.

| 과제 | 착수 조건과 보존할 판단 경계 |
|---|---|
| 입력 의미·발췌 보강 | Healthy 의미 매핑, 핵심 커널 메시지 전달, 긴 JSON 절단·앞줄 편향을 같은 사건의 실제 입력으로 확인. 오류뿐 아니라 정상 전후·반대 근거 포함. 호출 통합 효과와 섞지 않음 |

| 증상·원인·장치 관계 표현 | `observed_device_symptom` 등의 증상과 원인 후보 혼동을 검토. 재고 일치/독립 신원/현재 상태/원인을 구별하고 유효 가설 없음을 허용. 시각 누락은 해당 관측 범위에만 적용 |

| 캐시/증분 해석(F5) | 현재 동일 source 재사용을 유지. 독립 해석 캐시는 combined에서 추가하지 않음. 향후 재사용은 입력·scope·제한·모델/설정·prompt·출력 계약 일치 필요. 실패/부분/과거 검토 통과 재사용 금지. 증분은 새 원문+관련 과거 원문을 전체 재분석과 비교 |

| 운영 집계(F8) | 먼저 재생 JSONL/단계 evidence로 오프라인 집계. 호출/전송/복구/의미 수정과 수집 회차를 구분. 최종 미검토와 단계 생략, fast path·구 기록·미공개/attempt 중복 분리. 반복 조회 수요가 확인될 때 API/UI 검토 |
| NVSwitch/포트·오류별 지침 확대 | 유효한 스위치 재고·포트·상대 장치·시각 계약 확보 후 도입. GPU 재고/일반 D13으로 대체하지 않음. [기존 Runbook 전환 검토](../../../rcca-agent/runbooks/transition-review-20261014.json)의 미확정·정보성·병합 대상, 발행 hash/profile 검증은 별도 |
| 실제 품질·부하 | 원천 신원/시각/상태 대조, 큰 evidence/선택지, 동시 실행·조회 지연·RSS 측정. fixture는 운영 성능·정확도를 증명하지 않음 |

과거 F0/F1/F3-A/F3-B/F4 중 이번에 필요한 진단·재생·선택 계획·명시적 정책·입력 provenance는 R01~R12로 통합했다. 구 ‘규칙 후보 순위만 조정’ 계획과 이미 끝난 통합 호출의 착수 순서는 삭제했다. 과거 운영 수치/커밋별 재현 과정은 Git/PR·QA에서 확인하고 현재 구현 기준으로 복사하지 않는다.
