Fleet → Loki → Grafana Alert → RCA

Runbook 284건을 Fleet 로그 타입별 알림 경로에 대조한 검토 화면입니다. 카탈로그에 코드가 있다는 것, 로그가 Loki에 도착하는 것, Grafana가 발화하는 것, 발행된 Runbook으로 RCA가 실행되는 것은 각각 별도 조건입니다.

기준: 현재 저장소의 catalog-manifest.json 및 Runbook 초안, 사용자가 제공한 Xid-Catalog (2).xlsx 대조. Fleet 소스 분류 기준과 운영 배포 상태는 별도 확인이 필요합니다.

281건 수치의 해석: 284−3은 XID 133(매핑 없음), XID 63·64(식별 GPU의 RowRemapping 지원 조건부)를 뺀 수입니다. 다만 281에는 직접 alert를 만들지 않는 일반 GPU Node fallback 1건이 포함됩니다. 따라서 현재 표의 직접 로그 기반 알림 경로는 280건이며, XID 63·64의 proxy 상태는 같은 코드 이벤트가 아닙니다.

XID/SXID 알림 로그 타입 벤 다이어그램

다이어그램은 manifest의 Fleet event_type과 현재 저장소 alert rule의 주 경로를 나타냅니다. Warning/Info 158건에는 RowRemapping 지원 장치에서 조건부인 XID 63·64가 포함되어 있습니다.

281개 주장과 엄격한 경계

Fleet→Loki→Grafana→Incident→RCA

상태형 코드

Fatal/Critical → component_data health=Unhealthy/Degraded. 1분 반복 상태를 주 알림 경로로 사용합니다.

이벤트형 코드

Warning/Info → event. 현재 규칙은 10분 조회 창을 써도 이벤트 자체가 빠지면 복구할 수 없습니다.

비코드 컴포넌트

17개 Runbook → component_data Unhealthy. 현재 규칙의 Degraded는 범위 밖이며 의미 검토 없이 추가하면 상시 경고가 생길 수 있습니다.

RCA 연결 조건

저장소 284개는 작성 초안입니다. DB 등록·호환성 검토·승인·발행 및 Incident 정책까지 확인해야 코드별 RCA 보고서가 실제 작성됩니다.

SXID 12030: manifest상 Warning이라 event 경로입니다. event 줄이 없고 component_data 상태도 나오지 않는다면 Grafana LogQL만으로 알림을 만들 수 없습니다. FM 원본 로그를 Loki로 수집하거나 Fleet이 지속 상태를 내보내도록 producer 경로를 보강해야 합니다.

보강 제안

  1. Fatal/Critical: 상태 규칙(component_data, XID/SXID health Unhealthy|Degraded)을 주 경로로 유지합니다. 이벤트 규칙과 중복 발화하지 않도록 severity 분리를 유지합니다.
  2. Warning/Info: event_name=error_xid/error_sxid 기반 이벤트 규칙과 10분 조회 창을 유지합니다. 누락 보완이 목적이라면 FM/kmsg 원본 로그도 Loki에 수집하고, 코드·장치·노드 기준으로 중복을 정리합니다.
  3. 파일시스템: 별도 event 조건 `component="disk"`, `event_name="filesystem_read_only"`를 추가합니다. Warning event를 일반 Fatal/Warning 코드 필터에 기대지 않습니다.
  4. 검증/배포: 실제 배포된 Fleet 버전·컴포넌트 로그 형식·Grafana 규칙·Incident 정책·DB 발행 Runbook을 같은 시험 이벤트로 끝까지 확인합니다.
Warning/Info XID·SXID 이벤트 규칙 예시
sum by (cluster_id, component, event_type, code, device, reason, k8s_node_name, machine_id) (
  count_over_time(
    {cluster_id=~".+", job="fleet-intelligence-agent"}
      | json log_type=`attributes["log_type"]`, component=`attributes["component"]`,
             event_name=`attributes["event_name"]`, event_type=`attributes["event_type"]`,
             xid=`attributes["extra_info"]["data"]["xid"]`, sxid=`attributes["extra_info"]["data"]["sxid"]`,
             device=`attributes["extra_info"]["device_uuid"]`, reason=`body`,
             k8s_node_name=`resources["k8s.node.name"]`, machine_id=`resources["machine.id"]`
      | __error__="" | log_type="event" | event_name=~"error_(xid|sxid)" | machine_id!=""
      | label_format code=`{{ if .xid }}xid:{{ .xid }}{{ else }}sxid:{{ .sxid }}{{ end }}`
      | event_type!~"Fatal|Critical"
    [10m]
  )
)

이벤트 수집 지연에 여유를 주는 창입니다. Fleet이 event 줄을 만들거나 내보내지 않은 경우를 보완하지 않습니다. 그 경우엔 원본 kmsg/FM 로그의 Loki 수집 또는 Fleet 상태 producer 변경이 필요합니다.

파일시스템 read-only 이벤트 조건 예시
sum by (cluster_id, component, reason, k8s_node_name, machine_id) (
  count_over_time(
    {cluster_id=~".+", job="fleet-intelligence-agent"}
      | json log_type=`attributes["log_type"]`, event_name=`attributes["event_name"]`,
             component=`attributes["component"]`, reason=`body`,
             k8s_node_name=`resources["k8s.node.name"]`, machine_id=`resources["machine.id"]`
      | __error__="" | log_type="event" | component="disk"
      | event_name="filesystem_read_only" | machine_id!=""
    [10m]
  )
)

저장소 규칙 정의는 incident/grafana/alert-rules.yaml에 3개 규칙(state, XID/SXID event, component)이 있습니다. 사용자가 붙인 2-분기 규칙은 별도 배포 상태이므로 둘을 동일한 것으로 간주하지 마세요.

Runbook 전체 284건

검색 및 필터를 적용할 수 있습니다. `Unused / legacy`는 제공된 XID 표의 Description=Unused 63건과 저장소 manifest의 legacy 63건이 코드 단위로 일치한 표시입니다. 사용 중지·삭제를 뜻하지 않으며 GPU 세대/드라이버와 실제 producer를 확인해야 합니다.

분류 근거와 제한

  • 최신 저장소 `catalog-manifest.json`은 XID 173 + SXID 93(266개)과 component 17개, general 1개를 합해 284개를 기록합니다.
  • 첨부 XID-Catalog 시트는 XID 172행이며 `Description=Unused`가 63건입니다. 같은 63개 코드가 현재 runbook manifest에서 `unused_or_legacy`로 표시됩니다. XID 173은 첨부 표 범위 밖이며 NVIDIA 드라이버 nverror.h에도 C2C_FATAL_LINK_FAILURE로 정의됩니다.
  • XID 133은 manifest에서 `fleet_present=false`, event_type 없음입니다. 고정 Fleet commit 84f99be의 실제 Match→GetDetail 경로에서 XID 133은 details 매핑이 없어 제외됩니다. 별도 generated catalog에 숫자가 있다는 것과 실행 매핑은 다릅니다. XID 63·64는 shouldDiscardRowRemappingXID가 GPU를 식별하고 해당 제품의 RowRemapping 지원을 확인했을 때만 제외합니다. GPU 식별 실패 시에는 보존합니다.
  • component_data 건강 로그는 신호입니다. 로그 이벤트가 없어졌거나 RCA Runbook이 DB에서 발행되지 않은 상태를 해결해 주지는 않습니다.
  • 본 페이지는 저장소/제공 자료 기준 분류이며 실제 운영 클러스터의 Fleet version, Loki 수집, 알림 발화, 보고서 생성을 검증하지 않았습니다.
