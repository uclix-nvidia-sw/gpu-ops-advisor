## 1. 핵심 요약

GPU Ops용 **KSM·DCGM Exporter 메트릭의 수집·라벨 가공·중앙 전송을 Alloy로 통일**했습니다.

기존 Prometheus를 제거한 것이 아니라, GPU Ops 중앙 전송 경로에서 제외했습니다. 기존 서비스의 모니터링은 유지하고, 우리가 추가했던 remote_write와 중복 ServiceMonitor만 정리했습니다.

- Alloy 직접 수집으로 KSM 1개, DCGM Exporter 2개의 정상 수집을 CSC Mimir에서 확인했습니다.
- 테스트 Pod를 이용해 GPU UUID·노드·Namespace·Pod를 연결하고, KSM과 조회 시 조인한 Pod UID가 실제 Pod UID와 일치하는 것을 확인했습니다.
- 기존 환경의 DCGM 수집도 ServiceMonitor 정리 이후 정상 유지됐습니다.
- 마지막 Alloy 재배포 이후의 Loki 최신 로그 수신은 별도 최종 확인이 남아 있습니다.
- 현재까지는 수집·기본 매핑 검증이며, 운영 분석 Agent 구현이나 실제 GPU 연산 부하 검증까지 완료한 것은 아닙니다.

## 2. 기존 구조에서 변경한 점

| 항목 | 변경 전 | 현재 | 이유 |
|---|---|---|---|
| KSM·DCGM 수집 주체 | Prometheus | Alloy | GPU Ops 수집 경로 단순화 |
| 대상 발견 | Prometheus가 ServiceMonitor를 읽어 대상 선정 | Alloy가 Kubernetes EndpointSlice 기반으로 대상 발견 | Alloy에서 수집 설정 관리 |
| 라벨 가공 | ServiceMonitor·Prometheus 전송 설정에 분산 | Alloy 직접 수집 파이프라인으로 통합 | 출처·노드·GPU 식별 기준 통일 |
| 중앙 전송 | Prometheus → Alloy → Mimir | Alloy → Mimir | 중간 전송 단계 제거 |
| Prometheus remote_write | `cpc2-ksm-to-alloy` 사용 | 제거 및 실행 설정 반영 확인 | 중복 중앙 전송 방지 |
| Alloy 9999 포트 | Prometheus remote_write 수신 | 수신 컴포넌트·Service 포트 제거 | 사용하지 않는 경로 정리 |
| GPU Ops 전용 ServiceMonitor | `monitoring/gpuops-dcgm-exporter` | 백업 후 삭제 | 기존 수집 경로와 중복 해소 |
| Fleet 메트릭·로그 | Fleet → Alloy → Mimir·Loki | 경로 유지 | GPU·호스트 관측 기능 보존 |
| 기존 Prometheus | 기존 모니터링 수행 | 유지 | 기존 운영 환경 보호 |

ServiceMonitor는 메트릭을 직접 가져오는 프로그램이 아니라 **Prometheus에 수집 대상을 알려주는 설정 리소스**입니다. 이번 전환에서 실제 scrape 실행 주체가 Prometheus에서 Alloy로 바뀌었습니다.

## 3. 현재 구성과 데이터 흐름

```text
CPC-2
│
├─ GPU 노드: vessl-k8s-worker-01 / vessl-k8s-worker-02
│  ├─ Fleet Intelligence Agent
│  │    └─ GPU·호스트 메트릭, 상태·이벤트 로그 ──OTLP──┐
│  └─ DCGM Exporter                                  │
│       └─ GPU 활동·메모리 및 GPU↔Pod 매핑 메트릭      │
│              ▲ Alloy가 /metrics 직접 scrape        │
│              │                                     ▼
├─ KSM ────────┼────────────────────────────────── Alloy
│  Node·Pod·요청량·UID 메트릭                 Deployment 2개 복제본
│  ▲ Alloy가 /metrics 직접 scrape           클러스터링 / 가공 / 전송
│                                                    │
└─ 기존 Prometheus: 기존 환경 모니터링 유지            │
   GPU Ops 중앙 전송 경로에서는 제외                 │
                                                     ▼
CSC: Envoy Gateway 192.168.20.186:8080
  ├─ /api/v1/push      → Mimir: KSM·DCGM 메트릭
  ├─ /otlp/v1/metrics  → Mimir: Fleet 메트릭
  └─ /loki/api/v1/push → Loki: Fleet 로그
                           │
                      Grafana 통합 조회
```

### 통신별 주체·대상·방식

| 주체 | 행동·대상 | 방식·포트 | 확인 수준 |
|---|---|---|---|
| Fleet Agent | Alloy로 메트릭·로그 전송 | OTLP HTTP, CPC 내부 Alloy `4318` | 기존 연동 확인, 최종 재배포 후 Loki 로그는 추가 확인 필요 |
| Alloy | KSM에서 메트릭 가져오기 | HTTP `/metrics`, `8080`, 15초 scrape | 직접 수집 및 중앙 조회 확인 |
| Alloy | DCGM Exporter에서 메트릭 가져오기 | HTTP `/metrics`, `9400`, 15초 scrape | 두 GPU 노드 수집 및 중앙 조회 확인 |
| Alloy | KSM·DCGM 메트릭을 CSC로 전송 | Prometheus remote_write, Gateway `8080/api/v1/push` | 직접 수집 라벨이 있는 데이터 조회 확인 |
| Alloy | Fleet 메트릭을 CSC로 전송 | OTLP HTTP, 기본 endpoint `8080/otlp` | Fleet 두 노드 메트릭 확인 |
| Alloy | Fleet 로그를 CSC로 전송 | Loki push, Gateway `8080/loki/api/v1/push` | 경로 유지, 마지막 배포 이후 최신 도착 검증 대기 |
| Grafana | Mimir·Loki 조회 | 각 데이터소스의 조회 API | Mimir 조회 화면 확인 |

Alloy가 사용하는 Kubernetes API 접근은 **대상 발견·메타데이터 보완**이며, 관측 데이터의 중앙 전송과는 다른 관계입니다. Helm·kubectl은 관리자가 배포 설정을 변경하는 도구이며 데이터 전달 경로에 포함되지 않습니다.

## 5. 실제 수행한 작업과 결과

### 5.1 기존 DCGM Exporter 활용 및 GPU↔작업 매핑

1. 기존 설치된 DCGM Exporter를 확인하고, 처음에는 전용 ServiceMonitor로 Prometheus 수집을 연결했습니다.
2. GPU 1개를 요청하는 테스트 Pod를 실행했습니다.
3. 테스트 Pod에서 확인한 GPU UUID와 Exporter 메트릭의 UUID를 비교했습니다.
4. Exporter 메트릭에 작업 `namespace`, `pod`, `container`가 붙는 것을 확인했습니다.
5. KSM `kube_pod_info`와 조회 시 조인하여 실제 Pod UID와 일치함을 확인했습니다.

별도의 GPU↔Pod 매핑 프로그램은 개발하지 않았습니다.

### 5.2 Exporter 자체 Pod UID 옵션 시험과 원복

| 과정 | 확인 결과 |
|---|---|
| `DCGM_EXPORTER_KUBERNETES_ENABLE_POD_UID=true` 적용 | Exporter가 Pod 메타데이터 조회를 시도 |
| 로그 확인 | Pod 조회 권한 오류, 원본 `pod_uid` 공란 확인 |
| Pod 읽기 권한 추가 | `get pods` 허용 확인 |
| 추가 관찰 | client-side throttling 및 scrape timeout 지속 |
| UID 옵션을 `false`로 변경하고 rollout | 두 Exporter가 반복 확인에서 모두 `up`으로 회복 |
| 대체 방식 | Exporter의 Pod 매핑은 유지하고 UID는 KSM과 조회 시 결합 |

옵션 변경과 수집 불안정의 연관성은 관찰했지만, 정확한 내부 구현 결함이나 수정 버전까지 확정한 것은 아닙니다. 시험 중 추가한 Pod 읽기 RBAC는 유지 필요성 재검토 대상입니다.

### 5.3 Alloy 직접 수집 전환

- 기존 Helm values·manifest·Alloy 설정·Prometheus CR 백업.
- Alloy 클러스터링 및 2개 복제본 구성.
- KSM·DCGM 대상 발견에 필요한 기존 ServiceAccount 권한 확인.
- EndpointSlice 기반 수집 대상 발견 및 scrape 설정 추가.
- 직접 수집 데이터에 `collection_path="alloy-direct"` 추가.
- Alloy 설정 검증·Helm dry-run 후 배포.
- Mimir에서 직접 수집 데이터와 Pod UID 조인 검증.

### 5.4 기존 경로 정리

- Prometheus 추가 remote_write를 빈 목록으로 변경.
- 실제 실행 설정에서 이전 Alloy `9999` 주소가 사라진 것을 확인.
- 2026-09-15 15:12:43~44 KST 로그에서 해당 remote storage·WAL watcher 중지와 설정 재적재 완료 확인.
- Alloy의 기존 `9999` 수신 컴포넌트·포트 제거. 중앙 전송 writer는 유지.
- `monitoring/gpuops-dcgm-exporter` 백업 후 삭제.
- 기존 `runai/nvidia-dcgm-exporter` ServiceMonitor의 두 대상이 삭제 이후에도 모두 `up`인 것을 확인.

## 6. 수집 항목·식별 기준·분석 가능 범위

### 직접 수집 후 Mimir로 전송하는 항목

| 출처 | 메트릭 | 용도 |
|---|---|---|
| KSM | `kube_node_status_condition` | Kubernetes가 관측한 Node 상태 |
| KSM | `kube_pod_info` | Namespace·Pod·Node·UID 연결 |
| KSM | `kube_pod_container_resource_requests` | GPU 등을 포함한 Container별 요청량 |
| DCGM Exporter | `DCGM_FI_DEV_GPU_UTIL` | GPU 장치 활용률 |
| DCGM Exporter | `DCGM_FI_DEV_FB_USED`, `DCGM_FI_DEV_FB_FREE` | GPU 메모리 사용·여유량 |
| Alloy scrape | `up`, `scrape_duration_seconds` | 수집 성공 여부·소요 시간 |

위 목록은 Alloy 직접 scrape 경로의 선별 전송 항목입니다. Fleet OTLP 메트릭 전체 목록을 의미하지 않습니다.

### 식별 라벨

| 라벨 | 의미 |
|---|---|
| `cluster_id=cpc-2` | 출처 클러스터 |
| `node` | 데이터가 가리키는 대상 Kubernetes 노드 |
| `uuid` | GPU UUID |
| `namespace`, `pod`, `container` | 작업 정보 |
| `uid` | KSM에서 얻어 조회 시 결합하는 Pod 고유 식별자 |
| `node_group=prod-b`, `compute_zone=us-east-1c` | 현재 테스트 분류값 |
| `collection_path=alloy-direct` | 직접 수집 경로 구분값 |
| `exporter_namespace`, `exporter_pod`, `exporter_container`, `exporter_node` | 수집 대상 Exporter 자체 정보 |

- Exporter의 원본 `UUID`와 정규화한 `uuid`는 같은 GPU를 가리킵니다.
- KSM이 실행되는 노드를 모든 작업의 `node`로 덮어쓰지 않았습니다.
- Fleet와 Exporter는 `cluster_id + node + uuid`로 같은 GPU의 관측 정보를 연결합니다.
- Exporter와 KSM은 같은 시점의 `cluster_id + namespace + pod + node`로 작업을 연결하고 KSM의 UID를 가져옵니다.
- UID는 조인 결과에 붙는 것이며, Exporter 원본에 저장된 UID가 아닙니다.

### 현재 가능한 분석

- 어떤 클러스터·노드의 GPU가 어떤 Namespace·Pod·Container에 연결돼 있는지 조회.
- 해당 GPU의 활용률·메모리 추세와 작업의 GPU 요청량을 함께 조회.
- Fleet의 동일 GPU·노드 관측 정보와 연관 분석할 기반 확보.
- Namespace를 프로젝트로 간주하는 MVP 수준의 귀속 분석 준비.

### 아직 단정할 수 없는 분석

- 공유 GPU 전체 활용률을 개별 Pod·부서의 정확한 사용률로 분배.
- Namespace만으로 실제 부서·사용자를 자동 식별.
- 현재 순간 매핑만으로 과거 모든 작업의 사용 이력을 정확히 귀속.
- 이번 테스트만으로 연산 효율·학습 성능·실제 GPU 사용량 절감 효과를 입증.

테스트 Pod는 GPU를 요청하고 GPU 식별 정보를 출력한 뒤 대기합니다. 활용률 0은 매핑 실패가 아니라 연산 부하가 없는 상태일 수 있습니다.

관측 구간에서 정상 수집을 확인한 것이며, 모든 시점의 무손실이나 장애 시 자동 복구까지 입증한 것은 아닙니다.

## 8. 팀원이 다시 확인하는 방법

### 8.1 중앙 수집 상태

Grafana Explore에서 CSC Mimir 데이터소스를 선택하고 Instant 조회합니다.

```promql
count by (job) (
  up{cluster_id="cpc-2", collection_path="alloy-direct"} == 1
)
```

기대값: `kube-state-metrics=1`, `nvidia-dcgm-exporter=2`.

### 8.2 GPU↔Pod↔UID 매핑

다음은 기존 테스트에서 사용한 조회 방식입니다. 테스트 Pod가 현재 실행 중이며 데이터가 수집되는 시점에 확인해야 합니다.

```promql
DCGM_FI_DEV_GPU_UTIL{
  cluster_id="cpc-2",
  collection_path="alloy-direct",
  namespace="gpu-ops-test",
  pod="gpu-mapping-test"
}
* on (cluster_id, namespace, pod, node)
  group_left(uid)
max by (cluster_id, namespace, pod, node, uid) (
  kube_pod_info{
    cluster_id="cpc-2",
    collection_path="alloy-direct",
    namespace="gpu-ops-test",
    pod="gpu-mapping-test"
  }
)
```

결과의 `node`, `uuid`, `namespace`, `pod`, `container`, `uid`를 실제 Pod 정보와 비교합니다. 수치 자체는 GPU 활용률이며, KSM 정보값 1을 곱해 라벨을 결합하는 방식입니다.

테스트 Pod는 제한 시간이 지나면 `DeadlineExceeded`로 종료됩니다. 현재 조회가 비었다고 곧바로 수집 장애로 판단하지 않습니다. 같은 이름의 이전·현재 UID가 같은 조회 시점에 함께 남아 조인이 모호하면, UID를 임의로 제거하지 말고 시점·데이터 갱신 상태를 확인해야 합니다.

| 2 | 실제 연산 부하 검증 | 허용된 GPU 테스트 부하에서 활용률 상승과 작업 귀속을 함께 확인 |
| 3 | 보고서용 GPU 지표 기준 확정 | Fleet·Exporter 중 운영 활용률 기준과 중복 방지 규칙 명시 |

### 운영 분석 정확도를 위해 고려할 상황

| 상황 | 위험 | 필요한 보완 |
|---|---|---|
| 같은 이름의 Pod 재생성 | 이전·현재 작업 혼동 | UID와 같은 시점의 매핑을 활용하고 전환 구간 검증 |
| 짧은 작업·종료된 작업 | scrape 사이에 작업을 놓치거나 현재 조회에서 사라짐 | 수집 간격·이력 보관·보고서 시간 창 설계 |
| 메트릭 수집 시각 차이 | Fleet·Exporter·KSM 간 잘못된 시점 결합 | 시점별 조회, 시간 오차·공백 처리 규칙 |
| 공유 GPU·MIG 도입 | 장치 전체 값을 여러 작업에 중복 귀속 | 공유 방식별 지원 범위와 별도 지표·매핑 검증 |
| Namespace와 조직 정보 불일치 | 부서·사용자 귀속 오류 | 조직이 관리하는 Namespace↔프로젝트·부서 원장 |
| 과거 경로 데이터와 직접 수집 데이터 공존 | 이전·현재 경로 중복 집계 | `collection_path`와 전환 시점 기준 명시 |
| 요청한 GPU와 실제 활동의 차이 | 예약량을 실제 활용으로 오인 | 요청량·할당·장치 활용률·유휴 기준을 각각 정의 |

### 운영 안정성과 보안을 위해 고려할 상황

- **Alloy 저장 내구성:** 현재 확인한 Deployment에는 WAL 저장 경로를 위한 영속 볼륨이 없습니다. 재시작 시 미전송 데이터 손실 가능성을 고려해야 합니다.
- **CSC 연결 단절:** 경로마다 큐·WAL·재시도 특성이 다릅니다. 공통 무손실 시간을 가정하지 말고 복구 목표와 허용 손실량을 별도로 정해 시험해야 합니다.
- **클러스터링:** 2개 복제본과 정상 수집은 확인했으나, Pod·노드 장애 시 재분배·중복·공백은 별도 시험 대상입니다.
- **수집 장애와 노드 장애 구분:** `up=0`은 scrape 실패입니다. 이것만으로 GPU 노드 자체 장애를 확정하지 않습니다. KSM Node 상태와 Fleet 최신성 등을 함께 확인해야 합니다.
- **자원·저장소:** Alloy CPU·메모리 제한, Mimir·Loki 저장량·보관기간·백업·복구 기준이 필요합니다. CSC 보관기간 변경은 현재 보류 상태입니다.
- **전송 보안:** 현재 제시된 경로는 HTTP·내부 IP 기반 테스트 구성입니다. 운영 전 TLS·인증·네트워크 접근 제한·전송 자격 관리가 필요합니다.
- **tenant와 클러스터 라벨:** 기존 Mimir Gateway는 테스트 tenant를 지정하고, CPC는 `cluster_id`로 구분합니다. Loki의 tenant 설정과 동일하다고 가정하지 않습니다. 접근 격리는 라벨만으로 구현되지 않습니다.
- **정상 반복 로그:** 용량·빈도 측정 후 축소 정책을 설계합니다. 정상·회복·수집 불가를 혼동할 수 있으므로 `Healthy` 문자열만으로 전체 로그를 제거하지 않습니다.

## 결론

**CPC-2의 GPU Ops 메트릭 수집·가공·전송을 Alloy로 통합했고, 중앙에서 GPU와 작업을 연결할 수 있는 기본 데이터 경로와 매핑을 검증했습니다.**

다음 단계는 최신 로그 수신을 마무리 확인하고, 실제 연산 부하·시간별 작업 귀속·장애 시 데이터 손실 범위를 검증하여 운영 분석 Agent의 신뢰할 수 있는 입력 데이터로 정착시키는 것입니다.
