# 팀 개발 역할과 협업 규칙

팀은 **A — Frontend, B — Backend·DB, C-1 — RCA Agent, C-2 — Ops Agent**의 4명으로 구성한다. A/B/C-1/C-2는 실명 배정 전 역할 표기다. 인프라 전담 역할은 두지 않고, 배포·Kubernetes·공통 설정 변경은 작업마다 담당자를 지정하며 필요하면 리뷰를 요청한다.

이 문서는 협업 절차를 정한다. 프로젝트 공통 원칙과 검증 명령은 [CLAUDE.md](../CLAUDE.md)와 [한국어 번역](CLAUDE.ko.md)을 따른다. 구현 계약은 [Backend API](../backend/API.md), [Job Controller API](../job-controller/API.md), [공유 스키마](../shared/README.md), [Agent 실행 안내](../agents/README.md)를 기준으로 한다. 이 문서와 실제 코드가 다르면 구현·테스트를 확인하고 관련 문서를 함께 고친다.

**현재는 변경 내용과 관련 검사를 확인하고 사용자 승인 후 main에 직접 push할 수 있다.** 커밋과 push는 별도 작업이며, 커밋만 요청받았다면 로컬에 기록하고 끝낸다.

팀 공동 개발의 PR 방식은 팀이 전환 시점을 합의한 뒤 적용한다. 전환 후에는 **작업 등록 → 담당·완료 조건 합의 → 작업 브랜치 → 구현·검증 → PR·필수 CI 확인 → 병합 → 필요한 경우 별도 배포** 순서로 진행한다. PR은 변경 내용을 확인하고 main에 합치기 위한 요청이다. 현재도 필요하면 PR을 사용할 수 있지만 모든 변경의 필수 조건은 아니다.

**현재와 향후 공동 개발 모두 별도 팀원의 코드 리뷰·PR 승인(Approve)은 선택 사항이다.** 다른 사람의 승인이 없어도 작성자가 변경 내용과 관련 테스트를 확인하고, PR 방식이라면 필수 CI까지 통과한 뒤 반영할 수 있다. AI가 작성한 코드도 담당 개발자의 확인 책임은 같다. 이때 선택인 것은 동료 리뷰이지, 에이전트가 commit·push·병합·배포를 수행할 때 필요한 사용자 요청·승인이 아니다.

## 먼저 구분할 것

- **현재 프로그램의 동작**: 누가 분석을 접수하는지, DB를 어떻게 바꾸는지, CI가 무엇을 만드는지는 지금 저장소 코드에 대한 설명이다.
- **현재 적용할 작업 규칙**: 변경 검토·관련 검사·사용자 승인을 거쳐 main 직접 push를 허용한다. 커밋 메시지와 핵심 설명은 영어·한국어를 함께 적는다. main 작업 허용이 매번 push까지 자동 승인한다는 뜻은 아니다.
- **공동 개발 전환 후 적용할 규칙**: 작업 브랜치와 PR을 사용하고, 작성자 확인·필수 CI 통과 후 Squash 병합한다. 별도 팀원 리뷰는 선택이다. 이 단계에서는 main에 직접 push하지 않는다. 전환 시점을 팀이 합의해 이 문서에 기록하며, 에이전트가 임의로 전환됐다고 판단하지 않는다.
- **관리자가 별도로 켜야 하는 설정**: PR 전환 시 필수 CI가 통과하지 않으면 병합을 막는 기능은 GitHub에서 설정해야 한다. 별도 팀원 승인 인원은 기본 필수 조건으로 두지 않는다. 실제 확인 상태는 마지막 절에 적는다.

자주 나오는 Git 용어는 다음 뜻으로 사용한다.

| 용어 | 쉬운 뜻 |
|---|---|
| 저장소·repo | 코드와 변경 이력을 모아 두는 프로젝트 공간 |
| main | 검증한 코드를 모으는 기준 브랜치. 운영 서버와 같다는 뜻은 아님 |
| branch·브랜치 | 기준 코드에서 갈라져 특정 작업을 진행하는 변경 이력 |
| commit·커밋 | 선택한 변경을 내 컴퓨터의 Git 이력에 기록하는 것. 파일 저장이나 업로드와는 다름 |
| push | 내 커밋을 GitHub의 해당 브랜치로 보내는 것. 작업 브랜치 push만으로 main은 바뀌지 않음 |
| PR·동료 리뷰·Approve | 합쳐 달라는 요청·다른 팀원의 코드 검토·그 팀원의 승인 표시. 동료 리뷰와 Approve는 선택 |
| 사용자 승인 | 에이전트에게 특정 작업을 수행하도록 허용하는 것. 동료 리뷰 생략과는 별개 |
| merge·병합 | 검토한 변경을 main에 합치는 것 |
| CI | 코드를 올렸을 때 GitHub가 자동으로 빌드와 테스트 등을 실행하는 검사 절차 |
| 배포 | 검토한 코드로 만든 실행물을 실제 서버에 설치하거나 갱신하는 것 |

## 1. 담당 범위와 리뷰

아래는 공동 개발 시 사용할 역할 분담과 검증 책임이다. 현재 역할이 아직 배정되지 않은 작업은 사용자와 변경·검증 결과를 확인하고 작업 대화나 Issue에 남긴다. 동료 리뷰는 필요할 때 요청하며, 받지 않았다면 받았다고 쓰지 않는다.

| 담당 | 주요 경로 | 책임 |
|---|---|---|
| A — Frontend | `frontend/` | 자산·작업 현황, 분석 진행 상태, RCA 결과·운영보고서 화면과 API 연동 |
| B — Backend·DB | `backend/`, `incident/`, `job-controller/`, `shared/contract/`, `shared/migrations/` | API·DB 계약, 사건 접수, 정기 보고서 일정, 큐·슬롯·작업 상태, 결과 공개와 조회 |
| C-1 — RCA Agent | `rcca-agent/` | 사건 증거·Runbook·로그·메트릭을 이용한 장애 원인 조사, 근거와 진단 결과 생성 |
| C-2 — Ops Agent | `ops-agent/` | 기간별 GPU 사용률·성능·효율 분석, 공개 RCA 결과 인용, 개선 권고와 운영보고서 생성 |

- 작업마다 실행 담당자 1명을 정한다. 별도 리뷰 담당자는 선택이며, 요청할 때 지정한다. 담당 범위는 독점 수정 권한이 아니라 변경 영향을 확인하고 필요하면 상의할 범위다.
- B의 담당 범위가 넓으므로 API·Incident·JC·DB 작업마다 보조 담당자를 지정하고, 부재 시 확인할 사람과 적용 절차를 남긴다. 리뷰 담당자가 보조 담당자를 겸해도 된다. 매번 세 번째 사람을 추가하라는 뜻은 아니다.
- `shared/python/`, `agents/`, `grafana-mcp/`는 C-1/C-2 중 한 명이 작업하고 두 Worker에 대한 영향을 검증한다. 다른 한 명의 추가 리뷰를 권장하며, JC 계약·DB 저장에 영향을 주면 B에게 내용을 공유한다.
- 작성자는 API 응답 형식 변경 시 B·A 담당 모듈과 해당 API 사용 경로의 영향을 검증한다. **RCA 결과 형식의 영향 범위는 B·C-1·C-2·A**, 보고서 결과 형식은 B·C-2·A다. Ops Agent도 공개 RCA의 원인·상태·근거 필드를 사용하므로 RCA 변경에서 C-2의 사용 경로를 빼지 않는다. 담당자별 승인을 모두 받으라는 뜻은 아니다.
- Grafana alert rule·contact point·Incident 분석 정책은 B·C-1이 연결을 확인한다. 로그·메트릭의 라벨, 단위, 조회 기간과 근거 부족 처리 기준은 사용하는 Agent 담당자가 실제 관측 자료로 확인한다.
- `charts/`, `.github/`, 운영 설정과 배포 문서는 해당 작업에 담당자·영향받는 모듈을 적고 수정한다. 리뷰를 요청했다면 리뷰 담당자도 남긴다.

공통 계약 변경은 작성자가 영향받는 사용 경로의 검증 결과를 작업 대화·Issue 또는 PR에 남긴다. 관련 담당자에게 영향을 공유하고, 호환성이나 요구사항이 불명확하면 상의한다. 필요한 사용 모듈 수정은 같은 작업에 포함한다. 동료 리뷰가 선택이어도 계약 합의나 공유 DB 적용 일정 조율까지 생략한다는 뜻은 아니다.

여기서 **계약**은 모듈끼리 주고받는 데이터 이름·형식·의미에 대한 약속이다. 예를 들어 RCA 응답의 필드 이름을 바꾸면 화면뿐 아니라 그 필드를 읽는 Ops Agent도 깨질 수 있다. 작성자가 양쪽 사용 경로와 테스트를 확인하고 결과를 남겨야 한다. 리뷰를 요청하면 해당 팀원은 이 검증이 충분한지 추가로 살펴볼 수 있다.

문서·작은 수정은 작성자 확인과 관련 검사로 진행할 수 있다. DB 구조·공통 API·권한·비밀값·배포 변경처럼 영향이 큰 작업은 다른 팀원이나 별도 에이전트의 추가 검토를 권장한다. 별도 에이전트의 검토도 최종 책임이나 실제 테스트를 대신하지 않는다.

## 2. 모듈 사이의 작업 경계

담당자 B가 여러 모듈을 맡더라도 실행 주체와 DB 쓰기 권한은 기존 계약대로 구분한다.

| 작업 | 실행 주체 |
|---|---|
| RCA 접수 | Incident가 사건 증거 snapshot(분석에 쓸 증거 사본)을 저장하고 JC에 접수 |
| 즉시·정기 보고서 접수 | Backend가 요청·일정과 전달 상태를 관리하고 JC에 접수 |
| 작업 배분·시도·슬롯·최종 발행 | Job Controller(JC). 슬롯은 동시에 분석할 수 있는 자리 |
| 분석 및 결과 후보 저장 | 각 Agent Worker가 evidence(분석 근거)·result_candidates(공개 전 결과)를 저장하고 JC에 complete(완료 처리) 요청 |
| 공개 결과 조회·표시 | Backend가 공개된 결과를 조회하고 Frontend가 표시 |

Agent는 JC에 등록하고 작업을 가져오는 장기 실행 Worker다. 새 업무 큐, 일정 루프, 별도 aggregator나 Agent 직접 접수 API를 추가하지 않는다. RCA와 보고서의 JC kind는 각각 `rca`, `report`이며 상태값·오류 형식·결과 버전은 기존 계약을 재사용한다. 실제 장비 조치는 사람이 수행한다.

쉽게 말해 Incident는 사건 접수, JC는 작업 순서와 실행 자리 관리, Agent는 분석, Backend·Frontend는 조회와 화면 표시를 맡는다. Worker는 일을 기다리다가 받아 처리하는 프로그램이다. Agent가 결과를 DB에 썼다는 것만으로 사용자에게 공개되는 것은 아니다. JC가 완료 요청을 검사하고 결과를 확정해야 조회 대상이 된다. 문서에서 말하는 결과의 “공개”는 제품에서 조회 가능하다는 뜻이지 인터넷에 익명 공개한다는 뜻이 아니다.

## 3. 현재 main 작업과 향후 PR 절차

### 현재: main에서 검증 후 커밋·승인 후 push

1. 작업 목적과 변경 범위를 사용자와 확인한다. `git status`와 현재 브랜치를 확인하고, 기존 작업이나 관계없는 파일을 섞거나 버리지 않는다. main에서 직접 수정·커밋해도 되며 필요하면 작업 브랜치를 사용할 수 있다.
2. 변경 내용과 비밀값 포함 여부를 검토하고 관련 검사를 실행한다. 결과와 미확인 항목을 작업 대화나 Issue에 남긴다. DB·설정·배포 안전수칙은 main 작업에서도 그대로 지킨다.
3. 커밋 대상 파일과 한영 커밋 메시지를 확인한다. 요청받거나 승인받은 경우에만 커밋하고, 필요한 파일만 명시적으로 선택한다. 한 커밋은 한 목적에 집중한다.
4. **“커밋만 해줘”, “push하지 마”라는 요청이면 여기서 끝낸다.** 커밋 해시와 로컬 상태를 보고하며, GitHub 반영이나 CI 실행을 완료했다고 말하지 않는다.
5. push까지 요청받거나 승인받은 경우에만 원격 main의 최신 상태와 충돌 여부를 확인하고 일반 push를 수행한다. 원격 변경이 있거나 push가 거절되면 강제 push로 덮어쓰지 않고 변경을 보존한 채 확인한다. 실제 저장소 보호 규칙을 우회하지 않는다.
6. main push 후에는 해당 커밋의 CI 상태를 확인·공유한다. 대기·실행 중인 검사를 통과로 보고하지 않는다. CI 실패 시 원인을 확인하고 수정하며, 실패한 산출물은 배포하지 않는다. 배포는 별도의 요청·승인 범위다.

AI에 작업을 맡겼다는 이유만으로 commit·push·병합·배포까지 자동 승인된 것은 아니다. 사용자가 요청하거나 승인한 범위에서만 수행한다. “main 직접 push 허용”은 가능한 작업 방식이지 이후 모든 작업에 대한 포괄적인 push 승인이 아니다.

**이하 PR 절차와 명령 예시는 팀 공동 개발로 전환하거나 해당 작업에 PR을 사용하기로 한 경우에 적용한다.** 현재 main에서 커밋만 하는 작업에 PR 생성이나 작업 브랜치를 추가로 요구하지 않는다.

### PR 방식: 작업 시작

1. GitHub Issue에 목적, 범위, 완료 조건, 담당자를 적고, 리뷰를 요청할 경우 리뷰 담당자를 추가한다. API·DB·공통 코드·배포 영향이 있으면 함께 표시한다. Issue는 팀이 함께 보는 “할 일 카드”, 완료 조건은 “무엇을 확인하면 끝났다고 할지”를 뜻한다. 같은 목적의 Issue가 있으면 연결해서 쓰고, 사소한 수정마다 새 카드를 만들지는 않는다.
2. 구현 전에 관련 담당자와 입력·출력 필드, 단위, 상태, 정상·실패·근거 부족 응답 예시를 합의한다. 기존 계약으로 해결할 수 있으면 새 형식을 만들지 않는다.
3. 개인별 작업 폴더에서 최신 main을 기준으로 작업 브랜치를 만든다. 먼저 `git status`로 미완료 변경을 확인하고, 남아 있으면 보존·정리한 뒤 브랜치를 전환한다. 기존 변경을 강제로 버리지 않는다.

작업 카드 예시:

```text
목적: RCA 근거가 없을 때 화면이 빈칸 대신 이유를 보여주게 한다.
담당/리뷰(선택): A / 미요청 — 기존 응답을 사용하는 화면 변경
완료 조건: 근거가 있는 경우와 없는 경우가 구분되고 화면 테스트가 통과한다.
범위/영향: 기존 응답을 사용하는 화면 변경. API·DB 변경은 하지 않는다.
배포: 화면 변경을 반영할 배포 작업에 연결한다.
```

프로젝트 폴더가 아직 없는 팀원은 저장소 접근 권한을 확인하고, 원하는 상위 폴더에서 아래처럼 처음 한 번만 내려받는다. 이미 프로젝트가 있으면 이 단계는 건너뛴다. SSH 인증이 되지 않으면 먼저 계정·키·저장소 권한을 확인한다.

```bash
git clone git@github.com:uclix-nvidia-sw/gpu-ops-advisor.git
cd gpu-ops-advisor
```

프로젝트 폴더에서 `git status`를 먼저 실행한다. 변경이 없음을 확인한 뒤 다음 줄로 진행한다. 아래는 문서를 수정하는 예시이며 브랜치 이름은 자기 작업에 맞게 바꾼다.

```bash
git status
git switch main
git pull --ff-only origin main
git switch -c docs/team-development-guide
```

`--ff-only`는 내 main과 원격 main의 이력이 갈라졌을 때 임의로 합치지 않고 멈추게 하는 옵션이다. 명령이 실패하거나 “브랜치가 이미 있다”고 나오면 다음 명령까지 그대로 실행하지 않는다. 현재 브랜치와 변경을 확인하고 팀원에게 물어본다. `reset --hard`나 force push로 덮어쓰는 방식으로 해결하지 않는다.

브랜치는 `feat/기능`, `fix/문제`, `docs/문서`처럼 목적을 드러낸다. AI 도구에 지정된 접두사 규칙이 있으면 그 규칙을 따른다. 이 작업 환경의 Codex에는 기본 `codex/` 접두사가 지정되어 있다. 같은 작업 폴더를 여러 사람이나 AI가 동시에 수정하지 않는다. 병렬 작업은 별도 clone(저장소 복사본) 또는 worktree(브랜치별 작업 폴더)로 분리한다. 같은 파일을 읽고 리뷰하는 것은 괜찮다.

### 브랜치명 예시

사람이 직접 만드는 작업 브랜치는 `작업종류/짧은-영문-설명` 형태를 권장한다. 영문 소문자·숫자·하이픈을 사용하고 공백은 넣지 않는다. 아래는 이름 예시일 뿐, 해당 기능 개발을 확정하거나 브랜치를 실제로 만든 것은 아니다.

| 작업 | 브랜치명 예시 |
|---|---|
| RCA 분석 근거를 보여주는 화면 추가 | `feat/rca-evidence-ui` |
| Ops 사용률 보고서 기능 추가 | `feat/ops-utilization-report` |
| Incident의 중복 알림 처리 오류 수정 | `fix/incident-alert-dedup` |
| 팀 협업 문서 수정 | `docs/team-development-guide` |
| RCA 근거 부족 상황의 테스트 추가 | `test/rca-missing-evidence` |
| 기능은 유지하면서 공통 LLM 코드 정리 | `refactor/shared-llm-client` |
| Helm 설정 복사본 동기화 등 유지보수 | `chore/helm-config-sync` |

이 작업 환경의 **Codex가 브랜치를 새로 만들 때는** 지정된 `codex/` 접두사를 사용한다. 예를 들어 `codex/rca-evidence-ui`, `codex/fix-incident-alert-dedup`, `codex/team-development-guide`처럼 쓴다. 사용자가 특정 브랜치명을 지정하면 그 이름을 따른다.

한 브랜치에는 한 목적의 변경을 담고 `work`, `temp`, `test1`처럼 내용을 알 수 없는 이름은 피한다. 현재 main에서 직접 작업하기로 했다면 브랜치가 반드시 필요한 것은 아니다. 작업 브랜치를 쓰기로 한 경우에만 이 예시를 적용한다.

### PR 방식: 구현·리뷰·병합

1. 한 PR은 한 목적에 집중한다. 관련 없는 포맷 변경·이름 변경·기능 추가는 섞지 않는다. 작업 중 범위가 커지면 Issue와 담당자 합의를 갱신한다.
2. 변경한 모듈과 영향을 받는 사용 모듈을 검증한다. 구현과 함께 계약·설정 예시·가까운 문서를 갱신한다. AI가 작성한 코드도 PR 작성자가 이해하고 검증하며 결과에 책임진다.
3. 작업 브랜치를 원격에 push하고 main을 대상으로 PR을 연다. main에는 직접 push하지 않는다. 완료 전 공유가 필요하면 Draft PR(아직 병합 준비가 안 된 초안)을 사용한다.
4. 작성자가 최종 변경을 확인하고 최신 변경에 대한 `CI required`가 통과한 뒤 병합한다. 별도 팀원 리뷰·Approve는 필수가 아니다. 리뷰를 받았다면 지적된 문제를 확인·해결하고 처리 내용을 남긴다. 추가 변경이나 충돌 해결 후에는 관련 테스트와 CI를 다시 확인한다.
5. 기본 병합 방식은 **Squash and merge**로 하고 병합 권한이 있는 PR 작성자가 병합한다. 여러 작업 커밋을 목적이 드러나는 한 커밋으로 합치는 방식이다. 저장소에서 지원·허용되지 않으면 관리자와 방식을 합의한다. 작성자에게 권한이 없거나 부재하면 PR에 미리 지정한, 병합 권한이 있는 대리 담당자가 대신한다.
6. 병합 후 Issue에 결과와 남은 작업을 기록한다. 배포가 필요한 변경은 배포 담당자에게 인계한다. 병합 완료와 배포 완료를 구분한다.

### PR 방식: 변경을 올리는 명령 예시

아래는 앞에서 만든 문서 작업 브랜치에서 `docs/team-development.md`만 바꾼 경우다. 현재 브랜치가 main이 아닌지 확인하고, 파일 경로·메시지는 실제 변경에 맞게 바꾼다. 명령은 한 줄씩 결과를 보며 진행한다. push까지 승인된 경우의 예시이며, 커밋만 요청받았다면 마지막 push 명령은 실행하지 않는다.

```bash
git branch --show-current
git status
git diff -- docs/team-development.md
git add docs/team-development.md
git diff --cached
git commit -m "docs: clarify team workflow / 팀 협업 절차 보완"
git push -u origin HEAD
```

- `git diff`는 기존 파일의 수정 내용, `git diff --cached`는 다음 커밋에 들어갈 내용을 보여준다. 새 파일은 일반 `git diff`에 보이지 않으므로 편집기로 확인하고, `git add` 후 다시 확인한다.
- `git add`는 “이번 커밋에 넣을 변경을 선택”하는 단계다. 위 예시는 파일 하나만 선택한다. 다른 관련 파일도 바꿨다면 각각 확인해 추가하고, 무심코 폴더 전체를 올리지 않는다. 이미 선택되어 있던 다른 파일도 `git diff --cached`에서 확인한다. 관련 없는 파일이나 비밀값이 보이면 커밋을 멈추고 선택 범위부터 정리한다.
- `git push -u origin HEAD`는 현재 브랜치를 보낸다. main에서 실행하면 main을 보내므로 반드시 앞의 브랜치 확인을 먼저 한다. SSH 키나 Git 작성자 설정 문제가 나오면 그대로 중단하고 확인한다.
- GitHub에서 PR을 열 때 **base는 main, compare는 자기 작업 브랜치**인지 확인한다. base는 변경을 받을 곳, compare는 내가 만든 변경이 있는 곳이다.
- “테스트 통과”라고만 쓰지 말고 실행한 명령과 결과를 적는다. 빨간 CI 표시가 보이면 실패한 작업 로그를 확인하고 해결한 뒤 다시 검사를 받는다. 작성자 확인과 필수 검사 통과 전에는 병합하지 않는다. 에이전트가 병합을 수행하려면 별도로 그 작업이 요청·승인된 범위여야 한다.

작업 중 다른 PR이 먼저 main에 들어갔다면, 저장하지 않은 변경을 먼저 보존하고 자기 작업 브랜치에서 `git fetch origin` 후 `git merge origin/main`으로 최신 변경을 반영할 수 있다. 충돌은 “같은 부분을 서로 다르게 고쳐 자동으로 고를 수 없는 상태”다. 무조건 내 코드나 상대 코드로 덮지 말고 원래 수정자와 함께 해결한 뒤 다시 검증한다. 해결이 어렵다면 중단하고 도움을 요청한다.

Squash 병합한 브랜치는 다음 작업에 계속 쓰지 않는다. 최신 main에서 새 브랜치를 만들어야 이전 작업 이력이 다음 PR에 섞이지 않는다. 정리는 변경이 병합·보존되었는지 확인한 뒤 한다.

### 변경 기록에 남길 내용

커밋 메시지·PR 제목과 핵심 설명은 영어·한국어를 함께 적는다. 예: `feat: show RCA evidence / RCA 근거 표시`. 아래 형식은 현재 작업 대화·Issue에도, 전환 후 PR에도 사용할 수 있다. 해당하지 않는 항목에는 이유를 적는다.

제목만 두 언어로 쓰고 설명은 한 언어로 끝내지 않도록 목적과 핵심 변경도 각각 짧게 적는다. 명령·경로·긴 로그까지 두 번 복제할 필요는 없다. 출력이나 스크린샷을 붙이기 전에는 토큰·비밀번호·운영 데이터가 없는지 확인한다.

```markdown
## Purpose / 목적

- 변경 이유와 연결된 Issue:

## Changes and impact / 변경 및 영향

- 변경 범위, API·결과 계약·DB·설정 영향:
- 영향받는 사용 경로와 작성자의 검증 결과:
- 동료·별도 에이전트 리뷰(선택, 미요청이면 표시):

## Validation / 검증

- 실행한 명령과 결과:
- 실제 연결과 fixture 사용 범위:
- 미실행·미확인 항목과 이유:

## Deployment and recovery / 배포 및 복구

- 배포 필요 여부, 담당자와 적용 순서:
- 데이터 영향, 복구 방법 또는 전진 수정 계획:
```

fixture는 테스트용으로 미리 만들어 둔 데이터나 응답이다. 예를 들어 준비한 Grafana 응답으로 테스트가 통과했다면 “그 응답을 처리하는 코드가 맞다”는 근거이지 “실제 운영 Grafana 연결과 데이터까지 정상이다”라는 근거는 아니다.

## 4. 개발 환경·DB·완료 조건

### 개인 환경과 공통 설정

- 도구 버전과 검증 명령은 [공통 지침](CLAUDE.ko.md), 실행 방법은 각 모듈 README를 따른다. 이 문서에 별도 버전 목록을 복제하지 않는다.
- 일상 개발과 테스트는 개인용 로컬 DB 또는 격리된 테스트 DB를 사용한다. 공유 개발 DB는 지정된 통합 확인에만 사용하고 적용 담당자·시점을 먼저 합의한다. 테스트도 데이터를 생성·변경·삭제할 수 있으므로 운영 DB를 연결하지 않는다.
- **`backend/scripts/dev-server.ps1`을 공유·스테이징·운영 DB에 연결하지 않는다.** 기존 `DATABASE_URL`을 사용할 수 있고 migration(DB 구조 변경)과 데모 seed(연습용 데이터 넣기)를 활성화한다. 실행 전에 접속 서버와 DB 이름부터 확인한다. 주소에 비밀번호가 포함될 수 있으므로 전체 접속 문자열을 채팅·PR에 붙이지 않는다.
- 환경변수가 추가되면 해당 모듈의 예시와 실행 문서를 갱신한다. 실제 키·토큰·비밀번호·로컬 `.env`·운영 원본 로그는 커밋하지 않는다. 공유할 증거는 필요한 부분만 추리고 민감정보를 제거한다.
- Agent·JC·Incident 원본 설정을 바꾸면 [설정 복사본 규칙](CLAUDE.ko.md#설정-복사본)에 따라 Helm 내장 JSON도 함께 갱신한다. 로컬 예시만 고치고 배포용 복사본을 잊으면 내 컴퓨터와 서버가 서로 다른 설정을 쓰게 된다.
- Helm의 `configuration.agents`, `configuration.jobController`, `configuration.incident` override(덮어쓸 설정)는 해당 객체 전체를 교체한다. 바꿀 필드 하나만 보내면 나머지가 기존 값과 자동으로 합쳐지는 방식이 아니다. 모든 Helm 설정이 이 방식이라는 뜻은 아니며, 위 세 항목에 대한 주의다.
- JC와 Incident는 시작 시 파일/Helm 설정을 적용한다. DB를 직접 고친 값이 재시작 후 유지된다고 가정하지 않는다.
- Incident의 `analysis_policies` 내용을 바꿀 때는 해당 정책의 `revision`도 새 값으로 바꾼다. 이미 사용한 `gpu-alert-v1`의 내용을 덮어쓰기보다 `gpu-alert-v2`처럼 새 버전을 만든다는 뜻이다. 같은 revision에 다른 내용을 넣으면 시작에 실패한다. 원본 설정과 Helm 복사본을 함께 맞춘다.

로컬은 개인 연습 환경, 공유 개발 환경은 팀원이 함께 연결을 확인하는 곳, 스테이징은 운영 반영 전에 점검하는 곳, 운영은 실제 사용자가 쓰는 곳이다. 환경 이름만 믿지 말고 실제 연결 대상을 확인한다. 다른 PC나 서버를 가리키는 설정이 남아 있으면 로컬에서 실행한 명령도 그 서버의 데이터를 바꿀 수 있다.

### DB 변경

DB 변경은 B와 협의해 `shared/migrations/`에서 관리한다. 이미 적용된 SQL을 바꿔 기존 DB도 자동 수정될 것이라고 가정하지 않는다.

- 새 SQL 파일을 추가하는 것만으로 실행되지 않는다. 현재 구조에 맞춰 **embed 등록과 해당 서비스의 migration 적용 경로**까지 확인·수정한다. embed는 SQL 파일을 Go 실행 프로그램 안에 포함하는 등록이고, 적용 경로는 어떤 서비스가 그 SQL을 실행할지 정한 코드다. 파일만 만들어 두면 프로그램이 알아서 찾아 실행하지 않는다. 새 migration 프레임워크를 도입할 필요는 없다.
- 작업 대화·Issue 또는 PR에 기존 데이터 영향, 서비스 적용 순서, 적용 담당자, 백업 필요 여부와 복구 방법을 적는다. 공유 DB 적용 시간은 먼저 공지한다.
- 새 DB 초기화, 기존 DB 업그레이드, 적용 후 반복 시작을 검증한다. `shared/` Go 계약·migration 변경은 네 Go 모듈 모두 확인하고 관련 DB·E2E 테스트를 실행한다.
- 애플리케이션 또는 Helm 버전을 되돌려도 DB 변경은 자동으로 취소되지 않는다. 되돌릴 수 없는 변경은 복구용 백업이나 호환 가능한 전진 수정 계획을 준비한다.

예를 들어 DB 열을 지워 놓고 프로그램만 이전 버전으로 되돌리면, 이전 프로그램이 필요한 열을 찾지 못할 수 있다. 복구는 프로그램뿐 아니라 데이터와 DB 구조까지 함께 생각해야 한다. “전진 수정”은 과거 변경을 무조건 취소하는 대신, 새 수정으로 문제를 해결하는 방법이다. 삭제된 데이터가 저절로 돌아오는 것은 아니다.

### 내 변경에서 무엇을 검사할까?

로컬에서는 변경과 관련된 검사부터 실행한다. 정확한 명령은 [공통 지침의 검증 절](CLAUDE.ko.md#검증가장-작은-관련-검사부터)을 따른다. 아래는 범위를 고르는 예시이지, 영향을 받는 다른 검사를 생략해도 된다는 뜻은 아니다.

| 변경 예시 | 확인할 범위 |
|---|---|
| 협업 문서의 설명만 수정 | 링크·파일 경로·내용의 정확성. 실제 LLM·Grafana 연결은 이 변경에 해당 없음 |
| 기존 API를 쓰는 화면만 수정 | Frontend 검사와 화면의 정상·실패·빈 결과 표시 |
| 한 Agent의 분석 로직 수정 | 해당 분석 테스트와 관련 실행 흐름. 결과 형식이 바뀌면 이를 읽는 쪽도 확인 |
| 공통 Python·Agent 설정 수정 | RCA·Ops 두 Worker 및 관련 통합 검사 |
| 공통 Go 계약·migration 수정 | `shared`, `backend`, `job-controller`, `incident` 네 모듈과 관련 DB·E2E 검사 |
| chart·배포 설정 수정 | chart·CI 계약 검사와 필요한 배포 후 확인 계획 |

단위 테스트는 작은 코드 조각, 통합 테스트는 연결된 모듈, E2E 테스트는 접수부터 결과까지의 전체 경로를 확인한다. E2E도 외부 응답에 fixture를 쓸 수 있으므로 이름만 보고 “전부 실제 운영 환경에서 확인했다”고 해석하지 않는다. 현재 main 직접 push 방식에서는 로컬 검증 후 push하고 그 커밋의 CI 결과를 확인한다. PR 방식에서는 병합 전에 전체 필수 CI를 통과해야 한다. 로컬 커밋만으로 GitHub CI가 실행되지는 않는다.

### 검증·반영 완료 조건

- [ ] 사용자 요청 또는 Issue의 완료 조건을 충족하고, 변경한 동작과 영향받는 사용 경로를 확인했다.
- [ ] 관련 빌드·테스트를 실행했고, DB·통합·E2E가 필요한 경우 그 결과도 남겼다.
- [ ] API·결과 계약·설정 복사본·예시·관련 문서를 함께 갱신했다.
- [ ] 실제 LLM·Grafana 연결 검증과 fixture 기반 검증을 구분했고, 미확인 항목을 숨기지 않았다.
- [ ] 현재 방식: 변경·검증 결과와 요청 범위를 확인했고, 커밋만 요청받은 경우 push하지 않았다. push한 경우 해당 커밋의 CI 상태를 확인·공유했다.
- [ ] PR 방식 사용 시: 작성자가 최종 변경과 최신 `CI required` 통과를 확인했다. 리뷰를 요청했다면 결과와 처리 내용을 남겼다.
- [ ] 어느 방식이든 배포·복구 필요 여부를 확인하고, 요청 범위를 넘는 배포는 하지 않았다.

기본 단위 테스트 통과만으로 E2E 완료라고 쓰지 않는다. push·병합 전에 필요한 검증이 미완료라면 해결 전 원격에 반영하지 않는다. main push 후 CI가 대기·실행 중이라면 “push 완료, CI 미완료”로 구분한다. 외부 환경 검증을 배포 후 수행해야 하는 경우에는 그 조건·담당자·실패 시 대응을 작업 기록에서 합의하고 검증 완료로 표시하지 않는다.

변경과 관계없는 항목은 “해당 없음: 문서 설명만 바꾸어 DB·배포 영향 없음”처럼 이유를 적으면 된다. 아직 못 한 검사는 “미실행”, 해봤지만 실패한 검사는 “실패”로 구분한다. 둘 다 “통과”는 아니다.

## 5. main 반영과 배포는 별도 단계

현재 [CI·릴리스](ci-release.md)는 다음처럼 동작한다. 문서만 변경해도 같은 CI를 실행한다.

| 상황 | CI에서 하는 일 | 클러스터 적용 |
|---|---|---|
| PR | 테스트, 이미지 빌드, 검토용 Helm 패키지 생성. 레지스트리에는 미발행 | 없음 |
| main push·PR 병합 | 테스트 후 이미지 7개와 이미지 digest가 고정된 OCI Helm chart 발행 | 없음 |
| 별도 배포 작업 | 담당자가 성공한 CI의 정확한 chart 버전·설정을 선택해 적용 | 담당자가 수행 |

**main에 직접 push하거나 PR을 병합해도 Kubernetes에 자동 배포되지는 않는다.** PR용 패키지는 배포 가능한 이미지가 발행된 패키지가 아니므로 그대로 설치하지 않는다.

쉽게 말해 main 반영(push 또는 PR 병합)은 팀의 기준 코드를 갱신하는 일이고, 발행은 그 코드로 만든 실행물을 보관소에 올리는 일이며, 배포는 실제 서버가 그 실행물을 쓰게 하는 일이다. 문서만 바꾸는 작업은 보통 서버 배포가 필요 없다. 그래도 현재 CI는 이미지·chart를 만든다. 산출물이 생겼다고 매번 배포해야 하는 것은 아니다.

배포 문서에서 나오는 용어는 다음과 같다.

| 용어 | 쉬운 뜻 |
|---|---|
| 이미지·레지스트리 | 실행에 필요한 프로그램 묶음·그 묶음을 저장하는 보관소. 이 저장소는 GHCR에 발행 |
| Helm chart·values | Kubernetes 설치 방법을 묶은 패키지·환경별 설정값 |
| OCI chart | 레지스트리에 저장해 내려받는 형태의 Helm 패키지 |
| digest | 이미지 내용으로 정해지는 식별값. 이름만 같고 내용이 바뀐 이미지를 잘못 쓰지 않게 고정 |
| 클러스터·namespace·release | 실행 서버 묶음·그 안의 논리적 구역·Helm으로 설치한 묶음의 이름 |
| Pod | Kubernetes에서 프로그램이 실행되는 단위. 준비 상태만으로 분석 결과가 정상임을 보장하지 않음 |
| Secret | 비밀번호·키 등 민감한 설정을 전달하는 리소스. 실제 비밀값은 Git에 넣지 않으며, base64로 바꿔도 안전하게 숨겨지는 것은 아님 |
| PVC | DB·보고서 파일 등 계속 보존할 저장공간을 요청하고 연결하는 리소스 |

1. **배포가 필요한 작업**마다 배포 담당자 1명과 확인 담당자를 정한다. 대상 환경·클러스터·namespace·release, 현재 버전과 적용할 커밋·chart 버전을 기록한다.
2. 성공한 main 또는 릴리스 태그 CI의 산출물을 선택한다. main chart는 `1.3.0-ci.<run>.<attempt>` 같은 고유 버전이며 이미지 digest를 고정한다. 사용할 values·Secret 참조와 복구 절차를 준비하되 비밀값은 문서에 적지 않는다.
3. 신규 설치는 [설치 안내](helm-install.md), 업그레이드는 [기존 배포 업그레이드](helm-upgrade-existing.md)를 따른다. PostgreSQL·보고서 PVC를 함부로 삭제하거나 재생성하지 않는다.
4. Pod 준비 상태뿐 아니라 변경에 해당하는 접수 → 작업 실행 → 결과 공개·조회까지 확인한다. 공통 Agent 설정이면 두 Worker를 확인한다. DB 변경이 있으면 migration·기존 데이터도 확인한다.
5. Issue 또는 PR에 적용 시각·버전·결과·미확인 항목·복구 여부를 남긴다. 실패하면 합의한 복구 절차를 수행하고, 기존 버전 복귀만으로 DB도 복구됐다고 판단하지 않는다.

## 6. 함께 개발하는 예시

### GPU 사용률 저하 분석과 화면 표시

1. B·C-1·C-2·A가 기존 API와 결과 계약을 확인하고 필드·단위·상태·근거 참조·값이 없는 경우의 표시를 합의한다.
2. C-2는 기간별 사용률 추세와 자원 낭비 후보를 분석하고, C-1은 장애 사건으로 접수된 건의 원인과 근거를 조사한다. 로그 카테고리마다 별도 Agent를 만드는 것을 전제로 하지 않는다.
3. B는 기존 Incident·JC 접수, 결과 저장·조회 경로를 연결한다. A는 합의한 응답 예시로 화면을 개발한 뒤 실제 API에 연결한다.
4. 담당자들이 정상 결과뿐 아니라 실패·근거 부족·대기/실행 상태까지 확인한다. 공통 LLM·MCP·계산·결과 검증은 기존 `shared/python/`을 재사용하고 두 Worker의 영향을 확인한다.

### 모델 호출 timeout 조정

현재 저장소에서 출발점은 [chart values](../charts/gpu-ops-advisor/values.yaml)의 `llm.requestTimeoutSeconds`이며 기본값은 300초다. 이 값은 Worker의 `LLM_REQUEST_TIMEOUT_SECONDS`로 전달된다. 실제 요청 시간에는 작업의 남은 deadline도 적용되므로 이 값만 늘린다고 전체 작업 시간이 늘어나는 것은 아니다.

timeout은 모델에 보낸 요청의 통신 대기 제한, deadline은 분석 작업 전체의 마감 시간이다. Worker는 Agent 프로필의 `limits.deadline_seconds`와 JC가 준 `deadline_at` 중 먼저 끝나는 제한을 따른다. 모델 요청에 설정하는 timeout도 남은 시간보다 길게 잡지 않는다. 예를 들어 요청 timeout이 300초여도 전체 작업에 40초만 남았다면 그 요청 때문에 300초를 더 쓸 수 있는 것은 아니다.

1. 변경 담당자를 지정하고 추가 리뷰가 필요하면 요청한다. 담당자는 두 Agent의 호출과 deadline·슬롯·격리 정책 영향을 검증하고, C-1/C-2·B에게 관련 내용을 공유한다.
2. 변경할 원본 설정, 실제 배포에 쓰는 override, 목표 시간, 적용·복구 순서를 작업 대화·Issue 또는 PR에 적는다. 외부 모델 서버·프록시·Ingress·LiteLLM 등을 사용하는 환경이라면 해당 설정을 소유한 별도 저장소·담당자도 기록한다. 이 저장소가 그 외부 설정까지 관리한다고 가정하지 않는다.
3. main 반영과 CI 발행 후 지정한 사람이 적용한다. 실제 Worker 설정값, RCA·보고서 작업의 ID·상태·소요 시간·결과 공개 여부와 슬롯 상태를 확인한다. HTTP 성공만으로 검증을 끝내지 않는다.
4. timeout 뒤 원격 추론의 종료가 불명확하면 슬롯이 격리될 수 있다. 이후 요청이 성공했다고 이전 격리가 해제된 것은 아니다. [추론 격리와 취소](../job-controller/README.md#추론-격리와-취소)에 따라 원격 종료를 확인한 뒤 처리한다.

연결이 끊겼다고 모델 서버의 계산까지 멈췄다고 단정할 수는 없다. 슬롯 격리는 “기존 계산이 끝났는지 모르니 이 자리를 바로 다른 작업에 내주지 말자”는 안전장치다. 설정을 바꾸거나 새 요청을 성공시키는 것과 기존 작업의 종료 확인은 별개다.

공유 기록 예시이며, 실제 적용 결과는 아니다:

```text
변경: 모델 요청 시간 상한 조정 (기존 값 → 합의한 값)
담당/리뷰(선택): 변경 담당자 / 요청한 경우 담당자, 미요청이면 표시
적용: 커밋·CI 실행·chart 버전, 대상 환경·namespace·release, values 위치
확인: 실제 설정값, RCA·보고서 작업 ID·상태·소요 시간, 결과·슬롯 상태
미확인: 실행하지 못한 검증, 후속 담당자와 기한
복구: 변경 전 버전·설정, DB 영향 여부, 복구 순서
```

## 7. PR 공동 개발로 전환할 때 확인할 설정

아래는 **팀이 PR 방식으로 전환하기로 합의한 뒤** 적용할 체크리스트다. 현재 main 직접 push를 금지하는 설정이 이미 적용됐다는 뜻은 아니며, 문서를 바꾸는 것만으로 GitHub 설정이 바뀌지도 않는다. 2026-09-21 재검증에서 main은 `protected: false`, Squash 병합 허용 값은 `true`였다. 별도 rules 조회는 제한으로 확인되지 않았으므로 관리자가 전환 시점에 현재 지원 범위와 실제 설정을 다시 확인한다. 이는 확인 시점의 기록이지 이후에도 그대로라는 보장은 아니다.

즉, 현재는 검증·사용자 승인 후 직접 push할 수 있고, 이후 PR 중심으로 바꾸려면 팀의 작업 방식과 GitHub 설정을 함께 바꿔야 한다. PR 사용·CI 통과·동료 승인 인원은 서로 다른 설정이며, PR을 사용한다고 동료 승인을 반드시 요구할 필요는 없다.

- [ ] 팀이 PR 전환 시점을 합의하고 이 문서의 현재 적용 방식을 갱신한다.
- [ ] A/B/C-1/C-2에 실제 담당자를 배정하고 저장소 접근·리뷰 권한을 확인한다.
- [ ] main에 PR 병합과 `CI required` 통과를 요구하되, 별도 팀원 승인 인원은 기본 필수 조건으로 두지 않는다.
- [ ] main의 force push·삭제를 차단하고, 관리자 예외·우회 허용 범위를 확인한다.
- [ ] Squash 병합 사용 여부와 기본 병합 담당자를 확인한다.
- [ ] 공유 개발 환경·DB·배포 권한과 비밀값 전달 방법을 합의한다.

PR 전환 후에도 플랜·권한 때문에 보호 규칙을 강제할 수 없다면 그 한계를 팀에 알리고 합의한 PR·검증 절차를 수동으로 지킨다. 이를 보호 설정 완료로 표시하지 않는다. `CODEOWNERS`나 별도 PR 템플릿 파일은 실제 담당 계정과 반복 사용 필요가 정해졌을 때 추가한다.

실제 GitHub 설정이 이미 동료 승인을 요구한다면 문서만 바뀌었다고 우회하지 않는다. 관리자가 정책과 설정을 일치시키도록 확인한다. 이 문서 변경은 원격 보호 설정을 수정하라는 승인이 아니다.

`CODEOWNERS`는 경로별 리뷰 담당자를 GitHub에 알려주는 파일이고, PR 템플릿은 PR을 만들 때 설명 양식을 미리 채워주는 파일이다. 지금은 이 문서의 역할표와 복사할 양식으로 시작하고, 같은 누락이 반복될 때 파일로 자동화하면 된다.
